Concept 1 of 16 · 🔭 Plan literacy

A SQL query is a request, not a recipe — the engine decides how to run it.

You write what you want. A planner called the optimizer decides how. Learn the five stages once, and “slow” becomes a question you can actually answer.

❓ "What happens inside the database between pressing Run and getting rows back?"
👁 See it first
🎯 SQL says what you want; the optimizer decides how to get it — and a poor “how” is what most slow queries really are.
📖 Why did this need to exist?

You wrote SELECT … WHERE CustomerId = 42. Notice what you did not write: no loop, no “open this index first”, no join order. SQL is declarative — you describe the answer, not the steps.

Somebody has to choose the steps. That somebody is the query optimizer. It looks at your query, your tables and indexes, and its statistics about the data, and picks the plan it estimates will be cheapest.

So “my query is slow” has only two honest meanings: you asked for a lot of work, or the engine chose a poor way to do it. You cannot tell which one without seeing the plan — and that is the whole point of this lab. This page gives you the map; the next pages teach you to read it.

🧭 The five stages, one by one
1 · PARSE

📝 Is it valid SQL?

The text is checked for syntax and turned into a tree.

2 · BIND

🔗 Do these names exist?

Tables, columns and types are resolved. Docs call this step algebrizing.

3 · OPTIMIZE

🧠 Choose the plan

Inputs: the query tree, the schema and the statistics. Output: the cheapest estimated plan.

4 · CACHE

🗃️ Remember it

The plan is stored. An identical statement later can skip stages 1–3.

5 · EXECUTE

⚙️ Do the work

Operators run, pages are read, rows flow back to your app.

▾ Go one level deeper (60 seconds)

The plan cache is strict. To reuse a plan, the statement text must literally match a previously executed statement, character for character, and object names must be fully qualified. So WHERE CustomerId = 42 and WHERE CustomerId = 43 written as two different literals are two different statements — which is one reason applications send parameters instead (page 9).

Plans are shared; running is private. A compiled plan is read-only and shared. Each run gets its own execution context holding that run’s parameter values.

Cost-based, not “always best”. The optimizer balances how long it spends choosing against how good the plan is, so it uses heuristics and stops at a “good enough” plan instead of searching forever.

Other engines: PostgreSQL and MySQL have the same idea with different commands — EXPLAIN shows the planned steps, and EXPLAIN ANALYZE runs the query and adds real timings and row counts. The concepts in this lab transfer; the names change.

🔥 Interview recall
  • SQL is declarative: you say WHAT; the optimizer chooses HOW.
  • Stages: parse → bind (algebrize) → optimize → cache → execute.
  • The optimizer is cost-based and works from the query, the schema and statistics.
  • Plans are cached and reused when the statement text matches exactly.
  • Estimated plan = no run, no runtime info. Actual plan = runs the query, adds real row counts and warnings.
  • The gap between estimated and actual rows is the most common clue to a bad plan.
🎤 Say this in an interview
"A SQL statement describes what I want, not how to get it. The engine parses and binds it, the cost-based optimizer uses the schema and statistics to pick the cheapest estimated plan, the plan is cached, and then it executes. When a query is slow I look at the actual execution plan, because it shows what the engine really did and where its estimates were wrong."
⚠️ Common trap

“Slow query” is not a diagnosis. Rewriting SQL, adding an index or buying a bigger tier without reading the plan is guessing. Half the time the plan shows the query was fine and the problem was waiting, blocking, or the data volume.

Also: an estimated plan can look perfect and still be wrong — it is only the optimizer’s prediction. Only the actual plan tells you how far reality was from the prediction.

📐 Estimated plan

A prediction. The query does not run. Great for a first look and for risky statements.

vs.
📏 Actual plan

The same plan plus what really happened: real row counts, warnings, timings. This is the one you diagnose with.
