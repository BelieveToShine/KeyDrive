Concept 2 of 16 · 🔭 Plan literacy

The engine never reads a row — it reads 8 KB pages.

Every plan operator is really “read these pages”. Learn what a page is, what a heap is, and why a clustered table is stored in key order — and plans will start to make sense.

❓ "How does SQL Server physically store a table, and why does that matter for query speed?"
👁 See it first
🎯 The engine never reads “a row” — it reads a whole 8 KB page. So the cost of a query is, to a first approximation, how many pages it has to touch.
▶️ Watch it happen: the engine reads pages
📖 Why did this need to exist?

The last page ended on a promise: the optimizer picks a plan, and the plan is a tree of operators that read data. But read it from where? A table is not a spreadsheet in memory — it is a pile of fixed-size blocks on storage.

If you do not know that blocks exist, a plan makes no sense: “why does reading 10 rows cost 12,000 reads?” is a natural question, and its answer is “because those 10 rows were hiding in 12,000 pages and the engine had to look at every one”.

So before indexes (next page), you need exactly one mental picture: pages, and how a table’s pages are organised — as an unordered heap or as a sorted clustered structure.

🧱 Heap vs clustered table

🔑 Choosing a clustered key — four properties
NARROW

📏 Small

The clustered key is copied into every other index. A wide key makes all indexes bigger.

UNIQUE

☝️ One per row

If it is not unique, a hidden extra value is added to make it so — in every index too.

EVER-INCREASING

📈 Always growing

New rows go at the end. Random keys cause rows to land mid-structure and split pages.

IMMUTABLE

🔒 Never changes

Changing the key forces updates in every nonclustered index.

A single int or bigint filled by IDENTITY or a sequence meets all four. A uniqueidentifier is wider and, unless generated sequentially, not ever-increasing.

🎬 Real-world scenarios
🧾
Log table with no key

Rows are only ever appended and read in bulk. A heap can be fine here — a rare exception.

→ Heap is acceptable
🛒
Orders looked up by OrderId

Millions of lookups per day by id.

→ Clustered on OrderId
🎲
Clustered on a random GUID

Inserts land all over the structure and pages split constantly.

→ Use a sequential key
🔁
Key keeps being edited

An “email” used as the clustered key changes whenever the customer changes it.

→ Pick an immutable key
▾ Go one level deeper (60 seconds)

Extents. An extent is eight physically contiguous pages (64 KB). Uniform extents belong to one object; mixed extents can be shared by up to eight objects, which is how tiny new tables start. Since SQL Server 2016, user databases and tempdb use uniform extents except for the first eight pages of an object.

Bookkeeping pages. Special pages track space: GAM and SGAM pages track extent allocation, IAM pages map the extents an object uses, and PFS pages track free space inside pages.

Logical vs physical reads. A logical read is a page taken from the in-memory data cache; a physical read is a page fetched from disk. Logical reads are the stable measure of work; physical reads depend on what happened to be cached.

🔥 Interview recall
  • A page is 8 KB and is the unit the engine reads and writes; an extent is 8 pages = 64 KB.
  • A table without a clustered index is a heap: unordered; a clustered table stores its rows sorted by the key.
  • Docs’ advice: with few exceptions, give every table a clustered index.
  • Good clustered key: narrow, unique, ever-increasing, immutable (e.g. an IDENTITY bigint).
  • Logical reads = pages from memory; physical reads = pages from disk. Fewer logical reads = less work.
🎤 Say this in an interview
"The engine stores data in 8 KB pages and reads whole pages, so query cost is mostly pages touched. A table is either a heap or, with a clustered index, stored in key order. I choose a narrow, unique, ever-increasing, immutable clustered key — typically an identity bigint — because that key is copied into every other index."
⚠️ Common trap

The primary key is not automatically the best clustered key. It defaults to clustered, but if it is wide or random you can create it as nonclustered and cluster on a better column.

“Fewer rows” does not mean “cheaper”. What counts is how many pages had to be read to find those rows.

Unordered pile of pages. Fast to append, slow to find by key.
