❓ "What is the difference between a clustered and a nonclustered index, and between an index seek and a scan?"
👁 See it first
🎯 An index is a sorted shortcut: the engine walks a short tree to the right leaf instead of reading every page — a seek instead of a scan.
📖 Why did this need to exist?

The last page left you with a clustered table sorted by OrderId. Great for “find order 9001”. But your app mostly asks “show customer 42’s orders”, and the table is not sorted by customer — so the engine must read every page and discard almost all of it.

You cannot sort one table two ways. What you can do is keep a second, smaller, sorted structure — an index — that maps CustomerId to the row. That is a nonclustered index, and it is the single most common fix for a slow query.

This page covers what it is, how the engine uses it (seek vs scan), and why the engine sometimes ignores your index on purpose.

🧰 The two index kinds

🌲 Clustered index

the table itself, stored in key order✅ Pick it when
  • One per table — it IS the data, sorted
  • Lookups and range reads by the clustered key
  • Its leaf pages are the data pages
⛔ Look elsewhere when
  • You need a second sort order → add a nonclustered index
  • A wide or random key — it is copied into every other index

📇 Nonclustered index

a separate sorted structure that points to the rows✅ Pick it when
  • Searching by a column the table is not sorted by
  • Many allowed per table
  • Leaf rows hold the key plus a row locator back to the data
⛔ Look elsewhere when
  • Every index costs space and slows writes — do not add “just in case”
  • It cannot answer for columns it does not hold without a lookup

🚫 Why the engine ignores your index (on purpose)
TOO MANY ROWS

🧮 Lookups add up

If a big share of rows match, doing a key lookup for each one costs more than one scan. The optimizer weighs this.

WRONG COLUMN ORDER

↔️ Leading column

An index on (LastName, FirstName) helps find a last name, not a first name alone.

HIDDEN COLUMN

🙈 Function on the column

Wrapping the column in an expression usually prevents a seek (page 8).

BAD GUESS

🎲 Stale estimate

The optimizer thought many rows would match (page 5).

🧪 Plan lab · twelve rows out of a million

Before. No index on CustomerId. The query asks for customer 42’s twelve orders.

SET STATISTICS IO ON;
SELECT OrderId, OrderDate, Total
FROM   dbo.Orders
WHERE  CustomerId = 42;

-- illustrative: Table 'Orders'. Scan count 1, logical reads 12503

Numbers are illustrative and come from the page-count arithmetic on the previous page.

The fix. Add a nonclustered index on the column you filter by.

CREATE NONCLUSTERED INDEX IX_Orders_CustomerId
ON dbo.Orders (CustomerId);

-- illustrative after: Table 'Orders'. Scan count 1, logical reads ~40

~40 = about 3 page reads to reach the leaf, plus about 3 per key lookup × 12 rows. The page after next explains how to read such a plan operator by operator.

🎬 Real-world scenarios

“My orders” page

Filters orders by the logged-in customer on a million-row table.

→ Nonclustered index on CustomerId
📅
Nightly sales report

Needs 90% of last year’s rows. An index would add a lookup per row.

→ A scan is the right plan

Users type a last name; sometimes only a first name.

→ Index (LastName, FirstName) helps the first, not the second
📝
Audit log, write-heavy

Insert-only, rarely queried. Four extra indexes slow every insert.

→ Fewer indexes
▾ Go one level deeper (60 seconds)

B-tree / B+ tree. Index keys are stored in a tree (the docs describe rowstore indexes as B+ trees): a root page, optional intermediate levels, and a leaf level. The engine navigates the tree to find rows quickly.

Row locator. In a nonclustered index, each leaf row holds the index key plus a pointer to the data row. For a heap that pointer is a physical row address (RID); for a clustered table it is the clustered key — which is why a narrow clustered key keeps every index small.

Included columns let a nonclustered index carry extra columns so the engine never needs the lookup — the subject of page 7.

Other engines: PostgreSQL and MySQL also use B-tree indexes by default and show the choice as Index Scan / Seq Scan (PostgreSQL) or type=ref / ALL (MySQL EXPLAIN); the seek-vs-scan thinking is identical.

🔥 Interview recall
  • An index is a sorted copy of some columns in a B-tree: root → intermediate → leaf.
  • Clustered = the table itself in key order (one per table). Nonclustered = a separate structure whose leaf rows hold the key + a row locator.
  • Seek = navigate the tree to matching ranges. Scan = read everything.
  • A Key Lookup fetches missing columns from the table, one per row, and always sits with a Nested Loops.
  • Arrow thickness in a plan = rows flowing, not work done. Check logical reads.
  • Every index speeds some reads and slows every write.
🎤 Say this in an interview
"A nonclustered index is a sorted B-tree on one or more columns. A query with a selective predicate can seek straight to the matching leaf entries instead of scanning the whole table, then do key lookups for any columns the index does not hold. I verify the benefit by comparing logical reads before and after — and I remember each index costs write time and space."
⚠️ Common trap

“Seek good, scan bad” is too simple. A scan is perfect when most rows are needed, and a seek can still read huge ranges. Judge by logical reads and by how many rows you actually need.

Adding an index without checking the plan is the classic way to slow down writes for no read benefit.

🌲 Clustered index

The data itself in key order. One per table. Seeking it gets you the whole row.

vs.
📇 Nonclustered index

A separate lookup structure. Many per table. Gets you the key — and a pointer to the rest.
