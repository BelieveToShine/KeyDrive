📖 Why did this need to exist?

Reading about tuning and doing it are different skills. In real life nobody tells you which page of a book you need; you get a complaint and some numbers. The cases below start the way real tickets do.

All ten use the same ShopDB numbers as the rest of the lab, so you will recognise the plans. Every case is solvable with the ladder from page 11 — and every diagnosis is a place you have already been.

🩺 Case 1

The Pune report

Symptom. The Pune orders report takes 9 seconds. CPU time is only 2 seconds.

Evidence.

  • Actual plan: a Hash Match with a warning icon.
  • Customers seek: estimated 50 rows, actual 4,000.
  • Orders scan: 1,000,000 rows (expected).

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. Stale statistics: the optimizer expected 50 customers, sized the hash join’s memory for them, and spilled to tempdb when 4,000 arrived. The scan is not the problem — the estimate is.

Fix (one change). UPDATE STATISTICS dbo.Customers … WITH FULLSCAN; re-run with the actual plan: estimate ≈ 4,000, no warning, elapsed drops.

📖 Where to review: pages 5 and 6.

🩺 Case 2

Fast for everyone but BigCorp

Symptom. GetOrdersByCustomer takes 40 ms for most customers and about 6 seconds for BigCorp (80,000 orders). It started after Tuesday’s deploy.

Evidence.

  • The plan for every call: Index Seek + Key Lookup + Nested Loops.
  • Plan properties: compiled value 42, runtime value 7.
  • The seek estimated 12 rows; BigCorp returns 80,000.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. Parameter sniffing: the first call after the deploy was for a small customer; its plan (built for 12 rows) was cached and reused for BigCorp — 80,000 key lookups.

Fix. Confirm with OPTION (RECOMPILE) in a test; then use parameter sensitive plan optimization (compat level 160) or a targeted hint; force the last good plan in Query Store as a bandage.

📖 Where to review: pages 9 and 10.

🩺 Case 3

The slow “My orders” list

Symptom. The list for a large customer takes 3 seconds. The team says “but there is an index on CustomerId!”.

Evidence.

  • SET STATISTICS IO: 240,000 logical reads for 80,000 rows returned.
  • Plan: Index Seek (3%) + Key Lookup (97%).
  • The query returns CustomerId, OrderDate and Total.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. The index finds the rows but lacks two columns, so the engine does a lookup per row — and the optimizer even considered a scan cheaper.

Fix. A covering index: (CustomerId, OrderDate) INCLUDE (Total). Reads drop to a few hundred.

📖 Where to review: page 7.

🩺 Case 4

An index that is used but does not help

Symptom. An index exists on (OrderDate, CustomerId). The query WHERE CustomerId = 42 AND OrderDate >= '20260201' is still slow.

Evidence.

  • Plan: Index Seek, but seek predicate = OrderDate only; CustomerId is a residual predicate.
  • Rows read 40,000 — rows returned 12.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. Key order. With OrderDate first, customer 42’s rows are scattered among everyone’s; the engine seeks the date range and filters the rest.

Fix. Equality column first, range second: create (CustomerId, OrderDate) and drop the old one if nothing else uses it.

📖 Where to review: pages 7 and 3.

🩺 Case 5

The yearly report

Symptom. The yearly revenue report scans although OrderDate has an index.

Evidence.

  • Plan: Index Scan with Predicate: YEAR(OrderDate) = 2026 (not a Seek Predicate).
  • Logical reads ≈ the size of the whole index.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. A function wraps the column, so the engine must compute it for every row; the sort order is useless.

Fix. OrderDate >= '20260101' AND OrderDate < '20270101' — a half-open range on the bare column.

📖 Where to review: page 8.

🩺 Case 6

Fast in SSMS, slow in the app

Symptom. A lookup by order status takes 5 ms in SSMS and 1.2 seconds from the Java service.

Evidence.

  • App plan: Index Scan; SELECT shows a warning: type conversion “may affect SeekPlan”.
  • The column is VARCHAR; the driver sends the parameter as NVARCHAR.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. Implicit conversion: the lower-precedence type — the column — is converted for every row, so the seek is lost. SSMS used a VARCHAR variable, so it never showed.

Fix. Declare the parameter with the column’s type (or change the driver’s Unicode-parameter setting).

📖 Where to review: page 8.

🩺 Case 7

The order page that hangs

Symptom. The order page hangs for 30 seconds at 14:05. Query CPU time is 20 ms.

Evidence.

  • Elapsed ≫ CPU: it is waiting.
  • Sessions 77 and 80: blocking_session_id = 51.
  • Session 51: sleeping, open transaction, last statement an UPDATE on Orders.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. A head blocker: the app opened a transaction, updated the order, then called a slow payment API before committing; the exclusive lock stays until COMMIT.

Fix. Commit before the external call (never wait for an API inside a transaction); keep RCSI on so readers do not queue behind writers.

📖 Where to review: page 12.

🩺 Case 8

Twice a day an error

Symptom. Users see “Transaction was chosen as the deadlock victim” about twice a day.

Evidence.

  • Deadlock graph: UpdateOrderStatus updates Orders then Customers; ApplyLoyaltyPoints updates Customers then Orders.
  • Both run in transactions of a few statements.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. A lock cycle from opposite access order.

Fix. Touch the tables in the same order in both procedures; keep transactions short; retry the victim.

📖 Where to review: page 12.

🩺 Case 9

The import that got slow

Symptom. Importing 10,000 orders took 3 seconds a year ago; now it takes 8.

Evidence.

  • Orders has five indexes.
  • Usage stats: two indexes have 0 reads and 1,100,000 updates.
  • Query reads are still fast.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. Index overload: every insert maintains five structures, two of which nobody reads.

Fix. Save their CREATE scripts, watch a full business cycle, then drop the unused ones; measure the import again.

📖 Where to review: page 13.

🩺 Case 10

The nightly import in Azure SQL

Symptom. The nightly import of 5 million order lines takes 40 minutes in Azure SQL Database. The plan is a plain bulk insert.

Evidence.

  • CPU 30%, data I/O moderate.
  • avg_log_write_percent ≈ 100% during the import.
  • Waits include the log-rate governor.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. Not the query — the tier’s log write rate is the ceiling and the service throttles on purpose.

Fix. Moderately sized batches; scale to a tier with a higher log rate for the import window; re-measure.

📖 Where to review: page 15.

🩺 Case 11

Bonus: the 90-second dashboard

Symptom. The dashboard sums revenue per month over a 500-million-row history table. It takes 90 seconds.

Evidence.

  • Plan: Clustered Index Scan of 500M rows, row-mode aggregate.
  • The query needs 2 of the table’s 5 columns.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. A B-tree scan reads every column of every row for an aggregate.

Fix. Columnstore (with a bare-column date range, and partitioning if you archive by year) — a fraction of the bytes, batch mode.

📖 Where to review: page 14.

▾ Go one level deeper (60 seconds)

Patterns across the cases. Six of the ten are decided by a single number you already know how to get: estimated vs actual rows (cases 1, 2, 4), logical reads (3, 5), or waits and blocking (7, 8). The remaining ones need a second question: is a column hidden (6), is it writes (9), is it the tier (10).

False friends. Cases 3 and 4 both look like “an index exists but is not helping”. The difference is that case 3 has the right key and misses columns; case 4 has the right columns and the wrong order.

Make your own clinic. Take five real tickets, strip the diagnosis, keep only symptom and evidence, and run the same exercise with your team.

🔥 Interview recall
  • Method beats memory: running or waiting → estimates vs actual → heaviest operator → hidden column → tier limit.
  • One change, same measurement, check the other inputs.
  • Families: estimates (5, 6, 9), indexes (3, 7), query text (8), waiting (12), system & tier (13, 15), big data (14).
  • Symptoms that look alike (an index that “exists but does not help”) can have different causes — check key columns, key order, included columns and hidden columns.
  • Write down before/after numbers for every fix.
🎤 Say this in an interview
"I treat a slow query as an investigation, not a guess. I check whether it is running or waiting, then whether estimated and actual rows agree, then the heaviest operator and whether a column is hidden from its index, and finally whether the service tier is the limit. I change one thing, re-measure with the same input, check other parameter values, and keep a short log of before and after."
⚠️ Common trap

Pattern-matching too fast. “Slow + index exists” does not mean “add an index”. Cases 3, 4, 5 and 6 all start with that sentence and end with four different fixes.

Skipping the evidence. In every case the deciding fact was one number or one word in the plan. Look for it before you theorise.
