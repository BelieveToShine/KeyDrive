Functions, arithmetic, wildcards and silent type conversions — how a column gets hidden from its own index, how to spot it in a plan, and the rewrite for each.

❓ "What does it mean for a predicate to be SARGable, and how do you fix one that is not?"
👁 See it first
🎯 A perfect index only helps if the predicate leaves the bare column alone — wrap the column in a function and the engine can no longer seek.
▶️ Watch it happen: leave the column alone
📖 Why did this need to exist?

Page 7 gave you a covering index. But an index is a sorted structure: it can only help with questions about the sorted values themselves. “Is the date between these two?” is a question about the values. “Is the YEAR of the date 2026?” is a question about a calculation — and the index stores no calculations.

The word for a predicate the engine can use an index for is SARGable (Search ARGument-able). Most “my index is ignored” tickets are not index problems at all; they are predicates that stopped being SARGable the day someone added a convenient function.

This page is a catalogue of how columns get hidden, how to spot it in a plan, and the rewrite for each.

🧪 Plan lab · YEAR() on a date column

The ShopDB team added an index on OrderDate yesterday. The yearly report is still slow.

SELECT OrderId
FROM   dbo.Orders
WHERE  YEAR(OrderDate) = 2026;      -- hides OrderDate inside a function

Illustrative. We select only OrderId — it is the clustered key, so it is already inside the OrderDate index and the index covers the query (page 7). Logical reads here are roughly the size of the whole index.

The rewrite. Say the same thing as a half-open range on the bare column.

SELECT OrderId
FROM   dbo.Orders
WHERE  OrderDate >= '20260101'
  AND  OrderDate <  '20270101';     -- bare column, range on both sides

Why “< 2027-01-01” and not “<= 2026-12-31”? A half-open range works for date, datetime and datetime2 alike, with no risk of dropping the last day’s times. The YYYYMMDD literal form is unambiguous.

🔤 The silent one: implicit conversion

The plan tells you, if you look: a warning on the SELECT operator reads like “Type conversion in expression (CONVERT_IMPLICIT(…)) may affect “SeekPlan” in query plan choice”. In the plan XML the same thing is flagged as PlanAffectingConvert.

▾ Go one level deeper (60 seconds)

Seek predicate vs residual predicate. A seek can use equality and range conditions on the leading columns of an index. Conditions it cannot use to navigate become residual predicates, applied after the rows are read. If the leading column has no seekable predicate, you get a scan with a predicate.

Not every conversion blocks a seek. Whether a conversion hides the column depends on the types and the collation: for example, a VARCHAR column with a Windows collation can still seek against an NVARCHAR value, while one with a SQL collation cannot. Don’t rely on that — match the types.

Drivers. Some client drivers send string parameters as Unicode by default; the JDBC driver has a connection property for it (sendStringParametersAsUnicode). Changing it can fix the plan, but declaring the right parameter type in code is the cleaner fix.

Other engines: the same rule exists everywhere that uses B-tree indexes: functions on the indexed column hide it (PostgreSQL offers expression indexes to index the function result itself; MySQL 8 has functional indexes).

🔥 Interview recall
  • SARGable = the engine can use an index to narrow the search.
  • Bare column compared to a value or parameter, with =, range or LIKE ’abc%’ → seekable.
  • Function, arithmetic or CASE around the column, or a leading-wildcard LIKE → usually a scan with a predicate.
  • Implicit conversion: the lower-precedence type is converted — if that is the column, the seek is lost.
  • Spot it: Predicate (not Seek Predicate) on a scan, and the “may affect SeekPlan” warning.
  • Fix by rewriting the predicate or matching types — not by adding another index.
🎤 Say this in an interview
"A predicate is SARGable when the engine can use an index to seek. Wrapping the column in a function, doing arithmetic on it, using CASE, or having an implicit conversion that converts the column all force a scan with a predicate. I look for a Predicate instead of a Seek Predicate in the plan, and for the SeekPlan conversion warning, and I rewrite the filter as a range on the bare column or match the parameter type."
⚠️ Common trap

Adding another index to “fix” a non-SARGable predicate. The new index has the same problem — the function is still on the column. Fix the query.

Assuming a “Seek” in the plan means it is cheap. A leading-wildcard LIKE can show a Seek yet touch nearly every row. Always check logical reads.

✅ SARGable

WHERE OrderDate >= @from AND OrderDate < @to — the column is bare, the index sort order applies.
