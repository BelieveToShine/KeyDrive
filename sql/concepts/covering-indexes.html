INCLUDE columns, composite key order and filtered indexes — and the surprising moment when a naive index loses to a table scan.

❓ "What is a covering index and how do you choose its key and included columns?"
👁 See it first
🎯 A seek is only cheap if it does not have to go back to the table for every row — a covering index keeps the whole answer inside the index.
📖 Why did this need to exist?

Page 3 ended on a plan with a Key Lookup, and a note that twelve lookups are cheap. Page 6 showed a nested-loops join ending in the same lookup. Now scale up: what if the query returns 80,000 rows instead of 12?

Each lookup is a small trip through the clustered tree, per row. Multiply it by 80,000 and the “fast index” becomes the slowest part of the plan — the optimizer may even ignore your index and scan the table instead. That is the second reason (after page 3) an index sometimes “doesn’t get used”.

The cure is an index that already holds every column the query needs: a covering index. This page covers how to build one, how to order its columns, and when a filtered index is smarter.

🧬 What is inside a covering index
🧰 Three tools — pick the right one

🔑 Key column

sorted, searchable — decides seeks✅ Pick it when
  • Columns in WHERE, JOIN, GROUP BY or ORDER BY
  • Equality columns first, then a range column
  • Limits: up to 32 key columns and 1,700 bytes
⛔ Look elsewhere when
  • Columns you only return — INCLUDE is cheaper to maintain
  • Wide columns — they bloat every level of the tree

🎒 INCLUDE column

stored in the leaf only✅ Pick it when
  • Columns in the SELECT list you do not filter on
  • Removing a costly Key Lookup
  • Does not count toward the key limits; the order inside INCLUDE does not matter
⛔ Look elsewhere when
  • “Include everything” — wide indexes fit fewer rows per page and slow writes
  • A column cannot be both a key and an included column

🎯 Filtered index

an index on just a slice of the rows✅ Pick it when
  • A query always targets a small subset (e.g. open orders only)
  • Smaller, cheaper to maintain, more accurate statistics for the slice
⛔ Look elsewhere when
  • Columns in the filter that the query uses in a non-equivalent comparison or returns — add them as key or included columns
  • Queries that sometimes need the other rows
↕️ Key order — equality first, then range
🧪 Plan lab · from 80,000 lookups to none

Before. Customers from one city placed about 80,000 orders. We want OrderDate and Total for each. The only index is on CustomerId.

The fix. Key columns first (what we filter and sort on), then INCLUDE what we only return.

CREATE NONCLUSTERED INDEX IX_Orders_Customer_Date
ON dbo.Orders (CustomerId, OrderDate)
INCLUDE (Total);

-- illustrative logical reads for the 80,000-row result:
--   before: seek + 80,000 lookups  ≈ 240,000
--   after : covering seek           ≈ 400

Re-run with SET STATISTICS IO ON and compare logical reads — the plan shape changes first, the numbers prove it. Illustrative figures.

▾ Go one level deeper (60 seconds)

Limits. Included columns exist only on nonclustered indexes (tables and indexed views), at least one key column is required, and up to 1,023 columns can be included; they do not count toward the 32-key-column / 1,700-byte key limits. A column cannot appear in both the key and the INCLUDE list.

Index intersection is not a plan. Two narrow single-column indexes are not the same as one index on both columns; the optimizer can combine indexes in some plans, but it is rarely as good as one well-designed covering index.

Missing-index suggestions are estimates made for one query before it runs: only nonclustered disk-based rowstore indexes, no key-order advice, no size cost of included columns, and different queries can produce near-identical suggestions that should be merged. The DMV keeps a limited number of suggestions and clears on restart.

Other engines: PostgreSQL has INCLUDE columns for B-tree indexes and “Index Only Scan”; MySQL InnoDB secondary indexes always carry the primary key, giving “Using index” (covering) in EXPLAIN.

🔥 Interview recall
  • A Key Lookup costs one trip into the clustered index per row — cheap for a few rows, ruinous for many.
  • A covering index contains every column the query needs: key columns (sorted, searchable) + INCLUDE columns (leaf only).
  • Key order: equality columns first, then the range or sort column.
  • INCLUDE order does not matter; included columns do not count toward key size limits.
  • Filtered indexes cover just a slice of rows — smaller and cheaper, but only for queries aimed at that slice.
  • Missing-index suggestions are single-query estimates: use as hints, not as final designs.
🎤 Say this in an interview
"A nonclustered index seek is cheap, but every column it does not hold forces a key lookup per row, which explodes for large results — the optimizer may even switch to a scan. I fix that with a covering index: key columns for what I filter and sort on, equality columns before the range column, and INCLUDE for columns I only return. I verify with logical reads before and after, and I keep the index narrow because every write maintains it."
⚠️ Common trap

INCLUDE everything “just in case”. The index becomes as wide as the table, fits few rows per page, and every insert and update pays for it.

Applying the missing-index suggestion verbatim. It ignores key order and write cost, and may duplicate an index you already have.

🔑 Key column

Part of the sort order. Lets the engine seek and keeps rows in order.

vs.
🎒 INCLUDE column

Just carried in the leaf. Saves the lookup but cannot be searched or sorted on.
