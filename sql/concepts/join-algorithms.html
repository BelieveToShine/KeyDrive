Nested loops, hash and merge: what each needs, when each wins, and how a wrong estimate turns a good hash join into a spill.

❓ "What are the three physical join algorithms in SQL Server and when does each one win?"
👁 See it first
🎯 There is no “best” join — only the one that fits the row counts. Nested loops for few rows with an index, hash for big unsorted inputs, merge for sorted inputs.
▶️ Watch it happen: three ways to join
📖 Why did this need to exist?

The last page ended with a number: estimated 50 rows, actual 4,000. Why does a wrong row count matter so much? Because the optimizer uses it to pick the join algorithm — and each algorithm has a completely different cost curve.

Almost every slow multi-table query is slow in its joins. A nested-loops join that runs its inner side a million times, a hash join that runs out of memory, a merge join that has to sort first — each one looks fine in the query text and awful in the plan.

This page teaches you to recognise the three, to know what each one needs, and to spot the two classic failures: too many loops and a hash spill.

🧭 Which join will the engine pick?
🧰 The three joins, side by side

🔁 Nested Loops

for each outer row, search the inner input✅ Pick it when
  • The outer input is small
  • The inner input has an index on the join column
  • The join condition is not a simple equality (it supports any join predicate)
⛔ Look elsewhere when
  • Both inputs are large — total work is roughly outer rows × inner work
  • No index on the inner join column — every probe is a scan

#️⃣ Hash Match

build a hash table, then probe it✅ Pick it when
  • Large, unsorted inputs
  • No helpful index
  • Big joins and parallel plans — it is the workhorse for the largest joins
⛔ Look elsewhere when
  • Memory is tight — the hash table must fit in the memory grant or it spills to tempdb
  • You need the first rows fast — it must read the whole build input first

🧵 Merge Join

walk two sorted inputs together✅ Pick it when
  • Both inputs are already sorted on the join key (an index often provides that)
  • You need the output order preserved
⛔ Look elsewhere when
  • It needs at least one equality predicate
  • If the inputs are not sorted, a Sort operator is added — and that is the cost
🧪 Plan lab · the hash join that spilled

Remember the plan from page 4: a Hash Match joining a small customer list to the big Orders input. The customer seek estimated 50 rows and returned 4,000. A hash join needs a memory grant to hold its build input — and the grant is sized from the estimate.

Test one hypothesis: the estimate was wrong because statistics were stale (page 5). Change only that.

▾ Go one level deeper (60 seconds)

Hash join phases. The build phase reads the whole first input, hashes it on the join keys and builds an in-memory table; the probe phase reads the second input, hashes it the same way and looks for matches. It is “blocking”: it must finish the build input before returning any rows.

Spill levels. In a hash warning, recursion means the build input did not fit and was split into partitions processed separately; bailout means recursion hit its limit and the operator switched to an alternative way of finishing. Since SQL Server 2016 the warning shows how many threads and pages spilled.

Memory grants. In row-mode execution the initial memory grant cannot be exceeded; batch mode can grow the grant dynamically up to an internal threshold.

Adaptive joins. In newer versions (batch mode), an Adaptive Join defers the choice: it uses a threshold on the rows it actually sees to switch between hash and nested loops while running.

Row goals. A TOP or FAST hint tells the optimizer you need only the first rows, which makes nested loops more attractive.

Join hints (LOOP JOIN, HASH JOIN, MERGE JOIN, FORCE ORDER) exist, but they tie the optimizer’s hands. Use them to test a theory, not as the first fix: forcing a join type does not guarantee a better plan.

Other engines: PostgreSQL shows Nested Loop, Hash Join and Merge Join nodes with the same meaning; MySQL (8.0 and later) also has hash joins.

🔥 Interview recall
  • Three physical joins: Nested Loops, Hash Match, Merge Join.
  • Nested Loops: small outer + indexed inner. Cost grows with outer rows × inner work.
  • Hash Match: build + probe; needs a memory grant; spills to tempdb if the grant is too small (look for the warning icon).
  • Merge Join: both inputs sorted on the join key, at least one equality predicate; a Sort is added if unsorted.
  • The algorithm follows the estimated row counts — bad estimates give bad join choices and bad memory grants.
  • Join hints are a last resort; fix estimates and indexes first.
🎤 Say this in an interview
"There are three physical joins. Nested loops probes the inner side once per outer row, so it wants a small outer input and an indexed inner side. Hash match builds a hash table from one input and probes it with the other — great for big unsorted inputs but it needs a memory grant and can spill to tempdb. Merge join walks two sorted inputs. When a join is slow I check the estimated versus actual rows first, because the engine picks the algorithm and sizes the memory from the estimates."
⚠️ Common trap

Forcing a join hint to “fix” a slow join. If the cause was a wrong estimate, the hint freezes today’s data shape into the query — and breaks the day the data changes. Fix the estimate; use the hint only to prove a theory.

Reading “Hash Match” as “bad”. It is the right choice for large joins. The red flag is a hash warning, not the operator itself.

🔁 Nested Loops

Cost ≈ outer rows × inner work. Great when the outer side is small and the inner is indexed.

#️⃣ Hash Match

Cost ≈ read both inputs once, plus memory. Great for big joins; watch for spills.
