On Azure SQL, check the tier’s limits before you blame the query.

Resource governance, the tiers and purchasing models, serverless cold starts, automatic tuning, Query Performance Insight, Intelligent Query Processing and read replicas.

❓ "A query is slow in Azure SQL Database. How do you tell whether it is the query or the service tier?"
👁 See it first
🎯 Azure SQL adds one more suspect to every investigation: the tier’s limits. Check the resource percentages before you blame — or buy your way out of — a query.
📖 Why did this need to exist?

Pages 1–14 treated the database as one unlimited machine and asked: is the work reasonable? On a managed cloud database that is only half the question. The service gives you a slice of a machine, with hard ceilings and with helper features that a plain SQL Server does not have.

Two mistakes follow. Scaling up too early pays more to run the same bad plan. Tuning forever when the tier is simply too small wastes weeks. The method is the same as page 11 — measure first — with one extra measurement.

This page covers: how to read the limits, which tier does what, the built-in helpers (automatic tuning, Query Store, Intelligent Query Processing), and how to offload reads.

📏 Is it the query or the tier?
-- the last hour, one row per 15 seconds
SELECT AVG(avg_cpu_percent)       AS avg_cpu,
       MAX(avg_cpu_percent)       AS max_cpu,
       AVG(avg_log_write_percent) AS avg_log_write,
       MAX(max_worker_percent)    AS max_workers
FROM   sys.dm_db_resource_stats;

The view keeps roughly one hour of history (one row every 15 seconds); sys.resource_stats holds longer history. Microsoft’s rule of thumb: keep averages below about 90% and treat occasional short spikes to 100% as fine; if samples sit at 100% often, the tier does not fit. Managed Instance uses sys.server_resource_stats instead.

🧰 Which tier does what

🟦 General Purpose (vCore)

balanced; remote storage✅ Pick it when
  • Most business workloads
  • Read latency about 5–10 ms, write about 5–7 ms (per the docs’ tables)
⛔ Look elsewhere when
  • I/O-heavy workloads that need low latency → Business Critical or Hyperscale

⚡ Business Critical

local SSD, built-in replicas✅ Pick it when
  • Low-latency I/O (about 1–2 ms on average)
  • Includes additional high-availability replicas that can serve reads
⛔ Look elsewhere when
  • Cost: roughly 2.7× General Purpose in the docs’ comparison — check current prices

🚀 Hyperscale

very large databases, scale-out reads✅ Pick it when
  • Databases that outgrow other tiers
  • Up to 4 HA replicas and up to 30 named replicas for reads
  • Latency about 1–2 ms for the frequently accessed part of the data
⛔ Look elsewhere when
  • Named replicas that cannot keep up with the log make the primary slow its log generation

💤 Serverless (vCore, General Purpose)

auto-scales; can pause when idle✅ Pick it when
  • Spiky or idle workloads
  • You pay for storage while it is paused
⛔ Look elsewhere when
  • The first connection to a paused database fails (error 40613) while it resumes — your app needs retry logic
  • Open sessions and several features (geo-replication, failover groups, LTR…) block auto-pause

▾ Go one level deeper (60 seconds)

Wait types for governance. LOG_RATE_GOVERNOR (database), POOL_LOG_RATE_GOVERNOR (elastic pool), INSTANCE_LOG_RATE_GOVERNOR (instance), plus several HADR_THROTTLE_* waits for replication feedback. The delay is applied while log is generated, not when it is flushed.

Elastic pools. Databases in a pool share its limits; the percentages in resource views are relative to the pool configuration.

Hyperscale replicas. HA replicas (0 to 4) are failover targets and can serve reads with ApplicationIntent=ReadOnly; named replicas (up to 30) have their own compute size and cannot be failover targets; geo-replicas live in another region.

Serverless pause rules. General Purpose serverless auto-pause delay: minimum 15 minutes, default 60; resume typically takes under a minute. Retry settings in drivers matter — a single immediate retry will not outlast a resume.

Managed Instance supports automatic tuning’s force-last-good-plan option only.

Other engines: every managed cloud database has the same idea — AWS RDS/Aurora and Azure Database for PostgreSQL also meter CPU, I/O and connections per instance size; check the provider’s metrics before tuning.

🔥 Interview recall
  • Azure SQL resources have tier-dependent ceilings (CPU, log rate, workers, data I/O). At 100% the service throttles.
  • First check: sys.dm_db_resource_stats (≈1 hour, 15-s rows). Averages under ~90% are healthy; short spikes to 100% are fine.
  • Tiers: General Purpose (remote storage), Business Critical (local SSD, ~1–2 ms), Hyperscale (very large, scale-out reads), Serverless (auto-pause, error 40613 on resume).
  • vCore model offers serverless, Hyperscale and Hybrid Benefit; DTU bundles resources.
  • Automatic tuning: force last good plan on by default; create/drop index off by default. Needs Query Store.
  • IQP features depend on compatibility level; changing it can change plans.
🎤 Say this in an interview
"In Azure SQL Database I add one question to my method: is a resource near its tier limit? I check sys.dm_db_resource_stats for CPU, log write, workers and data I/O. If nothing is near the ceiling it is a query problem and I follow the usual ladder; if log write or CPU is pinned I tune the heaviest queries first and scale the tier only when they are reasonable. I also rely on Query Store with automatic force-last-good-plan, and I remember that serverless needs retry logic on resume."
⚠️ Common trap

Scaling up to fix a bad plan. You pay more to run the same plan and, if the cause is blocking or a spill, nothing improves.

Assuming a tier change is free of side effects. A different tier changes limits and latency; a different compatibility level changes the optimizer. Re-measure after either.

🔍 Query problem

No resource near its limit. The plan, estimates or indexes are the suspect — use the ladder.

📏 Tier problem

A gauge is pinned near 100%. The service is throttling — tune the heaviest consumers or scale.
