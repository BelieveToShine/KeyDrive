▶️ Watch it happen: measure the same way
📖 Why did this need to exist?

Page 9 left you with a fix for one problem — but in a real system you have thousands of queries. Which ones deserve your attention? And once you change something, how do you prove it helped, and keep proving it next week when the data has moved?

Without measurement you are tuning by feel: “it seems faster”. Feelings are shaped by cold caches, other users, and luck. A good engineer uses logical reads (stable) and CPU time (honest), not just a stopwatch.

This page gives you the three lenses and when to use each — and finishes with Query Store, the one that remembers.

🔬 Lens 1 — one query, right now

Turn these on, run the query, read the Messages tab. They are the “before” and “after” numbers for every fix in this lab.

SET STATISTICS IO ON;
SET STATISTICS TIME ON;

SELECT OrderId, OrderDate, Total FROM dbo.Orders WHERE CustomerId = 7;

-- Messages (illustrative):
-- Table 'Orders'. Scan count 1, logical reads 240000, physical reads 0 ...
-- SQL Server Execution Times: CPU time = 900 ms,  elapsed time = 1250 ms.

STATISTICS TIME reports milliseconds spent parsing, compiling and executing. STATISTICS IO reports pages per table: logical (from memory), physical (from disk), read-ahead.

NumberWhat it tells youTrust it for
Logical readsPages touched — the work doneComparing a query before and after a change (stable between runs)
Physical readsPages fetched from diskExplaining a slow first run; ignore for comparisons
CPU timeTime spent computingHonest cost; hard to fake with caching
Elapsed timeWall-clock time including waitingWhat users feel; if far above CPU, something was waiting
Parse and compile timeTime to build the planSpotting queries that are expensive to compile (page 9)
🔬 Lens 2 — the whole server, since it started

Dynamic management views (DMVs) hold running totals. They answer “which queries cost the most?” — but they only know about plans still in the cache.

SELECT TOP (5)
       qs.total_logical_reads,
       qs.execution_count,
       qs.total_logical_reads / qs.execution_count AS avg_reads,
       SUBSTRING(st.text, 1, 120) AS query_start
FROM   sys.dm_exec_query_stats AS qs
CROSS APPLY sys.dm_exec_sql_text(qs.sql_handle) AS st
ORDER BY qs.total_logical_reads DESC;

Cumulative totals: total_logical_reads is the lifetime sum across executions since the plan was compiled, and a row only updates when a query finishes. A cheap query run a million times can outrank an expensive one run once — that is why the example also shows the average.

Waits. sys.dm_os_wait_stats aggregates completed waits across the instance since start (not kept across restarts). In Azure SQL Database there is also sys.dm_db_wait_stats. Lock waits point to data contention; page I/O latch waits point to slow I/O.

🗄️ Lens 3 — Query Store, the one that remembers
-- is it on? (check, don't assume — the default may differ by product)
SELECT actual_state_desc FROM sys.database_query_store_options;

ALTER DATABASE CURRENT SET QUERY_STORE = ON;

-- force a plan for a regressed query (ids come from the report)
EXEC sp_query_store_force_plan @query_id = 48, @plan_id = 49;

The ids 48 and 49 are the docs’ own example values. Only plans that Query Store has already recorded can be forced; forcing a plan that has since become invalid (for example after an index is dropped) can fail.

▾ Go one level deeper (60 seconds)

Query Store’s three stores. A plan store, a runtime-statistics store and a wait-statistics store. It retains multiple plans per query, so it can enforce a policy that directs the optimizer to use a specific plan.

Estimated, not actual. The plans Query Store keeps are estimated plans; the actual row counts come from a plan you capture yourself or from runtime statistics.

Tuning recommendations. sys.dm_db_tuning_recommendations lists queries that regressed and the plan that might be used instead; with FORCE_LAST_GOOD_PLAN automatic tuning, SQL Server applies it and monitors the result. Forcing the last good plan is preferred because older plans can be invalid after statistics or index changes.

Azure SQL Database adds its own tooling on top (Query Performance Insight, automatic tuning, Intelligent Insights) — covered on page 15.

Other engines: PostgreSQL uses pg_stat_statements and, on Azure Database for PostgreSQL, its own Query Store; EXPLAIN (ANALYZE, BUFFERS) is the “one query now” lens there.

🔥 Interview recall
  • Three lenses: STATISTICS IO/TIME (one query now), DMVs (cumulative since start), Query Store (history).
  • Compare logical reads and CPU time, not just elapsed time.
  • DMV counters are cumulative and only cover plans still in the cache; wait stats reset on restart.
  • First question: running or waiting? Running → plans/resources; waiting → locks, I/O, tempdb, memory grants.
  • Query Store records queries, plans, runtime and wait stats; Regressed Queries + force plan; FORCE_LAST_GOOD_PLAN automates it.
  • Only plans Query Store has recorded can be forced; check force failures afterwards.
🎤 Say this in an interview
"I measure with the narrowest lens that answers the question: STATISTICS IO and TIME for one query, comparing logical reads and CPU, DMVs like dm_exec_query_stats to find the top consumers, and Query Store for history, regressions and plan forcing. First I decide whether the query is running or waiting. After a change I re-measure the same query with the same parameter and keep watching Query Store, including for the outlier parameter values."
⚠️ Common trap

Judging a fix by one elapsed-time reading. Caches, other users and parameter choice move it more than most fixes do. Use logical reads and CPU on the same input.

Forcing a plan and forgetting it. A forced plan hides the root cause and can fail silently after a schema change. Track it, and fix the underlying problem.

📈 DMV statistics

Cumulative totals in memory; vanish when the plan is evicted or the server restarts.

vs.
🗄️ Query Store

Persisted history of plans and runtime/wait statistics; survives restarts and shows change over time.
