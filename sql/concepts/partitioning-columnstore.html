To aggregate hundreds of millions of rows, read less — by column and by range.

Why B-trees stop helping for analytics, how columnstore and batch mode work, what partition elimination really does, and when not to use either.

❓ "A report aggregates 500 million rows and takes 90 seconds. How would you make it faster?"
👁 See it first
🎯 B-trees are built for finding a few rows. For aggregating hundreds of millions, store data by column (columnstore) and split it by range (partitioning) so the engine reads less.
▶️ Watch it happen: read less
📖 Why did this need to exist?

Everything so far was about finding a few rows fast: seeks, lookups, covering indexes. But an analytics question — “total sales per month for the last three years” — touches every row of a huge table. No B-tree seek can help: the work is a big scan and an aggregate.

For those workloads the cost is dominated by how many bytes you must read. Two ideas cut that number: store by column so only the needed columns are read (and compress well, because a column holds similar values), and partition by range so old data is skipped entirely.

This page covers both, and — just as important — when not to use them.

🧰 Four tools for big tables

🌲 Rowstore B-tree

the default; point lookups and updates✅ Pick it when
  • Transactions: find, insert and update individual rows
  • Selective queries that seek a few rows
⛔ Look elsewhere when
  • Scanning and aggregating huge tables all day

🧱 Clustered columnstore

the table stored by column✅ Pick it when
  • Big fact tables in a data warehouse
  • Scans and aggregates over many rows — typically about 10× compression
  • Queries touching a few columns of many
⛔ Look elsewhere when
  • Single-row lookups and frequent single-row updates (DML runs row by row)

➕ Nonclustered columnstore on a rowstore table

analytics on live OLTP data✅ Pick it when
  • Real-time analytics without a separate warehouse
  • Costs on average about 10% more storage
⛔ Look elsewhere when
  • It is an extra index to maintain on every write (page 13)

🗂️ Table partitioning

split one table by a range✅ Pick it when
  • Archiving and loading by whole ranges (sliding window)
  • Queries that filter on the partitioning column — partitions that cannot match are skipped
⛔ Look elsewhere when
  • Queries that do not filter on the partitioning column — no benefit, and can even get worse
  • Using it as a “make everything faster” switch
🧬 How columnstore stores data
ROWGROUP

📦 A slice of rows

The table is cut into rowgroups; each is compressed column by column.

SEGMENT

🧱 One column of a rowgroup

Stores its min and max, so whole segments can be skipped without being read.

DELTASTORE

🧺 A waiting room

Small inserts land in a B-tree deltastore until enough rows exist to compress.

BATCH MODE

⚡ Rows in groups

Operators process batches (usually up to about 900 rows) instead of one row at a time — typically 2–4× faster.

Bulk loads of at least 102,400 rows compress straight into the columnstore and skip the deltastore, so load in big batches.

🗂️ Partition elimination

Warning: partitioning rarely speeds up queries on its own. If a query does not filter on the partitioning column nothing is skipped — and the overhead of many partitions can make it worse. Query design and indexes remain the main performance levers.

🧪 Plan lab · a 500-million-row aggregate

Question: total of Total for 2026 on a 500-million-row Orders history table (about 50 GB as rowstore). All numbers illustrative.

SELECT SUM(Total) FROM dbo.Orders
WHERE OrderDate >= '20260101' AND OrderDate < '20270101';

Bare-column range, as in page 8 — a function around OrderDate would block segment and partition elimination too.

CREATE CLUSTERED COLUMNSTORE INDEX CCI_Orders ON dbo.OrdersHistory;

Illustrative: converts the history table to columnstore. For an active OLTP table you would add a nonclustered columnstore index instead.

▾ Go one level deeper (60 seconds)

Ordered columnstore. Sorting data before compression reduces the overlap of segment ranges so segment elimination works better — mostly for the first key column. Since SQL Server 2022 segment elimination also works on string, binary and GUID types.

Batch mode limits. Not every operator supports batch mode, and DML (insert, update, delete) runs one row at a time.

Index alignment. Indexes built on the same partition function and scheme are storage-aligned, which simplifies sliding-window management (it is not required).

Static vs dynamic elimination. With a constant in the query the optimizer can eliminate partitions at compile time; with a parameter it can eliminate at run time.

Other engines: PostgreSQL has declarative partitioning and uses partition pruning the same way; column-store layouts exist as extensions or in warehouse products (the idea transfers; the commands do not).

🔥 Interview recall
  • Rowstore B-tree: best for finding and changing a few rows. Columnstore: best for scanning and aggregating many rows over a few columns.
  • Columnstore = rowgroups → column segments with min/max → skipping; typically ~10× compression; batch mode typically 2–4× faster.
  • Small inserts go to the deltastore; bulk loads of ≥ 102,400 rows compress directly.
  • Partitioning = partition function + scheme; elimination only works when the query filters on the partitioning column.
  • ALTER TABLE … SWITCH moves whole partitions as a metadata operation.
  • Partitioning alone rarely speeds queries up; it is mainly a manageability tool.
🎤 Say this in an interview
"B-trees are made for finding a few rows. For analytic scans over hundreds of millions of rows I use columnstore: data stored and compressed by column, so only the needed columns are read, segments are skipped using min/max, and operators run in batch mode. I add range partitioning when I need fast archiving or when queries filter on the partition column, and I keep a rowstore index if I also need point lookups."
⚠️ Common trap

Partitioning to “speed things up”. Without a filter on the partitioning column nothing is skipped; you only added complexity.

Columnstore on an OLTP table. Single-row updates and lookups are not what it is for — use a nonclustered columnstore beside the B-tree, or keep the workloads apart.

🌲 Rowstore

Rows together. Fast to find and change one row; reads whole rows even when you need one column.

vs.
🧱 Columnstore

Columns apart and compressed. Fast to scan and aggregate; slow for single-row work.
