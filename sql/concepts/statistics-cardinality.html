📖 Why did this need to exist?

The last page ended on the best clue in any plan: estimated rows vs actual rows. A plan built for 50 rows and handed 4,000 is a plan built for a different world.

Where does the 50 come from? Counting would be as slow as the query itself. So the engine keeps statistics: a compact description of how values are spread in a column. The optimizer uses them to estimate how many rows each step will produce — the cardinality estimate — and then picks the cheapest plan for that estimate.

That makes statistics the quiet foundation of everything on the next pages: join choice, memory, even whether your new index gets used.

🔬 What is inside a statistics object
HISTOGRAM

📊 Up to 200 steps

Built on the first key column: values are sorted, counted, and grouped into at most 200 steps.

DENSITY

🧮 How repetitive?

For several columns together, “density” says how many duplicates to expect. Helps multi-column filters.

ROW COUNT

🔢 How big, how old

Total rows and when the summary was last updated.

THE RULE

⚖️ Even spread inside a step

Within one step, values are assumed to be spread evenly with the same frequency.

🧾 Reading a histogram (DBCC SHOW_STATISTICS)

Each row of the histogram is one step. These are the columns you will see — the numbers below are illustrative.

DBCC SHOW_STATISTICS ('dbo.Customers', 'IX_Customers_City');

Shows the header (rows, last updated), the density, and the histogram. A great first stop when estimated and actual rows disagree.

⏳ How statistics go stale

Automatic updates. The database option AUTO_UPDATE_STATISTICS is ON by default and the docs recommend keeping it that way; with it off, even statistics marked out of date are not refreshed and plans can degrade. The engine counts row changes since the last update and compares them to a threshold; for tables above 500 rows the classic threshold is 500 + 20% of the rows, and at compatibility level 130 and higher a lower, size-dependent threshold applies to big tables so they refresh more often.

🧪 Plan lab · fix the tour plan’s bad guess

On the last page the Customers seek estimated 50 rows and got 4,000. Test the “stale statistics” hypothesis — and only that one.

-- 1. look: when were the statistics last updated, and what do they say?
DBCC SHOW_STATISTICS ('dbo.Customers', 'IX_Customers_City');

-- 2. change ONE thing
UPDATE STATISTICS dbo.Customers IX_Customers_City WITH FULLSCAN;

-- 3. re-run the same query with the ACTUAL plan on, compare:
--    before: Index Seek estimated 50  / actual 4,000
--    after : Index Seek estimated 4,000 / actual 4,000   (illustrative)

FULLSCAN reads every row to build the histogram — accurate, but slower than the default sampling on very large tables. Numbers are illustrative.

🎬 Real-world scenarios
🆕
Last night’s orders

The report asks for rows added since midnight. The histogram’s last step ends yesterday, so there is no estimate for today.

→ Ascending-key problem
📦
Bulk import

10 million rows loaded in minutes; queries right after are slow until the engine refreshes the statistics.

→ Update statistics after big loads
🏙️
One giant city

90% of customers live in one city. “Even spread” is wrong for that step.

→ Check the histogram step
☁️
“Is auto-update on in Azure SQL?”

Do not assume — check the database setting (is_auto_update_stats_on in sys.databases).

→ Verify, don’t guess
▾ Go one level deeper (60 seconds)

Cardinality estimation (CE) is the part of the optimizer that turns statistics and your predicates into row estimates. Newer database compatibility levels use a newer CE model; the same query can get a different estimate — and plan — after an upgrade.

Multi-column predicates. The estimator uses density information to improve estimates for queries that filter several columns of the same table, but it cannot know every correlation in your data.

Other engines: PostgreSQL keeps column statistics too (refreshed by ANALYZE) and its EXPLAIN shows estimated rows — same idea, different command.

🔥 Interview recall
  • Statistics are the optimizer’s summary of a column: a histogram of up to 200 steps plus density information.
  • The optimizer turns them into row estimates (cardinality estimation) and builds the plan around those estimates.
  • Histogram columns: RANGE_HI_KEY, EQ_ROWS, RANGE_ROWS, DISTINCT_RANGE_ROWS, AVG_RANGE_ROWS.
  • Statistics go stale as data changes; auto-update is ON by default and refreshes them after enough changes.
  • Ascending keys, skew within a step and correlated columns are classic estimate-killers.
  • Fix a bad estimate with UPDATE STATISTICS first — one change, then re-measure.
🎤 Say this in an interview
"The optimizer plans from statistics — a histogram of up to 200 steps per column plus density — not from counting rows. When estimated and actual rows diverge I check whether the statistics are stale, whether the column is ascending or skewed, and update statistics as a single controlled change before touching the query or the indexes."
⚠️ Common trap

Rebuilding indexes “to fix statistics”. Statistics and index fragmentation are different things. A rebuild does refresh that index’s statistics as a side effect, but it is a heavy way to do a light job — update the statistics directly.

Turning auto-update off to “save time”. The docs warn it can lead to suboptimal plans and degraded performance.
