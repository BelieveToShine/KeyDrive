Every index slows every write — keep the ones that earn it.

Write amplification, how to find unused and duplicate indexes, and what fragmentation really is — with Microsoft’s rough rules for when to reorganize or rebuild.

❓ "How do you decide which indexes to keep, drop or maintain on a busy table?"
👁 See it first
🎯 Every index speeds up some reads and slows down every write. Index work is a budget — spend it on the indexes that earn it, and clean up the rest.
📖 Why did this need to exist?

Pages 3, 7 and 8 taught you how to add indexes, and each time the plan got faster. It would be easy to conclude: more indexes = faster. Page 12 hinted at the catch — writes hold locks while they update every index.

Over months a database collects indexes: one for a report that no longer exists, one added “just in case”, two that overlap, one suggested by a tool. Reads stay fast, but inserts, updates and deletes quietly get slower, the database grows, and backups and maintenance take longer.

This page is about the other side of the ledger: what an index costs, how to find the indexes that no longer earn their keep, and what “fragmentation” really is — and when it matters.

💸 What each kind of write costs
OperationWhat it must updateWhy it matters

DELETEThe clustered table and every nonclustered indexSame — a purge of millions of rows touches every index
UPDATE of a non-key columnThe table, plus only the indexes that contain that column (as key or INCLUDE)Wide INCLUDE lists make more updates expensive
UPDATE of the clustered keyThe table and every nonclustered index (they all store the clustered key)Why the clustered key should be immutable (page 2)
🕵️ Finding indexes that do not earn their keep

SQL Server counts how each index is used. The counters tell you how many times an index was read (seeks, scans, lookups) versus written (updates).

SELECT OBJECT_NAME(s.object_id) AS table_name, i.name AS index_name,
       s.user_seeks + s.user_scans + s.user_lookups AS reads,
       s.user_updates AS writes
FROM   sys.dm_db_index_usage_stats AS s
JOIN   sys.indexes AS i ON i.object_id = s.object_id AND i.index_id = s.index_id
WHERE  s.database_id = DB_ID() AND OBJECTPROPERTY(s.object_id, 'IsUserTable') = 1
ORDER BY writes DESC;

Illustrative query. The counters start empty whenever the service starts, so “zero reads” soon after a restart proves nothing. Observe across a full business cycle (month-end!) before deciding.

Azure SQL Database can do this for you (automatic tuning’s DROP INDEX option targets indexes unused for 90 days and duplicates, never unique or primary-key indexes) — but that option is off by default.

🧩 Fragmentation: what it is, and when it matters

Does it matter? Mostly for scans: if an index is used mainly for scan operations, removing fragmentation can speed them up; for indexes used mainly for seeks the benefit is much less noticeable. It is not the first suspect when a query is slow — plans, estimates and indexes are (pages 4–9).

Fragmentation (from sys.dm_db_index_physical_stats)Microsoft’s guidanceNotes
up to ≈ 5%Leave it aloneThe benefit is almost always outweighed by the cost of fixing it
between ≈ 5% and ≈ 30%ALTER INDEX … REORGANIZELight on resources; does not update statistics
above ≈ 30%ALTER INDEX … REBUILDHeavier and slower; also refreshes that index’s statistics

Microsoft stresses these cut-offs may vary from case to case — experiment to find what suits your environment. Also check avg_page_space_used_in_percent: page density can drop sharply without fragmentation rising, so a threshold script alone can miss a bloated index. Tiny indexes are not worth maintaining.

Usage statistics caveat. user_updates counts maintenance caused by inserts, updates and deletes; the seek/scan/lookup columns count reads and record when they last happened. All counters reset when the service restarts.

Rebuild vs reorganize. A reorganize defragments the leaf level in place and is interruptible and light; a rebuild creates the index afresh (and rebuilds its statistics). Cut-offs of 5%/30% are Microsoft’s starting point, not a law.

Missing-index suggestions are the opposite problem: they add indexes. Use both lists together (page 7).

Azure SQL automatic tuning. CREATE INDEX and DROP INDEX options verify the effect and revert if there is no significant improvement; index recommendations are not made for tables whose clustered index or heap is larger than 10 GB. FORCE LAST GOOD PLAN is enabled by default; CREATE and DROP INDEX are disabled by default.

Other engines: PostgreSQL reports usage in pg_stat_user_indexes and reclaims space with VACUUM / REINDEX; MySQL InnoDB uses sys.schema_unused_indexes.

🔥 Interview recall
  • Every index must be updated on every INSERT and DELETE; an UPDATE touches the indexes containing the changed columns.
  • Find unused indexes with sys.dm_db_index_usage_stats: reads (seeks + scans + lookups) vs user_updates — counters reset on restart.
  • Candidates, not automatic drops: save the CREATE script, observe a full business cycle.
  • Fragmentation = out-of-order pages and low page density, caused by page splits; it mostly matters for scans.
  • Microsoft’s starting points: under ~5% ignore, 5–30% reorganize, over ~30% rebuild — experiment.
  • Rebuild refreshes statistics; reorganize does not.
🎤 Say this in an interview
"Every index is a sorted copy that every insert and delete must maintain, so I treat indexes as a budget. I look at index usage statistics — reads versus updates — over a full business cycle, drop unused and duplicate candidates after saving their scripts, and keep covering indexes that are heavily read. For fragmentation I follow Microsoft’s rough 5 and 30 percent bands, but only where scans benefit, and I remember that rebuild refreshes statistics and reorganize does not."
⚠️ Common trap

Rebuilding every index every night. It burns CPU, I/O and log for indexes that were barely fragmented, and does little for seek-heavy workloads.

Dropping an “unused” index right after a restart. The counters were reset, and the quarterly job has not run yet.

🔧 REORGANIZE

In-place, light, interruptible. Does not update statistics. For moderate fragmentation.

vs.
🏗️ REBUILD

Builds the index again: heavier and slower, removes all fragmentation, and refreshes its statistics.
