The plan is built for the first value it sees — then shared with everyone.

Why one query can be fast for one customer and slow for another, why SSMS and the app disagree, and the five ways to fix it.

❓ "What is parameter sniffing and how do you diagnose and fix it?"
👁 See it first
🎯 The plan is built for the first parameter value it sees, then shared with everyone — so a plan that is perfect for one input can be terrible for another.
📖 Why did this need to exist?

Page 1 told you plans are cached and reused when the statement text matches. That is a good thing: compiling costs CPU, and most queries want the same plan every time.

But a parameterized query is one statement with many possible inputs, and data is rarely evenly spread (page 5). Customer 42 has 12 orders; one business customer has 80,000. A plan that suits one cannot suit the other (page 7 showed exactly why: lookups explode with the row count).

This is parameter sniffing. It is not a bug — it is the same feature that makes most queries fast — and it explains the most puzzling bug report in SQL: “it is fast in SSMS and slow in the app”.

🔍 See the damage in two pictures
🧪 Plan lab · “fast in SSMS, slow in the app”

A stored procedure GetOrdersByCustomer is slow in production for one customer. You run it in SSMS with that customer’s id — fast. Method, not magic:

  1. Get the app’s plan, not yours. Take the plan from the app’s execution (Query Store or the plan cache), not a fresh one you compile in SSMS — a fresh compile sniffs your value.
  2. Compare compiled vs runtime parameter values. The plan records the value it was compiled for and the value of the current run. Different values + a large cost gap = sniffing.
  3. Test with a recompile. Add OPTION (RECOMPILE) in a test copy. If the query is suddenly fast for the big customer, the cached plan was the cause.
-- Plan A is compiled for the first value it sees...
EXEC dbo.GetOrdersByCustomer @CustomerId = 42;   -- 12 rows → seek + lookups, cached
-- ...and reused for the next call
EXEC dbo.GetOrdersByCustomer @CustomerId = 7;    -- 80,000 rows → same plan → slow

-- the test: compile for each value
SELECT OrderId, OrderDate, Total FROM dbo.Orders
WHERE CustomerId = @CustomerId
OPTION (RECOMPILE);

Illustrative stored procedure and numbers. In the real plan look at the SELECT operator’s properties for the compiled and runtime parameter values.

🧭 Which fix?
🧰 The fixes, side by side

♻️ OPTION (RECOMPILE)

compile a fresh plan on every run✅ Pick it when
  • Rarely-run or wildly varying queries
  • You want the plan built from the actual values
⛔ Look elsewhere when
  • Hot queries: you pay compile CPU on every execution
  • It does not replace the cached plan for other callers of the same text

📌 OPTIMIZE FOR (value)

compile as if the parameter had a chosen value✅ Pick it when
  • One value clearly represents the typical case
  • You know the plan you want
⛔ Look elsewhere when
  • Only one value per variable; you must know the right one
  • Wrong for the outliers by design

🎲 OPTIMIZE FOR UNKNOWN

use the average, not the sniffed value✅ Pick it when
  • You want a stable “middling” plan
  • Same effect as copying the parameter into a local variable
⛔ Look elsewhere when
  • Density averages can be imprecise — the plan may be mediocre for everyone

🪄 PSP optimization

automatic: several plans for one statement✅ Pick it when
  • SQL Server 2022, or Azure SQL Database at compatibility level 160
  • Skewed data with parameterized queries
⛔ Look elsewhere when
  • It considers only the most at-risk predicates (up to three); it does not cover everything
  • Older versions or compatibility levels

▾ Go one level deeper (60 seconds)

How a plan is found. The cache lookup needs the statement to match a cached one character for character, with fully qualified object names. Plans are removed under memory pressure using a cost-based policy, and when statistics or schema change a plan can be recompiled — and a recompile samples the parameter values of that execution.

PSP in detail. On the first compile the optimizer looks at the column statistics histograms, spots non-uniform distributions, and evaluates up to three of the most at-risk parameterized predicates; the engine can then keep multiple active plans for one statement. It is enabled by database compatibility level 160 (SQL Server 2022 and Azure SQL Database).

Optional-parameter plan optimization uses the same multi-plan idea to pick plans depending on whether a parameter is NULL.

Other hints. OPTION (RECOMPILE) builds a plan from current values and its temporary plan does not replace the one in the cache for other callers. DISABLE_PARAMETER_SNIFFING turns sniffing off for a query, but blanket-disabling is rarely the best choice — it throws away the good with the bad.

Other engines: PostgreSQL’s prepared statements choose between custom plans (built for the actual values) and a generic plan; MySQL does not cache plans the same way.

🔥 Interview recall
  • Parameter sniffing = the optimizer compiles for the first parameter value it sees; the plan is cached and shared.
  • It is a feature, not a bug — it hurts only when the data is skewed.
  • Diagnose: compare compiled vs runtime parameter value in the plan; test with OPTION (RECOMPILE).
  • Fixes: RECOMPILE, OPTIMIZE FOR value / UNKNOWN, PSP optimization (SQL Server 2022 / compat 160), or a forced plan from Query Store.
  • Literals in SQL text → every value is a new plan; use real parameters.
  • Always capture the app’s plan — a fresh compile in SSMS sniffs your value, not theirs.
🎤 Say this in an interview
"A parameterized query is compiled once, for the first parameter value it sees, and that plan is cached and reused. With skewed data a plan that is perfect for a small input can be terrible for a large one. I confirm it by comparing the compiled and runtime parameter values in the plan and testing with OPTION (RECOMPILE), then choose a fix: PSP optimization where it is available, otherwise OPTIMIZE FOR or RECOMPILE, or force a known-good plan through Query Store."
⚠️ Common trap

Clearing the whole plan cache in production “to fix it”. Every query in the system must recompile at once, and the next unlucky first call picks the next accidental plan. The problem will return.

Concluding “the server is slow” because SSMS was fast. SSMS compiled a fresh plan for your value; the app was running someone else’s plan.

♻️ Compile every time

OPTION (RECOMPILE): always the right plan for the values, at the price of compile CPU.

vs.
🗃️ Reuse the cached plan

The default: cheap to run, but only as good as the value it was first built for.
