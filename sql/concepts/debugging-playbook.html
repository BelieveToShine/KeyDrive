▶️ Watch it happen: the method
📖 Why did this need to exist?

Pages 1–10 gave you the pieces: how a query runs, how pages and indexes work, how to read a plan, why estimates go wrong, how joins behave, how to hide a column from its own index, how plans get reused, and how to measure. Someone who knows all that can still tune at random — add an index, add a hint, restart, hope.

Random tuning has a name in operations: change roulette. It sometimes works, you never know why, and it leaves behind indexes and hints nobody dares to remove.

The fix is a repeatable method: a fixed order of questions, one change at a time, and a written before-and-after. This page is that method — the one you have seen as a small ladder on every page, now in full.

1 · MEASURE ★

📏 How slow, really?

Time, CPU, pages read — a number, not a feeling.

2 · READ ★

🗺️ Read the plan

What did the engine actually do?

3 · FIND ★

🎯 The biggest wrong thing

Where do estimate and reality disagree most?

4 · GUESS ★

💡 One hypothesis

Missing index? Bad estimate? Hidden column?

5 · CHANGE ★

🔧 Change one thing

Never two at once.

6 · PROVE ★

✅ Re-measure

Same numbers, same query, better result.

📝 The investigation log — five lines that save you later
-- 2026-10-13  GetOrdersByCustomer slow for BigCorp
-- BEFORE : 240,000 reads | CPU 900 ms | elapsed 1,250 ms | plan: seek + 80,000 key lookups
-- FOUND  : Key Lookup = 97% of cost; estimate 12 vs actual 80,000
-- CHANGE : CREATE INDEX IX_Orders_Customer_Date (CustomerId, OrderDate) INCLUDE (Total)
-- AFTER  : 400 reads | CPU 15 ms | elapsed 40 ms | plan: covering seek | small customer unchanged

Keep it next to the index definition (a comment, a ticket, a wiki). Six months later nobody wonders why the index exists — and everybody knows how to prove it still helps.

🚫 What NOT to do
Tempting moveWhy it backfiresDo this instead
Add an index for every slow queryEvery index slows every write, may never be chosen, and overlaps others (page 13 — coming)Read the plan, design one index for the real problem, test it
Reach for hints firstThey freeze today’s data shape into the query and break when the data changesFix estimates and indexes; use a hint only to test a theory
Clear the plan cache, or restart the serverEverything recompiles at once and the next accidental first call picks the next plan; the cause is untouchedFind the cause; force the last good plan if you need a bandage (page 10)
Change two things at onceYou cannot tell which one helped — or which one hurtOne change, then re-measure
Trust cost % or a missing-index suggestion blindlyCost % is an estimate; suggestions are single-query guesses with no key-order or write-cost adviceVerify with the actual plan and logical reads
Compare a cold run with a warm runCaches, not your fix, explain the differenceCompare logical reads on the same input
Buy a bigger tier before reading the planYou pay more to run the same bad plan — and it does nothing if the query is waiting on a lockRead the plan and the waits first (page 15 — coming)
✅ Ten questions before you touch anything
  1. How slow, in numbers — and slower than what?
  2. Always slow, or only sometimes? For which input?
  3. Is it one query or the whole system?
  4. Running (CPU) or waiting (locks, I/O, memory)?
  5. What does the actual plan’s heaviest operator say?
  6. Do estimated and actual rows agree?
  7. Any warnings (spills, type conversion)?
  8. What changed recently: data volume, a deploy, statistics, an index?
  9. What is my single hypothesis, and how will I prove it?
  10. How do I undo the change if it does not work?

▾ Go one level deeper (60 seconds)

CPU vs elapsed. Elapsed time includes waiting; CPU time is time spent computing. When elapsed is far larger than CPU, the query was mostly waiting; when they are close, it was running.

Why “one change at a time” is a statistical rule, not a style rule. With two simultaneous changes you cannot separate their effects, and if performance gets worse you cannot tell which change to roll back. The log makes the experiment repeatable.

Production safety. Prove a fix on a copy with realistic data first. Prefer changes that are easy to undo (a new index you can drop) over changes that are not. Check the query for other inputs — a fix tuned for BigCorp must not break the small customers (page 9).

When the problem is not the query. If the plan is sound and the estimates match, the remaining causes are the amount of data, waits (locks, I/O), or the resources of the service — the next four pages.

Other engines: the ladder is engine-independent. Replace “actual plan” with EXPLAIN (ANALYZE, BUFFERS) in PostgreSQL or EXPLAIN ANALYZE in MySQL, and “Query Store” with pg_stat_statements or the slow-query log.

🔥 Interview recall
  • Method: measure → read the plan → find the biggest wrong thing → ONE hypothesis → ONE change → prove with the same measurement → repeat.
  • First split: one query or everything? Then waiting or running? Then estimates ≈ actual?
  • Write the before/after numbers down (an investigation log).
  • Do not: index everything, hint first, clear the plan cache, change two things, trust cost % blindly, compare cold with warm, buy a tier before reading the plan.
  • Compare logical reads and CPU on the same input; check the other inputs too.
  • A wrong hypothesis is information — go round the loop again.
🎤 Say this in an interview
"I don’t tune at random. I measure a baseline with logical reads and CPU, decide whether the query is running or waiting, read the actual plan for the heaviest operator and for estimated-versus-actual gaps, form one hypothesis, make one change, and re-measure with the same input. I write down before and after, and I check the other parameter values so I don’t fix one customer and break another."
⚠️ Common trap

Declaring victory on one run. A faster run proves nothing until the same input, the same lens, the same cache state and the other inputs agree.

Skipping the log. Without it, the next person (or you in six months) removes the “weird” index and the slow query returns.

🎲 Tuning by feel

Add an index, add a hint, restart, hope. Sometimes works. Nobody knows why.

vs.
🧪 Tuning by experiment

Baseline, hypothesis, one change, same measurement. Always explainable and repeatable.
