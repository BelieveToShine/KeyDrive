Fast alone, slow together — because waiting is not computing.

Locks, blocking, deadlocks and isolation levels: how to find the head blocker, how to read a deadlock graph, and the fixes that actually work.

❓ "A query is slow only when many users are on the system. How do you find out if blocking is the cause, and what do you do?"
👁 See it first
🎯 Locks make concurrent changes safe — and make sessions wait. Blocking is one session holding a lock too long; a deadlock is two sessions each waiting for the other.
📖 Why did this need to exist?

The last page ended on a worry: a query that is fast alone can still crawl when many run together. Everything so far (plans, indexes, statistics) was about how much work one query does. This page is about waiting.

The database promises that concurrent transactions do not see each other’s half-finished work. To keep that promise it uses locks. Locks are not a bug — they are the price of correctness. The trouble starts when a transaction holds them for too long, or when two transactions take them in opposite order.

This is why page 10’s very first question was “running or waiting?”. Here is the waiting side, with the tools to find the blocker and the fixes that actually work.

🔑 Two lock kinds you must know
Held by →
Asked by ↓		Shared lock (a reader)Exclusive lock (a writer)
Wants to read (shared)✅ proceeds — readers share⏳ waits for the writer to finish
Wants to write (exclusive)⏳ waits for the readers to finish⏳ waits — one writer at a time

With classic lock-based READ COMMITTED, a reader needs a shared lock, so a writer’s exclusive lock blocks it — exactly session 77 above. Row versioning (below) removes that reader-versus-writer wait.

🔎 Finding the head blocker

Microsoft’s four steps: (1) find the head blocker, (2) find the query and transaction holding the locks, (3) understand why it holds them so long, (4) redesign the query or transaction.

-- who is waiting, and who are they waiting for?
SELECT r.session_id, r.blocking_session_id, r.wait_type, r.wait_time,
       SUBSTRING(t.text, 1, 100) AS sql_text
FROM   sys.dm_exec_requests AS r
CROSS APPLY sys.dm_exec_sql_text(r.sql_handle) AS t
WHERE  r.blocking_session_id <> 0;     -- 0 means “not blocked”

-- walk up the chain: the session that is NOT itself blocked is the head blocker.
-- then see what it holds:
SELECT * FROM sys.dm_tran_locks WHERE request_session_id = 51;

Illustrative. A point-in-time query misses blocking that has already cleared; for short-lived blocking use the blocked-process report (an Extended Events event).

Classic head-blocker pattern: a session that is sleeping with an open transaction — the app timed out or cancelled without issuing the ROLLBACK or COMMIT. It will not resolve itself. KILL ends the session, but it is a last resort; fix the application’s transaction handling. A session that is rolling back should be left to finish.

☠️ Deadlocks

Reading a deadlock graph (captured with the database_xml_deadlock_report Extended Events event) has three parts: a victim list, a process list (each session’s statement — and a plan hash you can look up in Query Store), and a resource list (what each one held and wanted). In the visual view the processes are ovals and the victim is crossed out.

🧭 Isolation levels — how much do you want to see of other people’s changes?
LevelYou may see…How it works
READ UNCOMMITTEDother sessions’ uncommitted (“dirty”) dataNo shared locks — fast, unsafe
READ COMMITTED (locks)only committed data — but values can change between two reads of yoursShared lock while reading; blocks behind writers
READ COMMITTED SNAPSHOT (RCSI)only committed data, as of the start of each statementRow versions: readers do not block writers, writers do not block readers
REPEATABLE READthe rows you read stay the same, but new rows may appear (“phantoms”)Holds shared locks to the end of the transaction
SNAPSHOTa consistent picture as of the start of your transactionRow versions for the whole transaction
SERIALIZABLEas if transactions ran one at a timeStrongest — and the most blocking

Defaults. RCSI is on by default in Azure SQL Database; in SQL Server it is off by default. Microsoft recommends the row-versioning form of READ COMMITTED for all applications, unless an application depends on the blocking behaviour of the lock-based form. Higher isolation levels and RCSI being turned off are listed among the causes of blocking.

🧰 What actually reduces blocking

⏱️ Shorter transactions

hold locks for less time✅ Pick it when
  • Never wait for a user, an API or a queue inside a transaction
  • Commit as soon as the changes are done
  • Fewer statements per transaction
⛔ Look elsewhere when
  • Splitting a transaction that must be atomic — correctness comes first

🧬 Row versioning (RCSI / snapshot)

readers stop waiting for writers✅ Pick it when
  • Many readers, some writers
  • Already the default in Azure SQL Database
  • Snapshot is best scoped to the transaction, not the whole database
⛔ Look elsewhere when
  • It does not stop writer-versus-writer blocking or deadlocks

📇 Better indexes

lock fewer rows✅ Pick it when
  • A scan that finds the row to update touches (and may lock) more than a seek would
  • Indexes shorten the time a statement holds locks
⛔ Look elsewhere when
  • Extra indexes also add lock and write work — page 13

🔁 Retry logic

for deadlock victims✅ Pick it when
  • Deadlocks cannot be fully eliminated
  • Retry the whole transaction a few times with a short pause
⛔ Look elsewhere when
  • Retrying forever hides a design problem

Lock granularity. The engine can lock a row, a page or a whole table, and may escalate many small locks into a bigger one. Row versioning reduces the locks a transaction needs and, with them, lock escalations and deadlocks.

RCSI is not magic. Readers no longer block writers and writers no longer block readers, but writers still block writers, and deadlocks can still happen. SNAPSHOT can also block and deadlock because transactions may hold locks on versioned data that others need.

Choosing the victim. The engine usually picks the transaction that is cheapest to roll back; SET DEADLOCK_PRIORITY can influence the choice.

Azure SQL Database. Changing the RCSI setting is done with ALTER DATABASE run from the master database. The deadlock ring buffer used for capture is capped at 4 MB.

Other engines: PostgreSQL uses row versions (MVCC) by default, so readers rarely block writers; deadlocks and long-held locks still occur, and pg_locks / pg_stat_activity show who waits for whom.

🔥 Interview recall
  • Blocking = one session holds a lock too long; the others wait. Deadlock = a cycle of waits; the engine kills one victim.
  • Elapsed ≫ CPU means waiting. Walk the blocking_session_id chain to the head blocker.
  • Classic head blocker: a sleeping session with an open transaction.
  • Fixes: short transactions (never wait for a user or an API inside one), row versioning, better indexes, retry for deadlock victims.
  • RCSI is on by default in Azure SQL Database; Microsoft recommends row-versioning READ COMMITTED for most applications.
  • A deadlock graph has a victim list, a process list and a resource list.
🎤 Say this in an interview
"When a query is slow but CPU is low, it’s waiting. I find the blocking_session_id chain to the head blocker and look at its transaction — often a session with an open transaction held across a slow call. I fix it by shortening the transaction, I rely on row versioning (RCSI, the Azure SQL default) so readers don’t queue behind writers, and for deadlocks I capture the graph, make access order consistent, and retry the victim."
⚠️ Common trap

Using NOLOCK / READ UNCOMMITTED to “fix” blocking. You trade waiting for wrong answers (dirty reads). Row versioning gives you non-blocking reads that are still correct.

Killing the blocker every time. It hides the application bug that opens transactions and never closes them.

⏳ Blocking

One session waits for another’s lock. It ends when the holder commits or rolls back.

vs.
☠️ Deadlock

A cycle: A waits for B and B waits for A. It never ends by itself — the engine picks a victim.
