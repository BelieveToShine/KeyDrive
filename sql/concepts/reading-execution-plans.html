A plan is the engine explaining itself. Here is a five-step routine, an operator cheat sheet, and one fully diagnosed example.

❓ "How do you read a SQL execution plan, and what do you look at first?"
👁 See it first
🎯 Read a plan right to left, start at the fattest arrow and biggest cost, then check one thing everywhere: did the engine guess the row counts right?
📖 Why did this need to exist?

Page 3 showed a plan with two or three boxes. Real plans have dozens, nested, with numbers everywhere. Staring at them without a method is how people end up “fixing” the wrong operator.

The plan is the engine’s own explanation of what it did. This page turns it into a reading routine you can apply to any plan in under a minute: where to look first, what each operator means, and which number is the most useful clue of all — the gap between estimated and actual rows.

🧭 The reading routine — five steps
1 · DIRECTION

⬅️ Right to left, top to bottom

Data flows from the leaf operators on the right into SELECT on the left. Arrows show that flow.

2 · WEIGHT

🎯 Fattest arrow, biggest cost

Thick arrow = many rows. High cost % = big estimated share. Start at the heaviest one.

3 · GUESS

📐 Estimated vs actual rows

A big gap means the optimizer planned for a different world. Often the root cause.

4 · WARNINGS

⚠️ Warning icons and scans

Look for warning markers and for scans that read a lot to return a little.

5 · PROPERTIES

🔍 Open the properties

Click an operator: seek predicate vs residual predicate, output columns, row counts.

📖 Operator cheat sheet — what you will meet most
OperatorPlain EnglishAsk yourself
Index Seek / Clustered Index SeekNavigates the tree to the matching rangeIs the range small? Check logical reads
Index Scan / Clustered Index Scan / Table ScanReads all rows of the index, clustered table or heap (the last one is a heap)Is it reading far more than it returns?
Key LookupFetches the missing columns from the clustered table, once per row; always paired with Nested LoopsHow many times does it run? (page 7)
Nested LoopsFor each row on the top input, probe the bottom inputIs the outer side small?
Hash MatchBuilds a hash table from one input and probes it with the other (joins, aggregates)Is it using lots of memory for big inputs?
Merge JoinWalks two sorted inputs side by sideAre both inputs already sorted?
SortPuts rows in orderCould an index already provide the order?
Parallelism (yellow circle with arrows)Part of the plan ran on several threadsParallel can be good — but a tiny query rarely needs it

A logical operator describes what must be done; a physical operator is the algorithm that does it (and carries the cost). Plans show physical operators.

🧪 Plan lab · diagnose the tour plan

You are handed the plan at the top of this page. Walk the five steps out loud.

  1. Direction. Two inputs meet in a Hash Match, which feeds SELECT.
  2. Weight. The Clustered Index Scan of Orders: 85% of the cost, a million rows. It is the heaviest thing, so look at it first.
  3. Guess. The Index Seek on Customers estimated 50 rows and got 4,000 — the optimizer expected a tiny customer list and was wrong by about 80 times. A wrong estimate on a join input is dangerous: the join sizes its memory for the small guess (page 6 shows what happens next). Page 5 explains why such errors happen.
  4. Warnings. None shown on this plan — but a scan feeding a join is worth a question, and a hash join whose input was underestimated is a prime suspect for a spill (page 6).
  5. Properties. Open the scan: it has no seek predicate. The join column Orders.CustomerId is not indexed — exactly the fix from the last page.
-- two hypotheses, tested one at a time
-- 1) is the estimate stale?
UPDATE STATISTICS dbo.Customers;

-- 2) can the join seek into Orders?
CREATE NONCLUSTERED INDEX IX_Orders_CustomerId ON dbo.Orders (CustomerId);

Change ONE thing, re-run with the actual plan on, compare logical reads and the plan shape. Never apply both and guess which one helped.

▾ Go one level deeper (60 seconds)

Estimates and percentages always come from the optimizer. Even in an actual plan the “cost %” numbers are estimates; only the row counts and runtime figures are real.

The actual plan can differ from the estimated one. If the real row counts differ from the estimate, the engine can change the plan while it runs to be more efficient.

Plans are XML. What SSMS draws is XML underneath; you can save a plan, send it to a colleague, and open it graphically. SSMS can also compare two plans side by side.

Other engines: PostgreSQL’s EXPLAIN (ANALYZE, BUFFERS) prints the same story as indented text: each node shows estimated rows next to actual time, rows and loops. Same reading routine, different notation.

🔥 Interview recall
  • Read right to left, top to bottom; arrows are data flow, thickness = rows.
  • Start with the heaviest operator (cost % and fat arrows).
  • Compare estimated vs actual rows on every operator — a big gap is the best single clue.
  • Cost % is always an estimate; only the actual plan has real row counts and runtime information.
  • Estimated plan = no execution; actual plan = executes the query. Both need SHOWPLAN permission.
  • Key Lookup always travels with Nested Loops.
🎤 Say this in an interview
"I read an actual execution plan right to left, start with the heaviest operator and the thickest arrows, and compare estimated with actual row counts everywhere. A large gap usually points to statistics; a scan carrying most of the cost points to a missing or unusable index. I change one thing and re-measure with logical reads."
⚠️ Common trap

Trusting cost %. It is the optimizer’s own estimate, so if the estimates are wrong the percentages are wrong too. A “5%” operator can be the real bottleneck.

Fixing the loudest operator instead of the earliest wrong guess. A scan may be a symptom: the real mistake is often an estimate several operators earlier.
