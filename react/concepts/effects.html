Concept 4 of 12 · ⚛️ Measure & optimise

An effect is for the world outside React — nothing else.

How an effect runs (setup, dependencies, cleanup), what Strict Mode does, and how to avoid effects you do not need.

❓ "When should I use useEffect — and when is it the wrong tool?"
👁 See it first
🎯 An effect keeps your component in sync with something outside React (network, timer, subscription). If there is no outside system, you do not need an effect.
▶️ Watch it happen: syncing with the outside
📖 Why did this need to exist?

Pages 1–3 kept everything inside the render. But real components must talk to the world: open a connection, start a timer, read the window size. Rendering must stay pure, so React gives that work its own place: after the commit.

The danger runs the other way: effects are so easy to write that people use them for work that never needed one — calculating a value from state, reacting to a click, resetting a form. Every such effect adds an extra render and a place for bugs.

So this page has two halves: how an effect lives (setup, dependencies, cleanup), and how to avoid writing one when you do not need it.

🧭 Do you even need an effect?
📋 The dependency array
You writeThe effect runsUse it for
useEffect(fn) — no arrayAfter every commitAlmost never; easy to cause loops
useEffect(fn, [])After the first commit (mount), cleanup on unmountOnly when the effect truly reads no props or state
useEffect(fn, [a, b])After the first commit, and again when a or b changed (compared with Object.is)Normal case: list every reactive value the effect reads

Let the linter fill the array. Forcing a wrong array (to “run only once”) is the usual cause of stale values and bugs. In development, Strict Mode runs one extra setup + cleanup cycle on mount to check your cleanup is correct — that is why you may see a request or a connect twice in development only.

🧪 Render lab · the effect that renders twice

ShopUI’s product list filters by the search text. Before: filtered products are copied into state by an effect. After: they are calculated during render. Type one character.

// ❌ Before — extra state + effect
const [filtered, setFiltered] = useState(products);
useEffect(() => { setFiltered(products.filter(p => p.name.includes(query))); }, [products, query]);

// ✅ After — calculate during render
const filtered = products.filter(p => p.name.includes(query));

🧪 Cleanup lab · the listener that never leaves
useEffect(() => {
  const onResize = () => setWidth(window.innerWidth);
  window.addEventListener('resize', onResize);
  return () => window.removeEventListener('resize', onResize);   // cleanup mirrors setup
}, []);

Without the returned cleanup, every mount of the component adds another listener that is never removed — a leak that Strict Mode’s extra mount makes visible in development.

▾ Go one level deeper (60 seconds)

Dependencies are reactive values — props, state, and anything declared in the component body. Each is compared with Object.is between renders.

Each render has its own effect. An effect “sees” the props and state of the render that created it — that is the snapshot idea from page 2, applied to effects.

Data fetching in effects works for small cases but has races and no caching; page 9 covers Suspense and data libraries.

Not for events. “When the user clicks buy, send an order” is an event handler, not an effect.

🔥 Interview recall
  • Effects run after the commit and synchronise with an outside system.
  • Setup and cleanup must mirror each other; cleanup runs before the next setup and on unmount.
  • The dependency array lists every reactive value the effect reads, compared with Object.is.
  • Strict Mode runs one extra setup + cleanup in development only.
  • Derive values during render; handle user actions in event handlers; reset with a key.
  • An effect that only sets state from other state usually means an extra render you can remove.
🎤 Say this in an interview
"Effects are for synchronising with something outside React. They run after the commit, they must clean up after themselves, and their dependencies must list everything reactive they read. Before writing one I ask whether the value can be calculated during render, whether it belongs in an event handler, or whether a key can reset the state — most effects I see in reviews are one of those."
⚠️ Common trap

Using an effect to “keep state in sync with other state”. It doubles the renders and shows stale frames. Calculate instead.

Silencing the dependency lint rule. It turns a warning into a stale-value bug.

🪝 Event handler

Runs because of a specific user action. Where side effects of that action belong.

⏱️ Effect

Runs because the component appeared or a value it reads changed. For syncing with the outside.
