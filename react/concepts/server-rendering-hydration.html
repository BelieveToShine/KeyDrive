Send finished HTML first — then make it interactive.

Client-only versus server rendering, how hydration works and why it must match, and what Server and Client Components change.

❓ "What is hydration, and how do Server Components differ from server-side rendering?"
👁 See it first
🎯 Send finished HTML first so users can read, then hydrate it so it becomes interactive. Server Components go one step further: some components never ship to the browser at all.
▶️ Watch it happen: HTML first, then interactive
📖 Why did this need to exist?

Pages 1–9 assumed everything runs in the browser. That means the user waits for JavaScript to download, run and fetch data before seeing anything — the slow first paint that data fetching (page 9) could not fully fix.

Server rendering moves the first render to the server: the response already contains the page. But HTML alone is dead — buttons need handlers — so the browser still downloads the same JavaScript and React hydrates the HTML. The code ships twice in effect: once as HTML, once as JavaScript.

Server Components attack that cost: components that only display data run on the server and send their output, not their code.

🔬 Hydration must match
// ❌ different output on the server and in the browser (isBrowser = a check for window)
function Price() {
  return <span>{isBrowser ? localPrice : '…'}</span>;
}
// ✅ same first render everywhere; use an effect for browser-only data
function Price() {
  const [price, setPrice] = useState('…');
  useEffect(() => { setPrice(readLocalPrice()); }, []);
  return <span>{price}</span>;
}

hydrateRoot expects the HTML it adopts to be identical to what the client would render. Since React 18 a mismatch is an error: React falls back to client rendering up to the closest Suspense boundary.

▾ Go one level deeper (60 seconds)

Streaming. For interactive apps the docs point to renderToPipeableStream on the server and hydrateRoot on the client; with Suspense (page 9) parts of the page can be sent as they become ready. The older renderToString does not stream: for a suspended part it emits the nearest Suspense fallback HTML and the client then renders it.

Stability. React 19 Server Components are described as stable, but the underlying APIs used to build a bundler or framework do not follow semver and may change between minor versions.

Security. The React team published a critical vulnerability disclosure for React Server Components in December 2025; keep React and your framework up to date.

In practice most teams get server rendering and Server Components through a framework rather than wiring them by hand.

🔥 Interview recall
  • Server rendering sends finished HTML; hydration attaches handlers to it (hydrateRoot).
  • The client’s first render must match the server HTML; mismatches are errors that fall back to client rendering up to the closest Suspense boundary.
  • Static generation renders at build time; server rendering renders per request.
  • Server Components render ahead of time, cannot use state hooks, and ship no component code; Client Components use 'use client'.
  • 'use server' marks Server Functions (network calls with serialised arguments), not Server Components.
  • Treat Server Function arguments as untrusted; validate and authorise.
🎤 Say this in an interview
"With client-only rendering users see nothing until the JavaScript has run. Server rendering sends the content as HTML and React hydrates it afterwards, as long as the first client render matches the server output. Server Components go further by running ahead of time and sending only their output, so only the interactive Client Components add to the bundle, and I treat Server Function arguments as untrusted input."
⚠️ Common trap

Assuming “visible” means “interactive”. Between HTML arriving and hydration finishing, clicks may do nothing.

Putting 'use client' at the top of the tree. Everything below it ships to the browser, undoing the benefit.

🖥️ Server-rendered

HTML made on the server; the same components also run in the browser to hydrate.

vs.
🧩 Server Component

Runs only on the server (ahead of time); its code is not sent to the browser.
