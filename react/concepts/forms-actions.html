📖 Why did this need to exist?

Every real app has forms: login, search, checkout. Forms mix two jobs — editing (what is in each field right now?) and submitting (send it, show progress, show the result). The built-in tools handle them differently.

Page 9 gave you transitions and Suspense; React 19 builds form actions on them, so submitting becomes a transition with pending state included. This page shows which approach to choose for editing, and the hooks for submitting.

The ShopUI checkout (12 fields) is the running example: it is where a naïve “everything is state” approach starts to cost renders.

📨 The submit lifecycle
🧪 Forms lab · the 12-field checkout
// Controlled — one state object; every key re-renders Checkout and its fields
const [form, setForm] = useState(initialForm);

// Form action — React passes FormData; pending and result come from hooks
async function placeOrder(prevState, formData) {
  const errors = validate(Object.fromEntries(formData));
  if (errors) return { errors };
  await submitOrder(formData);
  return { ok: true };
}
const [result, formAction, isPending] = useActionState(placeOrder, {});
<form action={formAction}>…<SubmitButton /></form>   // SubmitButton calls useFormStatus()

▾ Go one level deeper (60 seconds)

Actions are transitions. A function passed to action runs in a transition, so the page stays responsive and React can track pending state. Unlike onSubmit you do not call preventDefault.

useOptimistic returns the passed value unless an action is pending; then it returns the optimistic value you set. Call its setter inside an action or transition.

Server Functions (page 10) can be passed as form actions, so a form can submit to the server directly; treat the submitted data as untrusted.

🔥 Interview recall
  • Controlled = state holds the text (value + onChange); uncontrolled = the DOM does (defaultValue).
  • An input must not switch between controlled and uncontrolled.
  • <form action={fn}> calls fn with FormData inside a transition; no preventDefault.
  • useActionState gives result, action and pending; useFormStatus must be called inside the form; useOptimistic shows the expected result early.
  • Errors thrown in an action go to the nearest error boundary; return expected errors as state.
  • Always validate on the server as well.
🎤 Say this in an interview
"For editing I choose controlled inputs when I need every keystroke — live validation, formatting — and uncontrolled fields for big forms read through FormData on submit. For submitting I use form actions: they run in a transition, useActionState gives me the result and pending flag, useFormStatus drives the button, and useOptimistic shows the expected result early. Validation always repeats on the server."
⚠️ Common trap

Making every field controlled “by default”. A 12-field form then renders on every keystroke for no benefit.

Trusting browser validation. The request can be forged; the server must validate.

⌨️ onChange

Fires on every edit; use it when you need the live value.

vs.
📨 action

Fires on submit with the form data; runs in a transition.
