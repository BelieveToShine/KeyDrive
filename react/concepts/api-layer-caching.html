📖 Why did this need to exist?

Pages 9 and 4 showed that fetching inside components causes waterfalls, races, repeated requests and scattered error handling. In a real shop the same request — products, current user — is needed in many places.

Frameworks like Angular give you an official place for cross-cutting request logic (interceptors). React does not prescribe one: you build the place yourself — usually a thin API client function, plus a cache library or a framework’s data layer.

This page shows what belongs in that layer and what the cache adds, so ShopUI has one answer to “how do we call the server?”.

Caches. The React docs recommend a framework’s data fetching or a client-side cache and name TanStack Query, SWR and React Router. For example, TanStack Query treats cached data as stale by default, refetches stale queries in the background when a component mounts, the window is refocused or the network reconnects, and lets you invalidate queries by hierarchical key. Details differ per library — read its docs.

🧪 API-layer lab · seven places to change
// api.js — the one place that knows how to call the server
export async function api(path, { signal } = {}) {
  const res = await fetch(BASE_URL + path, {
    headers: { Authorization: `Bearer ${getToken()}` },
    signal,
  });
  if (!res.ok) throw new ApiError(res.status, await res.text());   // fetch does not reject on 404/500
  return res.json();
}

Illustrative sketch; token refresh and retry would live in the same function.

▾ Go one level deeper (60 seconds)

Interceptors elsewhere. Some frameworks and HTTP libraries have built-in interceptors; with plain fetch the wrapper function above plays that role. The idea is identical: a pipeline every request passes through.

Server Components (page 10) can read data directly on the server, so this layer matters most for client-side interactions and for what runs in the browser.

Cancellation. A request cancelled with an abort signal rejects with an AbortError; treat it as “ignore”, not as a failure.

🔥 Interview recall
  • Components should not call fetch directly; use one API client and a data hook.
  • fetch rejects only on network failure — check response.ok for HTTP errors.
  • Add auth headers, error normalisation, cancellation and (careful) retries in the client.
  • A cache library remembers results, refetches when stale and invalidates by key.
  • React has no built-in interceptor; the wrapper plays that role.
  • Never put secrets in client code.
🎤 Say this in an interview
"I keep network code in one API client — base URL, auth header, response.ok check, abort signal, token refresh and a single error type — and put a cache or the framework’s data layer in front, so components only ask for data. Because fetch does not reject on HTTP errors, the client turns them into errors the UI and error boundaries can handle."
⚠️ Common trap

Assuming a 404 makes fetch fail. It resolves; you must check ok.

Retrying everything. Non-idempotent requests (payments) can be applied twice.
