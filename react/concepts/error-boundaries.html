Deep dive · React lab · 🛟 Errors

Contain the damage: a failure should stay local.

What error boundaries catch and miss, how to write, place and reset one, and where to log errors.

❓ "How do error boundaries work, and what errors do they not catch?"
👁 See it first
🎯 An error boundary is a safety net around part of the tree: when something inside throws while rendering, it shows a fallback instead of losing the whole screen.
▶️ Watch it happen: a safety net
📖 Why did this need to exist?

Pages 1–11 assumed the happy path. Real data is messy: a product with a missing price, an API that returns something unexpected, a lazy chunk that fails to download (page 11). When a component throws during rendering, React cannot finish that render.

Without a net, the error travels all the way to the root. With an error boundary you decide how far it may travel: a widget, a section, a route. The rest of the page stays alive.

This page covers where boundaries catch errors and where they do not, how to write one, how to reset it, and the root-level callbacks for logging.

🧪 Error lab · one bad product
// ProductCard assumes price is a number — one record has none
function ProductCard({ product }) {
  return <li>{product.name} — {product.price.toFixed(2)}</li>;   // throws when price is missing
}

// Contain the damage around the product list only
<ProductsBoundary fallback={<p>Could not show products. <button>Retry</button></p>}>
  <ProductList />
</ProductsBoundary>

Illustrative sketch; ProductsBoundary is a class component or a wrapper from a package. Also fix the data: a boundary is a net, not a cure.

▾ Go one level deeper (60 seconds)

Root callbacks. In React 19 createRoot and hydrateRoot accept onCaughtError (an error caught by a boundary) and onUncaughtError (an error nothing caught), so one place can log everything.

Boundaries and Suspense are siblings: Suspense handles “not ready yet”, an error boundary handles “failed”. A data source that suspends and may fail normally sits inside both.

Fix the cause. A boundary hides a crash from users; it does not fix the bug or the bad data.

🔥 Interview recall
  • An error boundary catches errors thrown while rendering its descendants and shows a fallback.
  • It does not catch event-handler errors, async code, server-side rendering, or errors in itself.
  • Written as a class with getDerivedStateFromError (+ componentDidCatch for logging); there is no hook equivalent.
  • Place several boundaries around independent areas; give the fallback a Retry.
  • React 19 root options: onCaughtError and onUncaughtError.
  • Errors in transitions, form actions and failed lazy loads reach the nearest boundary.
🎤 Say this in an interview
"I put error boundaries around independent parts of the UI so one failing component shows a fallback instead of losing the page. They catch render-time errors — including in transitions, actions and failed lazy loads — but not event handlers or async code, which I handle with try/catch and state. I log everything in one place with the root error callbacks."
⚠️ Common trap

A single boundary at the root. Every bug becomes a full-page error.

Expecting a boundary to catch errors from a click handler or a fetch. It will not.

⏳ Suspense

Shows a fallback while something is not ready yet.

vs.
🛟 Error boundary

Shows a fallback when something has failed.
