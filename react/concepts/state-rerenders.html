Concept 2 of 12 · ⚛️ The render model

Components re-render for two reasons — and you control where the state lives.

State as a snapshot, batching, updater functions, what really triggers a render, and the cheapest fix: moving state down.

❓ "Why does my whole page re-render when I change one small piece of state?"
👁 See it first
🎯 A component re-renders when its own state is set or when its parent re-renders. The cheapest speed-up is usually to move state down to the component that really uses it.
▶️ Watch it happen: move state down
📖 Why did this need to exist?

Page 1 said every update starts with a trigger. This page is about the trigger: state. State is a component’s memory — what it must remember between renders, like “is the cart open?”.

But state has a surprising rule: it is a snapshot. Inside one render, a state variable never changes, even after you call the setter. React collects your updates, finishes the handler, and then renders once with the new value.

Both facts matter for performance and for bugs: state placed too high re-renders too much, and code that expects the variable to change immediately gives wrong answers.

🧪 Render lab · move the state down

ShopUI before: the cart-drawer flag lives in App because “it seemed simple”. Click the Cart button once.

// Before — state in App: one click renders App + SearchBox + ProductList + 500 cards + Cart
function App() {
  const [cartOpen, setCartOpen] = useState(false);
  return <><SearchBox /><ProductList />
    <Cart open={cartOpen} onToggle={() => setCartOpen(!cartOpen)} /></>;
}

// After — state lives in Cart, the only component that uses it
function Cart() {
  const [open, setOpen] = useState(false);
  return <button onClick={() => setOpen(!open)}>…</button>;
}

Illustrative sketch. The behaviour is identical; only the place where the state lives changed.

▾ Go one level deeper (60 seconds)

Same value, no render. If you set state to a value that is the same as the current one (compared with Object.is), React skips rendering that component and its children. React may still call the component once before it bails out — it will not touch your output.

Updaters must be pure. They run during rendering, and in development Strict Mode runs them twice to check.

Passing JSX as children is another way to stop a state change from re-rendering unrelated content: elements created by a parent that did not render are reused. We use it again on page 6.

🔥 Interview recall
  • A component renders when its own state is set or its parent renders (or a context it reads changes).
  • State is a snapshot: the setter does not change the variable in the running render.
  • Updates are batched: React renders once after the handler finishes.
  • Use the updater form (n => n + 1) when the new value depends on the old one.
  • Never mutate state; set a new object or array.
  • Move state down to where it is used; lift it only as far as the nearest common parent.
🎤 Say this in an interview
"State is a snapshot per render, and React batches updates and renders once after the handler. A component re-renders when its own state changes or its parent re-renders, and by default that includes all its children. So I keep state as close as possible to where it is used, use updater functions for updates that depend on the previous value, and never mutate objects in state."
⚠️ Common trap

Putting every piece of state in App “to keep it simple”. It is simple until one boolean renders the whole page.

Mutating state in place. React compares references; the same object means “nothing changed”.
