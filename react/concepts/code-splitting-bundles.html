Concept 11 of 12 · ⚛️ Shipping it

The fastest code is the code you never send.

What bundle weight costs, how lazy and dynamic import split it, what to split and what not to, and how to measure.

❓ "How do you reduce the JavaScript a React app sends on first load?"
👁 See it first
🎯 The fastest code is the code you never send. Split by route and by rarely-used feature, load the rest on demand.
▶️ Watch it happen: the fastest code is unsent
📖 Why did this need to exist?

Page 10 showed that even with server rendering the browser still downloads JavaScript to hydrate. Every kilobyte must be downloaded, parsed and executed before the page is interactive — on a slow phone this, not React’s render time, is often the biggest delay.

A typical app grows: checkout, admin screens, charts, rich-text editors. A single bundle sends all of it to every visitor. Code splitting cuts the bundle into chunks that load on demand.

React’s tool for this is lazy plus Suspense — the same Suspense boundary you met in page 9.

⚙️ How lazy loading works
📋 What to split — and what not to
Split itWhyDo not split
Routes / pages (checkout, account, admin)Most visitors never open most routesThe route every visitor lands on first
Heavy, rarely-used features (charts, editors, maps, PDF viewers)Large libraries, used by fewTiny components — an extra request costs more than it saves
Modals and drawers opened on clickOnly needed after an actionThings shown on every page load
Server-only logic (Server Components, page 10)Their code is never sent at all—

Constraints from the docs: lazy expects a default export, needs a bundler or framework that supports dynamic import(), and the lazy component (or a parent) must sit inside a <Suspense> boundary.

🧪 Bundle lab · lazy-load the checkout
// Before — everything in the first bundle
import Checkout from './Checkout';

// After — the checkout becomes its own chunk
const Checkout = lazy(() => import('./Checkout'));
<Suspense fallback={<CheckoutSkeleton />}>
  <Checkout />
</Suspense>

🎬 Real-world scenarios
📉
Home page is slow on 3G

Admin code and charts are in the main bundle.

→ Route-level lazy loading
📝
A rich-text editor adds hundreds of KB

Only editors need it.

→ Lazy-load the editor on first open
🖱️
Modal feels slow the first time

Chunk loads on click.

→ Preload on hover or focus
🚢
Errors right after each deployment

Old chunk names are gone.

→ Error boundary + refresh prompt
▾ Go one level deeper (60 seconds)

One call, cached. React does not call the load function until it first tries to render the component, and both the returned promise and its resolved value are cached, so it is never called twice.

Preloading. You can start the same import() early — for example when the user hovers a link — so the chunk is already there when the component renders.

With Server Components (page 10) code that stays on the server never reaches the browser, which is the strongest form of “not sending code”.

🔥 Interview recall
  • Bundle weight is download + parse + execute time on the user’s device.
  • lazy(() => import(...)) defers a component’s code until it first renders; it needs a default export.
  • A lazy component needs a Suspense boundary; a failed load goes to the nearest error boundary.
  • Split by route and by heavy, rarely-used features; do not split tiny components.
  • Measure with a bundle analyser first; then change one thing and re-measure.
  • Code that never ships (Server Components) beats code that ships late.
🎤 Say this in an interview
"I look at what the bundle contains with an analyser, then split by route and by heavy rarely-used features using lazy and dynamic import with a Suspense fallback, and an error boundary for failed loads. I keep the first route lean, preload on intent, and re-measure initial JavaScript to prove the saving."
⚠️ Common trap

Splitting everything. Dozens of tiny chunks mean dozens of requests and visible loading states.

No error boundary around lazy parts. One failed download breaks the whole screen.
