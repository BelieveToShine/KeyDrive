📖 Why did this need to exist?

ShopUI so far is one screen. A shop has many: product list, product detail, cart, checkout, account. Users expect the Back button to work, links to be shareable, and a refresh to land on the same page.

React itself renders components; it does not decide which screen to show for a URL. That is the router’s job. The React docs point you to a framework (Next.js, React Router, Expo) or, when building from scratch, a router such as React Router or TanStack Router, and note that routers are usually integrated with data fetching, code splitting and page rendering.

This page explains what a router does, so you can judge any of them: route tree and layouts, params, navigation, data, code splitting and access control.

Access control is a UX feature, not security. Hiding a route in the browser does not protect data: the server must check permissions on every request.

▾ Go one level deeper (60 seconds)

The History API. pushState adds a new session-history entry and replaceState updates the current one; neither fires popstate. That event fires when the user presses Back or Forward, so a router listens for it to re-render the right route.

Routing modes. Some routers are used purely in the browser; others work inside a framework that also renders on the server (page 10). Pick based on whether you need server rendering and loaders integrated with routes.

Choosing. The React docs recommend starting a new app with a framework; if you build from scratch, you must pick and wire a router, data fetching, code splitting and rendering approach yourself.

🔥 Interview recall
  • React does not choose screens by URL; a router (or a framework) does.
  • Client-side navigation uses the History API (pushState) — no full page load; Back/Forward fire popstate.
  • Nested routes: a layout route renders shared UI and an outlet; params like :id come from the URL.
  • Put page-defining state (filters, sort, selected id) in the URL.
  • Routes are natural places for data loading and code splitting.
  • Hiding routes in the browser is not security; the server must authorise.
🎤 Say this in an interview
"A router maps the URL to a tree of nested routes: layouts for shared UI, params for ids, search params for filters. Navigation uses the History API so there is no full reload, ideally in a transition so the old page stays until the new one is ready. Routes are also where I load data and split code, and access checks must be enforced on the server, not just hidden in the UI."
⚠️ Common trap

Keeping page-defining state in components. Refresh, sharing and Back all break.

Treating a client-side redirect as authorisation. Anyone can call the API directly.

🔗 Link

Navigates inside the app without a full reload (the router handles it).
