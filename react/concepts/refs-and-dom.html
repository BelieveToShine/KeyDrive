Deep dive · React lab · 📦 Refs

A ref remembers without rendering — and reaches the DOM.

Refs versus state, how DOM refs are filled, ref callbacks, passing refs to your own components, and when flushSync is justified.

❓ "When should you use a ref instead of state, and how do you focus an input in React?"
👁 See it first
🎯 A ref is a box React keeps for you between renders; filling it does not cause a render. It is also how you reach a DOM node.
▶️ Watch it happen: a box that does not re-render
📖 Why did this need to exist?

Hooks guide: state is for values the screen shows. But two kinds of work do not fit state — remembering something without re-rendering (a timer id, the previous value) and talking to the DOM directly (focus an input, scroll to an item, measure a size). React has no built-in way to do the DOM jobs, so it gives you refs.

Refs are an escape hatch: they step outside React’s declarative model. Used for the right jobs they are small and safe; used to store displayed values they cause stale screens.

This page covers when a ref is the right tool, how DOM refs are filled, how to hand a ref to your own component, and the one-line tool for reading the DOM right after an update (flushSync).

🧪 Refs lab · three ShopUI jobs
// 1. Focus the search box when the page opens
const inputRef = useRef(null);
useEffect(() => { inputRef.current.focus(); }, []);
<input ref={inputRef} />

// 2. Debounce: remember the timer id without re-rendering
const timer = useRef(0);
function onType(text) { clearTimeout(timer.current); timer.current = setTimeout(() => search(text), 300); }

// 3. Scroll to the item just added to the cart (needs the DOM updated first)
flushSync(() => setItems([...items, newItem]));
lastItemRef.current.scrollIntoView();

▾ Go one level deeper (60 seconds)

Ref callbacks. Instead of an object, you can pass a function to ref; React calls it with the DOM node when the ref is set and calls its cleanup when it is cleared. This is how you build a Map from item ids to nodes.

Why not read in render. Reading or writing a ref during render breaks the assumption that a component behaves like a pure function (page 1), and the lint rule flags it. Lazy initialisation of a ref is the allowed exception.

flushSync cost. It forces React to update the DOM right away, which the docs warn can hurt performance; they recommend avoiding it unless you really need it.

🔥 Interview recall
  • A ref holds a value that is not needed for rendering; changing it does not re-render.
  • State for what the screen shows; refs for timers, previous values and DOM nodes.
  • Never read or write ref.current during render; use handlers or effects.
  • DOM refs are set at commit; for many items use a ref callback.
  • React 19 passes ref as a prop; earlier versions need forwardRef.
  • flushSync and useLayoutEffect are last resorts with a performance cost.
🎤 Say this in an interview
"I use state for anything the screen shows and a ref for what I must remember without rendering — timer ids, previous values, DOM nodes. DOM refs are filled at commit, so I read them in handlers or effects, never during render, and I treat flushSync and useLayoutEffect as last resorts."
⚠️ Common trap

Showing a ref’s value on screen. It will be stale until something else renders.
