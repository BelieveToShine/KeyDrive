📖 Why did this need to exist?

Up to now every ShopUI component had its data at hand. In a real shop the products, reviews and search results come from a server — and that adds waiting. Waiting creates three problems: loading states (what do we show?), flicker (spinners flashing as the user types), and waterfalls (requests that start one after another).

Page 4 showed the do-it-yourself way: fetch in an effect. It works for small cases, but it starts late (after render), repeats itself (no cache) and has races. React gives better building blocks: Suspense for “show this while loading”, and transitions for “keep the old screen while the new one loads”.

This page is about those building blocks and about when each one helps.

⏱️ Start fetching early
🧰 The tools
ToolWhat it doesCareful
<Suspense fallback={…}>Shows the fallback until the children have finished loading, then swaps in the contentOnly works with Suspense-enabled sources: lazy components, a promise read with use, or a framework — not data fetched in an effect or event handler
use(promise)Reads a promise during render and suspends until it resolvesThe promise must be cached; one created during render is new each time and causes repeated fallbacks
useTransitionMarks an update as non-urgent; you get isPending for feedback; the update can be interruptedAlready-visible content is not replaced by a fallback; a new Suspense boundary still shows its fallback
useDeferredValue(value)Lets one part of the UI lag behind; if the update suspends, the old value stays on screenYou must opt in — urgent updates still show fallbacks
Framework loader or a data library (the docs mention TanStack Query, SWR, React Router)Starts fetching early, caches, de-duplicates, avoids waterfallsPick one; do not hand-roll it in effects for anything but small cases
🧪 Data lab · the flickering search

ShopUI’s search now asks the server. The user types “shi” — three keystrokes.

function Search() {
  const [query, setQuery] = useState('');
  const deferredQuery = useDeferredValue(query);          // the lagging copy
  const isStale = query !== deferredQuery;                // show “updating…” feedback
  const dim = { opacity: isStale ? 0.5 : 1 };
  return (<>
    <input value={query} onChange={e => setQuery(e.target.value)} />
    <Suspense fallback={<Spinner />}>
      <div style={dim}><Results query={deferredQuery} /></div>
    </Suspense>
  </>);
}

Illustrative sketch; Results must read its data in a Suspense-enabled way (a framework, or a cached promise with use).

▾ Go one level deeper (60 seconds)

What suspends. Per the docs, a Suspense boundary activates for lazy-loaded components, a promise read with use, stylesheets with a precedence prop, and Suspense-enabled frameworks. It does not detect fetches in effects or event handlers.

Transitions are interruptible. If the user types again, React can abandon the in-progress render and start over with the newest value.

Fallbacks and layout. Place boundaries around sections, not the whole page, so one slow part does not hide everything else.

🔥 Interview recall
  • Suspense shows a fallback until its children finish loading; it only detects Suspense-enabled sources, not effect-based fetching.
  • use reads a promise during render; the promise must be cached.
  • useTransition / useDeferredValue keep already-visible content instead of showing a fallback.
  • Effects start fetching late, do not run on the server and do not cache — hence waterfalls.
  • Start requests early (framework loader or data library) so they run in parallel.
  • Always give the user feedback while stale: isPending or a dimmed result.
🎤 Say this in an interview
"For server data I avoid waterfalls by starting requests early — through a framework or a data library, not nested effects. I wrap slow parts in Suspense boundaries, and I mark non-urgent updates with useTransition or useDeferredValue so the old content stays visible instead of flashing a spinner, with a pending indicator for feedback."
⚠️ Common trap

Expecting Suspense to catch an effect’s fetch. It cannot; the fallback will never show.

One giant Suspense boundary at the root. One slow component hides the whole page.
