Concept 1 of 12 · ⚛️ The render model

A render is React calling your function; a commit is React changing the page.

The three steps behind every update, the ShopUI practice app, and the one fact — children re-render with their parent — that the rest of the lab builds on.

❓ "What happens between calling setState and the screen changing?"
👁 See it first
🎯 A render is React calling your function to ask “what should the screen look like?”; a commit is React changing the DOM to match. Rendering is cheap to start and easy to repeat — that is why it is also easy to do too much of it.
📖 Why did this need to exist?

Early web pages were updated by hand: find an element, change its text, change its colour, and remember to change it back. As screens grew, nobody could say what the page looked like right now, because the answer depended on the order of a hundred little edits.

React’s answer is to stop editing. You describe the screen for the current state as a plain function — UI = f(state) — and React works out the edits. The price: React must call your function again every time the state changes, and by default that includes everything below it.

This whole lab is built on that one fact. Pages 2–3 explain why a component renders again; page 4 handles the outside world; pages 5–7 measure and fix needless renders; the rest scale it to a real app. We use one practice app, ShopUI, throughout.

📚 The rules of a render
StepWhat React doesWhat you must not do
TriggerSchedules a render: the initial mount (createRoot) or a state updateDo not call a component like a normal function; let React call it
RenderCalls your components, top-down, recursively; each returns JSX (a description)No side effects: no fetches, no DOM edits, no changing variables outside the function
CommitApplies the minimum DOM changes; sets refs; then the browser paintsDo not assume “render ran” means “the screen changed” — if the output is the same, the DOM is untouched
After commitRuns effects (page 4)Do not put render logic in effects

▾ Go one level deeper (60 seconds)

Not “the virtual DOM is fast”. React does not make rendering free. It makes updating the DOM minimal, by comparing the new output to the previous output and committing only the difference. The comparison itself costs time, which is why large trees still need care.

Purity. Given the same inputs (props, state, context), a component should return the same JSX. That is what lets React call it twice in Strict Mode, pause it, or skip it.

The first render is triggered by calling createRoot(...).render(...); every later render is triggered by a state update (page 2).

🔥 Interview recall
  • UI = f(state): a component is a function that returns a description of the screen.
  • Three steps: trigger → render → commit; effects run after commit.
  • A render is React calling your component; a commit is React editing the DOM.
  • React only changes DOM nodes where the new output differs from the last one.
  • Rendering must be pure: no side effects while rendering.
  • By default, when a component renders, all its children render too.
🎤 Say this in an interview
"In React a render means calling my component functions to get a description of the UI, and a commit means applying the minimal DOM changes. A render is triggered by the initial mount or a state update, and by default it re-renders every child below. Rendering must be pure; side effects belong in handlers or effects after the commit."
⚠️ Common trap

“Render” does not mean “the DOM changed”. A component can render a hundred times and commit nothing; the cost is the CPU spent calling the functions.

Optimising before measuring. 504 renders sounds scary, but if they take 2 ms nobody cares. Measure first (page 5).
