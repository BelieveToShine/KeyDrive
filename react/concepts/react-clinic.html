▶️ Watch it happen: how every case is solved
📖 Why did this need to exist?

Real tickets say “the checkout feels slow” or “the page went blank”, not “state too high”. The cases start the way tickets do, and all of them use the same ShopUI app and the same illustrative numbers as the lab.

Every case is solvable with the ladder: measure, read the profile, find the biggest wrong thing, one hypothesis, one change, prove it.

🧭 The ladder, React edition
1 · MEASURE ★

📏 How slow, exactly?

Commits and render milliseconds in the Profiler — a number, not a feeling.

2 · READ ★

🔬 What rendered, and why?

Read the flamegraph: which components, and what triggered them.

3 · FIND ★

🎯 The biggest wrong thing

One slow component, a render cascade, an effect loop, a heavy bundle?

4 · GUESS ★

💡 One hypothesis

State too high? Unstable props? Needless effect? Too much code shipped?

5 · CHANGE ★

🔧 Change one thing

Never two at once.

6 · PROVE ★

✅ Re-measure

Same interaction, fewer renders, fewer milliseconds.

Ask in this order: wrong or slow? → how many components rendered, and why? → what changed in their props or state? → does the cost come from rendering, from loading, or from shipping code? → what is the smallest change that tests my guess?

🩺 Case 1

Opening the cart is slow

Symptom. Clicking the Cart button takes ≈ 40 ms and the page stutters; nothing on screen changes except the drawer.

Evidence.

  • Profiler: one commit renders App, SearchBox, ProductList, 500 ProductCards, Cart = 504 components.
  • The cartOpen flag is declared in App.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. State is higher than the component that uses it, so its change renders everything below App.

Fix. Move cartOpen into Cart. Re-record: 1 component renders.

📖 Where to review: page 2.

🩺 Case 2

Delete a row, the wrong note stays

Symptom. Users type a note into a product row, delete the first row, and the second row now shows the first row’s note.

Evidence.

  • Code: products.map((p, i) => <Row key={i} … />).
  • Notes are local state in each Row.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. Index keys tie state to a position, not to a product.

Fix. key={p.id}. Delete the first row again to prove it.

📖 Where to review: page 3.

🩺 Case 3

memo added, nothing improved

Symptom. The team wrapped ProductCard in memo yesterday. Typing is still ≈ 41 ms per keystroke.

Evidence.

  • Profiler: all 500 cards still render; “props changed” is the only difference.
  • Code: onAdd={() => addToCart(p.id)} inside the map.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. A new function every render defeats memo’s prop comparison; memo only added work.

Fix. One stable addToCart (useCallback, id passed back by the card). Re-record: 4 components, ≈ 3 ms.

📖 Where to review: page 6.

🩺 Case 4

Results flash old data for a frame

Symptom. The product list briefly shows the previous results after each keystroke.

Evidence.

  • Profiler: two commits per keystroke, 504 + 504 = 1,008 renders.
  • Code: a filtered state set inside useEffect from query.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. State copied from state in an effect: render, commit, effect, set state, render again.

Fix. Calculate filtered during render. One commit per keystroke.

📖 Where to review: page 4.

🩺 Case 5

Add to cart renders the whole shop

Symptom. Adding one item to the cart takes ≈ 35 ms.

Evidence.

  • Profiler: 502 components render: Cart, CartBadge and all 500 cards.
  • Code: one AppContext holding { cart, theme, dispatch }; the cards read the theme.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. One context value changes with the cart, so every reader renders — including cards that only need the theme.

Fix. Split into CartStateContext, CartDispatchContext and ThemeContext. Re-record: 2 readers.

📖 Where to review: page 8.

🩺 Case 6

The spinner flashes on every keystroke

Symptom. Searching “shi” on a server-backed list flashes a spinner three times.

Evidence.

  • Results sit in a <Suspense> boundary.
  • The query state updates urgently; the old results disappear while the new ones load.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. An urgent update that suspends replaces visible content with the fallback.

Fix. Pass the results a useDeferredValue copy of the query and dim them while stale. Zero flashes after the first load.

📖 Where to review: page 9.

🩺 Case 7

Slow first load on phones

Symptom. Browsing products on a mid-range phone takes seconds before it responds; the Profiler shows fast renders.

Evidence.

  • Bundle analyser: initial JavaScript 420 KB; checkout 90 KB, charts 120 KB and the editor 30 KB are all in it.
  • Visitors who only browse never open those screens.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. Download and parse cost, not render cost: the first bundle carries rarely-used features.

Fix. Lazy-load the checkout, charts and editor behind Suspense. Initial JavaScript ≈ 180 KB.

📖 Where to review: page 11.

🩺 Case 8

Typing in checkout lags

Symptom. The 12-field checkout feels sluggish; the page is otherwise fast.

Evidence.

  • Profiler: each keystroke renders 13 components (Checkout + 12 fields).
  • All fields are controlled by one form state object in Checkout.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. Every keystroke changes state at the top of the form, so all fields render.

Fix. Uncontrolled fields with a form action (0 renders per key), or memoized field components with stable handlers (2).

📖 Where to review: forms deep dive, page 6.

🩺 Case 9

Bonus: one bad product blanks the page

Symptom. After an import, one product has no price, and customers see a blank page.

Evidence.

  • Console: an error thrown while rendering ProductCard.
  • There is no error boundary in the app.

Your move: which family is it, and what is your one change?

▾ Reveal the diagnosis

Diagnosis. A render-time error reaches the root; nothing contains it.

Fix. An error boundary around ProductList with a Retry fallback, and fix the data. Cart, header and search stay alive.

📖 Where to review: error boundaries deep dive.

▾ Go one level deeper (60 seconds)

Patterns. Cases 1, 3, 5 and 8 all look like “React is slow” but each has a different lever: state placement, stable props, context split, controlled versus uncontrolled. The profile tells you which — never the symptom alone.

Case 7 is not a render problem. The Profiler showed fast renders; only the bundle analyser exposed the cost. Match the tool to the layer (render, load, ship).

Make your own clinic. Take five real tickets, strip the diagnosis, keep symptom and evidence, and run it with your team.

🔥 Interview recall
  • Method: wrong or slow? → how many components rendered and why? → what changed? → render, load or ship? → smallest test of the guess.
  • One change, same interaction, same build, compare the profile.
  • Families: renders & state placement (1, 3, 5, 8), identity & effects (2, 4), loading & shipping (6, 7), resilience (9).
  • Similar symptoms, different causes: read the profile before theorising.
  • Measure the layer you suspect: Profiler for render, bundle analyser for shipping.
🎤 Say this in an interview
"I treat a React problem as an investigation: is it wrong or slow, how many components rendered and why, what changed in their props or state, and is the cost in rendering, loading or shipped code. I form one hypothesis, change one thing, and re-measure the same interaction in the same build."
⚠️ Common trap

Reaching for memo first. In four of nine cases the fix was moving state, keys, or splitting a context — not memo.

Skipping the evidence. In every case one number — renders, KB, or a key in the code — decided the diagnosis.
