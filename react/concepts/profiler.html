Do not guess what is slow — record it.

The Profiler tab, the Profiler component and the Performance tracks; reading a ranked profile; and measuring in the right build.

❓ "How do you find out why a React app is slow?"
👁 See it first
🎯 Do not guess what is slow — record it. The Profiler tells you which components rendered, how long they took, and in which commit.
▶️ Watch it happen: record, do not guess
📖 Why did this need to exist?

Pages 1–4 gave you a model of when React renders. A model is not a measurement. A tree of 504 components might be perfectly fast, or one innocent-looking component might eat 30 ms. Fixing the wrong thing costs time and adds complexity.

So every optimisation starts with the same two steps: record a profile of one real interaction, then read which component is the biggest wrong thing. Only then do you reach for a fix (page 6).

This page shows the tools — React DevTools’ Profiler tab, the <Profiler> component, and React’s Performance tracks — and the traps in measuring.

🧰 Three ways to measure
ToolWhat it gives youUse it when
React Developer Tools → Profiler tab (browser extension for Chrome, Firefox, Edge)Record an interaction; see each commit and how long each component tookYour first stop: “what rendered and how long?”
<Profiler id onRender> componentYour own callback gets the phase (mount, update or nested-update), actualDuration and baseDuration for that subtreeLogging numbers from tests or a staging build
React Performance tracks in the browser’s Performance panelA Components track and Scheduler tracks next to the browser’s own flame chartYou need to see React work next to layout, paint and network

actualDuration is the time spent rendering the profiled subtree for this update; baseDuration is an estimate of rendering the whole subtree with no optimisation. When memoization works (page 6), actualDuration drops well below baseDuration after mount.

⚠️ Measure in the right build
🧪 Profiler lab · record one keystroke
  1. Pick one interaction: type one character into the search box.
  2. Record: start the Profiler, type the character, stop.
  3. Read: how many commits? Which component is slowest? (ShopUI, illustrative: 1 commit, ≈ 40 ms, 504 components, ProductCards ≈ 35 ms.)
  4. Find the biggest wrong thing: 500 identical ProductCards rendering again.
  5. Guess one cause: their props did not change, so rendering them is wasted. (Fix on page 6; prove with a second recording.)

1 · MEASURE ★

📏 How slow, exactly?

Commits and render milliseconds in the Profiler — a number, not a feeling.

2 · READ ★

🔬 What rendered, and why?

Read the flamegraph: which components, and what triggered them.

3 · FIND ★

🎯 The biggest wrong thing

One slow component, a render cascade, an effect loop, a heavy bundle?

4 · GUESS ★

💡 One hypothesis

State too high? Unstable props? Needless effect? Too much code shipped?

5 · CHANGE

🔧 Change one thing

Never two at once.

6 · PROVE

✅ Re-measure

Same interaction, fewer renders, fewer milliseconds.

🩺 Debug checklist · measuring symptoms
You seeLikely causeWhat to try
Numbers jump between recordingsToo little data or background workRecord the same interaction 3 times; use the middle result
Everything looks twice as slow as users reportDevelopment build and Strict ModeCompare in a profiling build; always compare like with like
A component shows 0.1 ms but is rendered 500 timesMany cheap renders add upLook at the total, not one row
React is fast but the page still feels slowThe time is in layout, paint or network, not in ReactUse the browser Performance panel (Performance tracks show both)
You fixed something and the number did not changeWrong hypothesis, or a cached/stale buildRe-record; confirm the build contains your change
🎬 Real-world scenarios
⌨️
Typing in the search box drops frames

One commit is 40 ms.

→ Record, rank, find the 500 cards
🐢
A page is slow only the first time

Mount, not update.

→ Look at phase = mount (page 11)
🔁
Something re-renders on a timer

A hidden interval sets state.

→ Profile with the page idle
📱
Fast on a laptop, slow on a phone

Budget differs per device.

→ Profile on the slow device or throttle the CPU
▾ Go one level deeper (60 seconds)

Why a render is not a frame. React render time is only part of what a keystroke costs; the browser also runs layout and paint. The Performance tracks put React’s work on the same timeline as the browser’s.

If the extension is installed, the Components track lists every component, not just the ones inside a <Profiler>.

Profiling a build. Profiling builds are made by importing react-dom/profiling instead of react-dom/client; your bundler setup decides how you switch.

DevTools labels. Chart names, buttons and settings in React Developer Tools change between versions; if a label here differs from your version, trust your version.

🔥 Interview recall
  • Measure first: record one real interaction, read the slowest component, then change one thing.
  • React Developer Tools’ Profiler tab, the <Profiler> component and the Performance tracks are the three tools.
  • actualDuration = time rendering this update; baseDuration = estimated cost with no optimisation.
  • Development builds add checks (Strict Mode); compare before/after in the same build, ideally a profiling build.
  • Many cheap renders add up — look at the total.
  • A fast React render does not guarantee a fast page: layout, paint and network matter too.
🎤 Say this in an interview
"Before optimising a React app I record a profile of the real interaction in the Profiler — which components rendered, how many commits, and how long each took — and I compare before and after in the same build. Only the biggest cost gets a fix, and I re-record to prove the number moved."
⚠️ Common trap

Optimising without a profile. You will add memo everywhere and measure nothing.

Trusting development-mode milliseconds as user milliseconds. Dev builds do extra work on purpose.
