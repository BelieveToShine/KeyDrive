Concept 3 of 12 · ⚛️ The render model

A key answers one question: which one is this?

How React matches the new tree to the old one, when state is kept or reset, and how bad keys cause wrong behaviour and wasted work.

❓ "Why does my input lose its text, or the wrong row keep its state, when the list changes?"
👁 See it first
🎯 React decides “is this the same component as last time?” by type, position and key. Same → keep its state and update it. Different → throw it away and build a new one.
▶️ Watch it happen: same or different?
📖 Why did this need to exist?

Page 2 showed that React re-renders a tree often. But a re-render must not mean “start over”: if you typed a note into a row, that note must survive the next render. React needs a rule for matching the new tree to the old tree; that matching is called reconciliation.

The rule is simple: same component type at the same position (with the same key) = the same component. That is how state is kept. Lists are the tricky case because items can move, so React asks you for a key per item.

Wrong keys cause two kinds of problems: wrong behaviour (state attached to the wrong item) and wasted work (components destroyed and rebuilt on every render).

🧪 Render lab · three ways to key ProductList

The search box filters ProductList from 500 products to 480. Each ProductCard remembers whether it is expanded. What does React do?

products.map((p, i) => <ProductCard key={i} product={p} />)            // ❌ index
products.map(p => <ProductCard key={Math.random()} product={p} />)   // ❌ random
products.map(p => <ProductCard key={p.id} product={p} />)            // ✅ stable id

Illustrative sketch.

KeyWhat React does for 500 → 480 cardsResult
i (index)Updates the first 480 cards in place; removes the last 20Cards show other products’ expanded/not-expanded state ✗ — wrong behaviour
Math.random()No key matches last time: destroys all 500 cards and creates 480 new ones (980 mount/unmount operations)Correct picture, but slow, and typed input and focus are lost ✗
p.idKeeps the 480 matching cards with their state; removes the 20 that no longer matchCorrect and cheap ✅

Where the comparison happens. During render, React compares the new element tree with the previous one: same type at the same position and key → update; otherwise → unmount the old subtree and mount the new one.

Not the same as DOM identity. A key is about component identity; whether React edits or recreates DOM nodes follows from it.

Fragments and conditionals. {cond && <A />} keeps a slot (the “false” still occupies the position), which is why toggling often preserves siblings’ state.

Do not use useId for list keys — keys should come from your data.

🔥 Interview recall
  • Reconciliation: React matches the new tree to the old one by type, position and key.
  • Same type + same position (+ same key) = state is kept; otherwise it resets.
  • Keys must be unique among siblings, stable, and come from your data.
  • Do not use Math.random() as a key; use the index only for lists that never change order.
  • A new key deliberately resets a component’s state.
  • Never define a component inside another component.
🎤 Say this in an interview
"React reconciles by element type, position and key: the same type at the same position keeps its state, and anything else is torn down and rebuilt. In lists I key items by a stable id from the data, never by index in lists that change or by random values, and I use a key on purpose to reset a form when the entity changes."
⚠️ Common trap

Index as key “because it silences the warning”. It hides the warning and keeps the bug: state sticks to positions.

Random keys. Every render looks like a brand-new list, so everything remounts — slow, and the user loses focus and input.

🔑 key

Tells React which item is which across renders; never visible to your component.

vs.
🆔 id (data)

Your data’s own identity. A good key usually comes from it.
