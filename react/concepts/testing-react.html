Deep dive · React lab · 🧪 Testing

Test like a user — and wait for React.

Why tests need act, how to wait for async updates, what to test in ShopUI and what not to.

❓ "How do you test React components, and what do act and waitFor do?"
👁 See it first
🎯 A good React test acts like a user, waits for React to finish, and asserts on what is on the screen.
▶️ Watch it happen: test like a user
📖 Why did this need to exist?

The clinic fixes — moved state, stable props, split contexts — are exactly the kind of change that must not alter behaviour. Tests are how you know they did not. And tests that assert on internals (state values, render counts) fail on every refactor and teach the team to ignore failures.

There are two practical problems unique to React: updates are applied asynchronously, so a test can assert too early, and a test must query the screen the way a user finds things.

This page covers both: act and async queries, and what is worth testing in ShopUI.

🧪 Testing lab · three ShopUI tests
test('typing filters the list', async () => {
  render(<ShopUI />);
  await user.type(screen.getByRole('searchbox'), 'shi');
  expect(await screen.findByText('Shirt')).toBeVisible();
  expect(screen.queryByText('Shoes')).not.toBeInTheDocument();
});

test('adding an item updates the cart badge', async () => {
  render(<ShopUI />);
  await user.click(screen.getAllByRole('button', { name: /add to cart/i })[0]);
  expect(await screen.findByText('Cart (1)')).toBeVisible();
});

Illustrative sketch; user comes from user-event’s setup. Nothing here depends on how the state is stored — moving it down (page 2) leaves the tests green.

▾ Go one level deeper (60 seconds)

Act and the environment flag. Outside Testing Library, you must tell React it is in a test environment (IS_REACT_ACT_ENVIRONMENT); Testing Library already sets it.

Separate act calls for rendering and for dispatching events make sure every update is applied before you assert.

Performance tests. Render counts and milliseconds belong in profiling (page 5), not in unit tests; tests should check behaviour and let the Profiler check speed.

🔥 Interview recall
  • Test like a user: what is on the screen, after typing and clicking.
  • React applies updates asynchronously; act flushes them, and Testing Library wraps render and events in it.
  • For later updates use findBy… or waitFor, not sleeps.
  • Prefer user-event to raw events; avoid querying through container.
  • Do not test internal state, methods or lifecycle details.
  • The react-dom/test-utils act is deprecated in React 19; import act from react.
🎤 Say this in an interview
"I test React components the way users use them: render, interact with user-event, wait for updates with find queries or waitFor, and assert on what is visible — roles, labels and text — never on internal state. That keeps tests green through refactors and optimisations, and I leave render counts and timings to profiling."
⚠️ Common trap

Testing implementation details. Every refactor breaks tests that nobody can explain.

Fixed sleeps. Slow on a good day, flaky on a bad day.

🧪 act

Applies pending React updates so assertions see the result.

vs.
⏳ waitFor / findBy

Polls until something appears or a condition holds.
