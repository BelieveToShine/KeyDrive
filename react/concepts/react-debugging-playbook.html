📖 Why did this need to exist?

Pages 1–6 gave you facts: how renders start, how state and keys behave, what effects are for, how to measure, and how to skip work. Facts do not fix a bug at 5 pm on a Friday; a repeatable routine does.

Most React bugs fall into a few families — wrong values (snapshots, dependencies), wrong identity (keys), runaway work (effects), and slow renders. Each family has a first place to look.

This page is the checklist you can carry into any codebase. The same thinking ladder runs through the SQL and Cosmos labs; only the tools change.

🧪 Playbook lab · one change at a time

A teammate “fixed” ShopUI in one commit: added memo to the cards, moved cartOpen into Cart, and wrapped the filter in useMemo. The page is faster. Was it all three?

ApproachWhat you learnVerdict
Three changes, one recording“It got faster.” You cannot say which change mattered, or whether two of them are noise❌ Cargo cult

1 · MEASURE ★

📏 How slow, exactly?

Commits and render milliseconds in the Profiler — a number, not a feeling.

2 · READ ★

🔬 What rendered, and why?

Read the flamegraph: which components, and what triggered them.

3 · FIND ★

🎯 The biggest wrong thing

One slow component, a render cascade, an effect loop, a heavy bundle?

4 · GUESS ★

💡 One hypothesis

State too high? Unstable props? Needless effect? Too much code shipped?

5 · CHANGE ★

🔧 Change one thing

Never two at once.

6 · PROVE ★

✅ Re-measure

Same interaction, fewer renders, fewer milliseconds.

No evidence.

Different build or CPU.

▾ Go one level deeper (60 seconds)

Wrong versus slow. A wrong value is a correctness bug — fix the model first (pages 2–4). A slow render is a performance bug — measure first (page 5). Do not “optimise” a wrong value.

React Developer Tools’ Components tab lets you inspect a component’s props and state, which answers “what did it receive?” quickly.

Strict Mode is a debugging aid, not a bug: its extra render and effect cycle exist to expose impure code and missing cleanup.

🔥 Interview recall
  • The ladder: measure → read → find the biggest wrong thing → one hypothesis → one change → prove.
  • Triage by symptom: wrong value (2, 4), wrong identity (3), runaway effect (4), slow (5–6).
  • Change one thing at a time; re-record in the same build.
  • Revert changes the profile does not justify.
  • Correctness bugs first, performance second.
  • The profile — not intuition — picks what to fix.
🎤 Say this in an interview
"When a React screen is slow, I record the exact interaction in a profiling build, read which component is the biggest cost, form one hypothesis from how renders, state, keys and effects work, change one thing, and re-record to prove it. Anything the profile does not justify, I revert."
⚠️ Common trap

Changing three things at once. If it gets faster you do not know why; if it gets slower you cannot back out cleanly.

Declaring victory without a second recording. A fix you did not measure is a guess with a commit message.

🐞 Correctness bug

The UI shows the wrong thing. Fix with the model: snapshots, keys, effects.

vs.
🐢 Performance bug

The UI is right but late. Fix with measurement: profile, then skip or reduce work.
