Concept 8 of 12 · ⚛️ App architecture

Decide who owns each piece of state — and who reads it.

Local state, lifting, context and reducers; the context re-render rule; and how to split contexts so a cart change does not re-render 500 cards.

❓ "When should state be global, and why does changing a context re-render so much?"
👁 See it first
🎯 Keep state as low as possible, lift it only as far as needed, and use context for the rest — remembering that every reader re-renders when the value changes.
📖 Why did this need to exist?

Page 2 said: move state down to where it is used. But some state really is shared — the cart is shown in the header, the product page and checkout. Passing it through ten components as props (“prop drilling”) is painful.

Context solves the plumbing: a provider high up, any component below can read. But it has a performance rule that surprises people: when the provider’s value changes, all components that read it re-render, and memo does not stop that.

So the design question is “who owns this state, and who reads it?” — and this page gives you a ladder of answers.

🧪 Context lab · split the big context

ShopUI before: one AppContext holds cart and theme. Click “Add to cart”.

// Before — one value for everything
const value = { cart, theme, dispatch };   // a new object whenever cart or theme changes
<AppContext.Provider value={value}>

// After — split by what changes together; dispatch is stable
<CartStateContext.Provider value={cart}>
  <CartDispatchContext.Provider value={dispatch}>
    <ThemeContext.Provider value={theme}>{children}</ThemeContext.Provider>
  </CartDispatchContext.Provider>
</CartStateContext.Provider>

Illustrative sketch. “children” passed from outside stays the same JSX element, so the provider’s state change does not re-render them by itself (page 2).

▾ Go one level deeper (60 seconds)

Reducer. A reducer is a function (state, action) => newState. Components send actions with dispatch; the reducer is the one place that decides how state changes, which makes it easy to test and read.

Splitting a context inside a component. If one component needs only part of a context, it can read the context in an outer component and pass that part as a prop to a memoized inner component.

External stores. Libraries outside React (Redux, Zustand, and others) are a further option when shared state grows; they are outside this lab’s scope, and the same “who reads what” thinking applies.

🔥 Interview recall
  • Own each piece of state in one place; keep it low; lift it to the nearest common parent when siblings share it.
  • Context removes prop drilling but re-renders every reader when the value changes.
  • memo does not stop a component re-rendering for a context it reads.
  • Inline objects/functions in a provider value re-render all consumers on every provider render.
  • Split contexts by change frequency; keep state and dispatch in separate contexts.
  • A reducer centralises update logic; dispatch has a stable identity.
🎤 Say this in an interview
"I keep state local, lift it to the nearest common parent, and use context only for state that many distant components read. Because every reader re-renders when a context value changes and memo doesn’t prevent that, I split contexts by how often they change, keep the value stable, and put state and dispatch in separate contexts, with a reducer when updates get complicated."
⚠️ Common trap

One giant “AppContext”. Every setting change re-renders every consumer in the app.

Assuming memo shields you from context. It does not.

🧱 Props

Explicit, visible, easy to trace; verbose when drilled through many layers.

vs.
🌐 Context

Implicit sharing to any depth; every reader re-renders on change.
