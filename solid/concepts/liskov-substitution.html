Concept 4 of 12 · 🔤 The five principles

It compiles — but does it behave like the type it claims to be?

The Liskov Substitution Principle: contracts, the substitution rules, Square/Rectangle, and repairing a repository that throws on Save.

❓ "What is the Liskov Substitution Principle, and what is a classic example of violating it?"
👁 See it first
🎯 Anywhere you use a base type, any subtype must work — without the caller knowing which one it got and without surprises.
📖 Why did this need to exist?

Page 3 made behaviour pluggable through interfaces: the calculator accepts any IDiscountRule. That only works if every implementation behaves as the interface promises. A rule that returns a negative total, or a repository that refuses to save, makes the plug-in model unsafe.

Robert C. Martin’s summary is that derived classes must be usable wherever their base classes are. In type-theory terms, objects of type T may be replaced with objects of subtype S without altering the main behavioural properties of the program.

The classic illustration is Square and Rectangle: mathematically a square is a rectangle, but a square’s width and height are locked together, so code that sets width and height independently gets a surprise. “Is-a” in English is not enough; behaves-like-a is the test.

📜 The substitution rules
🧪 LSP lab · repair the repository
// BEFORE — compiles, but breaks the contract
public interface IOrderRepository
{
    void Save(Order order);
    Order? Find(int id);
}
public class ReadOnlyOrderRepository : IOrderRepository
{
    public void Save(Order order) => throw new NotSupportedException();   // callers did not expect this
    public Order? Find(int id) => /* query */ null;
}

// AFTER — say what each client really needs (ISP and LSP work together)
public interface IOrderReader { Order? Find(int id); }
public interface IOrderWriter { void Save(Order order); }

public class SqlOrderRepository : IOrderReader, IOrderWriter { /* both */ }
public class ReportingOrderReader : IOrderReader { /* read only: honest type */ }

public class OrderService
{
    public OrderService(IOrderWriter writer) { /* needs Save: cannot be given a reader */ }
}

Illustrative. The fix is not a cleverer subclass; it is a more honest abstraction: a type that cannot save should not claim to be able to (next page: Interface Segregation).

🎬 Real-world scenarios
💳
A “GiftCardPayment” cannot refund

It implements IPaymentMethod but throws on Refund.

→ Separate refundable from non-refundable
📦
A “DiscountRule” returns a negative total in one case

It breaks the postcondition.

→ Contract tests for every rule
🟦
Square extends Rectangle

Locked width and height.

→ Do not inherit; model both as shapes with area
🔌
A mock that returns null where the real one never does

Tests pass, production fails.

→ Make fakes honour the contract
▾ Go one level deeper (60 seconds)

Contract tests. Write one test suite against the interface and run it against every implementation; a new rule class must pass the same suite. This is how LSP becomes automatic.

Dynamic languages. Michael Feathers notes LSP still applies where inheritance is not required for substitution: what matters is behavioural compatibility.

Code Contracts. The older .NET Code Contracts tooling modelled preconditions, postconditions and invariants explicitly; check current guidance, since the tooling is dated.

🔥 Interview recall
  • LSP: subtypes must be usable wherever their base types are, without altering the program’s main behaviour.
  • A subtype may accept more and promise more; never demand more, deliver less, add new exceptions, or break invariants.
  • Compiling is not substituting: Square/Rectangle and ReadOnlyRepository both compile.
  • Smells: NotSupportedException overrides, is/as checks on subtypes, do-nothing overrides.
  • Fix by making the abstraction honest (smaller interfaces) or by using composition.
  • Run the same contract tests against every implementation.
🎤 Say this in an interview
"The Liskov Substitution Principle says any subtype must work wherever its base type is expected. Compiling isn’t enough — the subtype must honour the contract: accept at least the same inputs, promise at least the same results and not add surprising exceptions. When I see a subclass throwing NotSupportedException or callers checking the concrete type, I fix the abstraction, by splitting interfaces or using composition, and I run shared contract tests against every implementation."
⚠️ Common trap

“It is-a in real life, so it can inherit.” Square is-a rectangle in geometry, not in behaviour.

Throwing NotSupportedException to “comply” with a fat interface. The violation just moves to runtime.

🏷️ Same type

The compiler is satisfied: the method signatures match.

vs.
🤝 Same behaviour

The runtime is satisfied: the promises of the contract hold.
