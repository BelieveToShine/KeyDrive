Not every bird can fly — so Bird should not promise it.

The Liskov Substitution Principle with the Bird example: promises, penguins, and fixing it with small interfaces.

❓ "What is the Liskov Substitution Principle? Give an example."
👁 See it first
🎯 If something says “I am a Bird”, it must really work everywhere a Bird is expected — no surprises.
🌍 In real life

🔌 Imagine a plug that fits the wall socket but gives no electricity. It fits, but it does not work. In code the compiler only checks that the plug fits. The Liskov Substitution Principle (L in SOLID) is about whether it works.

The rule: a child class must keep every promise its parent made. If it cannot, it should not be that parent’s child.

🔧 The fix: make small promises
🧪 Tiny code
// BEFORE — Bird promises something not every bird can do
class Bird      { public virtual void Eat() { } public virtual void Fly() { } }
class Sparrow : Bird { public override void Fly() => Console.WriteLine("flap flap"); }
class Penguin : Bird { public override void Fly() => throw new NotSupportedException(); }  // 💥

foreach (var b in birds) b.Fly();       // crashes when it reaches the penguin

// AFTER — small promises
abstract class Bird { public void Eat() { } }
interface IFlyable { void Fly(); }
class Sparrow : Bird, IFlyable { public void Fly() => Console.WriteLine("flap flap"); }
class Penguin : Bird { }                // no Fly() at all: nothing to break

foreach (var f in flyers) f.Fly();      // flyers is a List<IFlyable>

The after-version is also the Interface Segregation Principle (the next page) in action: small interfaces, each with one promise.

🎯 Spot it: does this break the rule?
▾ A Penguin : Bird whose Fly() throws an exception

❌ Breaks the rule. Callers trust “every Bird flies”. The penguin breaks that trust.

▾ A Sparrow : Bird, IFlyable with a working Fly()

✅ Fine. It keeps every promise it made. Substituting it anywhere is safe.

▾ A Square : Rectangle where setting the width also changes the height

❌ Breaks the rule. Code that sets width and height separately gets a surprise. A square is a rectangle in maths, but it does not behave like one.

▾ A ReadOnlyList : IList whose Add() throws

❌ Breaks the rule. The interface promises you can add. This type cannot keep that promise. Give it a read-only interface instead (IReadOnlyList).

▾ A child class that does the same thing in a faster way

✅ Fine. Same promise, kept. Different inside is fine — that is the whole point of substitution.

👀 How to spot it in your own code
If you see…Do this
A method that does throw new NotSupportedException() or NotImplementedException()The child cannot keep the parent’s promise. Split the interface (I) or stop inheriting.
if (animal is Penguin) checks before calling a methodThe caller already knows the child breaks the rule. Move that method into a separate interface.
An override that is empty or returns a fake valueIt pretends to keep the promise. Same fix.
A subclass that rejects input the parent acceptedIt demands more than the parent did. The child must accept at least what the parent accepts.
🔥 Interview recall
  • LSP: a child must work everywhere its parent works — without surprises.
  • Compiling is not enough; the child must keep the parent’s promises (behaviour).
  • Bird → Eat() only; IFlyable → Fly() — small promises, the penguin never lies.
  • Smells: NotSupportedException overrides, is/as type checks, empty overrides.
🎤 Say this in an interview
"The Liskov Substitution Principle says anywhere you use a parent type, a child must work without surprises. If Bird promises Fly() but Penguin throws, the loop that flies every bird crashes. I fix it by making smaller promises: Bird only has Eat(), and flying moves into an IFlyable interface that only flying birds implement."
⚠️ Common trap

“A penguin is a bird, so it must inherit Fly().” In real life yes; in code, inheriting means promising the behaviour. Model what the type can really do.

➡️ Where this leads
Our fix used a small interface, IFlyable. Making interfaces small on purpose is the next letter: Interface Segregation. I — the Interface Segregation Principle →
