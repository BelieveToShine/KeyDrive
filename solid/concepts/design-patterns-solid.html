Patterns are the principles in a concrete shape.

Strategy, Decorator, Factory, Adapter and Observer: which principle each serves, C# examples, and the .NET features that are the same ideas.

❓ "Which design patterns relate to SOLID, and how would you add logging or caching without modifying a class?"
👁 See it first
🎯 Principles say what good design looks like; patterns are proven recipes for getting there. Learn the problem each pattern solves, not its diagram.
📖 Why did this need to exist?

In the catalog of design patterns (the “Gang of Four” collection, as presented on refactoring.guru), Strategy puts interchangeable algorithms in separate classes behind one interface, so the context can switch them; Decorator attaches new behaviour by placing an object inside wrapper objects that implement the same interface; Factory Method provides an interface for creating objects while letting subclasses alter the type created.

Adapter makes objects with incompatible interfaces work together, and Observer is a subscription mechanism that notifies several objects about events on the object they watch.

You have already built two of these without naming them: the IDiscountRule list on page 3 is a Strategy, and the interface seam on page 6 is where an Adapter or Decorator plugs in.

🎁 Decorator in one picture
🧪 Pattern lab · decorator, adapter, observer
// DECORATOR — add logging without touching SqlOrderRepository
public class LoggingOrderRepository(IOrderRepository inner, ILogger<LoggingOrderRepository> log) : IOrderRepository
{
    public void Save(Order order)
    {
        log.LogInformation("Saving order {Id}", order.Id);
        inner.Save(order);
    }
}
// Program.cs
builder.Services.AddScoped<SqlOrderRepository>();
builder.Services.AddScoped<IOrderRepository>(sp => new LoggingOrderRepository(
    sp.GetRequiredService<SqlOrderRepository>(), sp.GetRequiredService<ILogger<LoggingOrderRepository>>()));

// ADAPTER — depend on your interface, wrap the vendor's SDK once
public interface IPaymentGateway { PaymentResult Charge(decimal amount, string token); }
public class VendorPaymentAdapter(VendorClient vendor) : IPaymentGateway
{
    public PaymentResult Charge(decimal amount, string token)
    {
        var r = vendor.CreateCharge(new VendorChargeRequest { AmountCents = (long)(amount * 100), Source = token });
        return new PaymentResult(r.Status == "ok");
    }
}

// OBSERVER — the publisher does not know who listens
public class OrderService
{
    public event Action<Order>? OrderPlaced;
    public void Place(Order o) { /* save */ OrderPlaced?.Invoke(o); }
}
// listeners subscribe elsewhere:  service.OrderPlaced += emailSender.Send;

Illustrative (VendorClient is a made-up SDK). The same ideas appear in .NET itself: middleware wraps the next delegate, and HttpClient handlers chain the same way.

▾ Go one level deeper (60 seconds)

Patterns are vocabulary. Their main benefit is that a team can say “wrap it in a decorator” and mean the same thing. The code can be small; the naming is the value.

Registering decorators. The built-in container has no first-class decorator API in the pages checked for this lesson; the lab uses an explicit factory registration, and libraries exist for convention-based decoration.

Domain events vs events. A C# event works inside one process. Messaging between services is a different problem — see the Messaging pages in the Cloud labs.

🔥 Interview recall
  • Strategy: interchangeable algorithms behind one interface (OCP).
  • Decorator: wrappers with the same interface add behaviour without editing the class (SRP, OCP).
  • Factory: hide which concrete class is created (DIP).
  • Adapter: depend on your interface, wrap the foreign one (DIP, ISP).
  • Observer: publisher does not know its subscribers (OCP, DIP).
  • Start from pain, not from a pattern name.
🎤 Say this in an interview
"Principles tell me what good looks like; patterns are named recipes. I use Strategy when a behaviour has real variants, a Decorator to add logging or caching without editing the class, an Adapter to isolate a vendor API behind my own interface, and Observer when many parts react to one event. ASP.NET Core middleware and HttpClient handlers are decorator-style chains. But I choose a pattern because it removes a specific pain, not because it is on a list."
⚠️ Common trap

Pattern-first design. Forcing a pattern onto code that has no variation adds layers for nothing.

Confusing Decorator and Adapter. A decorator keeps the interface and adds behaviour; an adapter changes the interface.

🎁 Decorator

Same interface in, same interface out, extra behaviour.

vs.
🔌 Adapter

Different interface in, your interface out.
