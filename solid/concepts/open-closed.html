Concept 3 of 12 · 🔤 The five principles

Add behaviour by adding code, not by editing code that works.

The Open/Closed Principle, an if-chain turned into IDiscountRule plug-ins, and the techniques that keep a class closed.

❓ "What is the Open/Closed Principle, and how do you apply it without over-engineering?"
👁 See it first
🎯 Software entities should be open for extension but closed for modification: add behaviour by adding code, not by editing code that already works.
📖 Why did this need to exist?

Page 2 isolated pricing in one class, owned by finance. But finance adds a promotion every month, and a class that grows by editing the same if-chain is risky: each edit can break an older promotion that no one remembers.

Bertrand Meyer defined the principle in 1988; Robert C. Martin restates the goal as extending the behaviour of a system without having to modify that system, and ties its achievement to abstractions and the Dependency Inversion Principle: users depend on an API, and services implement it through inheritance or other polymorphism.

Martin is also clear that it is strategic, not absolute: no significant program can be 100% closed. You choose which axis of change to protect — here, “new promotions”.

🧱 The shape of the design
🧪 OCP lab · before and after
// BEFORE — closed to extension, open to edits
public decimal Price(Order o)
{
    decimal total = o.Items.Sum(i => i.Price * i.Quantity);
    if (o.Customer.IsVip) total *= 0.90m;
    else if (o.Date.Month == 11) total *= 0.80m;
    else if (o.Coupon == "SAVE5") total -= 5m;          // every new promotion = another branch
    return total;
}

// AFTER — add a class, do not edit the calculator
public interface IDiscountRule { decimal Apply(Order o, decimal total); }

public class VipDiscount : IDiscountRule
{
    public decimal Apply(Order o, decimal t) => o.Customer.IsVip ? t * 0.90m : t;
}

public class PricingCalculator
{
    private readonly IEnumerable<IDiscountRule> _rules;
    public PricingCalculator(IEnumerable<IDiscountRule> rules) => _rules = rules;

    public decimal Price(Order o)
    {
        decimal total = o.Items.Sum(i => i.Price * i.Quantity);
        foreach (var rule in _rules) total = rule.Apply(o, total);
        return total;
    }
}

Illustrative. The rules arrive through the constructor, so registering one more class is enough (page 7). Note the rule order may matter — a design decision to make explicit.

Two meanings. Meyer (1988) used “open” for a module that can be extended and “closed” for one that others can use; Martin’s later reading is that extending a module’s behaviour does not change its source or binary code.

Strategic. Martin: no significant program can be 100% closed; you guess where change will come from and protect that axis — and the guess can be wrong.

Link to D. Microsoft’s architecture guidance says dependency injection is built on the dependency inversion principle and is often key to achieving the open/closed principle.

🔥 Interview recall
  • OCP: open for extension, closed for modification — add code, do not edit working code.
  • Achieved with abstractions (interfaces, polymorphism), strategy, decorators, delegates.
  • It is strategic: choose the axis of change you protect; nothing is 100% closed.
  • Smell: a growing if/else or switch on a type; every feature edits one central class.
  • Do not add the interface until a second variation exists.
  • Dependency injection (D) is what usually delivers OCP in .NET.
🎤 Say this in an interview
"The Open/Closed Principle says extend behaviour by adding code, not editing it. For promotions I define an IDiscountRule interface and one class per promotion, so the calculator is closed for modification while the system is open to new rules. It is strategic — I protect the axis I expect to change — and I introduce the interface when the second variation shows up, not before."
⚠️ Common trap

Abstracting everything “just in case”. Interfaces for things that never vary add noise and indirection.

Extending through inheritance by default. It couples subclasses to the base class and can break substitutability.

🔒 Closed for modification

The calculator’s code does not change when behaviour is added.

vs.
🔓 Open for extension

New behaviour is added through new classes that plug into a seam.
