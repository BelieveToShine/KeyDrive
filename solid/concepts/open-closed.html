Concept 3 of 12 · 🔤 The five principles

Add new things without opening old code — like plugging into a power strip.

The Open/Closed Principle with a discount calculator and a power strip: why editing working code is risky, and how a socket (interface) avoids it.

❓ "What is the Open/Closed Principle? Give an example."
👁 See it first
🎯 Add new behaviour by adding new code — not by editing old, working code. “Open for extension, closed for modification.”
🌍 In real life

🔌 A power strip has sockets. When you buy a new device you just plug it in. You never open the power strip and rewire it. The strip is closed for editing but open for new devices.

Good code works the same way: it has “sockets” (an interface) and each new case is one more thing you plug in.

🔧 The fix: make a socket
🧪 Tiny code
// BEFORE — a new customer type means editing this method again
decimal GetDiscount(string type)
{
    if (type == "Regular") return 0m;
    if (type == "Gold")    return 0.10m;
    return 0m;                          // add Student here... and re-test everything
}

// AFTER — one small class per type; the calculator never changes
interface IDiscount { decimal Percent(); }
class RegularDiscount : IDiscount { public decimal Percent() => 0m; }
class GoldDiscount    : IDiscount { public decimal Percent() => 0.10m; }
class StudentDiscount : IDiscount { public decimal Percent() => 0.15m; }   // the only new code

class PriceCalculator
{
    public decimal Price(decimal amount, IDiscount discount) => amount * (1 - discount.Percent());
}

Adding StudentDiscount is a new file. PriceCalculator is untouched.

🎯 Spot it: does this break the rule?
▾ Adding a new else if (type == "Student") to a long method every time a customer type appears

Breaks the rule. Each new case edits old, working code.

▾ Adding a new class StudentDiscount : IDiscount and nothing else

Fine. New behaviour = new code. The old code is not touched.

▾ The same switch (paymentType) copied in five different files

Breaks the rule. A new payment type means hunting down five places and editing all of them.

▾ One small if for a rule that has never changed in ten years

Fine. Do not build sockets for things that never change. Wait until the second or third case appears.

👀 How to spot it in your own code
If you see…Do this
A long if / else if or switch on a “type” or “kind”Each new type edits it. Replace with one small class per type behind an interface.
The same switch appears in many placesA new case means many edits (“shotgun surgery”). Move the behaviour into the types.
Every feature request starts with “open this file and add…”Create a socket (interface) where change keeps happening.
You are afraid to touch a class because everything depends on itStop editing it; extend it from outside.
🔥 Interview recall
  • OCP: open for extension (add new classes), closed for modification (do not edit working code).
  • Make a “socket”: an interface where new things plug in.
  • Smells: long if/else or switch on a type; the same switch in many places.
  • Do it where change really keeps happening, not everywhere.
🎤 Say this in an interview
"The Open/Closed Principle says I should be able to add new behaviour without editing working code. If discounts are an if/else chain, every new customer type means editing and re-testing it. I introduce an IDiscount interface and one small class per type; the calculator stays the same and a new type is just a new class — like plugging a new device into a power strip."
⚠️ Common trap

“Always make everything extensible.” No — only where change really happens. A rule that never changes needs no socket (see page 11).
