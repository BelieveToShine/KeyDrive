Concept 5 of 12 · 🔤 The five principles

Give each client only the methods it needs.

The Interface Segregation Principle: fat interfaces, role interfaces, splitting without splitting the class, and when to stop.

❓ "What is the Interface Segregation Principle, and how does it relate to LSP?"
👁 See it first
🎯 Make small interfaces, shaped by what each client needs — no client should be forced to depend on methods it does not use.
📖 Why did this need to exist?

This is the same pain as page 4, one step earlier: if an interface is wide, some implementer eventually cannot honour all of it, and throws NotSupportedException. Narrow interfaces make that impossible.

The principle is usually worded “clients should not be forced to depend on methods they do not use”. Eric Lippert’s advice on Microsoft Learn’s blog archive points the same way: an interface should be a minimal group of members needed for one responsibility, designed from the point of view of the code calling it.

Microsoft’s .NET architecture guidance also says to keep cohesion high and the interaction points between pieces few. Small interfaces are how that looks in code.

✂️ After segregation
🧪 ISP lab · split the fat interface
// BEFORE — one interface, four jobs
public interface IOrderStore
{
    void Save(Order order);
    Order? Find(int id);
    string ExportCsv(DateOnly from, DateOnly to);
    void SendEmail(int orderId);
}
public class CheckoutService
{
    public CheckoutService(IOrderStore store) { /* only calls Save */ }
}

// AFTER — role interfaces
public interface IOrderWriter   { void Save(Order order); }
public interface IOrderReader   { Order? Find(int id); }
public interface IOrderExporter { string ExportCsv(DateOnly from, DateOnly to); }

public class SqlOrderRepository : IOrderWriter, IOrderReader, IOrderExporter { /* ... */ }

public class CheckoutService
{
    public CheckoutService(IOrderWriter writer) { /* cannot call anything else */ }
}

Illustrative. Email left the interface entirely: sending mail is a different job and belongs behind its own INotifier. DI registers one class under several interfaces.

▾ Go one level deeper (60 seconds)

Role interfaces. Name an interface after the role a client needs (IOrderReader), not after the class that implements it (IOrderRepository).

Do not overdo it. One-method interfaces everywhere become noise. Split when clients really differ in what they need; keep cohesive operations together.

.NET itself. The base library follows the idea: IReadOnlyList<T> and IList<T> give read-only and read-write views of a list. Prefer accepting the narrower one.

🔥 Interview recall
  • ISP: no client should be forced to depend on methods it does not use.
  • A fat interface couples unrelated clients and forces test doubles to implement everything.
  • Split by role, named after what the client needs; one class may implement several.
  • ISP prevents LSP violations: you cannot throw from a method that is not in the interface.
  • Do not shatter into one-method interfaces without a reason.
  • Accept the narrowest type that does the job (for example IReadOnlyList instead of List).
🎤 Say this in an interview
"The Interface Segregation Principle says clients shouldn’t depend on methods they don’t use. When I see a wide interface with stubs that throw, or a test double implementing ten methods for one call, I split it into role interfaces named after what each client needs. One class can implement several, so there’s no duplication — each consumer just gets a smaller, safer view. I keep it proportionate: split where clients genuinely differ."
⚠️ Common trap

“ISP means one method per interface.” It means shaped by clients’ needs; cohesive methods stay together.

Splitting the class instead of the interface. The class can implement several interfaces.
