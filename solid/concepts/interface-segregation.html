A plain printer should not be forced to carry a fax button.

The Interface Segregation Principle with a printer and a TV remote: fat interfaces, small interfaces and when to stop splitting.

❓ "What is the Interface Segregation Principle? Give an example."
👁 See it first
🎯 No class should be forced to have methods it does not use. Make small interfaces, each with one focused promise.
🌍 In real life

📺 A TV remote with 50 buttons when you only use 3. You can press the wrong one, and nobody can tell which buttons matter. A simple remote with just the buttons you need is safer and clearer.

In code, a fat interface is the 50-button remote. A small interface is the simple one. (It also fixes the penguin problem from the last page: IFlyable was a small interface.)

✂️ The fix: split it
🧪 Tiny code
// BEFORE — one fat interface
interface IMachine { void Print(); void Scan(); void Fax(); }

class BasicPrinter : IMachine
{
    public void Print() { /* works */ }
    public void Scan() => throw new NotSupportedException();   // forced to have it
    public void Fax()  => throw new NotSupportedException();   // forced to have it
}

// AFTER — small interfaces
interface IPrinter { void Print(); }
interface IScanner { void Scan(); }
interface IFax     { void Fax(); }

class BasicPrinter : IPrinter { public void Print() { /* works */ } }
class AllInOne     : IPrinter, IScanner, IFax { /* all three */ }

void RunJob(IPrinter printer) => printer.Print();   // works with both

The code that only prints now depends only on IPrinter.

🎯 Spot it: does this break the rule?
▾ An IWorker with Work() and Eat(), and a Robot class that must implement Eat()

Breaks the rule. The robot is forced to carry a method it cannot use. Split Eat into IFeedable.

▾ An interface with 20 methods, used by five different classes that each call only two or three of them

Breaks the rule. Every client depends on 17 methods it does not need. Split by what each client uses.

▾ An interface with just Open() and Close() — everyone who opens also closes

Fine. These always go together. Do not split things that belong together.

▾ A class that implements three small interfaces

Fine. That is exactly the design: many small promises, one class can keep several.

👀 How to spot it in your own code
If you see…Do this
A method that throws NotImplementedException because “the interface needs it”The interface is bigger than this class. Split it.
A fake/mock with a long list of empty methods just to run one testThe client depends on far more than it uses.
An interface named IManager or IService with 15+ methodsIt probably holds several jobs. Split by role.
A change to one method forces unrelated classes to recompile or re-testToo much sharing. Give each client its own small interface.
🔥 Interview recall
  • ISP: no class should be forced to implement methods it does not use.
  • Fat interface = remote with 50 buttons. Small interfaces = remotes with just the buttons you need.
  • One class can implement many small interfaces.
  • Do not over-split: keep things that always go together in one interface.
🎤 Say this in an interview
"The Interface Segregation Principle says clients should not be forced to depend on methods they don’t use. If a basic printer has to implement an IMachine with Scan and Fax, it ends up with fake methods. I split the interface into small ones — IPrinter, IScanner, IFax — and each class implements only what it can really do."
⚠️ Common trap

“ISP means one method per interface.” No — group methods that belong together and are always used together.
