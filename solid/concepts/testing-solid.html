Concept 10 of 12 · 🛠️ Making it real

Testability is the proof the design worked.

Fakes, stubs and mocks, a unit test and an integration test in C#, contract tests for LSP, and what bad tests say about your design.

❓ "How does SOLID make code easier to test, and what is the difference between a stub and a mock?"
👁 See it first
🎯 Testability is the proof that the design worked. If a class is hard to test, one of the principles is being bent.
📖 Why did this need to exist?

Microsoft’s unit-testing guidance describes the standard shape: arrange your objects, act on one of them, assert that something is as expected; and to isolate a component by replacing a dependency with a fake implementation so the test focuses on one thing.

It also gives useful vocabulary: a stub just supplies canned answers; a mock is like a stub except that you assert against it. “Fake” is the general word for any test stand-in. Mixing those words up leads other developers to the wrong assumptions about the test’s intent.

SOLID and testing feed each other: SRP gives small units to test, DIP supplies the seams, ISP keeps fakes tiny, LSP says the fake must behave like the real thing, and OCP means adding a rule adds a test rather than editing one.

🧪 Test lab · a unit test and an integration test
// UNIT TEST — fakes, no infrastructure
public class FakeOrderRepository : IOrderRepository
{
    public List<Order> Saved { get; } = new();
    public void Save(Order order) => Saved.Add(order);
}
public class FakeNotifier : INotifier
{
    public List<int> Told { get; } = new();
    public void OrderPlaced(Order order) => Told.Add(order.Id);
}

[Fact]
public void Place_saves_the_order_and_notifies()
{
    // Arrange
    var repo = new FakeOrderRepository();
    var notifier = new FakeNotifier();
    var service = new OrderService(new OrderValidator(), new PricingCalculator(new IDiscountRule[0]), repo, notifier);

    // Act
    service.Place(new Order(id: 42));

    // Assert
    Assert.Single(repo.Saved);
    Assert.Equal(42, Assert.Single(notifier.Told));
}

// INTEGRATION TEST — real host, swap only the outside world
public class OrdersApiTests(WebApplicationFactory<Program> factory) : IClassFixture<WebApplicationFactory<Program>>
{
    [Fact]
    public async Task Post_order_returns_created()
    {
        var client = factory.WithWebHostBuilder(b => b.ConfigureTestServices(s =>
            s.AddSingleton<INotifier, FakeNotifier>())).CreateClient();
        var response = await client.PostAsJsonAsync("/orders", new { id = 42 });
        Assert.Equal(HttpStatusCode.Created, response.StatusCode);
    }
}

Illustrative. The unit test needs nothing but code. The integration test runs the real pipeline and real registrations, replacing only the notifier so no mail goes out.

🎬 Real-world scenarios
⏰
A test passes on weekdays and fails at weekends

It reads DateTime.Now.

→ Inject the clock
📧
Developers learn not to run tests locally

They send real email.

→ FakeNotifier in unit tests; fake in integration tests
🔁
SqlRepo and InMemoryRepo disagree

The fake was written from memory.

→ One contract-test class, run against both
🧱
Refactoring breaks 60 tests

They mocked every call.

→ Assert on results, keep mocks at the boundary
▾ Go one level deeper (60 seconds)

Contract tests for LSP. Write the repository tests once as an abstract class (OrderRepositoryContract) and subclass it for each implementation: the in-memory fake and the SQL one. If both pass, substituting is safe.

Database tests. The EF Core documentation has a page on testing without your production database; use it for deciding between an in-memory substitute and a real test database, because they behave differently.

Mocking libraries. Libraries such as Moq or NSubstitute generate stubs and mocks for small interfaces; hand-written fakes are often clearer for stateful things like repositories.

🔥 Interview recall
  • Arrange, act, assert; isolate the unit by replacing dependencies with fakes.
  • Stub = canned answers; mock = you assert against it; fake = any stand-in.
  • DIP gives the seams, SRP the small units, ISP the tiny fakes, LSP the trustworthy fakes.
  • Many unit tests, some integration tests (swap only the outside world), few end-to-end.
  • Hard-to-test code is design feedback, not a testing problem.
  • Run one contract-test suite against every implementation, real and fake.
🎤 Say this in an interview
"I treat testability as the proof the design worked. With dependencies injected through small interfaces I can unit-test OrderService with in-memory fakes — arrange, act, assert, no infrastructure. I keep a few integration tests on the real host, swapping only the outside world with ConfigureTestServices, and I run one contract-test suite against both the fake and the real repository so substitution is safe. If a test needs huge setup or real I/O, that tells me which principle the code bends."
⚠️ Common trap

Mocking everything. Tests then mirror the implementation and break on every refactoring.

Fakes that drift from the real thing. They pass while production fails.

Adding an interface only to mock it. If nothing else varies, ask whether the test really needs it.

🧱 Stub

Gives canned answers; you do not assert on it.

vs.
🎯 Mock

You assert that specific calls happened.
