Easy tests are the proof the design worked.

Fakes, stubs and mocks in plain words, a fast unit test in C#, and what a hard-to-test class is telling you.

❓ "How does SOLID make code easier to test, and what is the difference between a stub and a mock?"
👁 See it first
🎯 Easy testing is the proof that the design worked. If a class is hard to test, a principle is being bent.
🌍 In real life

🚗 Before a driving test, you practise in an empty car park with a practice dummy, not on a busy road with real pedestrians. Tests do the same: they use stand-ins that look like the real thing but cannot hurt anyone.

A fake is a stand-in that works (in memory). A stub just gives canned answers. A mock is a spy that remembers who called it, so the test can check.

⚡ With sockets, tests use fakes
🧪 Tiny code
class FakeNotifier : INotifier
{
    public List<int> Told { get; } = new();
    public void OrderPlaced(Order order) => Told.Add(order.Id);     // just remembers
}

[Fact]
public void Placing_an_order_tells_the_customer()
{
    var notifier = new FakeNotifier();
    var service = new OrderService(new FakeRepository(), notifier);   // plug in the fakes

    service.Place(new Order(id: 42));                                  // act

    Assert.Equal(new[] { 42 }, notifier.Told);                         // assert on the fake
}

Arrange – Act – Assert: set things up, do one thing, check the result.

🧸 Stub, mock, fake — plain words
WordPlain meaningExample
Fakea simple working copya list that stands in for the database
Stubgives canned answersa clock that always says “Monday 9:00”
Mocka spy: you check what was called“was OrderPlaced called with 42?”

Microsoft’s .NET testing guidance separates mock and stub by where the assertions happen (against a mock, not a stub) and warns that mixing the words up misleads readers. “Fake” is the general word for any stand-in.

🎯 Spot it: what is the test telling you?
▾ “I cannot run this test without the internet”

A design smell. Something real is hard-wired inside (DIP). Hand it in through an interface.

▾ “Setting up the test takes 40 lines”

A design smell. The class needs too many things (SRP). Split it.

▾ “My fake passes but production crashes”

A design smell. The fake does not behave like the real thing (LSP). Run the same checks against both.

▾ “A test for one rule needs only one small object”

Healthy. That is what well-designed code feels like.

🔥 Interview recall
  • Testability is the proof of design: easy tests = small, separate, replaceable pieces.
  • Hand fakes in through interfaces; the test never touches the real database or mail server.
  • Fake = simple working copy, stub = canned answers, mock = a spy you check.
  • Arrange – Act – Assert; keep most tests small and fast, a few that use the real thing.
🎤 Say this in an interview
"I treat testability as the proof the design worked. Because OrderService receives its dependencies through interfaces, I can unit-test it with in-memory fakes — arrange, act, assert, in milliseconds, with no database or email. I keep a few integration tests on the real host, swapping only the outside world, and I make sure fakes behave like the real thing."
⚠️ Common trap

Mocking everything. Tests then copy the code and break at every refactoring. Check results, not every call.

Fakes that drift from the real thing. Check both with the same tests.

▾ Go one level deeper (60 seconds)

Integration tests. In ASP.NET Core you can start the real app in a test and replace just one registration (for example the notifier) with ConfigureTestServices, so real wiring is checked without sending real mail.

Same tests for real and fake. Write the repository checks once and run them against both the fake and the SQL one. If both pass, swapping is safe — that is Liskov in practice.
