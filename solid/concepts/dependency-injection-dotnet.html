Who builds the object graph?

Dependency injection in .NET: the composition root, service lifetimes, captive dependencies and the service-locator trap.

❓ "What are the DI service lifetimes in .NET, and what is a captive dependency?"
👁 See it first
🎯 Register once at startup, receive through constructors everywhere else. The container wires; your classes just declare what they need.
📖 Why did this need to exist?

Dependency injection is the technique that makes the Dependency Inversion Principle practical: Microsoft’s .NET architecture guidance notes that DI is often a key to the Open/Closed Principle too, and that a very large constructor is a smell (the class probably does too much — page 2 again).

ASP.NET Core and the .NET Generic Host include a built-in container, Microsoft.Extensions.DependencyInjection. You register services in IServiceCollection; the container resolves them when something asks.

It is also where the new bugs live: choosing the wrong lifetime, and hiding dependencies by calling the container from inside a class. The rest of this page is those two traps.

⏱️ Lifetimes: how long an instance lives
🧪 DI lab · wire it and avoid the captive dependency
// Program.cs — the composition root
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.AddSingleton<INotifier, SmtpNotifier>();
builder.Services.AddScoped<OrderService>();

var app = builder.Build();
app.Run();

// BAD — a singleton that holds a scoped service (a "captive dependency")
builder.Services.AddSingleton<OrderCache>();        // constructor takes IOrderRepository (scoped!)

// BETTER — a long-lived service creates a scope when it needs a short-lived one
public class NightlyJob(IServiceScopeFactory scopes)
{
    public void Run()
    {
        using var scope = scopes.CreateScope();
        var repo = scope.ServiceProvider.GetRequiredService<IOrderRepository>();
        // use repo, then the scope disposes it
    }
}

Illustrative. In ASP.NET Core Development, scope validation is on by default, so the captive dependency fails at startup instead of misbehaving in production; you can turn it on in every environment.

▾ Go one level deeper (60 seconds)

Background services. A hosted service is a singleton. Do not inject scoped services into its constructor — inject IServiceScopeFactory and create a scope for each unit of work, as in the lab above.

Disposal. The container disposes objects it created, at the end of their scope. Do not dispose injected dependencies yourself; objects you create with new are yours to dispose.

Middleware. Conventional middleware is created once, so a scoped service in its constructor behaves like a singleton. Put it on the InvokeAsync method instead.

🔥 Interview recall
  • DI hands collaborators in from outside; the composition root (Program.cs) is the one place that knows the concrete classes.
  • Lifetimes: Singleton (one per app), Scoped (one per request), Transient (new each time).
  • Captive dependency: a long-lived service that holds a short-lived one. Validate scopes; use IServiceScopeFactory.
  • Avoid the service locator, direct new of dependencies and stateful statics.
  • A big constructor is a smell — it points back at SRP.
  • Do not register IDisposable as transient; do not dispose what the container owns.
🎤 Say this in an interview
"Dependency injection is how we apply the Dependency Inversion Principle in .NET. Classes declare their dependencies as constructor parameters, and the composition root in Program.cs registers which implementation to use. I choose the shortest correct lifetime — singleton, scoped or transient — watch for captive dependencies, enable scope validation, and avoid calling the container from inside business code, which turns it into a service locator. A constructor with too many parameters tells me the class has too many responsibilities."
⚠️ Common trap

“Everything should be a singleton for performance.” Per-request state in a singleton leaks between users.

Resolving from the container inside methods. That hides the dependency and defeats testing.

Registering concrete classes with no interface where you need a seam. You then cannot substitute them.
