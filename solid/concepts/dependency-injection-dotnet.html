Who plugs things in? The electrician.

Dependency injection in .NET: the container as an electrician, Program.cs as the plan, and the three lifetimes with everyday pictures.

❓ "What are the DI service lifetimes in .NET, and what is a captive dependency?"
👁 See it first
🎯 Write the plan once at startup; every class just asks for what it needs in its constructor. That technique is called dependency injection.
🌍 In real life

🧰 When you move into a new flat, you do not wire the sockets yourself: an electrician follows the plan and plugs everything in. You just say “I need a lamp here”.

Dependency injection is the electrician. The container is built into .NET (Microsoft.Extensions.DependencyInjection), and Program.cs is where you hand it the plan.

⏱️ How long does each thing live?
🧪 Tiny code
// Program.cs — the plan
builder.Services.AddSingleton<IClock, SystemClock>();   // one for the whole app (the printer)
builder.Services.AddScoped<ISwitchable, Bulb>();        // one per web request (the notebook)
builder.Services.AddTransient<IReceiptNumber, ReceiptNumber>(); // new every time (the cup)
builder.Services.AddScoped<LightSwitch>();

// LightSwitch just asks for what it needs — it never says "new"
class LightSwitch
{
    private readonly ISwitchable _device;
    public LightSwitch(ISwitchable device) { _device = device; }
}

// BAD — a singleton that keeps something per-request (the printer keeping the notebook)
builder.Services.AddSingleton<CartCache>();   // its constructor takes a scoped IOrderRepository

In ASP.NET Core Development, scope validation is on by default and catches the bad case at startup; you can switch it on in every environment.

🎯 Spot it: is this a problem?
▾ A singleton service that keeps the current user’s shopping cart in a field

A problem. Everyone shares one singleton, so users would see each other’s carts. Use scoped.

▾ A scoped service that holds the database context for one web request

Fine. Exactly what scoped is for: one per request, thrown away afterwards.

▾ A method that calls serviceProvider.GetService<T>() in the middle of its code

A problem. That is the “service locator” trap: the class’s needs are hidden. Ask for them in the constructor instead.

▾ A class whose constructor takes 10 parameters

A problem. A warning smell: the class probably does too many jobs (page 2). Split it.

👀 Quick rules
LifetimeUse it forCareful
🖨️ Singletonshared, thread-safe things: a clock, configuration, a cachenever keep per-user/per-request data; must not hold scoped things
📓 Scopedper-request things: database context, “current user”do not capture in a singleton
🥤 Transientsmall, throw-away helpersavoid for things that need disposing (the container keeps them until the request ends)
🔥 Interview recall
  • DI = a class receives what it needs in its constructor instead of creating it.
  • Program.cs is the composition root: the one place that knows which class fits which interface.
  • Lifetimes: Singleton (one for the app), Scoped (one per request), Transient (new every time).
  • Captive dependency: a long-lived object keeping a short-lived one. Turn scope validation on.
  • A constructor with too many parameters is a smell — split the class.
🎤 Say this in an interview
"Dependency injection is how we apply the Dependency Inversion Principle in .NET. Classes ask for what they need in their constructor, and Program.cs — the composition root — registers which implementation to use. I pick the shortest correct lifetime: singleton, scoped or transient, I watch for captive dependencies, and I avoid calling the container from inside my classes, because that hides what they need."
⚠️ Common trap

“Make everything a singleton, it is faster.” Per-request data in a singleton leaks between users.

“Resolve things from the container inside methods.” That hides dependencies and makes tests hard (service locator).
