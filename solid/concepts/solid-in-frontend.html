📖 Why did this need to exist?

This site’s React and Angular labs already contain the mechanics: custom hooks, context and state architecture, an API layer, Angular’s dependency injection, services and state management. This page connects them to the principles.

React’s documentation says custom hooks let you share stateful logic but not state itself — each call to a hook is independent — and warns that wrapping a single useState in a custom hook is probably unnecessary. Components and hooks are also expected to be pure, with props treated as read-only. Those are SRP-and-contract ideas, even though the docs do not use the SOLID names.

Angular’s docs show the Dependency Inversion Principle in framework form: { provide: Logger, useClass: EvenBetterLogger } substitutes an alternative implementation; a TypeScript interface cannot be a DI key because interfaces disappear after compilation, so you use an InjectionToken (or an abstract class) as the key.

🧪 Lab · the same refactoring in React and Angular
// REACT — before: one component fetches, transforms and renders
function Orders() {
  const [orders, setOrders] = useState([]);
  useEffect(() => { fetch('/api/orders').then(r => r.json()).then(setOrders); }, []);
  return <ul>{orders.map(o => <li key={o.id}>{o.total}</li>)}</ul>;
}

// REACT — after: a hook owns the data, the component only renders; the source is a parameter
function useOrders(load) { /* load() -> Promise<Order[]>; state, loading, error live here */ }
function OrdersView({ orders }) { return <ul>{orders.map(o => <li key={o.id}>{o.total}</li>)}</ul>; }
function Orders({ load = fetchOrders }) { const orders = useOrders(load); return <OrdersView orders={orders} />; }
// tests pass a fake load; OrdersView needs no hook at all

// ANGULAR — token + providers
export interface OrderRepository { list(): Observable<Order[]>; }
export const ORDER_REPO = new InjectionToken<OrderRepository>('ORDER_REPO');

@Component({ /* ... */ })
export class OrdersComponent {
  private repo = inject(ORDER_REPO);
  orders$ = this.repo.list();
}
// app.config.ts:  providers: [{ provide: ORDER_REPO, useClass: HttpOrderRepository }]
// in a test:      providers: [{ provide: ORDER_REPO, useClass: InMemoryOrderRepository }]

Illustrative sketches in TypeScript/JSX (not compiled). React has no container: the “injection” is a parameter, a prop, a custom hook or context. Angular has one: providers and inject().

▾ Go one level deeper (60 seconds)

Do not import OO ceremony. React in particular rewards small functions and composition; you rarely need classes or interfaces. Use the principles as questions, not as a requirement to add layers.

Lightweight tokens. Angular documents a “lightweight injection token” pattern: a small abstract class used as the token while the real implementation is provided later.

See the labs. React: custom hooks, context and state architecture, API layer. Angular: dependency injection, state management, component communication.

🔥 Interview recall
  • The same design problems exist in components; only the tools differ.
  • React: logic in custom hooks, variation through children/props, dependencies as parameters or context.
  • Angular: services, content projection, providers and InjectionTokens.
  • Interfaces vanish at runtime in TypeScript, so Angular uses an InjectionToken (or abstract class) as the DI key.
  • Custom hooks share logic, not state; do not wrap a single useState without reason.
  • Use the principles as questions, not as a mandate for layers.
🎤 Say this in an interview
"The same problems appear in front-end code. In React I keep components pure and focused on rendering, put data logic in custom hooks or an API layer, let children and props carry the variable parts, and pass the data source as a parameter so tests can fake it. In Angular I use services, content projection, and providers with an InjectionToken so a component asks for an abstraction and the app config or test decides the implementation."
