From symptom to principle to a safe step.

Code smells mapped to SOLID, the refactorings that fix them, and the loop that keeps every step safe.

❓ "How do you refactor a large class safely, and which smells point to which SOLID principle?"
👁 See it first
🎯 Smells are the symptoms; principles are the diagnosis; refactorings are the treatment — applied in small, safe steps.
📖 Why did this need to exist?

Pages 2–7 each taught a principle from the “design” side. In real code you arrive from the opposite direction: a file that is painful to change. The ladder is smell → read → find → guess → change → prove, and this page is the “find” step.

Refactoring means changing structure without changing behaviour. Martin Fowler’s catalog names the small moves (Extract Class, Replace Conditional with Polymorphism and others); the 2nd edition of his book kept both of those. Smells fall into families such as bloaters (Large Class), change preventers (Divergent Change, Shotgun Surgery), couplers (Feature Envy) and object-orientation abusers (Switch Statements), as grouped in the refactoring.guru catalog.

The two change-preventer smells are mirror images: Divergent Change — one class changes for many reasons (SRP); Shotgun Surgery — one change needs edits in many classes (a responsibility was scattered, the opposite problem).

🔁 The safe loop
🧪 Refactoring lab · Feature Envy → Move Method
// BEFORE — OrderService reaches into Order's data to compute something Order owns
public class OrderService
{
    public decimal Total(Order order)
    {
        decimal sum = 0;
        foreach (var line in order.Lines)
            sum += line.UnitPrice * line.Quantity;
        return sum - order.DiscountAmount;
    }
}

// AFTER — the behaviour moves to the class that owns the data
public class Order
{
    public IReadOnlyList<OrderLine> Lines { get; }
    public decimal DiscountAmount { get; }

    public decimal Total() =>
        Lines.Sum(l => l.UnitPrice * l.Quantity) - DiscountAmount;
}
// OrderService now calls order.Total() — and the next pricing change touches Order, not the service.

Illustrative. Steps: (1) test Total as it is; (2) Extract Method inside OrderService; (3) Move Method to Order; (4) run tests; (5) commit. Each step compiles and passes on its own.

1 · SMELL

👃 What hurts?

A change that touches many files, a test that needs a database, a class nobody dares edit.

2 · READ ★

🔬 Who changes this, and why?

List the reasons the class changes and the things it depends on.

3 · FIND ★

🎯 The principle that is bent

One responsibility too many? A broken contract? A concrete dependency?

4 · GUESS ★

💡 One refactoring

Extract a class, introduce an interface, invert a dependency.

5 · CHANGE

🔧 One small, safe step

Keep tests green after every step.

6 · PROVE

✅ Re-measure

Fewer files touched per change; tests that need no database.

🎬 Real-world scenarios

Every change breaks something.

→ Pin with tests, then Extract Class one responsibility at a time
🔀
Adding a payment method means editing five switch statements

Shotgun surgery + OCP.

→ Polymorphism: one class per method
📦
A DTO full of logic in the controller

The controller computes what Order should.

→ Move Method to the owner of the data
🧪
A test needs 40 lines of setup

The class has too many dependencies.

▾ Go one level deeper (60 seconds)

Characterisation tests. For code without tests, first write tests that record what it does today, even if that behaviour is odd. They are scaffolding that makes the refactoring safe.

Tools help. IDE refactorings (Extract Method, Move, Rename) are mechanical and much safer than hand edits; use them for every step you can.

Not every smell is a bug. A smell is a hint to look, not an order to rewrite. The trade-off between design purity and effort is page 11.

🔥 Interview recall
  • Smell = symptom; principle = diagnosis; refactoring = treatment.
  • Divergent Change (one class, many reasons) and Shotgun Surgery (one reason, many classes) are mirror images.
  • Refactoring changes structure, never behaviour; one small step, then test, then commit.
  • Pin behaviour with a test before the first edit.
  • Common moves: Extract Class, Extract Method, Move Method, Replace Conditional with Polymorphism, Extract Interface.
  • Refactor code that costs you; leave stable ugly code alone.
🎤 Say this in an interview
"I start from the symptom: a class that changes for many reasons points to SRP, a repeated switch on type to OCP, a NotSupportedException override to LSP, stubbed interfaces to ISP, and new or statics in logic to DIP. I first pin the behaviour with a test, then apply one small refactoring such as Extract Class or Replace Conditional with Polymorphism, run the tests and commit. Refactoring never changes behaviour, and I only do it where the code is actually costing us."
⚠️ Common trap

“Refactor” and add a feature in one commit. If something breaks you cannot tell which change did it.

Rewriting instead of refactoring. Rewrites lose hidden behaviour.

Refactoring without tests. You are guessing, not proving.

🧹 Refactoring

Structure changes, behaviour stays the same.

vs.
🛠️ Feature work

Behaviour changes; tests change with it.
