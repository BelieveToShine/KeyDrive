Notice the clue, name the principle, make one small fix.

Code smells as clues, how each points to a SOLID principle, and the safe refactoring loop.

❓ "How do you refactor a large class safely, and which smells point to which SOLID principle?"
👁 See it first
🎯 Smells are clues, principles are the explanation, and a refactoring is a small, safe step that fixes it.
🌍 In real life

🩺 A doctor does not start with the cure. They notice a symptom (fever), work out the cause (infection), then give one treatment. Code review is the same: notice the smell, name the principle, make one small fix.

Refactoring means changing how code is built without changing what it does. Like rearranging a kitchen: the meals stay the same, but finding things gets easier.

🔁 The safe loop
🧪 Tiny code: Feature Envy → Move Method
// SMELL — Printer does maths with Invoice's own data ("Feature Envy")
class InvoicePrinter
{
    public decimal Total(Invoice invoice)
    {
        decimal sum = 0;
        foreach (var line in invoice.Lines) sum += line.Price * line.Quantity;
        return sum - invoice.Discount;
    }
}

// FIX — move the method to the class that owns the data
class Invoice
{
    public List<Line> Lines { get; } = new();
    public decimal Discount { get; set; }
    public decimal Total() => Lines.Sum(l => l.Price * l.Quantity) - Discount;
}

Steps: (1) test the total as it is; (2) extract the maths into its own method; (3) move that method to Invoice; (4) run the tests; (5) commit.

🎯 Spot it: which clue is this?
▾ “Every time we add a payment type we change five files”

A smell. Open/Closed + Shotgun Surgery: the same decision is scattered. Put each type in its own class.

▾ “My test needs a real database just to check a price”

A smell. Dependency Inversion: the price code builds or reaches for the database itself.

▾ “ReadOnlyList.Add() throws an error”

A smell. Liskov: it promised to be a list but cannot add.

▾ “This class is long, but it has one clear job and is rarely changed”

Not a problem. Long is not automatically bad. Leave stable, working code alone (page 11).

🔥 Interview recall
  • Smell = clue, principle = explanation, refactoring = small safe fix.
  • Five clues: many jobs (S), type if/else (O), NotSupported child (L), forced empty methods (I), new inside logic (D).
  • Refactoring changes structure, never behaviour.
  • Loop: pin with a test → one small step → run tests → commit → repeat.
🎤 Say this in an interview
"I look for clues: a class with many jobs, a repeated if/else on type, a subclass that throws NotSupported, empty methods forced by an interface, or new inside business code. Each points to a principle. I first pin the behaviour with a test, then make one small refactoring, run the tests and commit — structure changes, behaviour does not."
⚠️ Common trap

Refactoring and adding a feature in one go. If a test fails you cannot tell which change broke it.

Refactoring with no tests. You are guessing, not proving.
