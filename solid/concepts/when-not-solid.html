Concept 11 of 12 · ⚖️ Judgement

The best design is the one that pays for itself.

Yagni, DRY, KISS and over-engineering: how to decide when SOLID helps and when it just adds code.

❓ "Can SOLID be overdone? When would you not apply it?"
👁 See it first
🎯 SOLID is a set of tools for relieving real pain, not a score to maximise. If there is no pain, there may be nothing to do.
📖 Why did this need to exist?

Martin Fowler’s “Yagni” (“You Aren’t Gonna Need It”) note warns against presumptive features. Even if your guess about a future need is right, building it early has a cost of delay (effort not spent on something else) and a cost of carry (the extra code makes the software harder to modify and debug). He is careful to say that Yagni does not license neglecting internal quality.

Microsoft’s .NET architecture guidance makes the same point about duplication: the DRY principle (do not specify the same behaviour in several places) is good, but duplication is preferable to coupling to the wrong abstraction. And an older Microsoft patterns guide names “You ain’t gonna need it” as a warning against over-designing early when requirements are unclear.

So the earlier pages should be read with one question in mind: is this actually costing us? Every interface, factory and layer must pay for itself in changes made easier.

🧭 The decision
🧪 Judgement lab · the same feature, two sizes
// OVER-ENGINEERED — a report printer that will never have a second implementation
public interface IReportPrinterStrategy { void Print(Report r); }
public interface IReportPrinterFactory { IReportPrinterStrategy Create(ReportKind kind); }
public class ConsoleReportPrinterStrategy : IReportPrinterStrategy { public void Print(Report r) => Console.WriteLine(r.Title); }
public class ReportPrinterFactory : IReportPrinterFactory { public IReportPrinterStrategy Create(ReportKind kind) => new ConsoleReportPrinterStrategy(); }

// RIGHT-SIZED — one class, honest about what it does today
public class ReportPrinter
{
    public void Print(Report report) => Console.WriteLine(report.Title);
}

// ...and the day a second output appears (PDF), THEN extract the interface — a five-minute refactoring
// that the tests from page 10 make safe.

Illustrative. Extracting an interface later is cheap and safe when behaviour is covered by tests; building it early is a guess you carry forever.

SituationReasonable call
Throwaway script or prototypeKeep it simple; do not layer it
Small CRUD app with trivial rulesA few classes may be plenty
Business rules that change monthly (pricing, tax, eligibility)Invest: SRP, OCP, tests
Anything that touches I/O, time or a third partyPut a seam (interface) there — it pays in tests
Value types and stable framework types (string, List<T>)Do not abstract them
Code you will delete next sprintShip it
1 · SMELL ★

👃 What hurts?

A change that touches many files, a test that needs a database, a class nobody dares edit.

2 · READ ★

🔬 Who changes this, and why?

List the reasons the class changes and the things it depends on.

3 · FIND ★

🎯 The principle that is bent

One responsibility too many? A broken contract? A concrete dependency?

4 · GUESS

💡 One refactoring

Extract a class, introduce an interface, invert a dependency.

5 · CHANGE

🔧 One small, safe step

Keep tests green after every step.

6 · PROVE

✅ Re-measure

Fewer files touched per change; tests that need no database.

▾ Go one level deeper (60 seconds)

KISS. “Keep it simple” is the common name for preferring the simplest design that works; it is a rule of thumb rather than a standard, and it is the same instinct as Yagni.

Rule of three. A common heuristic: tolerate the first duplication, tolerate the second, and refactor on the third, when you can see what really varies.

Yagni is not “no design”. Fowler stresses that avoiding presumptive features is different from neglecting code quality: keep code clean and easy to change so that adding the feature later is cheap.

🔥 Interview recall
  • Design fails in both directions: tangled (under) and bloated (over).
  • Yagni: presumptive features cost delay and carry, even if you guess right; it does not excuse sloppy code.
  • DRY is good but duplication beats coupling to the wrong abstraction (Microsoft guidance).
  • Apply SOLID where there is pain: frequent change, bugs, painful tests, I/O seams.
  • Interfaces belong at real seams; you can extract one later, safely, with tests.
  • Stop when the next change is cheap.
🎤 Say this in an interview
"SOLID is a toolbox for relieving real pain, not a score. I apply it where code changes often or is painful to test — pricing rules, anything touching I/O or time — and I leave stable, simple code alone. Presumptive abstractions have a cost of delay and a cost of carry, and duplication is cheaper than the wrong abstraction. When a second implementation really appears, extracting an interface is a small, safe refactoring, especially with tests."
⚠️ Common trap

“Always an interface for every class.” That is habit, not design.

“Yagni means skip tests and structure.” It means skip speculative features, not quality.

Merging look-alike code too early. Wait until you see what really varies.

🧰 Tool

A principle you apply when it removes a pain.

vs.
📊 Score

A count of interfaces and layers; more is not better.
