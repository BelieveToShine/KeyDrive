Do not hire a lorry to carry one bag.

Yagni, over-engineering and when SOLID helps: how to decide, with a story of the same task done two ways.

❓ "Can SOLID be overdone? When would you not apply it?"
👁 See it first
🎯 SOLID is a toolbox for removing pain, not a score to maximise. If nothing hurts, there may be nothing to do.
🌍 In real life

🚚 You would not hire a lorry to carry one bag, and you would not carry a sofa by hand either. The skill is picking the right size for the job.

Martin Fowler calls the wrong kind of early building Yagni (“You Aren’t Gonna Need It”): a feature built for a guess costs time now (cost of delay) and makes the code heavier to change (cost of carry) — even if the guess turns out right. He also stresses it is not a licence for sloppy code.

🧭 When to reach for SOLID
SituationWhat to do
A quick script or prototypeKeep it simple. One class is fine.
Rules that change every month (prices, tax, eligibility)Invest: small classes, plug-ins for the changing part, tests.
Anything that talks to a database, email, the clock or a third partyPut a socket (interface) there. It pays for itself in tests.
Plain data and everyday types (string, List)Do not hide them behind interfaces.
Code that works, is stable and is rarely touchedLeave it alone, even if it is ugly.
🧪 Tiny code
// OVER-ENGINEERED — for something that will never have a second version
interface IPrinterStrategy { void Print(string title); }
class ConsoleStrategy : IPrinterStrategy { public void Print(string t) => Console.WriteLine(t); }
class ReportPrinterFactory { public IPrinterStrategy Create() => new ConsoleStrategy(); }

// RIGHT-SIZED — honest about what it does today
class ReportPrinter { public void Print(string title) => Console.WriteLine(title); }

// ...the day PDF arrives, THEN extract the interface (small, safe, and your tests keep you safe)

Adding an interface later is cheap when tests exist. Building it early is a guess you carry forever.

🎯 Spot it: is this over-engineering?
▾ An interface with exactly one class behind it, plus a factory that returns that class

Over-engineered. Nothing varies yet. Remove the layers until a second case appears.

▾ A switch on payment type repeated in five files and growing every month

Reasonable. This is real pain. Plug-ins (OCP) are worth it here.

▾ An interface around the database client so tests can use a fake

Reasonable. The database is slow and outside your control: a good place for a socket.

▾ A generic “framework” nobody asked for, “in case we need it”

Over-engineered. A guess about the future (Yagni). Delete it.

👀 Signs of over-engineering
If you see…Do this
Every class has an interface with one implementationInterfaces by habit. Keep them only at real seams.
A new teammate needs 9 jumps to follow one changeToo many layers that only forward calls. Collapse them.
“Generic” code for cases nobody hasDelete it; add it when the real case arrives.
Two similar pieces forced into one shared baseWait for a third example before sharing. Duplication is cheaper than the wrong abstraction.
🔥 Interview recall
  • Design can fail both ways: tangled (too little) or bloated (too much).
  • Yagni: building for a guess costs delay and carry, even if you guess right — but it is not an excuse for sloppy code.
  • Use SOLID where there is pain: frequent change, painful tests, databases/time/third parties.
  • Interfaces can be extracted later, safely, when tests exist.
🎤 Say this in an interview
"SOLID is a toolbox for removing pain, not a score. I use it where code changes often or is painful to test — pricing rules, anything touching a database, email or the clock — and I leave stable, simple code alone. Building abstractions for a guess has a cost of delay and a cost of carry, and duplication is cheaper than the wrong abstraction. When a second case really appears, extracting an interface is a small, safe refactoring."
⚠️ Common trap

“Always an interface for every class.” That is habit, not design.

“Yagni means skip structure and tests.” It means skip speculative features, not quality.
