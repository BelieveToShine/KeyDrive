Deep dive · SOLID lab · 🧩 Composition

Build with Lego bricks, not a family tree.

Why one subclass per combination explodes, how composition fixes it with a pizza example, and when a base class is still the right tool.

❓ "Why is composition often preferred over inheritance, and when is inheritance appropriate?"
👁 See it first
🎯 Inherit to say “is a kind of”. Compose to say “has” or “is built from”. When in doubt, compose.
🌍 In real life

🧱 A family tree is fixed: you cannot change who your grandparents are. Lego bricks are different: you can build any shape by snapping different bricks onto the same base, and change your mind later.

Inheritance is the family tree. Composition is Lego.

🧩 The fix: parts, not a family tree
🧪 Tiny code
// INHERITANCE — one class per combination
class Pizza { public virtual decimal Price() => 8m; }
class CheesePizza : Pizza { public override decimal Price() => base.Price() + 1m; }
class CheeseMushroomPizza : CheesePizza { public override decimal Price() => base.Price() + 1.5m; }
// ... and so on, for every combination

// COMPOSITION — one class, toppings are parts
interface ITopping { decimal Price(); }
class Cheese   : ITopping { public decimal Price() => 1m; }
class Mushroom : ITopping { public decimal Price() => 1.5m; }

sealed class Pizza(IEnumerable<ITopping> toppings)
{
    public decimal Price() => 8m + toppings.Sum(t => t.Price());
}

var order = new Pizza(new ITopping[] { new Cheese(), new Mushroom() });

sealed says “this class is not designed to be inherited” — Microsoft’s C# reference describes sealed as preventing other classes from inheriting from it.

🎯 Spot it: inheritance or composition?
▾ Dog and Cat are both kinds of Animal that really behave like one

Fine. A true “is a kind of”, and children keep the parent’s promises (Liskov). Inheritance is fine.

▾ A LoggedDiscountedTaxedOrder class, plus LoggedDiscountedOrder, plus LoggedTaxedOrder…

Prefer composition. One class per combination. Use parts: logging, discount and tax as small pluggable pieces.

▾ A child class that overrides most parent methods to do nothing

Prefer composition. It is not really a kind of parent. Compose instead (or split the interface).

▾ A base class created only so two classes can share five lines of code

Prefer composition. Inheritance used for reuse. Put the shared code in a helper class and use it.

✅ When inheritance is still right
SituationWhy it is fine
A true “is a kind of” where the child keeps every promise (Liskov passes)Substitutable; nothing breaks
A base class the framework designed for you to extendThe framework author planned for it
A small, shallow base class with one clear variation pointShared code in one place; keep it shallow
🔥 Interview recall
  • Inheritance = a fixed family tree: strongest coupling, one class per combination.
  • Composition = Lego: small parts behind interfaces, any combination, changeable at runtime.
  • Inherit only for true “is a kind of” that keeps every promise (Liskov).
  • Seal classes that are not designed to be inherited.
🎤 Say this in an interview
"I use inheritance only for a true is-a relationship where the child honours the whole parent contract, or for a base class a framework designed for extension. Otherwise I compose: one class holds small parts behind interfaces, so any combination is just what I pass in, instead of one subclass per combination."
⚠️ Common trap

“Inheritance is bad.” It is a tool with a high coupling cost. Use it where substitutability genuinely holds.

Inheriting just to reuse code. Reuse by calling a helper instead.
