Concept 9 of 12 · 🛠️ Making it real

One messy class, five principles, step by step.

A full refactoring of the ShopCore OrderService: the five steps, what each fixes and how to prove it.

❓ "Walk me through refactoring a large service class using SOLID."
👁 See it first
🎯 The principles are not five separate rules — they are five views of the same refactoring. Fix the biggest pain first, one small step at a time.
📖 Why did this need to exist?

In real code violations tangle: the pricing branch that needs OCP lives in a class that needs SRP and builds its own SQL repository, which is a DIP problem. You cannot fix “just one letter”.

Robert C. Martin has described SOLID as being about managing dependencies and keeping code easy to change; the aim is not to satisfy a checklist but to make the next change cheap.

So the order matters: split responsibilities (SRP) → make the growing part pluggable (OCP) → make sure each plug honours its contract (LSP) → keep interfaces small (ISP) → inject them (DIP). Each step is shippable and tested before the next.

🏁 After all five steps
🧪 Worked refactoring · five steps
// STEP 0 — pin today's behaviour with a test (golden-master: a few real orders → expected totals)

// STEP 1 · SRP — Extract Class for each reason to change
public class OrderValidator { public void Validate(Order o) { /* the old ≈ 40 lines */ } }
public class PricingCalculator { public decimal Total(Order o) { /* the old ≈ 120 lines */ } }

// STEP 2 · OCP — pricing grows, so make promotions pluggable
public interface IDiscountRule { decimal Discount(Order order); }
public class PricingCalculator(IEnumerable<IDiscountRule> rules)
{
    public decimal Total(Order o) => Base(o) - rules.Sum(r => r.Discount(o));
}

// STEP 3 · LSP + ISP — every rule honours the contract; interfaces are small and role-named
public interface IOrderRepository { void Save(Order o); }
public interface INotifier        { void OrderPlaced(Order o); }

// STEP 4 · DIP + DI — receive collaborators, register once
public class OrderService(IOrderValidator validator, IPricing pricing,
                          IOrderRepository repo, INotifier notifier)
{
    public void Place(Order order)
    {
        validator.Validate(order);
        order.Total = pricing.Total(order);
        repo.Save(order);
        notifier.OrderPlaced(order);
    }
}
// Program.cs: AddScoped<IOrderRepository, SqlOrderRepository>(); AddSingleton<INotifier, SmtpNotifier>(); ...

1 · SMELL ★

👃 What hurts?

A change that touches many files, a test that needs a database, a class nobody dares edit.

2 · READ ★

🔬 Who changes this, and why?

List the reasons the class changes and the things it depends on.

3 · FIND ★

🎯 The principle that is bent

One responsibility too many? A broken contract? A concrete dependency?

4 · GUESS ★

💡 One refactoring

Extract a class, introduce an interface, invert a dependency.

5 · CHANGE ★

🔧 One small, safe step

Keep tests green after every step.

6 · PROVE ★

✅ Re-measure

Fewer files touched per change; tests that need no database.

▾ Go one level deeper (60 seconds)

Why not start with DIP? You can — injecting the two biggest dependencies is often the cheapest first step because it unlocks tests. The order on this page is one sensible path, not a law: start where the pain is.

Constructor size. Four parameters is fine. If it grows past six or seven, ask whether OrderService has accumulated responsibilities again.

Stop condition. Stop when the next change is cheap. More layers after that is the over-engineering page 11 warns about.

🔥 Interview recall
  • The five principles interlock; real refactorings use several together.
  • Order used here: pin with a test → SRP → OCP → LSP/ISP → DIP/DI → compose in Program.cs.
  • Every step is small, compiles and passes the same pinned test.
  • Result: OrderService ≈ 40 lines, 1 reason to change, new promotion = 1 class, tests in memory.
  • Start where the pain is; stop when the next change is cheap.
  • The numbers on this page are illustrative, not measured.
🎤 Say this in an interview
"On our order service I’d first pin its behaviour with a test. Then split by reason to change — validation, pricing, persistence, notification — make the growing pricing part a list of rule classes so new promotions are new classes, keep the interfaces small, and inject them through the constructor so tests use fakes. Each step compiles and passes the same test, and I stop when the next change is cheap rather than chasing purity."
⚠️ Common trap

Doing it as one giant rewrite. You lose the safety net and the history.

Refactoring everything because the principles say so. Only the parts that hurt.

Forgetting the proof. A refactoring without a passing pinned test is just a hope.

🔤 Checklist thinking

“Does this class satisfy S, O, L, I, D?”

vs.
🧭 Pain-driven thinking

“What is hard to change or test, and which principle explains it?”
