One messy class, five habits, step by step.

A coffee-shop OrderService refactored with all five principles, step by step, in pictures.

❓ "Walk me through refactoring a large service class using SOLID."
👁 See it first
🎯 The five habits work together. Fix the part that hurts most first, then the next, one small step at a time.
🌍 In real life

☕ A coffee shop starts with one person doing everything. As it grows you hire a barista, a cashier and a cleaner (S), you let the menu grow without rebuilding the counter (O), and you give every worker the same standard tools so anyone can cover a shift (D).

You do not hire everyone on day one. You change what hurts, when it hurts.

🔌 Then plug the details in
🧪 Tiny code
// BEFORE — one class, everything inside
class OrderService
{
    public void Place(Order order)
    {
        /* validate: ~40 lines */
        /* price: ~120 lines of if/else */
        var db = new SqlConnection("...");       // saves directly
        var mail = new SmtpClient("...");        // emails directly
    }
}

// AFTER — a coordinator that is handed its helpers
class OrderService(IOrderValidator validator, PriceCalculator pricing,
                   IOrderRepository repository, INotifier notifier)
{
    public void Place(Order order)
    {
        validator.Validate(order);
        order.Total = pricing.Total(order);      // pricing owns the discount rules (plug-ins)
        repository.Save(order);
        notifier.OrderPlaced(order);
    }
}

🔥 Interview recall
  • Start with the pain: what is hard to change or test?
  • S splits by job, O lets the growing part take plug-ins, L keeps plug-ins honest, I keeps sockets small, D hands them in.
  • Pin behaviour with a test first; make one small step at a time.
  • Stop when the next change is cheap.
🎤 Say this in an interview
"On an order service I would first pin its behaviour with a test. Then split it by job — validation, pricing, saving, notifying — make the pricing rules plug-ins so a new promotion is a new class, keep the interfaces small, and inject them through the constructor so tests use fakes. Each step compiles and passes the same test, and I stop when the next change is cheap."
⚠️ Common trap

Doing it all in one giant rewrite. You lose the safety net. One small step, test, commit.

Refactoring code that is not hurting. Only the parts that cost you.
