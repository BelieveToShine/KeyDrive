One person doing every job in a restaurant — and one class doing the same.

The Single Responsibility Principle with a restaurant: why a class should have one reason to change, and how to split it.

❓ "What is the Single Responsibility Principle? Give an example."
👁 See it first
🎯 Give each class one job — one reason to change. If two different people could ask you to change it for different reasons, split it.
🔧 The fix: one person per job
🧪 Tiny code
// BEFORE — one class, three jobs (three reasons to change)
class Invoice
{
    public decimal Total() { /* maths: changes when tax rules change */ return 0; }
    public void Print()    { /* layout: changes when the design changes */ }
    public void SaveToDb() { /* storage: changes when the database changes */ }
}

// AFTER — one job each
class Invoice           { public decimal Total() { return 0; } }
class InvoicePrinter    { public void Print(Invoice invoice) { } }
class InvoiceRepository { public void Save(Invoice invoice) { } }

Each class now has one reason to change: tax rules, layout, or storage. A class that coordinates these small classes has one job too: coordinating.

🙋 Who asks for the change?
If this changes……who asks?…which class changes
the tax rate🧮 the accountantthe one that calculates
the printed layout🎨 the designerthe one that prints
the database🛠️ the engineerthe one that saves

Different people, different reasons — so they should not share a class. (This is Robert C. Martin’s way of explaining “one reason to change”.)

🎯 Spot it: does this class have one job?
▾ UserManager that checks the email, saves the user to the database and sends a welcome email

Breaks the rule. Three jobs: validation, storage, email. Three different reasons to change.

▾ EmailValidator that only checks whether an email looks right

Fine. One job, one reason to change.

▾ OrderService.Place() that calls a validator, a saver and a notifier — and does nothing else itself

Fine. Its one job is coordinating the steps. The real work lives in small classes.

▾ Logger with a method that also formats HTML reports

Breaks the rule. Writing logs and producing reports are different jobs.

👀 How to spot it in your own code
If you see…Do this
A class name with Manager, Helper, Utils or an “and” in what it doesProbably several jobs. List them and split.
One file that imports SQL, email and UI codeEach of those is a different job.
Different teammates keep editing the same file for unrelated reasonsEach reason deserves its own class.
Testing it needs a database and a mail serverToo many jobs in one place.
🔥 Interview recall
  • SRP: one class, one job, one reason to change.
  • Ask: “who would ask me to change this, and why?” Different answers → different classes.
  • A coordinator that only calls small classes also has one job.
  • Do not split too far: one tiny method per class is not the goal.
🎤 Say this in an interview
"The Single Responsibility Principle says a class should have one reason to change. I look at who would ask for changes — the accountant for tax, the designer for layout, the engineer for storage — and if those are different people, I split the class so each change has exactly one place to go."
⚠️ Common trap

“One responsibility means one method.” No — it means one reason to change. A class can have several methods that all serve the same job.
