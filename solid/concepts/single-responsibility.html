Concept 2 of 12 · 🔤 The five principles

One class, one reason to change — and a reason is a person.

The Single Responsibility Principle as Martin states it, the actor test, and splitting ShopCore’s OrderService into four focused classes.

❓ "What does the Single Responsibility Principle mean, and how do you tell when a class breaks it?"
👁 See it first
🎯 A class should have one, and only one, reason to change — gather together the things that change for the same reason, and separate the things that change for different reasons.
📖 Why did this need to exist?

Page 1 introduced the cost of change. The first principle tells you where to cut. Robert C. Martin’s answer is about people: a module’s “reasons to change” are the people (or tightly-knit groups, like a business function) who can ask for changes. In his payroll example, pay calculation changes come from finance, report format from operations, and database saving from technology — three reasons, so three modules.

He describes SRP as another way to define cohesion and coupling: cohesion should rise among things that change for the same reasons, and coupling should fall between things that change for different reasons.

A practical test follows: ask who could request a change to this class. If the answer names more than one stakeholder, there is more than one responsibility.

✂️ Splitting OrderService by actor
🧪 SRP lab · before and after
// AFTER — each class has one reason to change
public class PricingCalculator   { public decimal Price(Order o) { /* promotions and totals */ return 0m; } }
public class TaxCalculator       { public decimal Tax(Order o, decimal net) { /* tax rules */ return 0m; } }
public class OrderRepository     { public void Save(Order o) { /* SQL only */ } }
public class OrderNotifier       { public void Confirm(Order o) { /* e-mail only */ } }

public class OrderService
{
    private readonly PricingCalculator _pricing = new();     // still created here — page 6 fixes this
    private readonly TaxCalculator _tax = new();
    private readonly OrderRepository _repo = new();
    private readonly OrderNotifier _notifier = new();

    public void PlaceOrder(Order order)
    {
        var net = _pricing.Price(order);
        order.Total = net + _tax.Tax(order, net);
        _repo.Save(order);
        _notifier.Confirm(order);
    }
}

Illustrative. OrderService shrinks from ≈ 300 to ≈ 40 lines. It still creates its own collaborators with new; fixing that is the Dependency Inversion Principle (page 6).

1 · SMELL

👃 What hurts?

A change that touches many files, a test that needs a database, a class nobody dares edit.

2 · READ ★

🔬 Who changes this, and why?

List the reasons the class changes and the things it depends on.

🎯 The principle that is bent

One responsibility too many? A broken contract? A concrete dependency?

4 · GUESS ★

💡 One refactoring

Extract a class, introduce an interface, invert a dependency.

5 · CHANGE ★

🔧 One small, safe step

Keep tests green after every step.

6 · PROVE

✅ Re-measure

Fewer files touched per change; tests that need no database.

▾ Go one level deeper (60 seconds)

What SRP is not. It does not say “a class should do only one thing” in the sense of one method. Martin’s own wording is about reasons to change, and he admits the definition shifted over time and asks “what defines a reason to change?” — answering with people and business functions.

Related idea. Microsoft’s architecture guidance describes separation of concerns the same way: break an application up by its responsibilities so a growing codebase stays navigable.

Functions too. The same test works for methods, modules and services; a microservice with six reasons to change has the same problem at a bigger scale.

🔥 Interview recall
  • SRP: a class (module) should have one, and only one, reason to change.
  • Reasons to change are people/business functions: ask “who could request a change here?”.
  • Gather things that change for the same reasons; separate things that change for different reasons.
  • Smells: “and” in the description, many constructor parameters, “Manager/Utils” classes, conflicts in one file.
  • SRP is cohesion and coupling made practical; it is not “one method per class”.
  • After SRP, OrderService only orchestrates; it still creates its collaborators (fixed by D).
🎤 Say this in an interview
"The Single Responsibility Principle says a module should have one reason to change, and in practice a reason to change is a stakeholder who can ask for it. I test a class by asking who could request changes to it; if the answer is finance and operations and the database team, I split it by actor so each change lands in one place, and the original class just orchestrates."
⚠️ Common trap

Reading SRP as “one method per class”. You end up with a hundred tiny classes that always change together.

Splitting by technical layer only. Splitting “data functions” from “rules” can group things that change for different reasons.

🎯 Responsibility

A reason to change — usually one stakeholder or business function.

vs.
🔧 Method

A unit of code. One class can have many methods and still one responsibility.
