Who depends on whom? Flip the arrow.

The Dependency Inversion Principle: high-level policy vs low-level detail, who owns the interface, and replacing new with constructor parameters.

❓ "What is the Dependency Inversion Principle, and how is it different from dependency injection?"
👁 See it first
🎯 Business code should depend on abstractions that it owns, not on details — the database class conforms to the business layer, not the other way round.
📖 Why did this need to exist?

Robert C. Martin’s wording: high-level modules should not depend on low-level modules; both should depend on abstractions. Microsoft’s .NET architecture guidance puts it as dependency direction pointing toward abstractions rather than implementation details.

The consequence in that guidance: a calling class depends on an interface, a lower-level class implements it, and the compile-time dependency is inverted while runtime behaviour stays the same. This is what makes implementations swappable and code testable, and it is the idea behind the clean-architecture layout in Microsoft’s web-app guidance: infrastructure depends on the application core through interfaces defined in the core.

Martin has written that the SOLID principles are about managing dependencies; this is the principle where that is most literal.

🔄 After inversion
🧪 DIP lab · stop using new inside the business class
// BEFORE — high-level code builds its own low-level collaborators
public class OrderService
{
    public void Place(Order order)
    {
        var repo = new SqlOrderRepository(new SqlConnection(ConnectionStrings.Shop));
        repo.Save(order);
        new SmtpClient("smtp.shop.example").Send(/* confirmation */);
    }
}

// AFTER — depend on abstractions; receive them through the constructor
public interface IOrderRepository { void Save(Order order); }
public interface INotifier        { void OrderPlaced(Order order); }

public class OrderService
{
    private readonly IOrderRepository _repo;
    private readonly INotifier _notifier;

    public OrderService(IOrderRepository repo, INotifier notifier)
    {
        _repo = repo;
        _notifier = notifier;
    }

    public void Place(Order order)
    {
        _repo.Save(order);
        _notifier.OrderPlaced(order);
    }
}

Illustrative. Who passes the real objects in? Not this class — a single place near startup (page 7). Note that this change alone, passing interfaces into a constructor, is DIP in action; the container that automates it is a separate tool.

▾ Go one level deeper (60 seconds)

Three similar words. Dependency Inversion is the design principle (depend on abstractions you own). Dependency Injection is a technique for handing dependencies in. An IoC container is a tool that automates injection. You can follow DIP with plain constructors and no container.

Ownership matters. An interface defined in the same project as the database class, and merely referenced by the business layer, does not invert anything. The interface lives with its client.

Not everything needs one. Do not hide stable, deterministic things such as string or List<T> behind interfaces; invert at the boundaries that vary or are slow (I/O, time, randomness, third-party services).

🔥 Interview recall
  • DIP: high-level code and low-level code both depend on abstractions; details depend on policy.
  • The source-code arrow flips; the runtime call is unchanged.
  • The interface is owned by the client (the business layer), not by the implementation.
  • Receive collaborators through the constructor instead of calling new or static methods inside logic.
  • DIP (principle) ≠ DI (technique) ≠ IoC container (tool).
  • Invert at boundaries that vary or are slow: I/O, time, randomness, external services.
🎤 Say this in an interview
"The Dependency Inversion Principle says high-level policy shouldn’t depend on low-level details; both depend on abstractions, and the abstraction is owned by the business side. In practice OrderService takes an IOrderRepository through its constructor instead of creating a SqlOrderRepository, so the database class depends on the business layer rather than the reverse. I’d use constructor injection, and I distinguish the principle from DI, which is a technique, and from a container, which is just a tool."
⚠️ Common trap

“DIP means use a DI container.” The principle is about the direction of dependencies; a container is optional tooling.

Putting the interface next to the implementation. Then the business layer still depends on the infrastructure project.

An interface for every class. Abstract the boundaries that vary, not every type.
