Wire to a socket, not to one particular bulb.

The Dependency Inversion Principle with a light switch and a wall socket: why hard-wiring hurts and how an interface in the middle fixes it.

❓ "What is the Dependency Inversion Principle, and how is it different from dependency injection?"
👁 See it first
🎯 Depend on a socket, not on one particular bulb. Important code should depend on an abstraction (an interface), and details plug into it.
🌍 In real life

🔌 A wall socket does not care what you plug in: a lamp, a laptop charger, a fan. And the devices do not care which wall they are plugged into. Both sides agree on the standard shape of the socket — that is the interface.

Compare that with wiring a lamp straight into the wall: change the lamp and you must call an electrician.

🔧 The fix: a socket in the middle
🧪 Tiny code
// BEFORE — the switch creates its own bulb
class Bulb { public void On() { } public void Off() { } }

class LightSwitch
{
    private Bulb _bulb = new Bulb();               // hard-wired
    public void Press() => _bulb.On();
}

// AFTER — the switch is handed something that fits the socket
interface ISwitchable { void On(); void Off(); }
class Bulb : ISwitchable { public void On() { } public void Off() { } }
class Fan  : ISwitchable { public void On() { } public void Off() { } }

class LightSwitch
{
    private readonly ISwitchable _device;
    public LightSwitch(ISwitchable device) { _device = device; }   // "plug it in" from outside
    public void Press() => _device.On();
}

var lamp = new LightSwitch(new Bulb());
var cooler = new LightSwitch(new Fan());

Who plugs the bulb in? Someone outside the switch — that “someone” is dependency injection (next page).

🎯 Spot it: does this break the rule?
▾ A business method that does new SqlConnection(...) inside itself

Breaks the rule. It is hard-wired to one database. You cannot swap it or test it without a real database.

▾ A class whose constructor takes an ILogger

Fine. It asks for the abstraction. Any logger that fits can be plugged in.

▾ Business logic that calls DateTime.Now directly

Breaks the rule. The clock is a hidden dependency: a test cannot control what “now” is. Hand the clock in instead.

▾ A method that creates a plain new List<string>() for its own use

Fine. A list is just data, not a service you would ever swap. Do not put sockets everywhere.

👀 How to spot it in your own code
If you see…Do this
new SomethingBig() (database, email, web client) inside business codeReceive an interface through the constructor instead.
Static calls like File.ReadAllText or DateTime.Now in the middle of the logicHidden wiring. Wrap in an interface and hand it in.
The business project references the SQL / email packageWrong direction. The business code should own the interface; the details implement it.
Unit tests need a real database or networkDetails leaked into the important code.
🔥 Interview recall
  • DIP: important (high-level) code should not depend on details (low-level code); both depend on an abstraction.
  • Wall socket: any device fits; the socket does not care. The interface is the socket.
  • The arrow from the detail now points to the abstraction — the dependency is inverted.
  • Principle (DIP) ≠ technique (dependency injection) ≠ tool (container).
🎤 Say this in an interview
"The Dependency Inversion Principle says high-level code shouldn’t depend on low-level details — both should depend on an abstraction. A light switch that creates its own bulb can only switch that bulb. If it talks to an ISwitchable socket instead, any device can plug in and the switch never changes. In code that means receiving an interface through the constructor instead of calling new inside the class."
⚠️ Common trap

“DIP means use a DI container.” The principle is about which way the dependency points. Injection (and containers) are just ways to plug things in — the next page.

“Put an interface in front of every class.” Only where details vary or are slow to use: database, email, time, third-party services.
