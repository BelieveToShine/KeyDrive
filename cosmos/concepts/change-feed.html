Don’t make every reader query — push the changes into the shape each reader needs.

The change feed and its processor, what it is good for, how at-least-once delivery shapes your handlers, and a read-model plan priced in RU.

❓ "How would you serve a cross-partition dashboard cheaply from Cosmos DB?"
👁 See it first
🎯 Not every read should be a query. The change feed lets you push changes into the shape each reader needs — read models, search, caches — instead of making every reader pull with an expensive query.
▶️ Watch it happen: push changes to readers
📖 Why did this need to exist?

Page 6 ended with a problem: the dashboard asks a cross-partition question (“all open orders”) that fans out and costs RUs every time. Page 4 ended with another: a copied product name goes stale.

Both are the same shape: one write path, many read shapes. Instead of querying many partitions on every read, record what changed once and update a second structure that is already shaped for the read. Cosmos DB gives you the ordered record for free: the change feed.

📚 Four things it is good for
⚙️ How it behaves
QuestionAnswer
What is in it?A persistent, ordered record of changes to a container; consumers can read different partition key ranges in parallel
Who keeps the place?The client manages checkpointing — the change feed processor does this for you with a lease container
Delivery promise?The processor gives at-least-once processing: if your handler throws, the batch is sent again — make handlers idempotent
SDK support?The processor library is available for .NET and Java; other languages use the pull model
Freshness of what you build?Replication through the change feed is eventually consistent — the read model lags a little
🧪 Plan lab · the dashboard, cheaper

The “all open orders” dashboard from page 6 costs about 150 RU per refresh (fan-out over about 50 partitions). It is refreshed 10 times a second by 100 managers. (Illustrative numbers.)

// .NET-style sketch: the processor calls your handler with each batch of changes
var processor = container
    .GetChangeFeedProcessorBuilder("openOrdersBuilder", HandleChangesAsync)
    .WithInstanceName(Environment.MachineName)
    .WithLeaseContainer(leaseContainer)
    .Build();
await processor.StartAsync();

async Task HandleChangesAsync(IReadOnlyCollection changes, CancellationToken ct)
{   // must be idempotent: the same batch can arrive twice (at-least-once)
    foreach (var o in changes) await UpsertIntoReadModel(o);
}

Illustrative sketch; names follow the .NET SDK. Upsert (not insert) makes the handler safe to repeat.

▾ Go one level deeper (60 seconds)

Processor parts. The monitored container, a lease container that acts as state storage and coordinates workers, and a delegate that handles each batch.

Pull model. Instead of the processor you can read the feed yourself and manage checkpoints; the processor library adds automatic checkpointing and load balancing.

Dual writes. Writing to Cosmos DB and to a second system in the same code path can leave them out of step if one fails; driving the second system from the change feed avoids that.

Cost. The read model costs storage and write RU; the saving is in the reads. Do the arithmetic in RU before you build one.

Other engines. SQL has change tracking, CDC and triggers for similar jobs; DynamoDB has streams.

🔥 Interview recall
  • The change feed is a persistent, ordered record of changes to a container.
  • Change feed processor = workers + lease container (checkpoints) + your handler; at-least-once, so make handlers idempotent.
  • Processor library: .NET and Java; elsewhere use the pull model.
  • Uses: read models, search/cache/warehouse sync, event-driven actions, propagating copies.
  • Anything built from it is eventually consistent.
  • It turns a recurring fan-out query into a cheap read of a prepared structure.
🎤 Say this in an interview
"The change feed is an ordered record of changes to a container. I use the change feed processor — workers sharing a lease container — to build read models, sync search or a warehouse, and trigger actions, instead of running expensive cross-partition queries on every read. Delivery is at-least-once, so my handlers are idempotent, and I accept that what I build from it is eventually consistent."
⚠️ Common trap

Non-idempotent handlers. A redelivered batch double-counts and nobody notices for weeks.

Building a read model for a query that runs twice a day. A fan-out you can afford is cheaper than a pipeline you must operate.

📣 Change feed

Push changes to a consumer in order; the read model is prepared in advance.

vs.
🔎 Query

Pull on demand; each reader pays the RU every time.
