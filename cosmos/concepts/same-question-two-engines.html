1 · MEASURE ★

📏 What did it cost?

The RU charge and latency of one request — a number, not a feeling.

2 · READ ★

🔬 Read the diagnostics

Query metrics, partitions touched, indexed vs retrieved documents.

3 · FIND ★

🎯 The biggest wrong thing

A fan-out, a scan, a hot key, a fat document?

4 · GUESS ★

💡 One hypothesis

Wrong partition key? Missing composite index? Wrong shape?

5 · CHANGE ★

🔧 Change one thing

Never two at once.

6 · PROVE ★

✅ Re-measure

Same request, same data, lower RU charge.

🧰 Pick-card summary

🗄️ Reach for Azure SQL when…

relational strengths✅ Pick it when
  • Related tables, constraints, multi-table transactions
  • Ad-hoc queries and reports
  • A team strong in T-SQL
  • Mostly one region, scale-up is enough
⛔ Look elsewhere when
  • One writable primary cannot give the write latency you need globally

🌌 Reach for Cosmos DB when…

distributed strengths✅ Pick it when
  • Known, key-based access patterns
  • Flexible JSON items that change shape
  • Users on several continents
  • Very large scale spread by partition key
⛔ Look elsewhere when
  • Many ad-hoc cross-entity joins
  • No good partition key yet

▾ Go one level deeper (60 seconds)

What does not transfer. The optimizer: in SQL it chooses your plan; in Cosmos DB you choose the request shape and the key. And the failure cost: a SQL mistake is usually slower; a Cosmos mistake is slower and shows up as RUs on the bill.

What transfers fully. The ladder, writing down before-and-after numbers, one change at a time, and checking the other inputs (a different customer, a different key).

Other engines. PostgreSQL and DynamoDB follow the same two poles: relational with an optimizer, or key-partitioned with provisioned capacity.

🔥 Interview recall
  • Same method, different instruments: logical reads and plans (SQL) vs RU charge and query metrics (Cosmos).
  • SQL index ↔ Cosmos partition key + composite index: both exist to avoid reading what you do not need.
  • SQL blocking ↔ Cosmos 429s; SQL sniffing ↔ Cosmos hot key.
  • Joins in SQL; embed/reference in Cosmos.
  • Choose by workload: ad-hoc and relational → SQL; known patterns at global scale → Cosmos; often both.
🎤 Say this in an interview
"Both engines reward the same habit: measure, find the biggest wrong thing, change one thing, prove it. In SQL I read plans and logical reads and use indexes and sargable queries; in Cosmos DB I read RU charges and query metrics and choose the partition key, the item shape and composite indexes. I pick SQL for relational, ad-hoc work and Cosmos DB for known access patterns at global scale — and sometimes both, linked by the change feed."
⚠️ Common trap

Choosing by fashion. “NoSQL scales” and “SQL is safe” are both half-truths; the access patterns decide.

Porting a schema one-to-one. Tables copied into containers give you Cosmos prices with SQL’s joins missing.

🗄️ SQL optimiser

Chooses the plan for each query from statistics. You tune indexes and text.

vs.
🌌 Cosmos DB

No plan to tune; you choose the key, the shape and the request. You tune design and read RUs.
