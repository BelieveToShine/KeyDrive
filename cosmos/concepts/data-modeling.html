❓ "How would you model an order, its lines and its customer in Cosmos DB, and why?"
👁 See it first
🎯 In Cosmos DB you model for the reads: embed what is read together and stays small, reference what is shared, unbounded or changes often.
▶️ Watch it happen: model for the reads
📖 Why did this need to exist?

Page 1 told you there are no joins; page 3 told you every request costs RUs. Put together: the cheapest page load is the one that touches one item. That pushes you toward denormalising — storing data once where it is read, even if that means a copy.

The cost of that choice is on the write side: a copied value must be updated in every place. Modelling is therefore a trade — fewer, cheaper reads against more work when something changes — and it is decided per relationship, not per database.

🧭 Embed or reference? — five questions
AskEmbed if…Reference if…
How is it read?Read together every timeOften read alone
How many?One-to-few (a handful)One-to-many or many-to-many
Does it grow?Bounded and smallUnbounded (comments, events, log lines)
How often does it change?Rarely, or snapshots are fineOften, and everyone must see the latest
Is it shared?Belongs to this parent onlyShared by many parents (a product catalogue)

Hard limit to remember: an item can be at most 2 MB. Unbounded embedded arrays eventually hit it — and every change rewrites the whole item.

Page needs: the order, its lines, product names and the customer’s display name. (Illustrative RU; read the real RequestCharge.)

DesignWhat the page doesReads≈ RURound trips
A. Fully normalisedread order, then each line, then each product, then the customer1 + 2 + 2 + 1 = 6≈ 6–104 (in sequence)

What it costs on the write side. In design C, when a customer changes their display name, old orders still show the old name. For orders that is usually correct — an order is a snapshot of what was true at purchase time. For a profile photo shown on every comment it is not; there you would reference, or propagate the change (the change feed — page 10).

🧰 Three patterns to reach for

📦 Embed

one item, one read✅ Pick it when
  • Order + lines + shipping address
  • Data that is only meaningful with its parent
  • Snapshots that must not change later
⛔ Look elsewhere when
  • Unbounded arrays
  • Data many parents share and must see change at once

🔗 Reference

store an id, read it separately✅ Pick it when
  • Shared catalogues (products, tenants)
  • Frequently changing data
  • Many-to-many relationships
⛔ Look elsewhere when
  • Pages that need it on every request and cannot afford the extra read

🧬 Hybrid (denormalise a little)

reference + copy the fields you display✅ Pick it when
  • Show a product name and price on a list without reading the product
  • Precomputed totals on the parent
⛔ Look elsewhere when
  • Copying fields that change often with nobody to update them

▾ Go one level deeper (60 seconds)

Not only “embed everything”. The docs recommend embedding for contained, one-to-few relationships, data that changes infrequently, and data that does not grow without bound and is queried together; they recommend references for one-to-many and many-to-many relationships, frequently changing data, and unbounded sets.

Hybrid approach. Keep pre-calculated fields (such as a count or total) on the parent while the children live as separate items.

Transactions. Cosmos DB supports multi-item transactions within one partition key value (stored procedures, transactional batch), so you do not have to embed everything just to keep it consistent.

Item size limit. 2 MB per item in the NoSQL API (the length of the JSON as UTF-8); batch requests also have request-size limits.

Other engines. Document databases and DynamoDB share these rules; the SQL equivalent of “embedding” is denormalising a table — which SQL tolerates only for read-heavy reporting.

🔥 Interview recall
  • Model for the reads: the cheapest page load touches one item.
  • Embed: read together, bounded, rarely changes, belongs to the parent. Reference: shared, unbounded, changes often, many-to-many.
  • Unbounded embedded arrays grow toward the 2 MB limit and make every write dearer — use one item per child keyed by the parent id.
  • Denormalised copies need an update plan, or are deliberate snapshots.
  • Transactions work inside one partition key value.
  • Compare designs by RU charge and number of round trips.
🎤 Say this in an interview
"I model Cosmos DB data for the reads. I embed what is read together, bounded and mostly stable — like an order with its lines — and reference what is shared, unbounded or frequently changing. Unbounded arrays become one item per child keyed by the parent id, because items are capped at 2 MB and write cost grows with item size. For copied values I decide whether they are snapshots or need propagating, for example through the change feed."
⚠️ Common trap

Normalising by habit. “Third normal form” is a SQL virtue; here it multiplies requests, RUs and latency.

Embedding everything. The first viral post turns an innocent array into a 2 MB item that is rewritten on every comment.

📦 Embed

Copy or nest the data into the item that reads it. Fast reads, harder updates.

vs.
🔗 Reference

Store an id and read the other item. Easy updates, more reads and RUs.
