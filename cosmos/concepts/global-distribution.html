Concept 11 of 12 · 🌍 At scale

Add regions to bring data close to users — and decide how to handle two regions writing at once.

Single vs multiple write regions, failover, the conflict policies, and what every extra region costs.

❓ "How would you make a Cosmos DB application fast and resilient for users on three continents?"
👁 See it first
🎯 Add regions to bring data close to users and to survive a region loss. Choose single-write for simplicity, multi-write for local write speed — and plan for conflicts.
📖 Why did this need to exist?

Page 9 explained that data has copies and that readers choose how fresh a copy must be. Global distribution is the same idea at the scale of the planet: copies in several regions, so a user in Mumbai reads from Mumbai, and a region outage does not take the app down.

The new costs are real: more regions multiply storage and write RU, and multi-region writes introduce conflicts. This page covers the options, the failure story, and the conflict story.

🧰 The three configurations

📍 Single region

simplest and cheapest✅ Pick it when
  • Users in one geography
  • Early stage / dev-test
⛔ Look elsewhere when
  • Far-away users see high latency
  • A region outage is an outage

🌐 Multiple read regions, one write region

fast reads everywhere, one place for writes✅ Pick it when
  • Read-heavy global apps
  • Automatic regional failover (service-managed) promotes the next region in your priority order
  • No write conflicts to design for
⛔ Look elsewhere when
  • Writes from far regions pay the round trip to the write region

✍️ Multiple write regions

local writes everywhere✅ Pick it when
  • Write-heavy global apps that need low write latency in every region
  • You can tolerate conflict resolution
⛔ Look elsewhere when
  • Strong consistency is not available with multiple write regions (check the docs)
  • Service-managed failover and multi-write cannot be enabled together
  • Unique-value rules cannot be enforced across regions at write time
⚔️ When two regions write the same item

▾ Go one level deeper (60 seconds)

Failover. For single-write accounts, service-managed failover promotes the next region in the priority order you set; the original region is not promoted back automatically after it recovers. Manual failover should not be triggered during an outage of the source or destination region.

Per-partition failover. A newer capability redirects writes only for affected partitions to the next preferred region (single-write NoSQL accounts) — check availability.

Read-region outage. Clients redirect reads to other regions automatically; make sure those regions have enough provisioned RU for the extra traffic.

Bounded staleness. The docs suggest it for single-write accounts with two or more regions where near-strong behaviour across regions is wanted.

Other engines. Azure SQL’s geo-replication and failover groups (SQL page 15) and DynamoDB global tables answer the same question with different trade-offs.

🔥 Interview recall
  • Add regions for latency (readers near users) and resilience (region loss).
  • Single write region: no conflicts, service-managed failover promotes the next region in priority order; far writes pay latency.
  • Multiple write regions: local writes everywhere; conflicts resolved by a policy — Last Write Wins (default, by timestamp or a numeric property) or Custom merge procedure (conflicts feed otherwise).
  • Multi-write and service-managed failover cannot be enabled together; strong consistency is not available with multi-write.
  • Every region multiplies storage and write RU.
  • Best conflict policy: avoid conflicts (one home region per entity).
🎤 Say this in an interview
"I add regions to put data near users and survive a region loss. I start with multiple read regions and one write region — no conflicts and automatic failover — and move to multi-region writes only if write latency is a measured problem, keeping each entity’s writes in a home region and choosing a conflict policy: Last Write Wins on a meaningful property, or a custom merge procedure. I remember that regions multiply storage and write RU."
⚠️ Common trap

Multi-write “because global”. You gain write latency and take on conflicts; most apps need only read regions.

Forgetting RU per region. A read region that cannot absorb a failed-over region’s traffic turns an outage into 429s.
