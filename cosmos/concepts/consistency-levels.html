Consistency is a dial between fresh and fast — keep it at Session unless a feature needs more.

The five levels in plain English, what each costs in RU and latency, and how to match the level to the feature.

❓ "What are Cosmos DB’s consistency levels and how do you choose one?"
👁 See it first
🎯 Consistency is a dial between fresh and fast. Most apps want Session; choose stronger only for the feature that truly needs it.
▶️ Watch it happen: fresh versus fast
📖 Why did this need to exist?

Pages 2–8 were about spreading data and load. Spreading means copies: the data lives on several replicas, maybe in several regions. A read can then ask one nearby copy (fast) or insist on the latest (slower, dearer). That choice has a name: the consistency level.

It matters for cost too: page 3 told you strong and bounded-staleness reads cost about twice the RUs of the relaxed levels. So “just use strong to be safe” doubles your read bill.

📚 The five levels in plain English
LevelWhat a reader is guaranteedCost / latency notes
StrongLinearizable: the latest committed writeReads ≈ 2× RU; write latency ≈ 2× the round trip between the two farthest regions (+10 ms at p99); blocked by default beyond ≈ 5,000 miles (8,000 km)
Bounded stalenessReads lag by at most K versions or T timeReads ≈ 2× RU; if lag exceeds the bound, writes are throttled until it recovers
Session (default)Within one client session: read-your-writes, monotonic reads/writesLatency and throughput close to eventual
Consistent prefixReads never see writes out of order (A, A+B, A+B+C)Latency/throughput like eventual
EventualReplicas converge; no ordering guaranteeFastest; cheapest

Docs: read latency is under 10 ms at the 99th percentile for every level; the exception is write latency under Strong across regions. Session works by passing a session token — keep it if your app is spread over many servers.

▾ Go one level deeper (60 seconds)

Per-request overrides. You can relax the level for a request but not strengthen it beyond the account default. Newer options exist (for example LATEST_COMMITTED reads) — check the docs for your SDK.

Quorums. Strong and bounded-staleness reads use two replicas (a local minority quorum); the other levels read from one. Strong writes need commitment in every region; other levels use a local majority. Hence ≈ 2× read RU and roughly 2× read throughput for the relaxed levels.

Multi-region writes. With several write regions, strong consistency is not available, and conflicts are resolved by a policy (page 11).

Other engines. SQL’s isolation levels (SQL page 12) answer “what may I see of concurrent changes on one server”; consistency levels answer “which copy do I read”. Different problem, similar trade (freshness vs concurrency/speed).

🔥 Interview recall
  • Five levels, strongest → weakest: Strong, Bounded staleness, Session (default), Consistent prefix, Eventual.
  • Session = read-your-writes per client session (needs the session token).
  • Strong and bounded-staleness reads ≈ 2× RU; strong writes wait for all regions.
  • You can relax the level per request, not strengthen it.
  • Pick the weakest level the feature tolerates.
  • The integrated cache serves only session and eventual reads.
🎤 Say this in an interview
"Cosmos DB offers five consistency levels. I keep the account on Session, the default, because it gives read-your-writes at near-eventual cost and latency, and I only use strong or bounded staleness for features that truly need fresh cross-region reads, remembering they double read RU and strong slows cross-region writes. I can relax the level per request, and I pass the session token when my app runs on several servers."
⚠️ Common trap

“Strong is safer, so use it everywhere.” You pay twice for reads and slow writes for features that never needed it.

Losing the session token. With many app servers, “read your own write” silently stops working.
