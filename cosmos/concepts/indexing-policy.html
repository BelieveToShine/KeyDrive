Concept 5 of 12 · 🧠 Query & index

Everything is indexed by default — so tune by excluding and by adding composites.

Included and excluded paths, range vs composite indexes, how to cut write RU, and how to serve a sorted multi-property query.

❓ "How do you tune the indexing policy of a Cosmos DB container?"
👁 See it first
🎯 Cosmos DB indexes everything by default — convenient, but you pay for it on every write. Tuning the policy means excluding what you never query and adding composite indexes for sorted multi-property queries.
📖 Why did this need to exist?

In the SQL lab you added indexes one at a time and paid for each (pages 3, 7, 13). Cosmos DB reverses the default: everything is indexed, so a new query “just works”. The cost shows up as RU on every write (page 3) and as storage.

There is also a gap: a query that sorts on several properties does not just work — it needs a composite index. So the same page has two jobs: remove the indexes that cost without helping, and add the few that queries require.

🧱 The policy in five parts
PartWhat it doesTuning advice
Indexing modeconsistent: the index updates synchronously with every write. none: indexing off (a pure key-value store)Keep consistent unless the container is only ever read by id and partition key
Included pathsWhich JSON paths are indexed. Every policy must include the root /* as included or excludedInclude the root, then exclude (new properties are indexed automatically)
Excluded pathsPaths not indexed — saves write RU and storageExclude large text, blobs, and arrays you never filter on
Range indexThe default for string and number paths: equality, range, ORDER BY (single property), JOINNeeded for a single-property ORDER BY — it fails without a range index on that path
Composite indexA multi-property sort order, e.g. (customerId asc, orderDate desc)Add one per multi-property ORDER BY / multi-filter pattern; at most one range filter per composite, placed last

When included and excluded paths overlap, the more specific path wins. System properties id and _ts are always indexed in consistent mode; _etag is excluded by default. Spatial and vector index types also exist for geometry and similarity search.

🧪 Plan lab · two changes, tested one at a time

Change 1 — cut write cost. The 2 KB order has a long notes field and an embedded lines array that no query filters on. Measure an insert, exclude those paths, measure again.

{ "indexingMode": "consistent",
  "includedPaths": [ { "path": "/*" } ],
  "excludedPaths": [ { "path": "/notes/?" }, { "path": "/lines/*" }, { "path": "/\"_etag\"/?" } ],

▾ Go one level deeper (60 seconds)

How the index is stored. Cosmos DB uses an inverted index: each JSON path and value maps to the items that contain it. Range indexes are an ordered tree; they serve equality, range, ORDER BY and JOIN queries.

Multi-filter queries. For several filters, a property with a range filter is defined last in the composite index; each composite supports one range filter, so some patterns need two composites.

Partition key. The partition key path is not indexed unless you include it (and id is always indexed in consistent mode) — filters on the key still benefit from routing (page 6).

Computed properties can appear in included/excluded paths and composite indexes, but cannot have a spatial index.

Other engines. This is the mirror image of the SQL lab: there you add indexes; here you start with everything and remove, then add composites — the same cost model (page 13: every index slows every write).

🔥 Interview recall
  • Default: every path of every item is indexed (consistent mode); each path costs write RU and storage.
  • Policy = mode + included paths + excluded paths (+ composite/spatial/vector). The root /* must appear as included or excluded; the more specific path wins.
  • Recommended: include the root, exclude paths you never query.
  • Single-property ORDER BY needs a range index; multi-property ORDER BY always needs a composite index (matching order and direction).
  • In a composite: equality properties first, one range filter last.
  • A new composite index builds in the background; measure after it finishes.
🎤 Say this in an interview
"Cosmos DB indexes every path by default, which makes new queries work but adds write RU and storage for every indexed path. I keep the root included, exclude paths I never query — big text, embedded arrays — and add composite indexes for multi-property ORDER BY queries, with equality properties first and the sort order matching the query. I verify with the RU charge before and after."
⚠️ Common trap

Excluding a path someone queries. The query still works — as an expensive scan. Check query metrics after every policy change.

Adding composites “just in case”. Each one is another structure to maintain on every write — the same lesson as SQL page 13.

📇 Range index

Per path; serves equality, range and single-property ORDER BY.

vs.
🧩 Composite index

Across several paths in a fixed order; serves multi-property ORDER BY and multi-filter queries.
