❓ "How do you choose a partition key in Cosmos DB, and what goes wrong with a bad one?"
👁 See it first
🎯 The partition key decides which items sit together, how load spreads, and which queries stay cheap. It cannot be changed in place — choose it first, and choose it for the queries you will run.
▶️ Watch it happen: the key decides
📖 Why did this need to exist?

Page 1 left a promise: the key “decides where an item lives”. Here is why that matters. The engine can only spread data and load by placing different keys on different machines, and it can only run a query cheaply if it knows which machine to ask.

A good key makes the two common wishes agree: spread the load evenly (so no machine is overworked) and keep what is read together in one place (so most requests touch one partition). A bad key breaks one of them — and, unlike an index in SQL, you cannot simply add another; once chosen, a container’s key is fixed (changing it means copying the data to a new container).

This is why the Cosmos lab spends a whole page on a single property name.

⚖️ What makes a key good — three tests
1 · CARDINALITY

🎲 Many distinct values

A wide range of possible values lets the service spread items over many partitions.

2 · EVEN LOAD

⚖️ Requests and storage spread evenly

No single value (a “hot key”) should receive most of the traffic or most of the data.

3 · QUERY FIT

🎯 Your main queries include it

Queries that filter on the key go to one partition; the rest fan out (page 6).

LIMIT

📏 20 GB per logical partition

Once a logical partition is full you cannot write more to it. Plan for growth per key value.

🧰 Fixes when no single property is good enough

🧬 Synthetic key

combine properties into one✅ Pick it when
  • No single field has both high cardinality and fits your queries
  • e.g. customerId + month for write-heavy streams
⛔ Look elsewhere when
  • Queries that do not know every part of the key still fan out

🪜 Hierarchical partition key

up to three levels, e.g. tenantId → userId → sessionId✅ Pick it when
  • Multi-tenant data where one tenant could exceed 20 GB
  • Queries that give the first one or two levels are routed to a subset of partitions
  • Adding a unique last level (like the item id) keeps each logical partition tiny
⛔ Look elsewhere when
  • Choosing levels with no query that uses the first level

🧂 Add a suffix (salting)

spread one hot value over N buckets✅ Pick it when
  • A known hot value you cannot avoid
  • You will read it by fanning out over the N buckets
⛔ Look elsewhere when
  • It adds complexity — try a better key first

▾ Go one level deeper (60 seconds)

Logical vs physical. A logical partition is the set of items sharing a key value (max 20 GB). Physical partitions are the internal storage units; the service manages them, you cannot control them, and several logical partitions share one. Physical partitions split as data and throughput grow.

Hierarchical partition keys allow up to three levels. Queries that specify the first level (or the first two) are routed to the subset of physical partitions that hold the data; adding a unique final level such as the item id avoids the 20 GB limit.

Splitting does not cure a hot key. After a split, all items with the same key value are still on one physical partition.

Transactions. Stored procedures and transactional batches work inside one partition key value — another reason to keep data that changes together under the same key.

Other engines. DynamoDB has the same idea (partition key + hot key), and SQL’s table partitioning (SQL lab page 14) is a manageability feature, not a scale-out key — the two share a word, not a purpose.

🔥 Interview recall
  • Items with the same partition key value form a logical partition (max 20 GB, transactions stay inside it).
  • The key value is hashed; physical partitions are managed by the service.
  • Good key: high cardinality, even load and storage, fits the main queries.
  • The key cannot be changed in place — migrate to a new container.
  • Fixes: synthetic key, hierarchical partition key (up to 3 levels), unique last level to avoid the 20 GB limit.
  • Hot key signature: one partition at 100% normalized RU, 429s with low overall usage.
🎤 Say this in an interview
"The partition key decides which items live together and how load spreads. I look for high cardinality, even request and storage distribution, and a property that appears in my main queries. A logical partition is capped at 20 GB, so for multi-tenant data I consider hierarchical keys. Because the key can’t be changed in place, I get it right up front and I watch normalized RU consumption by partition to catch hot keys."
⚠️ Common trap

Choosing the key by habit. “Use id” spreads perfectly but makes every query a fan-out; “use date” makes every write hot. Pick the key from the queries and the load, not from the schema.

Adding RU/s to a hot partition. You pay for throughput that the busy partition cannot use — the other partitions just sit under-used.
