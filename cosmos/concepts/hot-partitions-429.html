📖 Why did this need to exist?

Page 2 warned about hot keys in theory; page 3 explained the budget; page 7 showed how to read one query. This page is the incident view: “we are getting 429s — now what?”.

A 429 is not an error to be afraid of by itself. The SDKs retry automatically, typically up to nine times, so many 429s never reach your application — and Microsoft’s own guidance is that 1–5% of requests being rate-limited with acceptable latency is a healthy sign that you are using the RU/s you pay for. The question is whether the 429s are evenly spread (you need more throughput or cheaper requests) or concentrated (a hot key).

🧭 Triage in one picture
🧰 Your options

📈 Autoscale

RU/s follows the load within 10%–100% of the max✅ Pick it when
  • Spiky load across all partitions
  • You want to stop paying for the peak all day
⛔ Look elsewhere when
  • A hot partition: it still hits its share of the maximum

⬆️ Raise RU/s

a stopgap✅ Pick it when
  • Right now, to stop an incident
  • When all partitions are busy
⛔ Look elsewhere when
  • As a long-term fix for skew — it over-provisions and costs more

🔑 Better partition key

the real fix for skew✅ Pick it when
  • One key value takes most of the load
  • A synthetic or hierarchical key spreads it
  • A new container + data migration
⛔ Look elsewhere when
  • When the load is simply high everywhere

🔁 Retry and backoff

in the client✅ Pick it when
  • Short bursts
  • Honouring the Retry-After value the service returns (check your SDK)
⛔ Look elsewhere when
  • Hiding sustained throttling

▾ Go one level deeper (60 seconds)

Normalized RU consumption is emitted per minute and is defined as the maximum RU/s utilisation across all partition key ranges in the interval; it does not always mean you saw a 429 when it hits 100%.

Finding the hot key. The diagnostic log table for partition-key RU consumption (CDBPartitionKeyRUConsumption, or the AzureDiagnostics category PartitionKeyRUConsumption) lets you sum request charge by partition key per second. Decide whether it is fundamental skew or a temporary spike.

Redistributing throughput across partitions (a preview feature per the docs) can give a hot partition more of the budget, but it is a workaround, not a fix.

Retries. Client SDKs and tools retry 429s automatically, typically up to nine times; check the retry-after value the service returns.

Other engines. DynamoDB’s “hot key / throttled requests” is the same story; in SQL the nearest cousin is a single blocking session (SQL page 12) — one thing starving the rest.

🔥 Interview recall
  • 429 = “request rate too large”: over the RU/s share. SDKs retry automatically.
  • 1–5% 429s with acceptable latency is healthy.
  • Normalized RU is the maximum across partitions; one hot partition can make it 100%.
  • Hot key: one partition near 100%, others low — fix the key; splitting does not help a single hot value.
  • All partitions high: more RU/s (autoscale) or cheaper requests.
  • Raising RU/s is a stopgap for skew.
🎤 Say this in an interview
"A 429 means a partition exceeded its share of the RU/s budget; the SDK retries automatically and a few percent is healthy. I check normalized RU consumption by partition key range: one partition at 100% means a hot key, which I fix with a better, synthetic or hierarchical partition key — raising RU/s only masks it. If all partitions are high I use autoscale and lower the RU charge of the expensive requests."
⚠️ Common trap

Buying throughput for a skew problem. You pay for ten partitions of headroom to fix one busy one.

Reading “normalized RU 100%” as “the container is full”. It is a maximum across partitions.

🔥 Hot partition

One key value takes most of the load. 429s while others idle.

vs.
📈 Under-provisioned

Every partition is busy. 429s everywhere at peak.
