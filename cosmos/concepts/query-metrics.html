❓ "A Cosmos DB query is expensive. How do you find out why?"
👁 See it first
🎯 In SQL you read a plan; in Cosmos DB you read query metrics. The one comparison to make first: documents retrieved vs documents returned.
▶️ Watch it happen: retrieved versus returned
📖 Why did this need to exist?

Page 6 gave you three request shapes; page 5 gave you an index policy. How do you know a specific query is behaving? You cannot open a plan like SQL’s, but every query can return metrics, and the docs make one rule the first step of any optimisation: get the query metrics for your query.

This page shows what the numbers mean, how to turn them into a hypothesis, and where to look when the problem is at the account level rather than one query.

🔬 The numbers that matter
MetricPlain EnglishWhat a bad value looks like
Request charge (RU)What the query costHigh for a small result
Retrieved document countHow many documents the engine loaded to evaluate the queryMuch larger than the output count
Output document countHow many documents matched and were returned—
Index utilisation / hit ratioHow much of the filtering the index didNear 0% with a high RU charge — a scan
Partitions queriedHow many physical partitions were visitedMany, for a result that fits in one (fan-out)
Execution / load timeWhere the time wentLarge document-load time: big items or many documents

Rule from the docs: if Retrieved Document Count is roughly equal to Output Document Count, the index is doing its job — minimise cross-partition queries and look at item size. If Retrieved is far larger, the problem is the index.

🧭 Triage in one picture
🧪 Plan lab · from 312 RU to 3 RU

The query from page 5: WHERE c.customerId = 42 ORDER BY c.orderDate DESC. A teammate reports it is “slow and expensive”. (All numbers illustrative.)

// .NET-style sketch: ask for the metrics and log them next to the RU charge
var opts = new QueryRequestOptions { PopulateIndexMetrics = true };
using var it = container.GetItemQueryIterator(query, requestOptions: opts);
while (it.HasMoreResults)
{
    var page = await it.ReadNextAsync();
    Console.WriteLine($"RU={page.RequestCharge}  count={page.Count}");
}

Illustrative. Option and property names depend on the SDK and version — check its docs; the portal and diagnostics logs show the same numbers.

▾ Go one level deeper (60 seconds)

Fan-out and index use are different axes. A cross-partition query can still use indexes; an in-partition query can still scan. The metrics let you tell them apart: partitions queried vs retrieved/output.

Index metrics. The service can also report which indexes a query used and which it could have used, which is how you find a missing composite index.

Throttling. A throttled query returns 429s that the SDK retries; the retried attempts are visible in diagnostics, not necessarily as application errors.

Other engines. This is the Cosmos counterpart of “estimated vs actual rows” (SQL page 4): a gap between what the engine looked at and what it returned.

🔥 Interview recall
  • First step of any query tuning: get the query metrics.
  • Retrieved ≫ Output ⇒ the index is not helping. Retrieved ≈ Output ⇒ look at partitions touched and item size.
  • Index utilisation near 0% with high RU = a scan.
  • Log RequestCharge and metrics for the top operations.
  • Insights, diagnostic logs and SDK diagnostics answer account-level questions.
  • Change one thing; re-measure the same query.
🎤 Say this in an interview
"For a costly Cosmos DB query I get the query metrics first and compare retrieved and output document counts. If far more documents were retrieved than returned, the index isn’t helping — usually an excluded path or a missing composite index — and I fix that. If they match, I look at how many partitions were queried and how big the items are. I change one thing and re-run the same query to compare the RU charge."
⚠️ Common trap

Optimising from the portal’s account-wide RU graph. It cannot tell you which query is dear — log request charge per operation.

Adding indexes blindly. If retrieved ≈ output the index is already working; more indexes only raise write RU.
