Concept 1 of 12 · 🌌 The model

Cosmos DB stores JSON items in containers — and you pay for every request.

The mental model for a distributed NoSQL database: the resource hierarchy, how SQL words translate, why there are no joins, and where tuning happens.

❓ "How is Cosmos DB for NoSQL organised, and how does it differ from a relational database?"
👁 See it first
🎯 Cosmos DB stores JSON items in containers, spread across machines by a key you choose — and you pay for every request in Request Units. Design for the reads you will do.
▶️ Watch it happen: items, containers, key, RUs
📖 Why did this need to exist?

The SQL lab ended with a database on one (large) machine: tables, joins, a plan you can read. That model is brilliant for related data and ad-hoc questions — and it has two limits. A single primary database mostly scales up, and the data and the users must live close to one place.

Cosmos DB is built for the opposite corner: data that must scale out across many machines, spread across regions close to users, with a flexible JSON shape. To spread data, the engine must decide where each item lives — and it cannot afford to join items that live on different machines.

So the rules change. You choose a partition key. You shape the data for the reads. And you pay in Request Units (RUs) rather than watching a plan. This page gives you the mental model; the next eleven give you the tuning.

🧰 When Cosmos DB fits — and when SQL still wins

🌌 Azure Cosmos DB (NoSQL API)

distributed, flexible JSON, global✅ Pick it when
  • Flexible JSON items and a shape that keeps changing
  • Users in many regions needing fast reads and writes
  • Huge scale: spread data and load over many partitions
  • Access patterns you know in advance (read by key, small result sets)
⛔ Look elsewhere when
  • Many ad-hoc joins and reports across entities
  • You cannot name a good partition key yet
  • Strict multi-table transactions on a small dataset

🗄️ Azure SQL (the SQL lab)

related tables, joins, ad-hoc questions✅ Pick it when
  • Related tables, constraints and multi-table transactions
  • Ad-hoc queries and reporting
  • Mostly scale-up with read replicas
⛔ Look elsewhere when
  • One writable primary is not enough for your global scale or latency

🩺 Debug checklist · habits that carry over from SQL — and bite
SQL habitWhat happens in Cosmos DBDo this instead
“I’ll just JOIN the tables”Items in different containers (or partitions) cannot be joined by the engineEmbed what you read together; or read the second item by id
“Put all comments in an array on the post”The item can grow without limit toward the 2 MB capOne item per child, keyed to the parent (page 4)
“Query for it by id”A query is not a point read and costs moreUse a point read with id + partition key
“The schema is flexible, so no design is needed”The partition key, and the shape per access pattern, decide cost and scaleDesign for the reads first
“Add indexes for every query”Every property is already indexed, and each costs write RUTune the indexing policy (page 5)

▾ Go one level deeper (60 seconds)

Other APIs. Cosmos DB also offers MongoDB, Cassandra, Gremlin (graph) and Table APIs. This lab covers only the NoSQL API — the native one with the SQL-like query language.

“Schemaless” still has a schema. It lives in your application code, not in the database. Items in one container can differ, but your queries and indexes assume shapes.

Throughput placement. RU/s can be provisioned per container or shared across the containers of a database (page 3). Storage and throughput scale by spreading data over physical partitions, which the service manages and you cannot control (page 2).

The ladder is the same. Pages 1–11 of the SQL lab taught a method: measure, read, find the biggest wrong thing, change one thing, prove it. Here “measure” is the RU charge and “read” is the query metrics and diagnostics — same discipline, different instruments.

🔥 Interview recall
  • Account → database → container → item. The container holds the partition key, throughput and indexing policy.
  • An item is JSON (up to 2 MB) identified by id + partition key value.
  • No joins across items or containers: embed what you read together.
  • Everything is indexed by default; cost is measured in Request Units (RU).
  • Transactions work inside one partition key value.
  • This lab covers the NoSQL API only.
🎤 Say this in an interview
"Cosmos DB for NoSQL stores JSON items in containers inside databases inside an account. Each container has a partition key that decides where items live, a throughput measured in request units, and an indexing policy. There are no joins across items, so I shape the data for the reads — typically embedding what is read together — and I measure cost by the RU charge on each request."
⚠️ Common trap

Treating Cosmos DB like SQL on JSON. Normalising into many small containers and “joining” in code makes every page load a dozen requests — and every request costs RUs.

Picking the partition key last. It is the one decision you cannot change in place (page 2).

🗄️ Relational (SQL)

Tables and joins; one primary, scale up; the optimizer plans each query.

vs.
🌌 Cosmos DB

Items and containers; spread by partition key, scale out; you design for known reads and pay per request in RUs.
