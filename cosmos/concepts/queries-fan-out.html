❓ "What is the difference between a point read, an in-partition query and a cross-partition query?"
👁 See it first
🎯 Cost depends on how many partitions you touch. Prefer point reads, then queries that include the partition key; treat a fan-out as a design smell.
▶️ Watch it happen: partitions touched
📖 Why did this need to exist?

Page 2 chose a key; page 5 tuned the index. Both only pay off if your queries use them. In SQL you wrote any query and the optimizer chose a plan; here the main decision is yours — which of three request shapes a screen or API call uses.

The shape matters more than the SQL text. A cross-partition query is, in effect, one query per physical partition: the same filter costs more every time the container grows, even though the answer stays the same size.

📄 Paging: continuation tokens

A query returns results in pages; the response includes a continuation token that you pass back to get the next page. Prefer continuation tokens over “skip N” style paging, and never assume a query returns everything in one response. For cross-partition queries, parallelism (MaxConcurrency) trades more simultaneous requests for lower latency — it does not lower the RU charge.

▾ Go one level deeper (60 seconds)

Why 2.5 RU per partition. A cross-partition query is essentially a separate query per physical partition, and each index check is charged a minimum even when nothing matches. Small containers barely notice; the docs flag it as significant for large throughput (tens of thousands of RU/s) or large storage (around 100 GB).

Fan-out vs index use are independent. A cross-partition query can still use indexes; the fan-out is about how many partitions are visited.

Hierarchical keys. Queries that specify the first level (or first two) are routed to the subset of physical partitions that hold the data.

Global secondary indexes (a feature the docs describe as preview) can turn a cross-partition query into an in-partition query on an index container — check availability before relying on it.

Other engines. This is the Cosmos counterpart of SQL’s “a scan reads everything”; the difference is that the unit of waste is a partition rather than a page.

🔥 Interview recall
  • Three shapes: point read (id + key), in-partition query (key in the filter), cross-partition query (fan-out).
  • A query by id is not a point read.
  • Cross-partition cost grows with physical partitions (≈ 2.5 RU minimum each).
  • MaxConcurrency lowers latency, not RU.
  • Fix a fan-out with the key in the filter, a re-key, or a second container/read model.
  • Page results with continuation tokens.
🎤 Say this in an interview
"I pick the request shape first: a point read when I have id and partition key, an in-partition query when I at least have the key, and I treat a cross-partition query as a design smell because it fans out to every physical partition and its cost grows with the container. Parallelism improves latency but not RU. For a screen that genuinely needs a cross-partition answer I build a read model, for example with the change feed."
⚠️ Common trap

“It is fast on my small test container.” Fan-out cost grows with partitions; the test container has one.

Querying by id with SQL. You pay query RUs for something a point read does for ~1.
