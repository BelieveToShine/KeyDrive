Concept 9 of 19 · ⚙️ Handling load

Scaling adds copies when load grows; resilience keeps you running when something fails — both come from never relying on just one of anything.

▶️ Watch it happen: never rely on just one
📖 Why did this need to exist?

The last concept put a load balancer in front of several copies of your app. Two questions follow at once. How many copies do you need? Too few and the app is slow at peak; too many and you pay for idle machines. What if a copy — or the whole building — fails?

Azure answers the first with autoscale: add copies when load rises, remove them when it falls. It answers the second with redundancy: copies in separate zones and, for the worst day, a second region. Microsoft's reliability guidance says it plainly: use layers of redundancy so there is no single point of failure, and start by working out how each part can fail.

🔁 How autoscale decides
🧰 The tools

📈 Autoscale

add and remove copies automatically✅ Pick it when
  • Traffic that rises and falls
  • Metric rules (CPU, queue length, memory) or a schedule
  • App Service, scale sets and Container Apps each have their own way to scale
⛔ Look elsewhere when
  • A single database server — it is not a pool of identical copies

🧱 Virtual Machine Scale Sets

a group of load-balanced VMs✅ Pick it when
  • Many identical VMs managed as one group
  • The group should autoscale
  • Microsoft recommends the Flexible orchestration mode
⛔ Look elsewhere when
  • A web app that App Service can host for you with less to manage

🏢 Availability zones

copies in separate datacenters✅ Pick it when
  • Survive the loss of one datacenter
  • Spread VMs or use zone-redundant services
⛔ Look elsewhere when
  • Do not expect data to copy itself — spreading VMs across zones does not replicate your data

🛟 A second region

for the biggest failures✅ Pick it when
  • The business cannot stop if a whole region fails
  • Backups and failover for a real disaster
⛔ Look elsewhere when
  • The cost is not justified by the app → zones are often enough
🎬 Real-world scenarios
🎟️
Ticket sales open at noon

A huge spike, then quiet. Add copies before it starts.

→ Scale on a schedule, plus metric rules
📬
A queue of jobs piles up

Workers should grow with the backlog and shrink when it clears.

→ Scale on queue length
🛍️
Weekend shopping peak

Traffic doubles every Saturday and drops on Monday.

→ Autoscale with a scale-in rule
🏢
One datacenter loses power

The site must stay up with no one waking up.

→ Copies spread across zones
🌪️
A whole region is unavailable

Rare, but the business cannot be offline for long.

→ A second region and a failover plan
🔌
A call to a dependency fails once

The next try would succeed.

→ Retry with a growing delay

▾ Go one level deeper (60 seconds) — build the app so it survives failure

Retry, but wisely. A transient fault is a short failure that fixes itself, so trying again after a short wait often works. Microsoft recommends exponential back-off (wait longer each time) plus a little random jitter, so thousands of clients do not all retry at the same instant.

Add a circuit breaker. If a dependency is really down, endless retries make things worse. A circuit breaker stops calling it for a while and lets it recover.

Make health checks honest. A health endpoint should check what the app really needs — the database, the cache, the queue — not just "the process is running".

Make work safe to repeat. If a function can be retried, design it to be idempotent: doing it twice has the same result as doing it once.

Zones are not backups. Spreading VMs across zones protects against a datacenter failure, but it does not copy your data and it does not recover from a deletion. That is the job of replication and backup (see the deep dive).

🔥 Interview recall
  • Scale up = bigger machine (has a ceiling). Scale out = more copies (autoscale works this way).
  • Autoscale uses a metric or a schedule, a time window, and rules. Pair every scale-out rule with a scale-in rule and keep a gap between thresholds to avoid flapping.
  • Scale sets run a group of load-balanced VMs that can autoscale; Flexible mode is the recommended one.
  • Zones survive a datacenter failure; a second region survives a regional one. Zones do not replicate data for you.
  • Retry with exponential back-off and jitter, add a circuit breaker, and make operations idempotent.
🎤 Say this in an interview
"I design for failure at three sizes: a server, a datacenter and a region. Several copies behind a load balancer cover a server, zones cover a datacenter, and a second region with backups covers a region. For load I scale out with autoscale rules on a metric or a schedule, always with a scale-in rule and a gap between thresholds so it does not flap. In code I use retries with back-off and jitter, a circuit breaker, and idempotent operations."
⚠️ Common trap

Autoscale only helps if the app can run as many copies. If it keeps session data or files on one server, a new copy will not know about them. Keep state outside the copies (a database, a cache, storage).

Second trap: "we are in two zones, so we have backups". Zones keep the app running; they do not protect you from someone deleting data or from corruption. Redundancy and backup are different things.

📈 Scaling

Match the number of copies to the load, in both directions. Mostly about performance and cost.

vs.
🛟 Resilience

Keep working when something fails. Mostly about availability and recovery.

▾ 💻 Tiny illustrative example 
# add an autoscale rule: more copies when average CPU is high (pair it with a scale-in rule!)
az monitor autoscale rule create --resource-group rg-shop-prod --autoscale-name as-shop \
    --condition "Percentage CPU > 70 avg 10m" --scale out 1

Illustrative shape only — the number and thresholds are examples, a real setup also needs the scale-in rule, and flags can change.
