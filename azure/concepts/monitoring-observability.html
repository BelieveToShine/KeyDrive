Monitoring tells you something is wrong; observability helps you find why — but only if you collected the signals before the incident.

Metrics, logs and traces in Azure Monitor, Log Analytics and Application Insights — plus alerts that turn signals into action.

❓ "How would you monitor an Azure application and get alerted before users notice?"
👁 See it first
🎯 Monitoring tells you something is wrong; observability lets you work out why — and both need metrics, logs and traces gathered in one place before the incident.
▶️ Watch it happen: from “something is wrong” to “why”
📖 Why did this need to exist?

Guardrails say what should happen. They do not tell you what did happen. The app is fast today and slower next week; a deployment looks fine and customers still see errors; the cost climbs and nobody knows which part grew. Without signals, every problem becomes guessing.

The skill is deciding what to collect before you need it. Metrics answer "is something off?". Logs answer "what exactly happened?". Traces answer "where did this one request spend its time?". Then alerts turn the signals into action, so a person (or an automatic fix) hears about trouble before the customers do.

🧰 The pieces

📡 Azure Monitor

the platform for all signals✅ Pick it when
  • Metrics, logs, traces and events in one service
  • Platform metrics and the activity log are collected automatically
  • Alerts, dashboards and workbooks on top
⛔ Look elsewhere when
  • Nothing — it is the base for the rest

🔎 Log Analytics

query logs with KQL✅ Pick it when
  • Search and join logs from many resources
  • Resource logs, after you create a diagnostic setting
  • Investigate an incident after the fact
⛔ Look elsewhere when
  • Resource logs are not collected until you turn them on

🧑‍💻 Application Insights

application performance monitoring✅ Pick it when
  • Requests, failures, dependencies and traces inside your app
  • Instrument with OpenTelemetry, a vendor-neutral framework
  • Distributed tracing across services
⛔ Look elsewhere when
  • Only watching the VM or the platform — add resource metrics and logs too

🚨 Alerts and action groups

turn a signal into action✅ Pick it when
  • Metric, log and activity-log alerts
  • Action groups: email, SMS, push, automation runbooks, Functions, Logic Apps, ITSM tickets, webhooks
⛔ Look elsewhere when
  • Alert on everything — people will start ignoring them

▾ Go one level deeper (60 seconds) — workspaces, settings and the traps

Two kinds of workspace. A Log Analytics workspace holds logs and traces, queried with KQL. An Azure Monitor workspace holds Prometheus and OpenTelemetry metrics, queried with PromQL. Application Insights data is stored in a Log Analytics workspace, so you can query it like other logs.

Diagnostic settings. Platform metrics and the activity log are collected automatically, but resource logs are not. A diagnostic setting sends them to a Log Analytics workspace, an event hub or storage. For new settings, Microsoft recommends the resource-specific table mode. You can roll them out at scale with built-in Azure Policy (concept 16).

Keep monitoring itself monitored. The guardrails from concept 16 need signals too: send Policy, Defender and Key Vault logs to the same place, and alert when something important turns off.

Cost. Logs are billed by volume, and a diagnostic setting cannot filter inside a category; collect what you will use. (Cost Management is the next concept.)

🔥 Interview recall
  • Three signals: metrics (numbers over time), logs (detailed records), traces (a request across services). Azure Monitor gathers them.
  • Platform metrics and the activity log are automatic; resource logs need a diagnostic setting; traces need instrumentation (Application Insights, OpenTelemetry).
  • Log Analytics workspace = logs/traces queried with KQL. Application Insights = application performance monitoring.
  • Alert rule (condition + window) fires an action group (notify, run automation, open ticket).
  • Decide what to collect before the incident; alerts without an owner become noise.
🎤 Say this in an interview
"I collect the three signals — metrics, logs and traces — in Azure Monitor. Metrics and the activity log are automatic, resource logs need diagnostic settings, and the app is instrumented with Application Insights and OpenTelemetry for traces. I query logs with KQL in Log Analytics, and I turn signals into action with alert rules and action groups. I deploy the diagnostic settings with Azure Policy so nothing is forgotten."
⚠️ Common trap

Assuming logs are on by default. Platform metrics and the activity log are, but resource logs are not collected until you create a diagnostic setting — so the one time you need them, they are missing.

Second trap: an alert for everything. A flood of alerts trains people to ignore them. Alert on symptoms users feel, give each alert an owner, and use dashboards for the rest.

Cheap, fast numbers over time. Tell you that something is off.

📜 Logs and traces

▾ 💻 Tiny illustrative example 
// KQL: failed requests per hour in Application Insights, last day
requests
| where timestamp > ago(1d) and success == false
| summarize failures = count() by bin(timestamp, 1h)
| order by timestamp asc

Illustrative only — table and column names depend on how the workspace and the app are set up.
