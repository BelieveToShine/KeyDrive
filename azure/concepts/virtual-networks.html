Without a network plan, every resource could be reachable from everywhere. Learn how VNets, subnets and security groups build a safe layout, how NSG rules are checked, and how peering connects networks.

❓ "What is an Azure virtual network, and how do subnets, NSGs, peering and private endpoints work together?"
👁 See it first
🎯 A virtual network is a private, fenced-off corner of Azure. Subnets split it into zones, and network security groups are the doors with rules: who may come in, from where, on which port.
▶️ Watch it happen: a fenced-off corner
📖 Why did this need to exist?

Identity decides who may ask Azure to do things. The network decides what can physically reach what. A database with a public address that anyone on the internet can try to connect to is a risk, even behind a strong password — the best protection is that it cannot be reached at all.

A virtual network gives your resources private addresses and a boundary. Subnets let you separate tiers (web, app, data). NSGs add simple allow-or-deny rules. Together they turn "everything can talk to everything" into "only the paths I planned".

📖 The words you need
🕸️ Virtual network (VNet)

Your private network in Azure. It lives in one region and one subscription, and it can span the availability zones of that region. Networks in different regions connect through peering.

🔢 Address space

The range of private IP addresses the VNet uses, written like 10.0.0.0/16. Use private ranges, and pick ranges that will not overlap other networks you may connect later.

🧱 Subnet

A slice of the address space. NSGs and route tables attach to subnets. Azure reserves five addresses in every subnet, so very small subnets run out quickly.

🛡️ Network security group

A list of allow and deny rules for traffic by source, destination, port and protocol. Associate one with every subnet.

🤝 Peering

A direct, private link between two VNets so their resources can talk to each other.

🔌 Private endpoint

A private IP address in your subnet that points at an Azure service such as storage or SQL. Explained in the deep dive below.

🔗 Ways to connect things

🌍 Public internet

a public IP address on the resource✅ Pick it when
  • Things meant for everyone: a public website or API
  • Quick experiments
⛔ Look elsewhere when
  • Databases, storage with private data and admin ports → keep them private

🤝 VNet peering

a direct link between two virtual networks✅ Pick it when
  • Two networks (for example Dev and Shared services) must talk privately
  • You want a simple, direct connection
⛔ Look elsewhere when
  • You expect traffic to pass through a middle network — peering is not transitive

🏢 VPN gateway or ExpressRoute

connect Azure to your office or datacenter✅ Pick it when
  • An on-premises network must reach Azure resources privately
  • A VPN is an encrypted tunnel over the internet; ExpressRoute is a private connection through a provider
⛔ Look elsewhere when
  • Everything is already in Azure → peering or private endpoints are enough

🔌 Private endpoint

a private IP for an Azure service✅ Pick it when
  • Reach Azure Storage, SQL and others without the public internet
  • Turn off the service's public access
⛔ Look elsewhere when
  • You only need a quick subnet allow-list → a service endpoint can be enough (see the deep dive)

🎬 Real-world scenarios
🛒
Website with a hidden database

Users reach the site. The database must never be reachable from the internet.

→ Web subnet + data subnet + NSGs
🧪
Dev and Prod, shared logging

Two VNets must send logs to a shared network, privately.

→ VNet peering
🏢
Office needs the Azure database

Staff on the corporate network must connect privately.

→ VPN gateway or ExpressRoute
🔌
App to storage, no internet

The web app must reach Blob Storage without a public path.

→ Private endpoint
🚫
Block remote desktop from the internet

Port 3389 must never be open to everyone.

→ An NSG deny rule (or no public IP)
🧮
Planning address ranges

Three teams each build a VNet and later want to connect them.

→ Non-overlapping ranges, planned up front

🔥 Interview recall
  • A VNet is your private network: one region, one subscription, can span zones. Subnets slice it; NSGs and route tables attach to subnets.
  • NSG rules run from the lowest priority number up (custom 100–4096; defaults 65000+); the first match wins and stops. Default rules cannot be deleted, only overridden.
  • Azure reserves five addresses in each subnet.
  • Peering is a direct link and is not transitive; address ranges must not overlap.
  • Use private endpoints to reach Azure services privately; plan your address ranges first.
🎤 Say this in an interview
"A virtual network is a private network scoped to a region and subscription. I split it into subnets by tier and attach a network security group to each, with allow rules for what is needed and a deny for the rest — rules are evaluated from the lowest priority number and the first match wins. I connect networks with peering, remembering it is not transitive, and I reach PaaS services privately with private endpoints."
⚠️ Common trap

The default rules are friendlier than you think. Traffic inside the virtual network — and from networks connected to it — is allowed by a default rule. If two subnets must not talk to each other, add your own deny rule with a lower number.

Second trap: peering is not transitive. Peering A–B and B–C does not connect A to C. Plan each path, or use a central network design (a later concept).

▾ 💻 Tiny illustrative examples 
# a network with one subnet
az network vnet create --name vnet-shop --resource-group rg-shop-prod \
    --address-prefixes 10.0.0.0/16 --subnet-name web --subnet-prefixes 10.0.1.0/24

# a rule: allow HTTPS in (priority 100 = checked first)
az network nsg rule create --nsg-name nsg-web --resource-group rg-shop-prod \
    --name allow-https --priority 100 --direction Inbound --access Allow \
    --protocol Tcp --destination-port-ranges 443

Illustrative shape only — real setups are written as templates (Bicep) and add more rules, route tables and diagnostics.
