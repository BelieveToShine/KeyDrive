Concept 10 of 19 · ⚙️ Handling load

A cache keeps a copy of an answer close to whoever asks — so the slow, expensive place is asked far less often.

Learn the layers of caching on Azure — browser, edge, shared app cache — the cache-aside pattern, and the freshness trade-off that every cache brings.

❓ "What is caching, where would you cache on Azure, and what is the cache-aside pattern?"
👁 See it first
🎯 A cache keeps a copy of an answer closer to whoever asks, so the slow, expensive place — usually the database — is asked far less often.
▶️ Watch it happen: a cache answers for the database
📖 Why did this need to exist?

You have copies of your app, a load balancer and autoscale. But look at what every copy does: for the same product page, every request asks the same database the same question. Adding more app servers makes it worse, because now more servers ask the database.

A cache fixes that by remembering recent answers. The result is faster pages for users and less load on the database. The price: a cached copy can be out of date. So caching is always a decision about what to copy, where to keep it, and how long it may stay.

🧰 Where to cache

🌐 Browser cache

on the visitor's device✅ Pick it when
  • Images, scripts and style files that rarely change
  • You control it with the response headers your app sends
⛔ Look elsewhere when
  • Anything private or fast-changing that must be fresh on every visit

🌍 Edge cache (Front Door)

a copy near the visitor✅ Pick it when
  • Static files and responses that are the same for everyone
  • Visitors spread across the world
  • You can purge it, set how long to keep things, and cache by query string
⛔ Look elsewhere when
  • Personal data that is different for every user

⚡ Azure Managed Redis

a shared in-memory cache✅ Pick it when
  • Data many app copies read again and again
  • Results of slow database queries
  • Sessions and other quick shared state
⛔ Look elsewhere when
  • Data you cannot afford to lose — it is a copy, not the source of truth

🧠 In-app memory cache

inside one app instance✅ Pick it when
  • Tiny, hot data that is the same everywhere
  • The fastest possible reads, with no network trip
⛔ Look elsewhere when
  • Several instances need to agree — each instance has its own private copy, so use a shared cache

⚖️ Cache-aside: the trade-offs

✅ Strengths
  • The cache holds only what is actually asked for
  • Works even when the cache has no built-in loading logic
  • If the cache is empty or gone, the app still works — it just reads the database
⚠️ Watch out for
  • It does not guarantee the cache and the database agree
  • Expire too early and you reload constantly; too late and you serve old data
  • A poor fit when most requests miss the cache anyway
  • Avoid caching sensitive data
🎬 Real-world scenarios
🛍️
Product pages, read a lot, changed rarely

Every visit asks the database the same question.

→ Managed Redis, cache-aside
🖼️
Logo, images and style files

The same bytes for every visitor, everywhere.

→ Edge cache + browser cache
🧾
A "my account balance" page

Different for every user and must be correct.

→ Do not cache — or only briefly
🔑
Login sessions with many app copies

Any copy must recognise the user.

→ Shared cache (Redis)
📰
A news homepage hit by a spike

Millions see the same page at once.

→ Edge cache with a short expiry
🧮
One small settings list used everywhere

Tiny and almost never changes.

→ In-app memory cache
▾ Go one level deeper (60 seconds) — freshness, and the names to check

Freshness is the whole game. Every cached item needs an expiry time, and you need a way to throw it away when the source changes (invalidate it). Short expiry = fresher but more misses. Long expiry = faster but staler.

A cache can also help when the origin is down. Microsoft notes that a cache can serve as a limited fallback if the data store is temporarily unavailable — one more reason to treat it as a layer, not just a speed-up.

Product names are moving. Azure Managed Redis is Microsoft's current recommendation for a Redis cache, with tiers such as Memory Optimized, Balanced, Compute Optimized and Flash Optimized (which moves less-used data to flash storage). The older Azure Cache for Redis tiers are being retired and Microsoft recommends migrating. On the edge side, use Azure Front Door Standard or Premium; Front Door (classic) and Azure CDN Standard (classic) are being retired. Always check the retirement pages for dates before planning.

Because a look-aside cache only holds copies of database records, moving to a new cache is usually easy: create the new one, point the app at it, and let it refill.

🔥 Interview recall
  • A cache keeps copies close to the asker so the slow source is asked less. The price is possible staleness.
  • Layers: browser → edge (Front Door) → app cache (Azure Managed Redis) → database.
  • Cache-aside: check the cache; on a miss read the database and save a copy; when data changes, write to the database and delete the cached copy.
  • Cache-aside does not guarantee consistency; expiry that is too short or too long both hurt. Avoid caching sensitive data.
  • A per-instance memory cache is private to that instance; use a shared cache when several instances need the same data.
🎤 Say this in an interview
"A cache trades freshness for speed. I cache in layers: the browser, an edge cache like Front Door for content that is the same for everyone, and a shared cache like Azure Managed Redis in front of the database. I use cache-aside — check the cache, on a miss read the database and save a copy, and on a change write to the database and delete the cached item. I set expiry times deliberately, and I do not cache sensitive or must-be-correct data."
⚠️ Common trap

Do not treat the cache as the source of truth. It is a copy and can disappear or go stale. Your app must still work, and recover, from the database alone.

Second trap: caching personal data in a shared place. An edge or shared cache that stores one user's page and serves it to another is a serious bug. Cache only what is the same for everyone, or key the cache carefully.

▾ 💻 Tiny illustrative example 
# cache-aside in plain pseudo-code
item = cache.get(key)
if item is None:               # miss
    item = database.read(key)  # slow path
    cache.set(key, item, expires_in=minutes)  # save a copy, with an expiry
return item

Illustrative pseudo-code only — real clients (for example a Redis client library) have their own method names and options.
