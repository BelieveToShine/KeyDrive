An Azure storage account is four doors — you pick the door by the shape of your data.

Photos, shared folders, jobs waiting to run and simple records are all different kinds of data. Azure keeps them in one place — the storage account — but each door works differently. Learn which door fits which data, and how many copies to keep.

📖 Why did this need to exist?

In the last step you gave your code a place to run. But a place to run is not a place to keep things. A virtual machine can be replaced, a container is thrown away and rebuilt, a function disappears between calls — anything your code saved on its own disk can vanish with it.

Real apps keep photos, invoices, backups and logs for years. Storage gives that data a safe home outside your compute, so your servers can come and go. And because "data" is not one shape — a photo, a shared folder, a job waiting to run and a simple record are all different — Azure gives you four doors instead of one.

🚪 Meet the four doors

📦 Blob (Containers)

a huge folder of files, each with a web address✅ Pick it when
  • Photos, videos, PDFs, backups, log files
  • Files that users download or your code reads by name
  • Data for analytics (a "data lake")
  • A static website
⛔ Look elsewhere when
  • You need a drive that machines "mount" like a normal folder → Files
  • You need to search rows with queries → a database

📁 Azure Files (File shares)

a shared drive in the cloud — SMB or NFS✅ Pick it when
  • An older app that expects a file path like \\server\share
  • Many VMs or containers must see the same folder
  • Moving an on-premises file server to Azure
⛔ Look elsewhere when
  • Millions of files served to web users → Blob
  • Plain app data with no need for a mounted drive → Blob

📬 Queues

a to-do list for background work✅ Pick it when
  • Hand simple jobs from one part of your app to another
  • A very large backlog, kept cheap
  • You do not need strict order or advanced features
⛔ Look elsewhere when
  • You need ordering, retries with a "bad message" bin, or many subscribers → Service Bus (see Messaging)
  • Messages bigger than about 64 KB → send a link to a blob instead

🗒️ Tables

a simple, cheap key → value store✅ Pick it when
  • Lots of small records looked up by a key
  • Device settings, audit entries, simple lookups
  • Cheap and simple matters more than rich queries
⛔ Look elsewhere when
  • You need joins, transactions or rich queries → a database
  • You need worldwide low latency → Azure Cosmos DB (it even has a Table API)
🧭 When to pick what
🎬 Real-world scenarios
📸
Photo app

Users upload profile pictures. Thousands of small files, each shown by its web address.

→ Blob
🏢
Old internal app

A company app expects a Z:\reports drive on three servers. You cannot change the code.

→ Azure Files
📧
Welcome emails

The website should answer fast and send the email later, in the background.

→ Queue (or Service Bus if retries matter)
🌡️
10,000 devices

Each device has a tiny settings record, always looked up by deviceId.

→ Table (Cosmos DB if it must go global)
🧾

PDFs that are almost never opened again, but must be kept.

→ Blob + a cheaper access tier
🎬
Training videos

Big files streamed to customers all over the world.

→ Blob

🔑 Who is allowed to open the doors?
✅ Microsoft Entra ID + RBAC

Best choice. Your app or user signs in as an identity, and roles say what it may do. No secret to leak.

⏱️ SAS link

A temporary link with limited rights ("upload this one file in the next 10 minutes"). Great for browsers and partners.

⚠️ Account key

Opens everything in the account, like a master key. Avoid it in apps; prefer the two options above.

▾ Go one level deeper (60 seconds)

Account types. For most work you create a general-purpose v2 storage account — the standard type that includes Blob, Files, Queues and Tables. Premium account types exist when you need very low latency for one specific job (block blobs, file shares or page blobs).

Data Lake Storage Gen2 is not a separate product: it is the Blob service with the hierarchical namespace switched on. That gives real folders (rename a folder in one step) and file-style permissions — handy for big analytics jobs.

Each service has its own endpoint, like myaccount.blob.core.windows.net. That is why a storage account is "four doors": the same account name, four different addresses.

🔥 Interview recall
  • A storage account holds four services: Blob (Containers), Files (File shares), Queues and Tables.
  • Blob = files as objects. Files = a mounted shared drive (SMB/NFS). Queue = simple background jobs. Table = simple key → value records.
  • It exists because compute is disposable — data needs a home outside your servers.
  • Redundancy: LRS (1 datacenter) → ZRS (3 zones) → GRS/GZRS (adds a paired region, copied asynchronously). RA- versions allow reading the second region.
  • Prefer Entra ID + RBAC; use SAS for temporary limited access; avoid account keys.
🎤 Say this in an interview
"A storage account is Azure's home for non-database data. It gives you four services under one account: Blob for objects like images and backups, Files for SMB/NFS shared drives, Queues for simple message passing and Tables for simple key-value data. I choose by the data's shape and how it is read, pick a redundancy level — LRS, ZRS, GRS or GZRS — to match how much failure I must survive, and I use Entra ID with RBAC for access instead of account keys."
⚠️ Common trap

Redundancy is not a backup. If someone deletes or overwrites a file, every copy is deleted or overwritten too — all those copies are kept in sync. To get a file back you need extra protection such as soft delete, versioning or a real backup.

A second trap: using Queues or Tables for more than they are built for. If you start needing ordering, retries and subscribers, you wanted Service Bus; if you start needing joins and rich queries, you wanted a database.

📦 Blob

An object (file) with a web address, in a container. Your code reads it by URL or SDK.

vs.
📁 Azure Files

A real shared drive that machines mount and use like a normal folder, with SMB or NFS.

▾ 💻 Tiny illustrative example 
from azure.identity import DefaultAzureCredential
from azure.storage.blob import BlobServiceClient

# sign in as the app's own identity — no account key in the code
service = BlobServiceClient("https://myaccount.blob.core.windows.net", credential=DefaultAzureCredential())
blob = service.get_blob_client(container="photos", blob="cat.jpg")

with open("cat.jpg", "rb") as f:
    blob.upload_blob(f, overwrite=True)   # the file now lives at .../photos/cat.jpg

Illustrative shape only — a real app adds error handling, and the identity needs a role (such as Storage Blob Data Contributor) on the account.
