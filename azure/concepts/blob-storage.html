Deep dive · Storage · 📦 Blob

A blob is a file with a web address — and the colder it gets, the cheaper it is to keep.

Blob Storage is where most apps keep their files. Learn how a blob is addressed, which of the three blob types to pick, how a browser can upload safely, and how access tiers turn "old files" into savings.

❓ "When would you use Azure Blob Storage, and how do access tiers and SAS links work?"
👁 See it first
🎯 A blob is a file with a web address, kept in a container, inside a storage account — and the cooler it gets, the cheaper it is to keep.
📖 Why did this need to exist?

On the Storage page you met the four doors. Blob is the one almost every app opens first, because almost every app has files: photos, PDFs, videos, backups, logs.

A normal disk cannot do this job well. It fills up and you must resize it, it belongs to one machine, and it cannot hand a file to a user on the other side of the world. Object storage fixes all three: there is no disk to manage, the amount of data can grow very large, and every object gets its own web address that any permitted app can use.

🧱 The three kinds of blob
🟦 Block blob

The normal one. Photos, documents, videos, backups. Big files are uploaded in pieces ("blocks") and joined. Choose this unless you have a reason not to.

➕ Append blob

You can only add to the end. Perfect for log files: write a new line, never change an old one.

💽 Page blob

Fast random reading and writing in the middle of the file. This is what virtual-machine disks use under the hood.

🎬 Real scenario: users upload profile photos
Why this design? Your API stays small and fast because the file bytes skip it. The SAS link is short-lived and limited, so a leaked link stops working soon. And the thumbnail step is event-driven: nothing polls, the event simply arrives (you will meet Event Grid properly in the Messaging concept).

⚖️ Strengths and limits

Blob Storage at a glance

✅ Strengths
  • Very low cost per GB, and cheaper still in cooler tiers
  • Grows to very large amounts of data without disks to manage
  • Redundancy from LRS up to geo-zone-redundant (see Storage)
  • Publishes events (like BlobCreated) so other services can react
  • Works with Entra ID, RBAC and short-lived SAS links
⚠️ Watch out for
  • It stores files, it does not search inside them — use a database or analytics tool for that
  • No true folders unless you turn on the hierarchical namespace
  • Each read/write operation is billed, and Archive reads are slow
  • A public container or a leaked SAS link exposes data — keep public access off unless you truly need it
  • Not a mounted drive — for that, use Azure Files
🔐 Keep it locked down — quick checklist
1 · Private by default

Keep anonymous public access off unless the files are meant for everyone.

2 · Entra ID first

Give your app an identity and an RBAC role. If you need a SAS, prefer a user delegation SAS (signed with Entra credentials, not the account key).

3 · Short expiry

Make SAS links last minutes, not months, and give them only the permission needed.

4 · Undo button

Turn on soft delete and versioning so a mistake can be rolled back. Use immutable (write-once) storage for rules that forbid changes.

🔥 Interview recall
  • URL = https://<account>.blob.core.windows.net/<container>/<blob name>. Account → containers → blobs.
  • Three blob types: block (normal files), append (logs), page (VM disks / random access).
  • Tiers: Hot → Cool (30 days) → Cold (90 days) → Archive (180 days, offline). Cooler = cheaper to store, dearer to read.
  • Let browsers upload with a short-lived SAS link so files skip your API. Prefer user delegation SAS.
  • A lifecycle management rule moves or deletes blobs automatically by age.
  • Data Lake Storage Gen2 = Blob with the hierarchical namespace turned on.
🎤 Say this in an interview
"Blob Storage is Azure's object store. Data lives as blobs in containers inside a storage account, addressed by URL. I use block blobs for ordinary files, append blobs for logs and page blobs for disks. To control cost I use access tiers — Hot, Cool, Cold and Archive — and a lifecycle policy to move data down automatically. For uploads from browsers I issue a short-lived user delegation SAS, so files go straight to storage."
⚠️ Common trap

Folders in Blob are just part of the name. 2025/trip.jpg looks like a file in a folder, but without the hierarchical namespace there are no real folders — "renaming a folder" means copying every blob. If you need real folders, rename operations or file-style permissions, enable the hierarchical namespace (Data Lake Storage Gen2) when you create the account.

Second trap: a SAS link is a password in URL form. Anyone who has it can use it until it expires — so keep the lifetime short and the permission small.

📦 Blob Storage (flat)

A flat list of blobs per container. The slash in a name is only a naming convention.

▾ 💻 Tiny illustrative example — make a short-lived upload link 
from datetime import datetime, timedelta, timezone
from azure.identity import DefaultAzureCredential
from azure.storage.blob import BlobServiceClient, BlobSasPermissions, generate_blob_sas

service = BlobServiceClient("https://myaccount.blob.core.windows.net", credential=DefaultAzureCredential())
now = datetime.now(timezone.utc)
key = service.get_user_delegation_key(now, now + timedelta(minutes=15))   # signed with Entra, not the account key

sas = generate_blob_sas(account_name="myaccount", container_name="photos", blob_name="u42/cat.jpg",
                        user_delegation_key=key, permission=BlobSasPermissions(create=True, write=True),
                        expiry=now + timedelta(minutes=10))
upload_url = f"https://myaccount.blob.core.windows.net/photos/u42/cat.jpg?{sas}"   # hand this to the browser

Illustrative shape only — real code also validates the user, picks a safe blob name and handles errors. Check the current SDK docs for exact signatures.
