Infrastructure as code turns your environment into files you can review, repeat and roll back.

Bicep, Terraform and ARM templates: why clicking resources together stops working, how a preview protects you, and which tool to pick.

❓ "What is infrastructure as code, and would you use Bicep or Terraform on Azure?"
👁 See it first
🎯 Infrastructure as code means your environment is described in files that you can review, repeat and roll back — instead of being a pile of clicks nobody remembers.
▶️ Watch it happen: files instead of clicks
📖 Why did this need to exist?

By now the system is dozens of resources: networks, apps, databases, caches, queues, functions. Someone clicked them together in the portal. Ask three questions: Can we build the same thing again? (a second environment, or after a disaster) Who changed what, and why? Does production really match staging? With clicking, the honest answer to all three is "not sure".

Infrastructure as code (IaC) answers all three. You write what you want — declaratively: "there should be a storage account like this" — and a tool makes Azure match. The file is the record, it goes through review like code, and it is the plan for the disaster-recovery day from the Scaling concept.

🧰 Which tool?

💪 Bicep

Azure-native, declarative✅ Pick it when
  • You work on Azure only
  • Microsoft's own language for Azure resources
  • No state file — Azure itself tracks deployments
  • The default tool for the Azure Developer CLI
⛔ Look elsewhere when
  • You also manage other clouds or non-Azure services in the same code

🌐 Terraform

multi-provider, with a state file✅ Pick it when
  • One tool across Azure, other clouds and services
  • Plan and apply with a recorded state
⛔ Look elsewhere when
  • You want Azure to hold the record — Terraform keeps its own state file that you must store and protect

📜 ARM templates (JSON)

what Azure Resource Manager runs✅ Pick it when
  • You already have working templates
  • Bicep files are turned into this format when deployed
⛔ Look elsewhere when
  • Writing new ones by hand — Bicep is shorter and easier to read

▾ Go one level deeper (60 seconds) — modules, parameters and drift

Parameters let one file build many environments (dev, test, prod) with different names and sizes. Modules package a pattern so you reuse it instead of copying it. Azure Verified Modules are ready-made, versioned modules from Microsoft for both Bicep and Terraform, aligned with the Well-Architected Framework.

Idempotent: deploying the same Bicep file twice leaves the existing resources as they are — the result is the same, not a duplicate.

Drift is when the real environment stops matching the file, usually because someone changed something in the portal. Treat the portal as read-only for anything the code owns, and let the pipeline (next concept) do the deploying.

Scopes. A deployment can target a resource group, a subscription, a management group or the tenant — matching the hierarchy from concept 1.

🔥 Interview recall
  • IaC = the environment described in reviewed, versioned files; repeatable, reviewable, recoverable.
  • Bicep: declarative, Azure-native, no state file. Terraform: multi-provider, keeps a state file. ARM templates: the JSON underneath.
  • what-if previews changes (create, modify, delete) without changing anything.
  • Incremental mode (default) leaves extra resources alone; complete mode deletes resources not in the file — what-if first.
  • Drift = reality no longer matches the file; avoid portal edits for code-managed resources.
🎤 Say this in an interview
"I define environments as code so they are repeatable, reviewable and recoverable. On Azure only I use Bicep, which is declarative and needs no state file; if I must manage several providers I use Terraform and protect its state. Before deploying I run what-if, I use incremental mode by default, and I keep the portal read-only for anything the code owns so there is no drift."
⚠️ Common trap

Complete mode with a missing resource. It will delete whatever is not in the file. Always preview with what-if, and use complete mode on purpose, not by habit.

Second trap: leaving the Terraform state file somewhere unprotected. It is the tool's record of your infrastructure and can contain sensitive data; store it remotely, with access limited and backups on.

▾ 💻 Tiny illustrative example 
// a storage account in Bicep — declare what you want, not the steps to get it
param location string = resourceGroup().location

resource sa 'Microsoft.Storage/storageAccounts@2023-05-01' = {
  name: 'stshopprod001'
  location: location
  sku: { name: 'Standard_LRS' }
  kind: 'StorageV2'
}

Illustrative only — the API version, the name and the SKU are examples; storage account names must be globally unique, and real files add tags, network rules and more.
