Pipelines, deployment slots, swaps, traffic splits and passwordless sign-in: how to ship to Azure safely and roll back fast.

❓ "How would you set up CI/CD to Azure with zero downtime and a safe rollback?"
👁 See it first
🎯 CI/CD means every change is built, tested and released by the same automatic steps — so shipping is routine, and undoing a bad release is one move.
📖 Why did this need to exist?

The environment is code now. The app is code too. If a person still copies files onto a server by hand, every release is different, every release is slow, and every release is a little scary — so teams release rarely, in big batches, which makes each one riskier.

CI (continuous integration) builds and tests every change automatically. CD (continuous delivery or deployment) takes the tested package and ships it by a repeatable path. The second half of the skill is how it goes live: all at once, to a few users first, or beside the old version with a quick way back.

pipelines in Azure DevOps✅ Pick it when
  • You use Azure DevOps boards and repos

⛔ Look elsewhere when
  • You are fully on GitHub and want one place

🚦 Deployment slots

a staging copy of an App Service app✅ Pick it when
  • Zero-downtime releases: warm up, then swap
  • Fast rollback by swapping back
  • Available on Standard, Premium and Isolated tiers
⛔ Look elsewhere when
  • Free and basic tiers do not have slots

🔐 OIDC sign-in

workload identity federation✅ Pick it when
  • The pipeline needs to deploy without a stored secret
  • Microsoft recommends it over passwords or publish profiles
⛔ Look elsewhere when
  • Nothing — treat stored deployment passwords as the thing to avoid

▾ Go one level deeper (60 seconds) — details that bite

Build once, deploy the same package everywhere. If each environment builds its own copy, "it worked in staging" proves little.

Slot settings. Some settings (such as connection strings marked "slot setting") stay with the slot and do not move during a swap. Mark them deliberately, or the swapped app can end up pointing at the wrong database.

Slots share the plan. A staging slot runs on the same App Service plan as production, so it uses the same capacity; scaling the plan affects all slots.

Preview the swap. App Service can apply the target slot's settings to the source slot before the swap completes, so you can check behaviour first and then complete or cancel.

Other services. Containers and Functions have their own release features (revisions, slots) — the ideas are the same: ship beside, check, switch, and keep a way back.

🔥 Interview recall
  • CI builds and tests every change automatically; CD ships the tested package by a repeatable path.
  • Deployment slots (Standard tier and above): deploy to staging, warm up, swap into production; swap again to roll back.
  • Traffic routing can send a percentage of requests to a slot first — a canary-style test in production.
  • Prefer OIDC / workload identity federation to stored passwords for pipeline sign-in.
  • Build once and deploy the same package everywhere; mind slot-specific settings.
🎤 Say this in an interview
"I use a pipeline in GitHub Actions or Azure Pipelines: every change is built and tested, then deployed to a staging slot, warmed up, and swapped into production — swapping back is my rollback. For risky changes I route a small share of traffic to the slot first. The pipeline signs in with OpenID Connect so there is no stored secret, and it deploys the Bicep file and the app together."
⚠️ Common trap

Deploying straight to production. Microsoft's guidance is to deploy to a non-production slot and swap, so you can validate first and roll back by swapping again.

Second trap: a stored deployment password. It is a long-lived secret that leaks through logs, forks and screenshots. Use short-lived tokens through OIDC.

🔁 Swap (blue-green)

Everyone moves to the new version at the same moment, after it has been warmed up and checked.

🐤 Traffic split (canary)

▾ 💻 Tiny illustrative example 
# deploy the new version to the staging slot, then swap it into production
az webapp deploy --resource-group rg-shop-prod --name app-shop --slot staging --src-path app.zip
az webapp deployment slot swap --resource-group rg-shop-prod --name app-shop --slot staging --target-slot production

Illustrative shape only — a real pipeline builds and tests first, and runs these steps with an OIDC sign-in; flags and options can change.
