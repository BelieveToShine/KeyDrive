Security is layers, not a wall — and governance is guardrails that hold for every resource, even when nobody is watching.

Zero Trust, defense in depth, Azure Policy, Defender for Cloud, WAF and private access: how an architect applies protection consistently across everything.

❓ "How would you secure and govern an Azure environment at scale?"
👁 See it first
🎯 Security is layers, not a wall; governance is guardrails that apply to every resource, so the rules hold even when nobody is watching.
📖 Why did this need to exist?

Secrets were one slice. But look at the whole system now: dozens of resources, many people deploying, pipelines creating things at night. What stops someone creating a storage account open to the internet? What shows you that a server is under attack? What protects the web app from common web attacks?

The answer is not one product. Microsoft's Zero Trust model says: verify explicitly (check identity, device and location every time), use least privilege (just enough access, just in time), and assume breach (limit the damage with segmentation, encryption and monitoring). Azure gives you tools for each — and governance, so the guardrails apply to everything, consistently.

🧰 The tools

📜 Azure Policy

guardrails for every resource✅ Pick it when
  • Stop or flag resources that break your rules
  • Apply rules across a whole management group or subscription
  • Prove compliance with a report
⛔ Look elsewhere when
  • Deciding who may do things — that is RBAC (concept 3)

🛡️ Defender for Cloud

see your posture, detect threats✅ Pick it when
  • A secure score and recommendations across subscriptions
  • Threat protection plans for servers, containers, storage, databases
  • A free foundational posture tier, with a paid tier for more
⛔ Look elsewhere when
  • You expect it to fix everything by itself — recommendations still need action

🧱 Web Application Firewall

block common web attacks✅ Pick it when
  • Public web apps and APIs
  • On Application Gateway (regional) or Front Door (edge)
  • Rules based on OWASP, custom rules, rate limiting
⛔ Look elsewhere when
  • Volumetric network floods — pair it with DDoS Protection

🔒 Private access

keep services off the internet✅ Pick it when
  • Databases, storage and vaults that only your apps need
  • Private Endpoints and NSGs from concept 4
  • Shrink what can be attacked
⛔ Look elsewhere when
  • Treating the network as the only defense — identity is still the first line

▾ Go one level deeper (60 seconds) — rolling out guardrails safely

Roll out in stages. A deny rule applied everywhere on day one can break deployments. Start with audit, read the compliance report, fix the real problems, then switch to deny. Microsoft recommends exactly this order.

Evaluation order. Deny is evaluated before audit, so an undesired resource is not logged twice.

Remediation needs identity. Modify and DeployIfNotExists run with a managed identity, which must have the minimum role it needs to make the change. With an initiative (a group of policies), remediation tasks are created per policy.

The WAF and DDoS split. A WAF understands web requests (layer 7) but is not built for volumetric network floods. Microsoft recommends using DDoS Protection and a WAF together for web workloads. On Front Door, only the Premium tier offers managed rule sets; Standard supports custom rules.

Posture vs protection. Defender for Cloud has two jobs: posture management (find weak settings, give a score) and workload protection (detect attacks on servers, containers, databases). Resource locks can also protect critical resources from accidental deletion.

🔥 Interview recall
  • Zero Trust: verify explicitly, least privilege, assume breach. Security is layers: identity, network, compute/apps, data.
  • RBAC = who may do what; Azure Policy = what is allowed to exist. Policy effects: deny, audit, modify, deployIfNotExists.
  • Start a new policy with audit, then enforce. Policy is inherited down the hierarchy; assign guardrails at the management group.
  • Defender for Cloud = posture (secure score, recommendations) plus workload protection plans.
  • WAF blocks web-layer attacks (OWASP-based rules); DDoS Protection handles volumetric floods — use both for web workloads.
🎤 Say this in an interview
"I think of security as layers — identity first, then network, compute and data — guided by Zero Trust: verify explicitly, least privilege, assume breach. For governance I use Azure Policy at the management group: audit first, then deny, with modify and deployIfNotExists to fix gaps and a remediation task for existing resources. Defender for Cloud gives posture and threat detection, and a WAF with DDoS Protection guards public web apps."
⚠️ Common trap

Assigning a deny policy everywhere on day one. It can block legitimate deployments and halt teams. Audit first, fix, then enforce.

Second trap: trusting the network as the only defense. A private network does not help if a stolen identity can reach everything. Identity is the first line of defense; the network supports it.

🪪 RBAC

Controls who can perform actions. Attached to people and identities.

📜 Azure Policy

Controls what resources may look like. Applies to the resource, no matter who creates it.

▾ 💻 Tiny illustrative example 
# assign a built-in policy at a management group, in audit mode first
az policy assignment create --name audit-allowed-locations \
    --policy <built-in-policy-id> --scope /providers/Microsoft.Management/managementGroups/<mg-id> \
    --params '{ "effect": { "value": "Audit" } }'

Illustrative shape only — the policy ID and parameter names depend on the built-in policy you choose, and the flags can change.
