🎯 Keep secrets out of code and out of pipelines: ask for them at run time from a guarded place, using the app's own identity — or avoid having a secret at all.
▶️ Watch it happen: ask for the secret at run time
📖 Why did this need to exist?

The last concept built a pipeline that deploys without a stored password. But the app itself still needs things: a database connection string, an API key for a payment provider, a certificate, and plain settings like "which environment is this?" or "is the new checkout switched on?".

The classic leak is putting those in code or in a pipeline variable. Both get copied, logged and shared. The fix has two halves. Secrets (things that must stay hidden) go to a vault with access control, audit and rotation. Settings (things that just change) go to a configuration store, so you can change them without redeploying.

🧰 The pieces

🪪 Managed identity

no stored secret at all✅ Pick it when
  • The target service accepts Entra ID tokens
  • Microsoft recommends it over shared keys, for Azure workloads
  • Nothing to store, rotate or leak
⛔ Look elsewhere when
  • The other side only understands passwords or keys → get them from Key Vault

🔑 Azure Key Vault

secrets, keys and certificates✅ Pick it when
  • Passwords, API keys, connection strings, certificates
  • Audited, access-controlled, soft-delete and purge protection
  • Rotation, with the app always reading the latest version
⛔ Look elsewhere when
  • Plain settings and feature flags — App Configuration fits them better

⚙️ Azure App Configuration

settings and feature flags✅ Pick it when
  • Settings shared by many apps and environments
  • Feature flags to release a feature without a deployment
  • It can hold a pointer to a Key Vault secret
⛔ Look elsewhere when
  • Anything that is a secret itself — keep that in Key Vault, and reference it

🔗 Key Vault references

a setting that points to a secret✅ Pick it when
  • App Service and App Configuration can resolve a secret from Key Vault at run time
  • The app never sees the vault wiring
⛔ Look elsewhere when
  • The app's identity has no access to the vault — the reference will not resolve

▾ Go one level deeper (60 seconds) — rotation, recovery and access models

Rotation. Secrets in memory or config files stay exposed for the whole life of the app, so rotate them regularly. For zero downtime, use two credentials and switch between them; Key Vault stores each new value as a new version. Apps should read the latest version and refresh any cached value when a secret rotates.

Protect the vault itself. Soft delete keeps deleted vaults and items recoverable for a retention period. Purge protection blocks permanent deletion until that period ends, and once on it cannot be switched off by anyone.

Access. Use Azure RBAC for the data plane (built-in roles such as Key Vault Secrets User). Older vaults may still use access policies. Two permission questions exist: who can manage the vault, and who can read its contents.

Storage keys. Microsoft prefers Entra ID with a managed identity over shared account keys, and where rules allow you can switch shared-key access off, which removes key rotation altogether.

App Configuration tip. Watch one "sentinel" key and refresh everything only when it changes, instead of polling every key.

🔥 Interview recall
  • Best to worst: no secret (managed identity) → Key Vault → config file → in the code.
  • Key Vault = secrets, keys, certificates, with access control, audit, soft delete, purge protection. App Configuration = settings and feature flags, changeable without redeploy.
  • App Configuration can hold a Key Vault reference — a pointer, not the secret.
  • Read the latest secret version and refresh caches on rotation; use two credentials for zero-downtime rotation.
  • Use RBAC roles (for example Key Vault Secrets User, App Configuration Data Reader) — least privilege.
🎤 Say this in an interview
"I avoid secrets where I can: managed identity for anything that accepts Entra ID. Where a secret is unavoidable it lives in Key Vault, with RBAC, soft delete and purge protection, and the app reads the latest version so rotation does not break it. Plain settings and feature flags go to App Configuration so I can change them without redeploying, and it can reference Key Vault secrets instead of storing them. Nothing sensitive goes in code or pipeline variables."
⚠️ Common trap

Putting the secret in the pipeline variable "just for now". Variables are copied into logs, forks and screenshots. Use OIDC for the pipeline and managed identity or Key Vault for the app.

Second trap: using Key Vault but never rotating. A vault protects where a secret lives, not how long it lives. Without rotation, one leaked secret works forever.

▾ 💻 Tiny illustrative example 
# create a vault, then let the app's managed identity read secrets (RBAC)
az keyvault create --name kv-shop-prod --resource-group rg-shop-prod --enable-rbac-authorization true
az role assignment create --assignee <app-identity-id> \
    --role "Key Vault Secrets User" --scope <vault-resource-id>

Illustrative shape only — vault names are globally unique, real setups also enable purge protection and network rules, and flags change.
