Deep dive · Databases · ⚖️ Choosing

Cosmos DB and Azure SQL are both great — they answer different questions.

Choosing between them is one of the most common architecture questions. Here is a plain-English comparison with pictures, strengths, weaknesses and real examples — so you can decide in minutes, not meetings.

❓ "When would you choose Azure Cosmos DB over Azure SQL Database, and what are the trade-offs?"
👁 See it first
🎯 Azure SQL keeps data correct by relating tables. Cosmos DB keeps data fast by storing things together and spreading them out. Neither is "better" — they answer different questions.
▶️ Watch it happen: correct versus fast and spread
📖 Why did this need to exist?

The Databases page gave you the map. This page exists because people still mix these two up — both can store "an order", both are fully managed, and both are popular. The real difference is what each one is built to be good at.

Azure SQL is built for correctness across related data: strict tables, relationships and transactions. Cosmos DB is built for speed and scale for access patterns you know in advance: flexible items, spread over partitions and regions. If you know which one your problem looks like, the choice is easy. This page shows you how to tell.

⚡ The quick comparison
Azure SQL (relational)Azure Cosmos DB (NoSQL)
Data modelTables, rows and columnsJSON items inside containers
RelationshipsForeign keys and joins across tablesEmbed related data in the item, or link by id. A JOIN works only inside one item
TransactionsAll-or-nothing across many tablesAll-or-nothing inside one partition key (transactional batch)
SchemaFixed. Changes need a migrationFlexible. Each item can look different
GrowingMostly a bigger machine, plus readable copiesSpread out across partitions
WorldwideCopies in other regions for reading and failover; one writable primaryReplicate to many regions; can be set up to accept writes in more than one
QueriesRich ad-hoc SQL: joins, grouping, reportsFast when the query includes the partition key. Queries across partitions cost more
You pay forCompute (vCores or DTUs) and storage. Serverless can pause when idleRequest Units per second (set, autoscaled, or pay-per-use serverless) and storage. Each extra region adds cost
Think of it asA smart system with strict rulesA very fast filing cabinet sorted by one label (the key)
⚖️ Strengths and watch-outs

🟦 Azure SQL

✅ Strengths
  • Relationships and constraints keep data correct
  • Powerful SQL for reports and questions nobody planned for
  • All-or-nothing transactions across many tables
  • Mature tools, and many people already know T-SQL
  • Managed backups and high availability; serverless and Hyperscale options
⚠️ Watch out for
  • Writes mostly scale by using a bigger machine
  • One writable primary — worldwide multi-writer is not built in
  • Schema changes need planning and migrations
  • Very high worldwide traffic gets expensive and complex

🌍 Cosmos DB

✅ Strengths
  • Designed for single-digit-millisecond reads and writes
  • Scales out by partition key
  • Replicates to many regions, with multi-region writes available
  • Flexible items — the schema can change freely
  • Indexes all properties by default
  • Five consistency levels let you trade freshness for speed
⚠️ Watch out for
  • The partition key is a big early decision — hard to change later
  • No foreign keys; a JOIN works only inside one item
  • Transactions stay inside one partition key
  • Cost is measured in Request Units — an expensive query burns many
  • Cross-partition queries fan out and cost more
  • You model the data around your queries, which is a new habit
🔑 The partition key — the one decision that matters
Rule of thumb: pick a key that (1) has many different values, (2) shows up in most of your queries, and (3) spreads reads and writes evenly. And remember the unit of cost: a Request Unit (RU) is Cosmos DB's currency for work — reading one small item by its id and partition key is the cheapest thing you can ask for.

🤝 You do not have to pick one — use both
✅ Decide in 30 seconds

🟦 Choose Azure SQL when…

correctness across related data is the job✅ Pick it when
  • Your data is naturally tables that relate to each other
  • You need all-or-nothing transactions across several tables
  • People will ask new questions you cannot predict (reports, analytics)
  • Your team already knows SQL Server / T-SQL
⛔ Look elsewhere when
  • You need fast writes in many regions at once
  • Your data shape changes every week

🌍 Choose Cosmos DB when…

speed and scale for known access patterns is the job✅ Pick it when
  • You can name the main queries up front
  • Users are spread across the world and need low latency
  • Items vary in shape (a catalog, profiles, events)
  • Traffic is huge or unpredictable and must scale out
⛔ Look elsewhere when
  • You need many joins between lots of different entities
  • You cannot pick a good partition key
  • Strict multi-table transactions are the core of the app

🔥 Interview recall
  • Azure SQL = related tables, joins, multi-table transactions; Cosmos DB = JSON items, spread by partition key, fast at scale.
  • Cosmos DB: choose a partition key with many values that appears in most queries. A bad key creates a hot partition.
  • A JOIN in Cosmos DB works only inside one item; transactions stay inside one partition key.
  • Cost: Azure SQL = compute + storage. Cosmos DB = Request Units + storage (+ each extra region).
  • Cosmos DB has five consistency levels — Strong, Bounded staleness, Session (default), Consistent prefix, Eventual.
  • Using both together is normal (polyglot persistence).
🎤 Say this in an interview
"Azure SQL is my default when data is relational and correctness across tables matters — it gives me joins, constraints and transactions, and scales mostly up with read replicas. Cosmos DB is for known access patterns at global scale: flexible JSON items, partitioned by key, replicated across regions, with tunable consistency and cost measured in Request Units. The partition key is the critical design choice. Many real systems use both — SQL for orders and payments, Cosmos for catalog and sessions."
⚠️ Common trap

Cosmos DB is not "SQL Server with JSON". If you design its data like a relational database — many small items that you JOIN together — you will fight it. Model the data around the questions you ask.

The opposite trap: choosing Azure SQL "because we know it" when the real need is writes in many regions at once, or choosing Cosmos DB "because it sounds modern" when the real need is reports across related tables.

🔑 Primary key (SQL)

Uniquely identifies a row in one table. The database enforces it.

vs.
🔑 Partition key (Cosmos DB)

Decides which partition stores the item. It is about where data lives and how load spreads, not only about uniqueness.

▾ 💻 Tiny illustrative examples 
-- Azure SQL: relationships are enforced by the database
CREATE TABLE Orders (
  Id INT PRIMARY KEY,
  CustomerId INT NOT NULL REFERENCES Customers(Id)   -- a foreign key
);

# Cosmos DB (Python SDK): the partition key is chosen when the container is created
container = database.create_container_if_not_exists(
    id="orders", partition_key=PartitionKey(path="/customerId"))

Illustrative shapes only — real setups also choose throughput (or serverless), indexing and security settings.
