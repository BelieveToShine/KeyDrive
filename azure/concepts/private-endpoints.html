Deep dive · Virtual Networks · 🔌 Private endpoints

A private endpoint puts an Azure service inside your own network, with a private IP address.

Azure services have public addresses by default. Learn how a private endpoint brings one into your network, how it differs from a service endpoint, and the DNS detail that decides whether it works.

❓ "What is the difference between a service endpoint and a private endpoint in Azure?"
👁 See it first
🎯 A private endpoint gives an Azure service a private IP address inside your own network — so your app reaches it privately, and you can close its public door.
▶️ Watch it happen: a private address for a service
📖 Why did this need to exist?

The Virtual Networks page showed how to keep your resources private. But your app also calls Azure services — storage, SQL, a vault — and those have public addresses by default. How do you let your network reach them without sending that traffic over the public internet, and without leaving them open to everyone?

Azure offers two answers. Service endpoints are the older, simpler one: the service keeps its public IP but can be told to trust your subnet. Private endpoints (built on Private Link) go further: the service gets a private IP in your network. Microsoft recommends Private Link.

🔎 The part that trips everybody up: DNS

🧭 Which one?

🧱 Service endpoint

the quick subnet-level allow-list✅ Pick it when
  • You only need "allow my subnet" on the service's firewall
  • You want zero DNS changes
⛔ Look elsewhere when
  • You need access from on-premises
  • You need to restrict to one specific instance
  • You want the service to have no public path

🔌 Private endpoint

a private IP for one resource✅ Pick it when
  • You want private-only access to a specific resource
  • On-premises users must reach it over VPN or ExpressRoute
  • You want to disable public access
⛔ Look elsewhere when
  • You cannot manage the DNS side
  • A simple subnet allow-list is enough

🔥 Interview recall
  • A private endpoint = a network interface with a private IP in your subnet, connecting you to one resource over Private Link.
  • A service endpoint keeps the service's public IP and only changes what the service sees (your subnet).
  • Service endpoints cover the whole service and do not work from on-premises; private endpoints are per resource and do.
  • DNS must resolve the service name to the private IP — usually with a private DNS zone.
  • A private endpoint lets you disable public access. Microsoft recommends Private Link.
🎤 Say this in an interview
"A private endpoint puts a network interface with a private IP from my subnet in front of a specific Azure resource, using Private Link, so traffic stays private and I can disable public access. A service endpoint keeps the service's public IP and just lets the service trust my subnet; it covers the whole service and does not help on-premises users. With private endpoints I must also fix DNS so the service name resolves to the private IP."
⚠️ Common trap

"I made a private endpoint but nothing changed." Almost always DNS. If the service name still resolves to the public IP, your app still goes over the public path. Check what the name resolves to from inside the network.

Second trap: creating a private endpoint does not close the public door. It adds a private one. Turn off public network access on the resource separately when you are ready.

🧱 Service endpoint

Public IP stays. The service learns the request came from your subnet. Whole-service scope.

vs.
🔌 Private endpoint

A private IP in your subnet for one resource. Works from on-premises. Needs DNS.

▾ 💻 Tiny illustrative example 
az network private-endpoint create --name pe-storage --resource-group rg-shop-prod \
    --vnet-name vnet-shop --subnet data \
    --private-connection-resource-id "<storage-account-resource-id>" \
    --group-id blob --connection-name conn-storage

Illustrative shape only — you also create a private DNS zone, link it to the network, and then disable public access on the storage account.
