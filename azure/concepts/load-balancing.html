Concept 8 of 19 · ⚙️ Handling load

A load balancer spreads traffic across healthy copies — and the real choice is how much of the request it should understand, and how far it should reach.

Azure has four tools for sending traffic where it should go: Load Balancer, Application Gateway, Front Door and Traffic Manager. Learn what each one sees, how far it reaches and when to pick it.

❓ "When would you use Azure Load Balancer, Application Gateway, Front Door or Traffic Manager?"
👁 See it first
🎯 A load balancer is a front door that spreads traffic across healthy copies of your app — and the real choice is how much of the request it should understand, and how far it should reach.
▶️ Watch it happen: spreading traffic over healthy copies
📖 Why did this need to exist?

The last concept ended with one app server and one database — a working instance. But one instance is a single point of failure, and it can only handle so much traffic. The obvious fix is more copies. The new problem: who decides which copy gets each request?

That is what a load balancer does. It sits in front, spreads requests across the copies, and stops sending traffic to a copy that is unhealthy (it checks with health probes). Azure has four tools for this, because "spread the traffic" means different things: spreading raw connections inside one region is not the same job as sending a visitor on another continent to the nearest healthy region.

🧰 The four tools

⚖️ Azure Load Balancer

layer 4 · TCP and UDP · one region✅ Pick it when
  • Any TCP or UDP traffic, not just web traffic
  • Spreading connections across VMs inside one region
  • Zone-redundant setups that survive a datacenter failure
⛔ Look elsewhere when
  • You need URL routing, TLS termination or a WAF → Application Gateway
  • You need to reach several regions

🚪 Application Gateway

layer 7 · web traffic · one region✅ Pick it when
  • HTTP and HTTPS apps in one region
  • Route by URL path or by host name (several sites behind one gateway)
  • Terminate TLS at the gateway; add a web application firewall (WAF)
⛔ Look elsewhere when
  • Non-web traffic → Load Balancer
  • Users in many regions → Front Door

🌍 Azure Front Door

layer 7 · web traffic · global✅ Pick it when
  • A web app with users in many places
  • Fast routing to the nearest healthy region, with failover
  • Edge features: a WAF and caching at the edge
⛔ Look elsewhere when
  • Non-HTTP traffic
  • A small app that lives in a single region

🧭 Azure Traffic Manager

DNS-based · global · any protocol✅ Pick it when
  • Non-web traffic that must be spread across regions
  • Routing by priority, weight, performance or geography
  • You want a simple DNS-level switch between regions
⛔ Look elsewhere when
  • You need fast failover — DNS answers can be cached by clients
  • You need to read or change web requests

▾ Go one level deeper (60 seconds) — health probes and what "unhealthy" means

Every tool above decides where to send traffic based on health. Load Balancer uses health probes (TCP, HTTP or HTTPS) and stops sending new connections to an instance that fails them. The others have their own health checks as well.

Make the health check honest. A probe that only checks "is the server on?" will say "healthy" while the database is down. A good health endpoint checks the things the app really needs.

Sticky sessions. Application Gateway can keep one user on one server with cookie-based affinity. It works, but it makes scaling and failover harder — storing session data outside the server (see the next concept, and Caching) is usually better.

SKUs and retirements. Use the current ones: Load Balancer Standard (the Basic SKU has been retired) and Application Gateway V2 (V1 has been retired). Front Door Standard and Premium are the current offerings.

🔥 Interview recall
  • Four tools, two questions: web traffic or not, one region or many.
  • Load Balancer = layer 4 (TCP/UDP), one region. It does not read web requests.
  • Application Gateway = layer 7 for one region: URL routing, TLS termination, optional WAF.
  • Front Door = layer 7, global, at the edge: WAF, caching, fast failover. Traffic Manager = DNS-based, any protocol, slower failover because of DNS caching.
  • Every one of them relies on health checks — a bad health check hides real failures.
🎤 Say this in an interview
"Azure has four ways to spread traffic. Load Balancer works at layer 4 for TCP and UDP inside a region. Application Gateway works at layer 7 for web traffic in one region, with URL routing, TLS termination and an optional WAF. Front Door is the global layer-7 entry point with WAF, caching and fast failover. Traffic Manager is DNS-based, works for any protocol, and fails over more slowly because clients cache DNS answers. I pick by two questions — web traffic or not, one region or many."
⚠️ Common trap

Do not choose Traffic Manager for a web app that needs fast failover. It only answers DNS, and clients may keep an old answer. For web traffic across regions, Front Door is usually the better fit.

Second trap: a load balancer is not a firewall and does not make a single database highly available. It spreads traffic to the copies that you have. If every copy depends on one database, that database is still your single point of failure.

⚖️ Load Balancer

Spreads connections (layer 4). Cannot see the URL. Works for any TCP or UDP traffic.

vs.
🚪 Application Gateway

Understands the web request (layer 7). Can route by path and host, and terminate TLS.

▾ 💻 Tiny illustrative example 
# create a Standard public Load Balancer — it needs a public IP, backends and a health probe to be useful
az network lb create --name lb-shop --resource-group rg-shop-prod \
    --sku Standard --public-ip-address pip-shop --frontend-ip-name fe \
    --backend-pool-name be

Illustrative shape only — real setups also add a health probe and load-balancing rules, and the flags can change.
