Deep dive · Scaling & Resilience · 🛟 Disaster recovery

Disaster recovery starts with two numbers — how much data you can lose, and how long you can be down.

RPO and RTO, the three multi-region patterns, and when to use Site Recovery, Azure Backup or a database's own replication.

❓ "What are RPO and RTO, and how would you design disaster recovery on Azure?"
👁 See it first
🎯 Disaster recovery starts with two questions — how much data can we lose, and how long can we be down? — and then buys exactly that much protection, no more.
📖 Why did this need to exist?

Autoscale and zones keep the app running through everyday failures. They do not help if someone deletes the wrong data, ransomware encrypts it, or a whole region is unavailable. For those days you need copies of the data and a plan to run somewhere else.

The trap is buying too much or too little. Protection that survives anything costs a fortune; protection that is too cheap fails on the day you need it. RPO and RTO turn that argument into numbers the business can agree to.

▾ Go one level deeper (60 seconds) — failover, failback and backups done well

Failover moves production traffic from a region that is unavailable to one that works. Failback moves it back when the first region has recovered. Plan both.

Keep backups separate from what they protect. Store them somewhere an attacker or a regional failure cannot reach with the same stroke — typically in another region. Azure Backup offers soft delete (you can recover deleted backups for a period you set), immutable vaults that block deleting recovery points, and Cross Region Restore.

Make the second region easy to build. Define your environment as code (a later concept in this journey) so you can create it quickly, and keep identity and settings in step between regions.

Test it. Microsoft recommends regular drills, because they find hidden dependencies on one region that nobody remembered.

🔥 Interview recall
  • RPO = how much data you can lose. RTO = how long you can be down. The business sets them.
  • Cold standby (cheapest, slowest) → warm standby (a balance) → active-active (fastest, costliest).
  • Site Recovery = replicate and fail over VMs. Backup = restore earlier copies after damage. Databases use their own replication.
  • A replica copies mistakes; a backup lets you go back in time. Keep backups separate, often in another region.
  • A plan that was never tested is a guess — run drills.
🎤 Say this in an interview
"I start from the recovery objectives: RPO is how much data we can lose, RTO is how long we can be down. Then I choose the cheapest pattern that meets them — cold standby, warm standby or active-active. For VMs I use Site Recovery to replicate and fail over, for damaged data I use Backup and keep it separate, and for databases I use their own replication. And I test the plan with drills."
⚠️ Common trap

A replica is not a backup. If someone deletes a table, replication copies the deletion within moments. You need a restore point from before the mistake.

Second trap: using Site Recovery for a database. Microsoft's guidance is to use the database's native replication instead.
