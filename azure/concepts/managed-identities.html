Deep dive · Identity & Access · 🪪 Managed identities

A managed identity lets an app prove who it is — with no password in your code.

Passwords in config files are a classic way for cloud accounts to be broken into. Learn how Azure gives your app its own identity, the difference between system-assigned and user-assigned, and the three steps to use one.

❓ "What is a managed identity, and when do you use system-assigned versus user-assigned?"
👁 See it first
🎯 A managed identity lets an Azure resource prove who it is without a password: Azure creates the identity, hands your code a token, and you control access with ordinary roles.
▶️ Watch it happen: no password needed
📖 Why did this need to exist?

On the Identity page, apps could be given roles through a service principal. But a service principal that signs in with a secret has the same old problem: a password that must be stored somewhere, kept safe and replaced before it expires. Passwords in config files are one of the most common ways cloud accounts get broken into.

A managed identity removes the secret from the picture. It is a special service principal that Azure creates and looks after for you, and it can only be used by Azure resources. Your code asks for a token, Azure provides it, and the identity can do only what the roles you assigned allow.

🔀 System-assigned or user-assigned?
🧭 Which one should I pick?

🔒 System-assigned

the simple one-to-one choice✅ Pick it when
  • One app needs its own access and nothing else uses it
  • You want the identity cleaned up automatically with the resource
  • The quickest way to start
⛔ Look elsewhere when
  • Several apps need exactly the same access → user-assigned
  • The resource is often deleted and re-created and you want to keep the role assignments → user-assigned

🤝 User-assigned

one identity, many resources✅ Pick it when
  • A group of resources should share the same permissions
  • You want to create the identity and its roles before the resource exists
  • The identity must outlive any single resource
⛔ Look elsewhere when
  • A single resource that needs a private identity → system-assigned is simpler
  • You do not want to remember to delete a leftover identity
🪜 Three steps to use one
1 · Turn it on

Enable the identity on the app (or create a user-assigned one and attach it).

2 · Give it a role

Assign an RBAC role to the identity, on the resource it needs — for example a Blob data role on the storage account. A new identity has no access by default.

3 · Let the library do the rest

In code, use the Azure Identity library. It asks for the token for you. For a user-assigned identity you also pass its client id.

🎬 Real-world scenarios
🌐
Web app reads blobs

The site shows files from Blob Storage and must not hold a password.

→ System-assigned + a Blob data role
⚙️
Three apps, same access

A web app, an API and a worker all read the same storage account.

→ One user-assigned identity
🔑
App reads secrets

The code needs a secret from a vault, and the vault should not need a secret to open.

→ Managed identity + vault access
🖥️
A VM calls Azure

A VM must list resources through Azure Resource Manager.

→ Managed identity with a role on that scope
🧰
Re-created every deploy

The app is rebuilt on each release but access must stay the same.

→ User-assigned (it survives)
🚫
Code on a laptop

A developer running locally has no managed identity.

→ Sign in with their own Entra account
🔥 Interview recall
  • A managed identity is a service principal that Azure manages for an Azure resource — no credentials in your code.
  • System-assigned: tied to one resource, deleted with it, not shareable. User-assigned: a separate resource, shareable, deleted by you.
  • It has no access until you assign RBAC roles. Code asks for a token (Azure Identity library); user-assigned needs the client id.
  • Use it for Azure-to-Azure calls; local development uses your own account.
🎤 Say this in an interview
"A managed identity gives an Azure resource an identity in Microsoft Entra ID without any secret to manage — Azure issues tokens to the code on request. System-assigned identities share the resource's lifecycle and cannot be shared; user-assigned identities are standalone resources that several resources can use. Either way, the identity starts with no access and I grant it least-privilege RBAC roles."
⚠️ Common trap

"Forbidden" right after enabling it is normal. Turning on a managed identity creates the identity, not its permissions. Until you assign a role at the right scope, every call fails with an authorization error.

Second trap: a managed identity only exists for Azure resources. Your laptop and an on-premises server do not have one — code that works in Azure may need a different sign-in locally.

🪪 Managed identity

Azure creates and looks after it. No secret to store or rotate. Only usable by Azure resources.

vs.
🤖 Service principal with a secret

You create it and keep its password or certificate safe, and renew it before it expires. Works anywhere, but carries a secret.

▾ 💻 Tiny illustrative example 
from azure.identity import DefaultAzureCredential
from azure.storage.blob import BlobServiceClient

# system-assigned identity: nothing extra to pass
credential = DefaultAzureCredential()

# user-assigned identity: say which one by its client id
# credential = DefaultAzureCredential(managed_identity_client_id="<client-id>")

service = BlobServiceClient("https://myaccount.blob.core.windows.net", credential=credential)

Illustrative shape only — the identity still needs a role such as Storage Blob Data Reader on the account.
