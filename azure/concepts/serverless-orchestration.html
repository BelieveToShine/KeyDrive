▶️ Watch it happen: work runs when the trigger fires
📖 Why did this need to exist?

Look at what the earlier concepts gave you: an app that scales and is fast. But not all work looks like a web app. A file arrives. A timer fires. An order is approved. Between those moments, nothing happens. Keeping a server running just to wait for them is paying for idle capacity.

Serverless flips that. You write a small unit of work, tell Azure what should start it, and Azure supplies the compute when it fires. When there is a lot to do it scales out; when there is nothing, it can scale to zero. The skill is picking the right tool for what kind of work it is: reacting, coding, connecting, or orchestrating many steps.

🧰 The four tools

📣 Event Grid

routes "something happened" events✅ Pick it when
  • React to changes without polling
  • One event, many interested handlers
  • Azure service and SaaS events
⛔ Look elsewhere when
  • You need strict order, transactions or duplicate detection → Service Bus

⚡ Azure Functions

small code, run on a trigger✅ Pick it when
  • Your own logic: transform data, call an API, run a job
  • HTTP, timer, queue, event and storage triggers
  • Unique data transformations and utility code
⛔ Look elsewhere when
  • Long, multi-step flows in plain functions — use Durable Functions

🔀 Logic Apps

workflows built in a designer✅ Pick it when
  • Connect many systems with prebuilt connectors
  • Business processes, approvals, notifications
  • Little or no code
⛔ Look elsewhere when
  • Heavy custom code or tight performance work → a Function

🎼 Durable Functions

code-based orchestration✅ Pick it when
  • Several steps in order, or in parallel then combined
  • Work that waits and must survive restarts
  • You prefer to write the flow as code
⛔ Look elsewhere when
  • A single quick action — a plain Function is enough

▾ Go one level deeper (60 seconds) — habits that keep serverless safe

Triggers and bindings. A Function starts from a trigger (a message, a timer, an HTTP call) and can read or write other services through bindings, so you write less plumbing code.

Cold start. When nothing is running and a trigger fires, the platform must start an instance first, which adds a delay. Plans differ: Flex Consumption can keep always-ready instances, Premium keeps pre-warmed workers, and Dedicated runs continuously. Pick based on how much delay the user can accept.

Be idempotent. Events and messages can arrive more than once, and retries happen. Design the work so doing it twice is safe.

Keep functions short and stateless. Anything that needs to remember something between steps belongs in a database, storage, or a Durable Functions orchestrator — not in the function's memory.

Use managed identity (concept 3) so a Function can reach storage, databases and other services without secrets in its settings.

🔥 Interview recall
  • Serverless = you supply the work and the trigger; Azure supplies compute only while it runs, and it can scale to zero.
  • Event Grid routes events. Functions = code-first. Logic Apps = designer-first with many connectors. Durable Functions = code-based orchestration that checkpoints progress.
  • Fan-out/fan-in = start activities in parallel then combine; function chaining = run steps in order.
  • Flex Consumption is the recommended serverless plan for new Functions apps; Premium keeps pre-warmed workers; Dedicated does not scale on events.
  • Need order, transactions or duplicate detection → Service Bus, not Event Grid.
🎤 Say this in an interview
"Serverless means I provide the code or workflow and a trigger, and Azure runs it only when needed. Event Grid routes events, Functions run my own code, Logic Apps connect systems with a designer, and Durable Functions orchestrate multi-step work in code with checkpoints. For new Functions apps I start with the Flex Consumption plan, and I make the work idempotent. When I need ordering or transactions I use Service Bus instead."
⚠️ Common trap

"Serverless" does not mean "no servers" — and it is not always the right tool. There are still servers; you just do not manage them. Long-running, steady, heavy work may fit a plan with always-on capacity better than one built for short bursts.

Second trap: using Event Grid where you need guarantees. Event Grid routes events; it does not give ordering, transactions or duplicate detection. When losing or reordering a message would hurt, use Service Bus.
