Deep dive · Messaging · 🌊 Event Hubs

Event Hubs is a giant, replayable log for huge streams of events — many readers, each at its own position.

When thousands of devices or users send millions of small events, you need a pipe built for volume and replay — not a mailbox for single jobs. Learn partitions, consumer groups, Capture and when Event Hubs is the right tool.

❓ "When would you choose Event Hubs over Service Bus, and what are partitions and consumer groups?"
👁 See it first
🎯 Event Hubs is a replayable log: events are appended, kept for a while, and every reader group keeps its own place in the stream.
▶️ Watch it happen: a replayable log
📖 Why did this need to exist?

Service Bus treats each message as a precious job and takes care of it one by one. That care costs throughput. Now imagine 10,000 sensors sending a reading every second, or every click on a busy website: millions of tiny events, where losing one is fine but keeping up is not — and several teams want to read the same data.

Event Hubs is built for that: very high volume in, many independent readers out, and the ability to replay what happened. It is a log, not a mailbox.

📬 vs 📜 Mailbox or log?
📖 The words you need
🏢 Namespace

The container that holds your event hubs, with one address and shared settings.

📜 Event hub

One named stream — for example "telemetry". It is split into partitions.

🧱 Partition

An ordered sequence of events. Order is kept inside a partition, not across them. More partitions = more parallel readers.

👥 Consumer group

An independent view of the whole stream. Analytics and alerts each use their own group, so they never disturb each other.

📍 Checkpoint

A reader's saved position, so after a restart it carries on where it stopped.

🗃️ Capture

Automatically saves the stream in batches to Blob Storage or Data Lake for long-term keeping.

🔌 Already using Kafka?
Event Hubs speaks the Apache Kafka protocol, so existing Kafka producers and consumers can usually point at an Event Hubs endpoint instead of running their own Kafka cluster. This is available from the Standard tier up.
🏷️ Which tier?
TierWhat it is forGood to know
BasicLow-cost entry for simple streamingNo Capture, no Kafka
StandardThe general-purpose choiceCapture, Kafka endpoint and geo-disaster-recovery are available
PremiumResource isolation and higher performanceFor demanding or sensitive workloads
DedicatedA single-tenant cluster for the very largest workloadsBiggest scale
Plan your partitions early. You choose the partition count when you create the event hub, and only the Premium and Dedicated tiers let you increase it later. Retention is a limited window that depends on the tier, so use Capture if you must keep data longer.

🔥 Interview recall
  • Event Hubs = a partitioned, replayable event log for high-volume streams.
  • Order is kept inside a partition, not across partitions. Same key → same partition.
  • Each consumer group has an independent view and its own checkpoint; many groups can read the same events.
  • Events are not deleted when read — they stay for the retention time. Capture saves them to Blob / Data Lake.
  • Event Hubs has a Kafka-protocol endpoint (Standard tier and above). Choose the partition count up front.
🎤 Say this in an interview
"Event Hubs is Azure's event-streaming service — a partitioned, append-only log built for very high throughput. Producers append events; each consumer group reads the whole stream independently with its own checkpoint, so events can be replayed or processed by several systems. Order is guaranteed within a partition. I use Capture to archive to Blob or Data Lake, and the Kafka endpoint to migrate Kafka workloads. For per-message reliability like orders and payments I would use Service Bus instead."
⚠️ Common trap

Reading does not delete. Unlike a queue, an event is still there after a reader has processed it — which is a feature (replay) but means you must track progress with checkpoints.

Second trap: expecting order across the whole event hub. Order is kept only inside a partition, so put events that must stay in order (one device, one customer) on the same partition with the same key.

📨 Service Bus

Broker: handles each message with care and removes it when done. Built for reliable jobs.

vs.
🌊 Event Hubs

Log: appends events, keeps them, lets many readers replay them. Built for volume.

▾ 💻 Tiny illustrative example — send a batch of events 
from azure.identity import DefaultAzureCredential
from azure.eventhub import EventHubProducerClient, EventData

producer = EventHubProducerClient("mynamespace.servicebus.windows.net",
                                  eventhub_name="telemetry", credential=DefaultAzureCredential())
with producer:
    batch = producer.create_batch()
    batch.add(EventData('{"deviceId": "d1", "temp": 21.5}'))
    producer.send_batch(batch)           # many events go in one efficient call

Illustrative shape only — real producers choose a partition key, handle errors, and the identity needs a role such as Azure Event Hubs Data Sender.
