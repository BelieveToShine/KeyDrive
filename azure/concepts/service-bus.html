Deep dive · Messaging · 📨 Service Bus

Service Bus is a safe post office for business messages — it holds each one until someone confirms it was handled.

Use it when losing, duplicating or mixing up a message would cost you money or trust: orders, payments, workflows. Learn queues, topics, peek-lock, dead-letter queues and sessions.

❓ "What is the difference between a Service Bus queue and a topic, and what happens to a message that keeps failing?"
👁 See it first
🎯 A queue hands each message to one worker. A topic gives every matching subscription its own copy. Both keep the message until someone confirms it was handled.
▶️ Watch it happen: queue versus topic
📖 Why did this need to exist?

Some messages are too important to lose: an order, a payment, a stock change. Dropping one costs money; handling one twice costs trust. A plain queue cannot promise much beyond "it is in there".

Service Bus is the broker for these messages. It holds a message until a worker confirms it was handled, retries if the worker fails, moves messages that keep failing to a side queue, and can keep messages in order. That is the difference between "a list of jobs" and "a reliable post office".

🧰 Features that make it "enterprise"
🎟️ Sessions

Messages with the same session id are handled in order, one session at a time. Use the customer id so each customer's steps stay in order.

🧟 Dead-letter queue

Every queue and subscription has one. Bad or expired messages land there instead of blocking everyone.

🪞 Duplicate detection

Drops a message that is sent twice with the same MessageId within a time window. It protects the sending side only.

⏰ Scheduled delivery

Send a message now, deliver it later — "remind the customer in 24 hours".

🔗 Transactions

Group operations so they succeed or fail together.

➡️ Auto-forwarding

Chain queues and subscriptions so messages flow on to another queue automatically.

🔥 Interview recall
  • Queue = one message, one worker (competing consumers). Topic = every matching subscription gets its own copy.
  • Peek-lock: receive → lock → Complete() removes it; failure or lock expiry returns it and raises the delivery count. Too many tries → dead-letter queue (default limit 10).
  • Sessions keep messages with the same session id in order.
  • Topics need the Standard or Premium tier; Basic has queues only.
  • Delivery is at-least-once — make the handler idempotent. Duplicate detection only stops duplicate sends.
🎤 Say this in an interview
"Service Bus is Azure's enterprise message broker. A queue delivers each message to one of several competing workers; a topic copies each message to every subscription whose filter matches. With peek-lock the message is locked while a worker processes it and removed only when completed; repeated failures move it to the dead-letter queue. I use sessions for ordering, and I make handlers idempotent because delivery is at least once."
⚠️ Common trap

At-least-once means duplicates can happen. If a worker finishes the work but crashes before it calls Complete(), the message comes back. Duplicate detection will not help — it only catches the same message being sent twice. Make the handler safe to run twice.

Second trap: a message that matches no subscription filter on a topic is not delivered to any subscription — it is effectively dropped. Add a catch-all subscription if you need to see everything.

🔒 Peek-lock

Receive → locked → you complete it. If you fail, it comes back. At-least-once. The safe default for important work.

vs.
🗑️ Receive-and-delete

The message is removed the moment it is received. If you crash, it is gone. At-most-once — only for work you can afford to lose.

▾ 💻 Tiny illustrative example — receive and complete 
with client.get_queue_receiver("orders") as receiver:
    for msg in receiver:
        handle(str(msg))                 # your code — must be safe to run twice
        receiver.complete_message(msg)   # tell Service Bus it is done, so it is removed

Illustrative shape only — real code also handles errors (abandon or dead-letter the message) and renews long locks.
