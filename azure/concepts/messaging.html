Concept 11 of 19 · ⚙️ Handling load

Messaging lets one part of your app hand off work without waiting — and without crashing together.

When parts of an app call each other directly, the slowest or most broken part drags everyone down. Azure gives you four messaging tools — and the skill is knowing which one to reach for.

❓ "What is the difference between Service Bus, Event Hubs, Event Grid and Storage Queues, and when do you use each?"
👁 See it first
🎯 Do not make parts of your app wait for each other — put a message in between. The sender drops it and moves on; the receiver picks it up when ready.
📖 Why did this need to exist?

At first, parts of an app call each other directly. It is simple, but it has a hidden cost: the slowest part slows everyone, a broken part breaks everyone, and a sudden rush of traffic hits the weakest part at full force.

Messaging adds a safe waiting room between the parts. Now each part can speed up, slow down or fail on its own. Azure has four messaging tools because there are really three different needs: messages ("please do this job"), events ("this just happened") and streams (a huge, constant flow of events).

🧠 First, the big idea: message or event?
🧰 The four Azure messaging tools

📬 Storage Queues

the simple, cheap to-do list✅ Pick it when
  • Simple background jobs
  • A very large backlog, kept cheap
  • No special features needed
⛔ Look elsewhere when
  • You need ordering, a bad-message bin or many subscribers → Service Bus
  • Messages larger than about 64 KB → store a file in Blob and send its address

📨 Service Bus

the reliable post office for business messages✅ Pick it when
  • Orders, payments, workflows — losing a message costs money
  • Order must be kept (sessions)
  • Retries and a dead-letter queue
  • One message to many subscribers (topics)
⛔ Look elsewhere when
  • Millions of tiny telemetry events → Event Hubs
  • Just reacting to "a file was created" → Event Grid

⚡ Event Grid

the doorbell that tells everyone something happened✅ Pick it when
  • React to things that happen in Azure (a blob was created)
  • Wire services together without polling
  • Serverless, event-driven designs
⛔ Look elsewhere when
  • You need ordered, guaranteed job processing → Service Bus
  • You need to replay old events later → Event Hubs

🌊 Event Hubs

the giant, replayable log for streams✅ Pick it when
  • Telemetry, clicks and logs at huge volume
  • Many readers each need the whole stream
  • You want to replay or archive the stream
⛔ Look elsewhere when
  • Single business commands that need per-message handling → Service Bus
  • A few rare events → Event Grid

▾ Go one level deeper (60 seconds)

Delivery is "at least once". With Service Bus peek-lock, a message that is not completed in time is delivered again. So your handler must be idempotent: doing it twice must be as safe as doing it once.

Big payloads — the claim-check pattern. Do not push big files through a queue. Save the file in Blob Storage and put only its address in the message. Both Storage Queues and Service Bus guides recommend this.

They work together. A common design: Blob Storage emits an event (Event Grid) → a Function reads it and puts a job on a Service Bus queue → workers process the job.

🔥 Interview recall
  • Message = "do this job" (expects it done). Event = "this happened" (anyone may react). Stream = a huge constant flow of events.
  • Storage Queues = simple, cheap. Service Bus = reliable business messaging (queues, topics, sessions, dead-letter). Event Grid = push events to handlers. Event Hubs = replayable stream log.
  • Messaging lets each part scale and fail independently — the sender does not wait.
  • Delivery is at-least-once, so handlers must be idempotent. Use the claim-check pattern for big payloads.
  • Services combine well: Service Bus for orders, Event Hubs for telemetry, Event Grid for reactions.
🎤 Say this in an interview
"Messaging decouples parts of a system so they can scale and fail independently. For commands that must be processed reliably — orders, payments — I use Service Bus: queues for one consumer, topics for many, with sessions for ordering and a dead-letter queue for failures. For reacting to things that happen, I use Event Grid, which pushes events to handlers. For high-volume telemetry that I need to replay, I use Event Hubs. For simple, cheap background jobs, Storage Queues. And I make handlers idempotent, because delivery is at least once."
⚠️ Common trap

Event Hubs is not "a bigger Service Bus". Service Bus is a broker: it hands each message to a worker and removes it when done. Event Hubs is a log: events stay, and every reader tracks its own position. Using the wrong one means missing features you assumed were there.

Second trap: assuming a message arrives exactly once. It is at least once — so a duplicate must not double-charge a customer.

📨 Service Bus

A broker for messages: one message, handed to a worker, removed once handled. Built for reliability.

vs.
🌊 Event Hubs

A log for streams: events are kept, many readers each read all of them. Built for volume and replay.

▾ 💻 Tiny illustrative example — send a message 
from azure.identity import DefaultAzureCredential
from azure.servicebus import ServiceBusClient, ServiceBusMessage

client = ServiceBusClient("mynamespace.servicebus.windows.net", DefaultAzureCredential())
with client.get_queue_sender("orders") as sender:
    sender.send_messages(ServiceBusMessage('{"orderId": 42}'))   # returns fast — the worker handles it later

Illustrative shape only — the app's identity needs a role such as Azure Service Bus Data Sender, and real code adds error handling.
