❓ "How do you choose between Azure VMs, App Service, Container Apps, AKS, Functions and Container Instances?"
👁 See it first
🎯 Compute is where your code runs. The real choice is how much of the machine you want to look after — the more you hand to Azure, the less you manage and the fewer knobs you get.
📖 Why did this need to exist?

You now have a safe network. Your code still needs somewhere to run. The oldest answer is a virtual machine: rent a computer in the cloud. It works for everything, but you inherit everything — patching the operating system, installing the runtime, planning how to add more copies when traffic grows.

Azure offers a ladder of options because teams want different trade-offs: control or convenience. The skill is picking the most managed option that still meets your needs — and moving down the ladder only for a hard requirement.

🧰 The six options

🖥️ Virtual Machines

a whole computer in the cloud✅ Pick it when
  • You need the operating system itself, or software installed on the machine
  • Lift-and-shift of an existing server
  • Special needs such as GPUs or long-running batch work
⛔ Look elsewhere when
  • A normal web app — you would take on patching you do not need

🌐 App Service

managed hosting for web apps and APIs✅ Pick it when
  • A web app or HTTP API that you want to just deploy
  • Azure should handle the OS and runtime
  • Built-in autoscaling and deployment slots
⛔ Look elsewhere when
  • You need per-service scaling for many small containers
  • You need scale to zero — App Service does not scale to zero

📦 Container Apps

containers, without running Kubernetes✅ Pick it when
  • Microservices or containerised APIs
  • Each app should scale on its own, and most can scale to zero
  • Microsoft suggests looking at it first for containers when you do not need the Kubernetes API
⛔ Look elsewhere when
  • You need direct access to the Kubernetes API → AKS

☸️ Azure Kubernetes Service (AKS)

managed Kubernetes✅ Pick it when
  • You need Kubernetes itself: its API, custom controllers, CRDs
  • The most customisation and control for containers
⛔ Look elsewhere when
  • A small team that wants less to operate → Container Apps
  • It takes the most operational effort of the container options

⚡ Azure Functions

small code that reacts to events✅ Pick it when
  • Event-driven work: a message, a timer, a webhook
  • Small pieces of logic that do not need a server of their own
⛔ Look elsewhere when
  • A long-lived web app with many routes → App Service or Container Apps

⏱️ Container Instances

run a single container, no cluster✅ Pick it when
  • A one-off job or a quick task in a container
  • You do not want to provision a VM or a bigger service
⛔ Look elsewhere when
  • Autoscaling services — it does not scale beyond the container group

▾ Go one level deeper (60 seconds) — patching and the shared-responsibility line

Virtual machines (IaaS): Microsoft looks after everything below the operating system — the datacenter, hardware and host. The guest OS is yours to patch, with help from tools such as Azure Update Manager.

App Service (PaaS): Azure patches the OS and the runtime for you. You look after your application and its data.

Container Apps is built on Kubernetes and uses KEDA for event-driven scaling, but it does not expose the Kubernetes API. If you need that API, that is the reason to choose AKS.

Not covered here: how to add more copies automatically and survive failures (Scaling & Resilience), and how Functions really work (Serverless & Orchestration). Both are later concepts in this journey.

🔥 Interview recall
  • Compute is a ladder: VMs (most control) → AKS → Container Apps → App Service → Functions (least to run).
  • VMs: you patch the OS. App Service: Azure runs the OS and runtime. Container Apps: containers without Kubernetes. AKS: you need the Kubernetes API.
  • Functions = event-driven code. Container Instances = a single container or a one-off job.
  • App Service scales the plan and does not scale to zero; Container Apps scales each app and most can scale to zero.
  • Start with the most managed option that fits; move toward control only for a hard requirement.
🎤 Say this in an interview
"Compute on Azure is a trade-off between control and operational effort. Virtual Machines give full control but I patch the OS. App Service is managed hosting for web apps and APIs. Container Apps runs containers without exposing Kubernetes, with per-app scaling. AKS is for when I really need the Kubernetes API. Functions is for event-driven code, and Container Instances for one-off containers. I start with the most managed option that meets the requirement."
⚠️ Common trap

Do not pick a VM just because it feels familiar. A VM works for everything, but it is the option that gives you the most work: patching, hardening, backup and scaling are all yours. Use it when you have a reason.

Second trap: Kubernetes is a tool, not a goal. Choosing AKS "because everyone does" means taking on the most operational effort of the container options. If you do not need the Kubernetes API, Container Apps is usually enough.

🌐 App Service

A single web process or API, deployed as code, scaled per plan. No Dockerfile needed.

📦 Container Apps

Containers, with each service scaled on its own and most able to scale to zero.

▾ 💻 Tiny illustrative example 
# run a container as a Container App — Azure runs and scales it, no cluster for you to manage
az containerapp create --name shop-api --resource-group rg-shop-prod \
    --environment env-shop --image mcr.microsoft.com/k8se/quickstart:latest \
    --target-port 80 --ingress external

Illustrative shape only — you first create the environment, and real apps use their own image, identity, secrets and scale rules.
