The burger counter: choose the parts, then build.

The Builder pattern with a burger: why long constructors hurt and how step-by-step building reads like a sentence.

❓ "What is the Builder pattern and when would you use it?"
👁 See it first
🎯 Build a complicated object one named step at a time, then ask for the finished result.
🌍 In real life

🍔 At a burger counter you do not shout eight things in a fixed order. You say: “sesame bun, add cheese, add tomato — done.” The cook collects your choices and then builds the burger.

refactoring.guru: Builder lets you construct complex objects step by step, and the same construction code can produce different representations.

🍔 The fix: choose, then build
🎭 Who is who
Role in the patternIn our storyIn code
Productthe burgerBurger
Builderthe person at the counter collecting choicesBurgerBuilder
Steps“add cheese”, “add tomato”AddCheese() …
Build“that’s all, please make it”Build()
🧪 Tiny code
// BEFORE — what does each value mean?
var b = new Burger("sesame", "beef", true, false, true, "none", false, true);

// AFTER — a builder with named steps
class BurgerBuilder
{
    private string _bun = "plain"; private bool _cheese, _tomato;
    public BurgerBuilder WithBun(string bun) { _bun = bun; return this; }
    public BurgerBuilder AddCheese()         { _cheese = true; return this; }
    public BurgerBuilder AddTomato()         { _tomato = true; return this; }
    public Burger Build() => new Burger(_bun, _cheese, _tomato);
}

var burger = new BurgerBuilder().WithBun("sesame").AddCheese().AddTomato().Build();

Each method returns the builder itself (return this), so the calls chain like a sentence. The finished Burger can then be kept unchangeable.

🔎 Where you already see it
You write…It is…
new StringBuilder().Append(…).Append(…).ToString()assemble a string step by step, then take the result
WebApplication.CreateBuilder(args) … builder.Build()the ASP.NET Core host is configured step by step, then built
new UriBuilder(…)piece-by-piece construction of a URI

Calling these “builders” is the usual classification; the classes themselves are documented by Microsoft.

🎯 Spot it: is the pattern a good fit?
▾ An object with 2 simple fields

❌ Overkill. A normal constructor is clearer. No builder needed.

▾ A constructor with eight parameters, many optional

✅ Good fit. A builder gives names to each choice and defaults to the rest.

▾ You need the same steps to make different kinds of results (a burger and a veggie wrap)

✅ Good fit. The same construction code can produce different products — a classic Builder use.

▾ You want to read a test setup like a sentence

✅ Good fit. Test-data builders make setups easy to read.

👀 How to spot the need in your own code
If you see…Do this
A constructor or method with 5+ parameters, several of the same typeIntroduce a builder (or named/optional parameters).
Many overloaded constructors for each combinationReplace them with one builder.
Callers pass null/false for options they do not care aboutLet the builder default them.
🔥 Interview recall
  • Builder = build a complex object step by step with named steps, then call Build().
  • It fixes “telescoping constructors” and unreadable calls.
  • Methods return this so calls chain like a sentence.
  • StringBuilder and WebApplication.CreateBuilder are builders you already use.
🎤 Say this in an interview
"The Builder pattern constructs a complex object step by step: I choose parts by name, in any order, then call Build() to get the finished object. It replaces constructors with long lists of unnamed parameters, defaults the parts I skip, and reads like a sentence. I would not use it for a simple object with a couple of fields."
⚠️ Common trap

Builders for tiny objects. A plain constructor is clearer.

Forgetting to validate in Build(). That is where required parts should be checked.
