Concept 13 of 24 · 💬 Behavioral

The traffic light: each mode knows what to do and what comes next.

The State pattern with a traffic light: replace repeated if/else on a status with one small class per state.

❓ "What is the State pattern and how is it different from Strategy?"
👁 See it first
🎯 Give each mode its own small class that knows what to do in that mode and which mode comes next.
🌍 In real life

🚦 A traffic light does not look up a rulebook each time. Red means cars stop and the next colour is green; Green means go and next is yellow. Each colour carries its own rules.

refactoring.guru: State lets an object alter its behaviour when its internal state changes — it appears as if the object changed its class.

🚦 The fix: one class per mode

🧪 Tiny code
interface ILightState { string Cars(); ILightState Next(); }

class Red    : ILightState { public string Cars() => "stop"; public ILightState Next() => new Green(); }
class Green  : ILightState { public string Cars() => "go";   public ILightState Next() => new Yellow(); }
class Yellow : ILightState { public string Cars() => "slow"; public ILightState Next() => new Red(); }

class TrafficLight
{
    private ILightState _state = new Red();
    public string Cars() => _state.Cars();          // behaviour depends on current state
    public void Next()   => _state = _state.Next(); // the state decides what comes next
}

Compare with Strategy: a strategy is chosen from outside; a state changes itself.

🔎 Where you already see it
You write…It is…
Order status: New → Paid → Shipped → Deliveredeach status allows different actions
Media player: playing, paused, stoppedeach button does something different per state

These are the usual textbook uses.

🎯 Spot it: is the pattern a good fit?
▾ Behaviour changes a lot with a status and the same if/else is in many methods

✅ Good fit. One class per state.

▾ A status flag used in one place

❌ Overkill. A simple if is fine.

▾ Rules like “you can only ship a paid order”

✅ Good fit. States make illegal moves impossible.

▾ Choosing between pricing methods from outside

❌ Overkill. That is Strategy, not State.

👀 How to spot the need in your own code
If you see…Do this
The same switch (status) in many methodsIntroduce state classes.
“If state is X then throw” checks scattered aboutMake illegal actions unavailable in that state.
🔥 Interview recall
  • State = an object changes behaviour when its internal state changes, via one class per state.
  • States know the next state.
  • Removes repeated switch on status.
  • Strategy: chosen from outside; State: changes itself.
🎤 Say this in an interview
"The State pattern replaces repeated if/else on a status with one small class per state. Each state defines the behaviour and the next state, like a traffic light. The context delegates to its current state. It differs from Strategy, where the caller picks the algorithm; here the object moves between states itself."
⚠️ Common trap

Confusing State with Strategy. Look at who changes it.

Too many states. Draw the state diagram first.
