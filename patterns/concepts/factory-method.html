The pizza shop that decides which pizza to bake.

The Factory pattern with a pizza shop: why scattered “if cheese… else if…” code hurts and how one factory fixes it.

❓ "What is the Factory pattern and when would you use it?"
👁 See it first
🎯 Put “which one to make” in one place — a factory — and ask it for the thing you need.
🌍 In real life

🍕 In a pizza shop the customer says “one cheese pizza, please”. They do not go into the kitchen and pick the flour. The kitchen decides how it is made.

refactoring.guru describes Factory Method as providing an interface for creating objects while letting subclasses alter the type of objects that will be created. The simple version in this page — one place that decides — is the idea beginners meet first.

🏭 The fix: one kitchen
🎭 Who is who
Role in the patternIn our storyIn code
Product (the thing made)a pizzaIPizza
Concrete productsCheese, Pepperoni, VeggieCheesePizza …
Factory (the decider)the kitchenPizzaFactory.Create(name)
Client (asks for one)order screen, phone app, kioskany code that needs a pizza
🧪 Tiny code
// BEFORE — every client decides for itself
IPizza p = type == "cheese" ? new CheesePizza() : new PepperoniPizza();   // copied in 3 places

// AFTER — one factory decides
interface IPizza { void Bake(); }
class CheesePizza    : IPizza { public void Bake() { } }
class PepperoniPizza : IPizza { public void Bake() { } }

static class PizzaFactory
{
    public static IPizza Create(string type) => type switch
    {
        "cheese"    => new CheesePizza(),
        "pepperoni" => new PepperoniPizza(),
        _ => throw new ArgumentException("unknown pizza")
    };
}

IPizza pizza = PizzaFactory.Create("cheese");     // clients just ask

This is the “simple factory” — the easiest form. The classic Factory Method lets subclasses choose the product; the idea (creation in one place, clients use an interface) is the same.

🔎 Where you already see it
You write…It is…
ILoggerFactory.CreateLogger(...)a factory that makes loggers (documented in Microsoft’s logging docs)
IHttpClientFactory.CreateClient()a factory for HTTP clients (documented in Microsoft Learn)
services.AddScoped<IPizza, CheesePizza>()the DI container acts as a factory for everything you register
🎯 Spot it: is the pattern a good fit?
▾ You create one simple object with new and nothing will ever vary

❌ Overkill. No pattern needed. Just write new.

▾ The same “which class?” if/else appears in many places

✅ Good fit. A factory removes the duplication; adding a type becomes a one-place change.

▾ The class to create is chosen at run time from a setting or user input

✅ Good fit. A factory is the natural home for that decision.

▾ Every class gets its own factory “just in case”

❌ Overkill. That is over-engineering. Add a factory when a real variation exists.

👀 How to spot the need in your own code
If you see…Do this
The same if/switch that creates objects in several filesMove it into one factory.
Client code mentions concrete class names like new CheesePizza() everywhereAsk a factory (or DI) and depend on the interface.
Adding a type means editing many filesCreation is scattered. Centralise it.
🔥 Interview recall
  • Factory = one place decides which concrete class to create; clients ask it and use the interface.
  • It removes copied “if type == …” code and makes adding a type a one-place change.
  • Simple factory = one method; Factory Method = subclasses choose the product.
  • DI containers and IHttpClientFactory are factories you already use.
🎤 Say this in an interview
"The Factory pattern puts the decision of which concrete class to create in one place. Clients ask the factory for an interface — like ordering a pizza without knowing the recipe — so adding a new type changes only the factory instead of every caller. I use it when creation logic is repeated or chosen at runtime, and I skip it when a plain new is enough."
⚠️ Common trap

A factory for everything. If nothing varies, new is fine.

Putting business logic in the factory. It should only decide and create.
