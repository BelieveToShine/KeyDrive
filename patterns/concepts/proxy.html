The receptionist: a stand-in that guards the real thing.

The Proxy pattern with a receptionist: control access to an object (check, delay, cache) while looking exactly like it.

❓ "What is the Proxy pattern and what are its common types?"
👁 See it first
🎯 Put a stand-in with the same shape in front of the real object, so it can check, delay or remember before passing the request on.
🌍 In real life

💁 A receptionist looks like the way into the Director’s office. They check your appointment first; if it is fine you go through, otherwise “sorry”.

refactoring.guru: a proxy controls access to the original object, allowing you to perform something either before or after the request gets through.

💁 The fix: a receptionist

🧪 Tiny code
interface IDirector { void Meet(string visitor); }

class Director : IDirector { public void Meet(string v) => Console.WriteLine($"Meeting {v}"); }

class DirectorProxy(IDirector real, IAppointments appointments) : IDirector
{
    public void Meet(string visitor)
    {
        if (!appointments.Has(visitor)) { Console.WriteLine("Sorry, no appointment"); return; }   // guard
        real.Meet(visitor);                                                                         // pass on
    }
}

Other kinds: a lazy proxy delays creating something expensive until it is used; a caching proxy remembers answers; a remote proxy talks to something far away as if it were local.

🔎 Where you already see it
You write…It is…
Lazy<T>delays creating an object until first use (a lazy-loading idea)
A generated client for a remote web servicelooks local, talks over the network (a remote proxy)

Mapping .NET features to proxy types is a common classification, not a quote.

🎯 Spot it: is the pattern a good fit?
▾ Check permissions before every call to a sensitive service

✅ Good fit. A protection proxy does exactly that.

▾ Delay loading a huge image until it is scrolled into view

✅ Good fit. A lazy proxy.

▾ Add milk to a coffee

❌ Overkill. That is a Decorator: it adds behaviour. A proxy controls access.

▾ A proxy for an object that is cheap and always safe to use

❌ Overkill. No benefit.

👀 How to spot the need in your own code
If you see…Do this
Permission or cache checks scattered at the start of many methodsMove them into a proxy.
An expensive object created at startup though rarely usedA lazy proxy can delay it.
🔥 Interview recall
  • Proxy = a stand-in with the same shape that controls access to the real object.
  • Kinds: protection, lazy, caching, remote.
  • Client cannot tell proxy from real.
  • Decorator adds behaviour; Proxy controls access.
🎤 Say this in an interview
"A Proxy is a stand-in with the same interface as the real object that controls access to it — a receptionist checking appointments. It can guard, delay creation, cache, or hide a remote call, and the client can’t tell the difference. Unlike a Decorator, its purpose is control, not adding features."
⚠️ Common trap

Proxy vs Decorator. Same structure, different intent: control access vs add behaviour.

Hidden slowness. A remote proxy looks local but may be slow.
