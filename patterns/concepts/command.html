The order slip: turn a request into a thing you can keep, queue or undo.

The Command pattern with a restaurant order slip: wrap a request in an object so it can be stored, delayed, logged and undone.

❓ "What is the Command pattern and how does it support undo?"
👁 See it first
🎯 Wrap a request in an object (a “command”) that knows what to do, so you can keep it, queue it, log it or undo it.
🌍 In real life

🧾 A waiter does not shout into the kitchen. They write an order slip. The slip is a thing: it can wait on a spike, be passed between cooks, be logged, or be cancelled.

refactoring.guru: Command turns a request into a stand-alone object that contains all information about the request, which lets you pass requests as arguments, delay or queue them, and support undoable operations.

🧾 The fix: the request becomes an object

🧪 Tiny code
interface ICommand { void Execute(); void Undo(); }

class Lamp { public void On() { } public void Off() { } }

class LightOn(Lamp lamp) : ICommand
{
    public void Execute() => lamp.On();
    public void Undo()    => lamp.Off();
}

class Remote
{
    private readonly Stack<ICommand> _history = new();
    public void Press(ICommand cmd) { cmd.Execute(); _history.Push(cmd); }
    public void Undo() { if (_history.Count > 0) _history.Pop().Undo(); }
}

Queues, logs and macros are the same idea: keep a list of command objects.

🎯 Spot it: is the pattern a good fit?
▾ You need undo/redo for user actions

✅ Good fit. Commands with Undo and a history are the standard answer.

▾ You must queue work to run later or on another thread

✅ Good fit. A command object is the unit of work.

▾ A one-off call nobody will ever log or undo

❌ Overkill. Just call the method.

▾ Every tiny method wrapped in a command class

❌ Overkill. Overkill.

👀 How to spot the need in your own code
If you see…Do this
Requirements for undo, redo, audit logs or retryModel requests as commands.
Buttons or menu items hard-wired to specific methodsBind them to command objects.
🔥 Interview recall
  • Command = a request wrapped as an object with Execute (and Undo).
  • Enables queuing, logging, retry and undo.
  • Invoker triggers, receiver does the work.
  • History stack gives undo.
🎤 Say this in an interview
"The Command pattern turns a request into an object that knows how to execute — and possibly undo — itself. Like a waiter’s order slip, it can be queued, logged, retried or reversed. I keep a history stack for undo, and the invoker needs to know nothing about the receiver."
⚠️ Common trap

Commands that cannot truly undo (emails already sent). Say so.

Too many tiny command classes for trivial actions.
