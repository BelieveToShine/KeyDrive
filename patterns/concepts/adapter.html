The travel plug: make a foreign thing fit your shape.

The Adapter pattern with a travel plug: wrap a class that has the wrong shape so the rest of your code can use it unchanged.

❓ "What is the Adapter pattern and when would you use it?"
👁 See it first
🎯 Wrap the thing with the wrong shape in a small adapter, so your code can use it the way it already expects.
🌍 In real life

🧳 A travel adapter does not change your laptop or the hotel wall. It has your plug shape on one side and the wall’s shape on the other.

refactoring.guru: Adapter lets objects with incompatible interfaces collaborate.

🧳 The fix: a small adapter in the middle
🎭 Who is who
Role in the patternIn our storyIn code
Client (expects one shape)the laptopyour code using IPaymentGateway
Adaptee (has another shape)the hotel socketa vendor SDK with CreateCharge(cents)
Adapterthe travel adapterVendorPaymentAdapter : IPaymentGateway
🧪 Tiny code
// Your code expects THIS shape
interface IPaymentGateway { bool Charge(decimal amount); }

// The vendor SDK has a different shape (you cannot change it)
class VendorClient { public int CreateCharge(long cents) { return 200; } }

// The adapter translates between the two
class VendorPaymentAdapter(VendorClient vendor) : IPaymentGateway
{
    public bool Charge(decimal amount) => vendor.CreateCharge((long)(amount * 100)) == 200;
}

IPaymentGateway gateway = new VendorPaymentAdapter(new VendorClient());
gateway.Charge(9.99m);               // your code never knows about VendorClient

VendorClient is invented for illustration. When the vendor changes, only the adapter changes.

🎯 Spot it: is the pattern a good fit?
▾ You depend on a vendor SDK in 30 places and might switch vendors

✅ Good fit. Wrap it once in an adapter behind your interface.

▾ You own both classes and can simply make them match

❌ Overkill. Just change one of them; no adapter needed.

▾ A legacy class has the right behaviour but the wrong method names

✅ Good fit. An adapter gives it the names your code expects.

▾ You add an adapter around every class “just in case”

❌ Overkill. Overkill. Adapt only foreign or legacy shapes.

👀 How to spot the need in your own code
If you see…Do this
Vendor types (VendorClient, VendorResponse) used all over your codeWrap them in one adapter behind your own interface.
Conversions (cents ↔ decimal, XML ↔ object) repeated in many placesPut the translation in one adapter.
🔥 Interview recall
  • Adapter = a wrapper that converts one interface into the one your code expects.
  • Use for third-party/legacy code you cannot change.
  • Client and adaptee stay unchanged.
  • Adapter changes the interface; Decorator keeps it and adds behaviour.
🎤 Say this in an interview
"An Adapter wraps an object whose interface doesn’t match what my code expects — like a travel plug. I define the interface my code wants, write a small adapter that translates to the vendor’s API, and keep all vendor types out of the rest of the system, so switching vendors only changes the adapter."
⚠️ Common trap

Confusing Adapter and Decorator. An adapter changes the interface; a decorator keeps it and adds behaviour.

Leaking vendor types through the adapter. Return your own types.
