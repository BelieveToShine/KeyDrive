❓ "What is a design pattern, and what are the main categories?"
👁 See it first
🎯 A design pattern is a named, proven recipe for a problem that keeps coming back — a blueprint, not code you copy.
🌍 In real life

🍳 A cookbook does not give you one dish; it gives you techniques: how to make a roux, how to fold, how to sear. You use them in a thousand dishes and every chef knows what you mean when you say “make a roux”.

Design patterns are the cookbook of code. refactoring.guru describes them as typical solutions to commonly occurring problems in software design — more like a blueprint than a piece of code you can copy; you follow the plan and write the details yourself.

🗂️ Four families, four questions
📇 What is on a pattern card?
PartPlain meaning
Intentthe problem and the solution in one line
Motivationa short story of why it is needed
Structurethe parts (roles) and how they connect — a small diagram
Code examplea few lines to see it work

That is exactly how every page in this lab is built, with an animated story as the “structure”.

👀 Patterns you already use
You already write…It is the pattern…

services.AddSingleton<T>()Singleton — one instance for the whole app (as a DI lifetime)
IObservable<T> / IObserver<T> and eventObserver — subscribers are told when something happens
ASP.NET Core middlewareChain of Responsibility — each step handles or passes on

The Observer and Singleton rows are documented by Microsoft (Observer design pattern; DI lifetimes). The other rows are common classifications of .NET features, not quoted from a standard.

🎯 Spot it: which family?
▾ “I want to create objects without naming the exact class.” Is that creational?

✅ Yes. Yes — creational patterns are about making objects (Factory, Builder, Singleton).

▾ “I want to wrap an object to add behaviour.” Is that behavioral?

❌ No. No — wrapping to add extras fits is a structural pattern (Decorator).

▾ “Many parts must be told when something changes.” Is that behavioral?

✅ Yes. Yes — Observer is behavioral: it is about how objects communicate.

▾ “Split reads and writes of a whole system into separate models.” Is that a GoF pattern?

❌ No. No — that is CQRS, an architecture pattern from the cloud-patterns catalog.

🔥 Interview recall
  • A design pattern = a named, proven solution to a common problem — a blueprint, not copy-paste code.
  • Card: intent, motivation, structure, code.
  • Families: creational (making), structural (fitting), behavioral (talking), architecture (whole systems).
  • Patterns give teams a shared vocabulary.
  • Use a pattern when it removes a real pain — not to look clever (see “Choosing a pattern”).
🎤 Say this in an interview
"A design pattern is a named, proven solution to a problem that keeps coming back — a blueprint rather than code to copy. They fall into creational, structural and behavioral families, plus patterns like CQRS and Saga for whole systems. Their biggest value is a shared vocabulary: saying ‘use a Factory’ or ‘wrap it in a Decorator’ explains the design in one word."
⚠️ Common trap

“More patterns = better code.” A pattern is a cost: more classes, more indirection. Use one when it removes a real pain.

“Patterns are code to copy.” They are plans; the details depend on your problem.
