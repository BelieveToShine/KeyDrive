Concept 11 of 24 · 💬 Behavioral

The YouTube bell: tell everyone who subscribed.

The Observer pattern with a channel and its fans: a publisher keeps a list of subscribers and notifies them without knowing who they are.

❓ "What is the Observer pattern and how is it implemented in .NET?"
👁 See it first
🎯 Let listeners subscribe; the publisher just notifies “whoever is on my list” — and never needs to know who they are.
🌍 In real life

🔔 You press the bell on a channel. You do not email the creator; the platform keeps a list and sends you a notification when something new appears. You can switch it off any time.

refactoring.guru: Observer is a subscription mechanism that notifies multiple objects about events that happen to the object they observe. Microsoft’s .NET docs describe IObservable<T>/IObserver<T>: the provider’s Subscribe returns an IDisposable so observers can unsubscribe.

🔔 The fix: a subscriber list

🧪 Tiny code
class Channel
{
    public event Action<string>? NewVideo;                 // the subscriber list lives here
    public void Publish(string title) => NewVideo?.Invoke(title);
}

var channel = new Channel();
channel.NewVideo += t => Console.WriteLine($"Asha sees: {t}");
channel.NewVideo += t => Console.WriteLine($"Ben sees: {t}");

channel.Publish("Design patterns!");     // both are told

C# event is built-in Observer. Remember to unsubscribe (-=) when a listener is no longer needed, or it stays alive.

🎯 Spot it: is the pattern a good fit?
▾ Many unrelated parts must react when one thing changes

✅ Good fit. Publish once; whoever subscribed is told.

▾ Exactly one fixed listener, always

❌ Overkill. A direct call is clearer.

▾ Listeners come and go at run time

✅ Good fit. Subscribe/unsubscribe is built for it.

▾ Listeners must run in a strict order that matters

❌ Overkill. Hidden ordering makes bugs; call them explicitly.

👀 How to spot the need in your own code
If you see…Do this
Publisher code that lists every listener by nameReplace with a subscriber list or event.
Objects polling “has it changed?” in a loopLet the source notify instead.
🔥 Interview recall
  • Observer = publisher keeps a subscriber list and notifies them; it never knows who they are.
  • C# events are built-in observers; IObservable/IObserver are the interfaces.
  • Always unsubscribe to avoid leaks.
  • Do not rely on the order listeners run.
🎤 Say this in an interview
"Observer decouples a publisher from its listeners: subscribers register, the publisher notifies the list, and neither side knows the other’s details — like the YouTube bell. In C# that’s an event, or IObservable/IObserver, and I make sure listeners unsubscribe so they don’t leak."
⚠️ Common trap

Forgetting to unsubscribe. The publisher keeps the listener alive — a memory leak.

Surprise cascades. A listener that triggers more events can be hard to follow.
