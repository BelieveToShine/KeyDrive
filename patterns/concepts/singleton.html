One office printer — and why “only one” can be risky.

The Singleton pattern with an office printer: what it guarantees, how .NET does it for you with DI, and why hand-made singletons are often a trap.

❓ "What is the Singleton pattern, and what are its drawbacks?"
👁 See it first
🎯 Make sure there is exactly one instance, and give everyone the same one.
🌍 In real life

🖨️ An office has one printer. Everyone sends jobs to the same machine; nobody buys their own. That works well — until the printer jams and everyone is stuck, or someone changes its settings and surprises everybody.

refactoring.guru: Singleton ensures a class has only one instance and gives a global access point to it. The same page lists drawbacks: it solves two problems at once, can hide bad design, and makes unit testing harder because many test frameworks rely on inheritance when creating mocks.

1️⃣ The fix: one shared instance

🧪 Tiny code
// The classic hand-made singleton
sealed class Settings
{
    private static readonly Lazy<Settings> _instance = new(() => new Settings());
    public static Settings Instance => _instance.Value;     // global access point
    private Settings() { }                                   // nobody else can create one
    public string Currency { get; set; } = "USD";
}

// The modern .NET way: let the DI container keep one for you
builder.Services.AddSingleton<ISettings, Settings>();        // one for the whole app
class BillingService(ISettings settings) { }                  // asked for, not reached for

Prefer the second form: the class is a normal class, a test can hand in a fake, and the container guarantees one instance. A hand-made static singleton is a hidden dependency.

🎯 Spot it: is the pattern a good fit?
▾ A shared clock, configuration or cache used by the whole app

✅ Reasonable. One shared instance makes sense. Register it with AddSingleton.

▾ Per-user data (a shopping cart) kept in a singleton

❌ Risky. Everyone would share one cart. Use a per-request (scoped) lifetime.

▾ A hand-made static Instance used all over business code

❌ Risky. It hides a dependency and makes tests hard. Inject an interface instead.

▾ A logging service that must be one for the whole process

✅ Reasonable. Fine — ideally provided through DI.

👀 How to spot the need in your own code
If you see…Do this
SomeClass.Instance.Method() appearing deep in business codeA hidden global. Inject it instead.
Tests that fail depending on the order they runShared singleton state leaks between tests.
A singleton holding per-user or per-request dataWrong lifetime; it will leak between users.
🔥 Interview recall
  • Singleton = exactly one instance + one access point.
  • Good for truly shared, thread-safe things: configuration, clock, cache.
  • Risks: hidden global, hard to test, shared state, thread-safety.
  • In .NET prefer AddSingleton through DI over a hand-written static instance.
🎤 Say this in an interview
"A Singleton guarantees one instance and a way to reach it. It suits genuinely shared things like configuration or a clock. But a hand-written static singleton is a hidden global that makes testing hard, so in .NET I let the DI container provide a singleton lifetime and I never keep per-user data in one."
⚠️ Common trap

“Singleton is the easy way to share data.” It becomes a global variable with a nice name.

Thread-safety forgotten. Many callers share one object; it must be safe to use at the same time.
