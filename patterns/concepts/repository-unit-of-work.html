The librarian and the shopping basket: a simple door to your data.

The Repository and Unit of Work patterns: hide storage details behind a collection-like interface and save a group of changes together.

❓ "What are the Repository and Unit of Work patterns, and does Entity Framework already implement them?"
👁 See it first
🎯 Hide how data is stored behind an object that behaves like a collection (Repository), and save a group of changes together (Unit of Work).
🌍 In real life

📚 In a library you ask the librarian: “find me this book”, “add this book”. You never walk the stacks or learn the shelving code. And at the till, your basket holds several books and you pay once — all or nothing.

Microsoft’s EF documentation describes DbContext as combining the Unit of Work and Repository patterns, with the unit of work executed when SaveChanges is called.

📚 The fix: a librarian and a basket

🧪 Tiny code
interface IOrderRepository
{
    void Add(Order order);
    Order? Find(int id);
}

// With EF Core you often get both for free:
// DbContext = Unit of Work (SaveChanges),  DbSet<Order> = collection-like access
class OrderService(ShopDbContext db)
{
    public void Place(Order order)
    {
        db.Orders.Add(order);          // "librarian": add to the collection
        db.SaveChanges();              // "basket": save the group together
    }
}

Microsoft’s guidance says EF Core’s DbContext already implements both patterns, so a custom repository is worth adding when the application is complex enough to benefit.

🎯 Spot it: is the pattern a good fit?
▾ A domain with rich rules that you want to test without a database

✅ Good fit. A repository interface gives you a seam for fakes.

▾ A tiny CRUD app already using EF Core directly

❌ Overkill. DbContext is enough; an extra layer only adds code.

▾ Several changes must succeed or fail together

✅ Good fit. Unit of Work gives all-or-nothing saving.

▾ A repository method per screen, with joins and filters

❌ Overkill. That becomes a query dumping ground; consider the read side separately (CQRS).

👀 How to spot the need in your own code
If you see…Do this
SQL strings or DbContext usage scattered through business logicHide it behind a repository.
A test that needs the real database to check a business ruleA repository interface gives a seam.
🔥 Interview recall
  • Repository = collection-like access to data that hides storage details.
  • Unit of Work = track changes and save them together (SaveChanges).
  • EF Core’s DbContext already is a unit of work and repository-like.
  • Add your own repository only when it pays for itself.
🎤 Say this in an interview
"A Repository hides how data is stored behind a collection-like interface, and a Unit of Work collects changes and saves them together. With EF Core, DbContext already provides both, so I add a custom repository only for complex domains or testability. Otherwise it’s extra layers for nothing."
⚠️ Common trap

A repository on top of a repository. EF already is one.

A giant repository with a method per query. Split reads from writes.
