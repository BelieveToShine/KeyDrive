The notebook of answers: check it before doing the slow work.

The Cache-Aside pattern with a notebook: load data into a cache on demand so repeated reads are fast.

❓ "What is the Cache-Aside pattern and how do you keep the cache correct?"
👁 See it first
🎯 Look in a fast cache first; if the answer is not there, get it from the slow source and keep a copy for next time.
🌍 In real life

📓 A teacher keeps a notebook of answers to questions students ask a lot. Next time someone asks, they read the notebook instead of working it out again. If the textbook changes, they cross out the old answer.

The Azure Architecture Center describes Cache-Aside as optimising access to frequently read data by introducing a cache that is populated on demand; consistency (stale data) is a trade-off.

📓 The fix: check, miss, store

🧪 Tiny code
async Task<Product?> GetProduct(int id)
{
    if (cache.TryGetValue(id, out Product? cached)) return cached;     // 1. hit: fast

    var product = await db.Products.FindAsync(id);                      // 2. miss: slow read
    if (product is not null)
        cache.Set(id, product, TimeSpan.FromMinutes(5));                // 3. keep a copy (with expiry)
    return product;
}

async Task Update(Product p)
{
    await db.SaveChangesAsync();        // change the real data
    cache.Remove(p.Id);                 // invalidate the old copy
}

cache is, for example, IMemoryCache in ASP.NET Core or a distributed cache such as Redis.

🎯 Spot it: is the pattern a good fit?
▾ Data that is read often and changes rarely

✅ Good fit. The ideal cache candidate.

▾ Data that changes every second and must always be exact

❌ Overkill. A cache would be stale.

▾ Answers that are slow to compute and the same for many users

✅ Good fit. Cache them.

▾ Per-user private data in a shared cache with the same key for everyone

❌ Overkill. Leaks data between users: include the user in the key or do not cache it.

If you see…Do this

🔥 Interview recall
  • Cache-Aside = app checks cache; on a miss loads from the source and stores a copy.
  • Invalidate or expire entries when data changes.
  • Trade-off: briefly stale data.
  • Have a fallback if the cache is down.
🎤 Say this in an interview
"In Cache-Aside the application looks in the cache first; on a miss it reads the source, stores the result in the cache, and returns it. I give entries an expiry and invalidate them on writes, accept that data can be briefly stale, and fall back to the database if the cache is down."
⚠️ Common trap

Forgetting to invalidate. Users see old data.

Caching per-user data under a shared key. A security bug.
