The bank statement: keep every change, work out the balance.

Event Sourcing with a bank account: store the list of things that happened and rebuild the current state from it.

❓ "What is Event Sourcing and when is it worth the extra complexity?"
👁 See it first
🎯 Store every change as an event in an append-only list, and work out the current state by replaying them.
🌍 In real life

🏦 Your bank does not just tell you “you have 70”. It gives a statement: every deposit and withdrawal, in order. The balance is the result of that history, and you can check any past date.

The Azure Architecture Center describes Event Sourcing as treating state change as a series of events captured in an immutable, append-only log.

🧪 Tiny code
abstract record AccountEvent;
record Opened() : AccountEvent;
record Deposited(decimal Amount) : AccountEvent;
record Withdrew(decimal Amount)  : AccountEvent;

static decimal Balance(IEnumerable<AccountEvent> events) =>
    events.Aggregate(0m, (sum, e) => e switch
    {
        Deposited d => sum + d.Amount,
        Withdrew w  => sum - w.Amount,
        _ => sum
    });

var history = new List<AccountEvent> { new Opened(), new Deposited(100), new Withdrew(30) };
Console.WriteLine(Balance(history));      // 70

Real systems add snapshots (a saved total) so replay stays fast.

🎯 Spot it: is the pattern a good fit?
▾ You must prove exactly what happened and when (audit)

✅ Good fit. The event list is the audit trail.

▾ Simple settings screen: last value wins

❌ Overkill. Overkill.

▾ You want to rebuild different read models later from history

✅ Good fit. Replay gives you that.

▾ The team has never run an event store

❌ Overkill. Count the learning cost before choosing it.

👀 How to spot the need in your own code
If you see…Do this
Requirements like “show history of changes”, “undo”, “what did it look like on date X”Consider events.
Tables full of “audit_log” copies of the main dataThe audit log may be the real model.
🔥 Interview recall
  • Event Sourcing = store events (immutable, append-only), derive state by replay.
  • Gives full history, audit and rebuildable read models.
  • Costs: complexity, schema evolution of events, replay speed (snapshots).
  • Often paired with CQRS.
🎤 Say this in an interview
"With Event Sourcing I store every change as an immutable event and compute the current state by replaying them, like a bank statement. It gives a complete audit trail and lets me rebuild read models, but it’s more complex — events must evolve carefully and replays need snapshots — so I use it where history really matters."
⚠️ Common trap

Editing past events. They are facts; correct with a new event.

Event Sourcing for simple CRUD. Heavy for the benefit.
