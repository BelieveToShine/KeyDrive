Start with the pain, then pick the tool.

A problem-to-pattern map, look-alike pairs, combinations and the pattern-first trap.

❓ "How do you decide which design pattern to use?"
👁 See it first
🎯 Start from the pain, not from the pattern. A pattern is a tool you pick up when a specific problem shows up.
🌍 In real life

🧰 You do not buy every tool in the shop and then look for things to hit. You see a loose screw, then pick the screwdriver. Patterns work the same way.

Azure’s catalog says it plainly: choose a pattern based on the problem you need to solve, not the technology you want to use — and expect trade-offs.

🧭 Two ways to start
📋 Look-alikes: which one?
PairHow they differ
Adapter vs DecoratorAdapter changes the shape; Decorator keeps the shape and adds behaviour.
Decorator vs ProxySame structure; Decorator adds features, Proxy controls access.
Strategy vs StateStrategy is chosen from outside; State changes by itself.
Factory vs BuilderFactory picks which class; Builder assembles one complex object step by step.
Observer vs CommandObserver notifies many listeners; Command packages one request.
Retry vs Circuit BreakerRetry fixes short hiccups; Breaker stops hammering a broken service. Use both.
CQRS vs Event SourcingCQRS splits read/write models; Event Sourcing stores changes as events. Can be used together or alone.
🔗 Patterns that work well together
CombinationWhy
Factory + StrategyThe factory chooses which strategy to hand out.
Decorator + Proxy chains (middleware)Cross-cutting layers: logging, caching, retry, auth.
CQRS + Event SourcingEvents feed the read models.
Saga + Retry + Circuit BreakerSteps are retried safely; failing services are not hammered.
Repository + Unit of WorkCollection-like access with grouped saving.
🎯 Spot it: which pattern would you try first?
▾ “Adding a payment method means editing five switch statements.”

✅ Right idea. Strategy (one class per method), possibly with a Factory to pick it. Page 10 + 2.

▾ “The vendor SDK’s types are all over our code.”

✅ Right idea. Adapter behind your own interface. Page 5.

▾ “The user wants undo.”

✅ Right idea. Command with a history. Page 12.

▾ “Our service falls over whenever a dependency is slow.”

✅ Right idea. Circuit Breaker with Retry and a fallback. Page 20.

🔥 Interview recall
  • Start from the pain; the pattern is the answer, not the starting point.
  • Patterns have costs: more classes, more indirection.
  • Know the look-alike pairs: Adapter/Decorator, Decorator/Proxy, Strategy/State.
  • Combine patterns when the problem needs it.
  • Prefer the smallest pattern that removes the actual pain.
🎤 Say this in an interview
"I start from the problem — repeated creation, a foreign API, behaviour to add, many ways of doing one thing, many listeners, reliability — and pick the smallest pattern that removes exactly that pain, knowing each one costs extra classes and indirection. I can tell look-alikes apart, like Adapter versus Decorator or Strategy versus State, and I combine patterns where it helps."
⚠️ Common trap

Pattern-first design. You end up with layers nobody needs.

Memorising diagrams. Learn the problem each pattern solves.
