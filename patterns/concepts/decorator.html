Concept 6 of 24 · 🔧 Structural

Coffee with milk and sugar: wrap it, do not rebuild it.

The Decorator pattern with a coffee order: add behaviour by wrapping an object in another that has the same shape.

❓ "What is the Decorator pattern and how does it differ from inheritance?"
👁 See it first
🎯 Add behaviour by wrapping an object in another object of the same shape — extras become stackable layers.
🌍 In real life

☕ A coffee does not turn into a new drink when you add milk: you take the same coffee and add a layer. Add sugar: another layer. Each layer adds a little to the price, and the result is still “a coffee”.

refactoring.guru: Decorator attaches new behaviours to objects by placing them inside wrapper objects that contain the behaviours; wrappers implement the same interface as the wrapped object, so to the client they look identical.

☕ The fix: wrap, wrap, ask
🎭 Who is who
Role in the patternIn our storyIn code
Component (the shape)“a coffee”ICoffee
Concrete componentthe espressoEspresso
Decoratorsmilk, sugarMilk(ICoffee inner)
🧪 Tiny code
interface ICoffee { decimal Cost(); }

class Espresso : ICoffee { public decimal Cost() => 2.00m; }

class Milk(ICoffee inner) : ICoffee
{
    public decimal Cost() => inner.Cost() + 0.50m;      // ask the inner one, add my bit
}
class Sugar(ICoffee inner) : ICoffee
{
    public decimal Cost() => inner.Cost() + 0.20m;
}

ICoffee order = new Sugar(new Milk(new Espresso()));     // layers
Console.WriteLine(order.Cost());                          // 2.70

Each wrapper holds the thing it wraps (inner) and implements the same interface.

You write…It is…

A logging or caching wrapper around a repositorythe everyday use of Decorator

Middleware and handler chains are described by Microsoft; calling them decorator-like is a common reading.

🎯 Spot it: is the pattern a good fit?
▾ Add logging to every call of a repository without editing it

✅ Good fit. A logging decorator wraps the repository and delegates.

▾ You can simply add a parameter to the one class

❌ Overkill. Do the simple thing.

▾ Extras should be combinable in any order at run time

✅ Good fit. Stackable wrappers are the classic fit.

▾ Wrappers that must know about each other’s internals

❌ Overkill. Then they are not independent layers; reconsider.

👀 How to spot the need in your own code
If you see…Do this
Subclass names like LoggedCachedRepositoryCombination classes. Use wrappers.
Boolean flags like withMilk, withSugar in one classThe class grows with every extra. Wrap instead.
Cross-cutting needs (logging, caching, retry, timing)Decorators fit these well.
🔥 Interview recall
  • Decorator = a wrapper with the same interface that adds behaviour.
  • Stackable in any order; each layer delegates to the inner one.
  • Replaces subclass-per-combination.
  • Adapter changes the interface; Decorator keeps it.
🎤 Say this in an interview
"A Decorator wraps an object in another that implements the same interface and adds behaviour before or after delegating. Like adding milk and sugar to a coffee, the layers stack in any order, and I avoid a subclass for every combination. I use it for cross-cutting concerns like logging and caching."
⚠️ Common trap

Order matters. Wrapping retry outside or inside logging gives different results.

Too many layers make stack traces hard to read.
