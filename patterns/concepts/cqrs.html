The café: a menu board for looking, an order counter for changing.

CQRS (Command Query Responsibility Segregation) with a café: use one model to change data and a separate one to read it.

❓ "What is CQRS, and what are its trade-offs?"
👁 See it first
🎯 Use one model for changing data (commands) and another for reading it (queries), so each can be built for its own job.
🌍 In real life

☕ A café has a menu board everyone can read quickly, and a separate order counter where staff check the rules (is this in stock? is it paid?). You do not queue at the menu board, and you do not read the menu from the till.

The Azure Architecture Center describes CQRS as segregating the read and write operations for a data store into separate data models, which lets you optimize each independently — at the cost of complexity and eventual consistency.

✋ The fix: two sides

🧪 Tiny code
// Write side: rules live here
record PlaceOrder(int CustomerId, List<int> ProductIds);
class PlaceOrderHandler(IOrderRepository repo)
{
    public void Handle(PlaceOrder cmd)
    {
        if (cmd.ProductIds.Count == 0) throw new InvalidOperationException("empty order");
        repo.Add(Order.Create(cmd.CustomerId, cmd.ProductIds));
    }
}

// Read side: no rules, just shape
record OrderSummary(int Id, string Customer, decimal Total);
class OrderQueries(ReadDb db)
{
    public List<OrderSummary> ForCustomer(int id) => db.OrderSummaries.Where(o => o.CustomerId == id).ToList();
}

You can start simple: two code paths over the same database. Separate stores come later, if needed.

🎯 Spot it: is the pattern a good fit?
▾ Reads and writes have very different shapes or load

✅ Good fit. CQRS lets you tune each side.

▾ A small CRUD screen

❌ Overkill. CQRS adds complexity for nothing.

▾ Reads must always show the very latest write

❌ Overkill. With separate stores, reads can lag. Be sure that is acceptable.

▾ Complex business rules on writes, many read-only views

✅ Good fit. A classic fit.

👀 How to spot the need in your own code
If you see…Do this
One entity class stuffed with fields only some screens needSplit read shapes from the write model.
Reporting queries slowing down the same tables used for ordersA separate read model helps.
🔥 Interview recall
  • CQRS = separate models for commands (change) and queries (read).
  • Each side can be optimised and scaled independently.
  • Cost: more code, and eventual consistency if the stores are separate.
  • Often used with Event Sourcing — but you can use one without the other.
🎤 Say this in an interview
"CQRS separates the write model, which holds the business rules, from the read model, which is shaped for fast queries — like a menu board versus an order counter. It lets each side be optimised and scaled independently, but adds complexity and, with separate stores, eventual consistency, so I use it only where reads and writes really differ."
⚠️ Common trap

CQRS everywhere. It is not a default architecture.

Ignoring staleness. Decide how fresh the read side must be.
