Booking a trip: if a later step fails, undo the earlier ones.

The Saga pattern with a trip booking: coordinate a task across several services using small steps, each with a compensating undo step.

❓ "What is the Saga pattern and why are distributed transactions avoided?"
👁 See it first
🎯 Split a long task into small steps, and give each step an “undo” step, so if something fails you run the undos backwards.
🌍 In real life

🧳 If you book a flight, a hotel and a car and the car is sold out, you do not just give up: you cancel the hotel and the flight. Each cancel is the “undo” of a booking.

The Azure Architecture Center describes Saga as managing data consistency across microservices with independent data stores, using a sequence of local transactions with compensating actions to reverse failures; retryable steps should be idempotent.

🧳 The fix: steps with undo steps

🧪 Tiny code
class BookTripSaga(IFlights flights, IHotels hotels, ICars cars)
{
    public bool Run()
    {
        var f = flights.Book();
        var h = hotels.Book();
        if (h is null) { flights.Cancel(f); return false; }           // undo step 1
        var c = cars.Book();
        if (c is null) { hotels.Cancel(h); flights.Cancel(f); return false; }   // undo 2, then 1
        return true;
    }
}

Real sagas run over messages (queues) and must make each step and each undo safe to repeat (idempotent). This sketch shows the idea only.

🎯 Spot it: is the pattern a good fit?
▾ A business process across services with separate databases

✅ Good fit. Sagas keep it consistent without a global transaction.

▾ Everything lives in one database

❌ Overkill. Use a normal database transaction.

▾ Some steps cannot be undone (an email already sent)

❌ Overkill. Plan for it: order such steps last, or use a different design.

▾ You need steps to be safe to retry

✅ Good fit. Design each step to be idempotent.

👀 How to spot the need in your own code
If you see…Do this
A multi-service process with manual “clean up” scripts for failuresMake the undo steps part of the design.
Two-phase commit across servicesConsider a saga instead.
🔥 Interview recall
  • Saga = sequence of local transactions, each with a compensating (undo) action.
  • Replaces distributed transactions across services.
  • Steps and compensations should be idempotent.
  • Watch for temporary inconsistency while the saga runs.
🎤 Say this in an interview
"A Saga coordinates a long business process across services without a distributed transaction: it runs local steps in order and, if one fails, runs compensating actions for the earlier steps in reverse, like cancelling a hotel and flight when the car can’t be booked. Steps need to be idempotent, and the data is briefly inconsistent while it runs."
⚠️ Common trap

Undo is not always possible. Some actions cannot be reversed.

No idempotency. Retries create duplicates.
