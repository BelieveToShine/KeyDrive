The “to send” tray: save the message in the same step as the data.

The Transactional Outbox pattern: record the message to send in the same database transaction as the data change, then deliver it separately.

❓ "What problem does the Transactional Outbox solve?"
👁 See it first
🎯 Write the data and the “message to send” in one database transaction, and let a separate worker deliver the message.
🌍 In real life

📮 An office keeps an outgoing-mail tray. When you finish a form you put the form in the file and a note in the tray in one go. A clerk later empties the tray and posts the letters, trying again if the post office is closed.

This pattern is widely used with messaging; the Azure Architecture Center’s messaging and saga guidance discusses reliable publishing. This page describes the usual form.

🔧 The pattern fixes it
🧪 Tiny code
using var tx = db.Database.BeginTransaction();
db.Orders.Add(order);
db.Outbox.Add(new OutboxMessage("OrderPlaced", JsonSerializer.Serialize(order)));
db.SaveChanges();
tx.Commit();                                   // both saved, or neither

// separate background worker
foreach (var m in db.Outbox.Where(m => m.SentAt == null))
{
    broker.Publish(m.Type, m.Payload);          // may be sent more than once → receivers must be idempotent
    m.SentAt = DateTime.UtcNow; db.SaveChanges();
}

Sketch only. Delivery is “at least once”, so consumers must tolerate duplicates.

🎯 Spot it: is the pattern a good fit?
▾ You must update a database AND publish an event, reliably

✅ Good fit. Outbox gives you that.

▾ Everything stays inside one database

❌ Overkill. No messaging, no outbox.

▾ Losing an occasional message is acceptable

❌ Overkill. Then simpler publishing may do.

▾ Consumers cannot cope with duplicates

❌ Overkill. Fix idempotency first.

👀 How to spot the need in your own code
If you see…Do this
Code that saves to the database and then publishes in the next lineA crash between the two loses the event.
🔥 Interview recall
  • Outbox = store the outgoing message in the same transaction as the data; deliver later.
  • Avoids lost messages without distributed transactions.
  • At-least-once delivery → idempotent consumers.
🎤 Say this in an interview
"The Transactional Outbox stores the message to publish in the same database transaction as the data change, and a separate relay delivers it, retrying on failure. It avoids the gap where the data is saved but the event is lost, at the cost of at-least-once delivery, so consumers must be idempotent."
⚠️ Common trap

Forgetting idempotency. Duplicates will happen.
