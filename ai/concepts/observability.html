Concept 18 of 19 · 🚀 Shipping it

Observability shows you exactly what happened on the one request that went wrong.

Evaluation scores the system overall. Observability is what you need when one specific real request fails and you have to find out why, not just that it did.

❓ "A user says the answer was wrong. How do you find out what actually happened?"
👁 See it first
🎯 Observability = being able to see exactly what the system did on one specific real request, not just its overall score.
📖 Why did this need to exist?

Evaluation gives you an aggregate score across many test cases, but it doesn't explain a specific failure a real user actually hit in production — which step went wrong, and why, for that one request.

Observability means logging and being able to inspect every step of a real request — what was retrieved, what tools were called, what the model actually saw and produced — so a specific failure has a specific, findable cause instead of an unreproducible mystery.

▾ Go one level deeper (60 seconds)

This matters even more for agent and tool-using systems than for a single prompt-response, simply because there are far more steps where something can go wrong — a bad retrieval, a wrong tool call, a misread observation. A useful trace covers the whole loop (plan, act, observe), not just the final output.

Evaluation and Observability answer different questions and both stay necessary: "is the system good overall" versus "what exactly happened in this one case."

🔥 Interview recall
  • Observability = a full, inspectable trace of one specific real request.
  • It exists because an aggregate evaluation score can't explain one user's specific failure.
  • A useful trace covers the whole agent loop, not just the final answer.
  • Evaluation (aggregate) and Observability (specific) answer different questions — you need both.
🎤 Say this in an interview
"Observability means logging and being able to inspect every step of a real request — what was retrieved, what tools were called, what the model saw and produced — so a specific failure has a findable cause. It answers a different question than evaluation: not 'is the system good overall,' but 'what exactly happened in this one case.'"
⚠️ Common trap

A great evaluation score doesn't mean you don't need observability. Evaluation and observability solve different problems — one tells you the system is good on average, the other tells you what happened in one specific case. Skipping either leaves a real gap: no way to catch systemic issues, or no way to debug a specific complaint.

📊 Evaluation

Aggregate score across many test cases.

🔍 Observability

▾ 💻 Tiny illustrative example 
# Every step of the loop gets logged as it runs, not reconstructed after the fact
trace = []
def run_step(name, fn, *args):
    result = fn(*args)
    trace.append({"step": name, "input": args, "output": result})
    return result
# a bad answer now has a findable cause: read back through `trace`

Illustrative shape only — real observability tooling adds timing, cost, and structured search over traces like this.
