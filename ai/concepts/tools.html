Concept 11 of 17 · 🤖 Acting on goals

Tools let "act" mean doing something real, not just generating text about it.

The agent loop needs a real "act" step. Tools are the real functions — an API, a calculator, a database query — that turn a decision into an actual action.

❓ "Does the model itself run the tool, or does something else?"
👁 See it first
🎯 Tools = real functions an agent can call, so "act" means doing something real, not generating text about it.
📖 Why did this need to exist?

An agent that can only produce text can't actually check today's weather, run a calculation, search the web, or send an email — it can only generate plausible-sounding text about doing those things, which isn't the same as doing them.

Tools give the agent real functions to call — a search API, a calculator, a database query. That makes "act" in the agent loop mean actually doing something, and "observe" mean seeing a real result, not an imagined one.

▾ Go one level deeper (60 seconds)

The model itself never runs the tool. Its job is to decide which tool fits the current step and what arguments to call it with — that decision comes out as structured output, not free text. Separate code around the model — not the model — actually executes the call (hits the API, runs the query) and hands the real result back into the model's context for its next step.

That separation matters: the model can be wrong about which tool to use or what arguments to pass, but it never directly touches the outside world itself.

🔥 Interview recall
  • Tools = real functions (API calls, calculators, queries) an agent can invoke.
  • The model decides which tool and which arguments — it doesn't execute the tool itself.
  • Separate surrounding code actually runs the call and returns the real result.
  • Tools are what makes "observe" in the agent loop see something real, not imagined.
🎤 Say this in an interview
"Tools are real functions an agent can call — a search API, a calculator, a database query. The model decides which tool to use and what arguments to pass, as structured output; the surrounding system actually executes the call and returns a real result, which becomes the agent's next observation."
⚠️ Common trap

The model doesn't run the tool — the system around it does. Saying "the model called the API" is shorthand; the more precise version is "the model decided to call the API, and the surrounding code actually called it." That separation is exactly what keeps a model's mistake from directly touching a real system unchecked.

▾ 💻 Tiny illustrative example 
# The model decides; the surrounding code executes
tools = {"get_weather": get_weather_api, "search": web_search}

decision = model.generate(prompt, available_tools=tools)  # model picks tool + args
if decision.tool_call:
    result = tools[decision.tool_call.name](**decision.tool_call.args)  # system runs it
    # result feeds back in as the agent's next observation

Illustrative shape only — real tool-calling APIs add schemas, validation, and error handling around this core idea.
