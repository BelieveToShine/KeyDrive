Concept 17 of 19 · 🚀 Shipping it

Evaluation turns "it seems to work" into an actual number.

You have a real application now. Evaluation is how you find out — with evidence, not a vibe — whether it actually works, and whether a change made it better or worse.

❓ "How do you know a change to the prompt or model actually helped?"
👁 See it first
🎯 Evaluation = running test cases through the real system and scoring outputs against known-good answers.
📖 Why did this need to exist?

"It seems to work" isn't rigorous enough once real users depend on it. AI systems can fail in subtle, inconsistent ways that a handful of manual checks won't catch, and a change that helps one case can quietly break another.

Evaluation runs a set of test cases with known-good answers through the actual system, compares real outputs against what was expected, and turns that into a repeatable score — so "did this change help or hurt" has an actual, checkable answer.

▾ Go one level deeper (60 seconds)

Grading isn't always an exact match, and not every method even needs a pre-written "expected" answer. The test-cases-with-known-answers shape above is the easiest to explain, but it's one of several recognized ways to grade:

✅ Exact match

Output equals a known-good answer exactly. Strict — fine for short, deterministic outputs.

📄 Reference-based

Scored by similarity to a known-good answer, not exact equality — for open-ended text.

⚖️ Rubric / LLM judge

A human rubric or another model grades the output against specific criteria — no fixed answer needed.

🧑 Human evaluation

A person reviews the output directly — slower, but catches what automated checks miss.

🔀 Pairwise comparison

Two outputs are compared head-to-head — which is better — rather than scored in isolation.

🎯 Task/outcome success

Did the task actually get done (e.g. booking completed)? Judged by outcome, not answer text.

Whichever method fits, the goal is the same: a repeatable score, not a one-off impression.

🔥 Interview recall
  • Evaluation = running the real system against a set of cases and scoring the outputs — known-good answers are the common shape, not the only one.
  • It exists because "seems to work" doesn't catch subtle, inconsistent failures.
  • Grading methods: exact match, reference-based, rubric/LLM judge, human review, pairwise comparison, task/outcome success.
  • A good score only covers what the test set actually tests — see Observability for the rest.
🎤 Say this in an interview
"Evaluation runs a set of test cases with known-good answers through the real system and scores the actual outputs against expectations, so you get a repeatable number instead of a one-off impression. For open-ended output, grading usually needs a rubric or a judging model rather than an exact text match."
⚠️ Common trap

A good score only covers what your test set actually tests. A narrow or stale set of test cases can hide real failures on the inputs that actually show up in production. A high evaluation score is evidence, not proof — it's part of why watching real, live traffic (Observability, next) still matters.

▾ 💻 Tiny illustrative example 
# Run the real system against known-good test cases, then grade it
test_cases = load_test_cases()   # inputs + expected answers
results    = [ai_app.run(c.input) for c in test_cases]

score = grade(results, [c.expected for c in test_cases])  # e.g. 0.87

Illustrative shape only — real evaluation pipelines track many scores over time, not just one run.
