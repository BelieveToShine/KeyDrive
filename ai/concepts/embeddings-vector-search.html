Concept 7 of 19 · 🛠️ Using the model

Embeddings turn meaning into numbers you can compare.

Prompting steers a model with words. But finding the single most relevant document out of thousands needs a way to compare meaning directly, not just match text — that's what embeddings and vector search do, and it's what RAG's "retrieve" step actually relies on.

❓ "How does a computer know 'vacation policy' and 'time off rules' mean roughly the same thing?"
👁 See it first
🎯 Embeddings = converting text into a vector positioned so similar meaning ends up nearby; vector search finds the closest ones.
📖 Why did this need to exist?

Comparing text by matching exact words breaks down constantly. "Vacation policy" and "time off rules" share no words but mean nearly the same thing; "python" the language and "python" the snake share a word but mean nothing alike. Keyword matching can't tell these apart reliably.

Embeddings convert a piece of text into a vector — a long list of numbers — positioned so that texts with similar meaning end up as nearby vectors. Vector search then just means finding the nearest vectors to a query vector, which is a reasonable numerical stand-in for finding the most similar meaning.

▾ Go one level deeper (60 seconds)

"Nearby" is measured with a distance or similarity calculation between two vectors — cosine similarity is a common choice. An embedding model is itself a trained model (the same Machine Learning idea from earlier in this journey, just producing a vector instead of a single prediction), trained so that its notion of "nearby" lines up with actual similarity in meaning.

At real scale — millions of documents — comparing a query vector against every single stored vector one by one gets slow. Production vector search uses specialized indexes built to find the nearest matches quickly without checking every candidate, but the underlying idea is exactly the "find the closest vectors" concept shown here.

Nothing about this idea is specific to text, either. Images, audio, and other kinds of data can be embedded the same way — turned into a vector positioned by similarity in whatever sense matters for that data — which is part of what makes multimodal search and retrieval possible.

🔥 Interview recall
  • Embeddings convert text into a vector positioned by meaning, not by exact words.
  • Similar meaning → nearby vectors; unrelated meaning → distant vectors.
  • Vector search = finding the nearest vectors to a query vector.
  • An embedding model is itself a trained model — this is Machine Learning, applied to produce a vector.
🎤 Say this in an interview
"Embeddings convert text into a vector positioned so that texts with similar meaning end up close together in that vector space. Vector search compares a query's embedding against stored embeddings and returns the nearest ones, which is how systems match by meaning instead of by exact keywords."
⚠️ Common trap

A close vector means related meaning, not a correct or sufficient answer. Vector search can reliably surface material that's topically similar to a query and still miss the one document that actually answers it, or return something related but wrong. Treat it as a strong first filter for relevance, not a guarantee of correctness.

📍 Embeddings & Vector Search

Compares meaning as numbers, to find relevant material — the mechanism behind RAG's retrieval step.

▾ 💻 Tiny illustrative example 
# Embed once, then find the nearest stored vectors to a query
doc_vectors = [embed(doc) for doc in documents]   # done ahead of time

query_vector = embed("time off rules")
scores = [cosine_similarity(query_vector, v) for v in doc_vectors]
top_matches = top_k(documents, scores, k=3)  # the 3 closest in meaning

Illustrative shape only — real vector search uses an index rather than scoring every document one by one.
