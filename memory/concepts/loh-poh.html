The oversize parcel shelf — big things get their own place.

Why objects of 85,000 bytes or more are stored separately, what “not compacted” means, and what pinned objects do to memory.

❓ "What is the Large Object Heap and why does it matter?"
👁 See it first
🎯 Objects of 85,000 bytes or more go to the Large Object Heap, which is collected with gen 2 and not compacted by default.
🌍 In real life

📦 The post office has a normal shelf for ordinary parcels and a separate floor area for oversize ones. Oversize parcels are too heavy to keep shuffling around, so they stay where they were put. When one leaves, it leaves a gap exactly its size.

A new oversize parcel only fits if the gap is big enough.

📌 Pinned objects: the ones that cannot move
📍 The pinned object heap: pinned buffers kept out of the way
🧾 The heaps at a glance
HeapHoldsCollected withCompaction
Small object heapobjects below the 85,000-byte thresholdgen 0 / 1 / 2 as they agesurvivors can slide together (compaction)
🐘 Large object heap (LOH)objects of 85,000 bytes or more (big arrays, big strings)gen 2not by default: holes stay
📌 Pinned object heap (POH)arrays allocated as pinned with GC.AllocateArray(..., pinned: true)gen 2never moved (that is its purpose; per the API docs)
🛠️ How to be kind to the LOH

Avoid creating many large temporary arrays (for example a new 100 KB buffer per request). Reuse them — ArrayPool<T> (page 28) was made for this.

The POH exists so pinned buffers do not sit in the middle of the normal heap and block its compaction. You rarely use it directly; it matters mostly to libraries that talk to native code.

🧪 Tiny code
var small = new byte[1_000];       // small object heap, generation 0
var big   = new byte[100_000];     // ≥ 85,000 bytes → large object heap (collected with gen 2)

// pinned buffer for native interop (the "pinned object heap")
byte[] buf = GC.AllocateArray<byte>(4096, pinned: true);

The threshold (85,000 bytes) is the documented default; it is the size of the object, not the count of elements.

♻️ Who clears this memory?

The GC — but only during gen 2 collections, which are rare. A program that keeps allocating big arrays can use a lot of memory before they are reclaimed. Reuse big buffers instead of allocating new ones.

🎯 Check yourself
▾ A 100,000-byte array is allocated in generation 0.

❌ Wrong. It goes to the large object heap, which is collected with gen 2.

▾ The LOH is not compacted by default.

✅ Right. Yes — freed space stays as holes.

▾ Pinned objects make compaction easier.

❌ Wrong. They cannot be moved, so they cause fragmentation.

🔥 Interview recall
  • ≥ 85,000 bytes → LOH (collected with gen 2).
  • LOH not compacted by default → holes stay → fragmentation.
  • Pinned = must not move; POH keeps pinned arrays apart.
🎤 Say this in an interview
“Objects of 85,000 bytes or more are allocated on the large object heap, which is collected with generation 2 and, by default, is not compacted. Pinned objects can’t be moved, so too many of them fragment the heap; arrays pinned on purpose can go on the pinned object heap.”
⚠️ Common trap

Allocating a new big buffer (a large array or string) per request. Each one waits for a gen 2 collection and can fragment the LOH.
