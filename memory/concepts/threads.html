Concept 24 of 29 · 🧵 Threads & async

Workers with their own desks and one shared warehouse.

What happens to memory with one thread versus many: every thread gets a private stack, but the heap and static fields are shared — and shared memory needs care.

❓ "How do threads relate to stack, heap and static memory in .NET?"
👁 See it first
🎯 Each thread has its own stack; all threads share the heap and static memory.
🌍 In real life

🏢 An office with several workers. Each has a private desk (stack) with their own notes. The warehouse (heap) and the lobby notice board (statics) are shared by everyone.

Your notes are safe; but if two workers grab the same item from the warehouse and change it at the same time, they can step on each other.

💥 Why shared memory needs care: a race
🗺️ What is private and what is shared?
MemoryPer thread?Notes
📚 Stack (locals, parameters)🔒 private to each threadone stack per thread; each thread’s stack is its own set of GC roots
🏠 Heap objects🌍 sharedany thread with the reference can read or change them
📌 Static fields🌍 sharedone copy for the app, visible to every thread
📌 [ThreadStatic] / ThreadLocal<T>🔒 one copy per threada static that is deliberately per-thread
🛡️ Making shared data safe
ToolUse it for
lockonly one thread at a time inside a block
Interlocked.Incrementa single atomic add on a number
immutable objects (all fields readonly / init-only)objects that never change after creation cannot race
don’t share: give each thread its own copythe simplest safe approach
🧪 Tiny code
class Counter { public int Value; }

var c = new Counter();                    // one heap object, shared

// ❌ unsafe: two threads can lose updates
Parallel.For(0, 1000, _ => c.Value++);

// ✅ safe: one atomic step
Parallel.For(0, 1000, _ => Interlocked.Increment(ref c.Value));

[ThreadStatic] static int perThread;      // each thread sees its own copy

Locals (the reference c itself, i) are private to each thread; the Counter object they point at is shared.

♻️ Who clears this memory?

A thread’s stack goes away when the thread ends. Heap objects are cleaned by the GC when no root can reach them; the roots are every thread’s stack plus the statics. So an object stays alive as long as any one thread still holds a reference to it.

🎯 Check yourself
▾ Two threads share the same local variables.

❌ Wrong. Each thread has its own stack, so its own locals.

▾ Two threads holding a reference to the same object can both change it.

✅ Right. Yes — the heap is shared, which is why races happen.

▾ static fields are private to each thread by default.

❌ Wrong. They are shared unless marked [ThreadStatic].

🔥 Interview recall
  • One stack per thread; heap and statics shared.
  • Races happen on shared heap/static data (including a captured local), not on locals only one thread can reach.
  • Fix with lock/Interlocked, immutability, or not sharing.
🎤 Say this in an interview
“Each thread has its own stack, so locals are private; the managed heap and static fields are shared, so any mutable shared state needs synchronisation — lock, Interlocked, or immutability. ThreadStatic gives a per-thread copy of a static.”
⚠️ Common trap

Assuming Value++ is a single step. It is read-modify-write and can lose updates when shared.
