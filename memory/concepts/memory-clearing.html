Leaving a hotel room vs returning the key.

A clear, complete answer to “when is memory freed?”: stack on return, heap objects at a later GC, and files, sockets and handles only when you dispose them.

❓ "When and how is memory released in .NET, and what are Dispose and finalizers for?"
👁 See it first
🎯 Memory is cleared by place: stack on return, heap at some later GC, outside resources only when you Dispose them.
🌍 In real life

🏨 Leaving a hotel room (becoming unreachable): you walk out and nobody can use your things — but the room is only cleaned when housekeeping (the GC) next comes round. And if you borrowed a key card or a towel (a file, a socket), housekeeping doesn’t know about it: you must return it yourself at the desk (Dispose).

🔑 With using: Dispose releases the file, not the memory
⚠️ Without using: the file stays locked until a finalizer

🧰 The right habits

Use using for anything that implements IDisposable (files, streams, HttpClient responses, database connections).

Remember what Dispose does: it releases what the object owns (a handle, a connection). The object’s own heap memory is still reclaimed by the GC later.

Do not write a finalizer unless your class directly owns a raw native handle; even then prefer wrapping it in a SafeHandle.

Do not call GC.Collect() to “free memory”. The GC picks the best time itself; forcing it usually slows the app down. Microsoft’s ASP.NET Core guidance says production apps should generally not call it; it is a diagnostic tool.

🔬 Honest note on finalizers

Microsoft documents Dispose, SuppressFinalize and SafeHandle. How exactly the GC queues finalizable objects, and that they live through an extra collection, is described in older Microsoft articles; the lab draws a teaching picture without claiming internal queue details. The handle value and object layout in the pictures are illustrative.

🧪 Tiny code
using (var file = File.OpenRead("data.txt"))   // IDisposable
{
    // use the file
}                                              // Dispose() runs here, even if an exception was thrown

// same thing, shorter (C# 8+): disposed at the end of the enclosing scope
using var stream = File.OpenRead("data.txt");

// DON'T:  GC.Collect();   // forcing a collection is almost never the answer

The GC would free the FileStream’s memory eventually, but the file could stay locked until then.

♻️ Summary

Stack: the frame is popped on return. Heap: some later GC after the object is unreachable. Outside resources: when you Dispose. Statics: stay alive for the whole run (they are roots). If you remember one rule: let the GC handle memory, and use using for everything else.

🎯 Check yourself
▾ Memory is freed the instant an object becomes unreachable.

❌ Wrong. It is reclaimed during a later garbage collection.

▾ using guarantees Dispose is called at the end of the block.

✅ Right. Yes, even when an exception is thrown.

▾ Dispose frees the FileStream object’s heap memory.

❌ Wrong. It releases the file handle; the heap memory is reclaimed by a later GC.

▾ A finalizer is a good replacement for calling Dispose.

❌ Wrong. It runs late and unpredictably — only a safety net.

🔥 Interview recall
  • Unreachable ≠ freed: the GC reclaims later.
  • using/Dispose for files, sockets, connections.
  • Dispose frees the file, not the heap memory.
  • Finalizer = late safety net; SafeHandle for native handles.
  • Do not call GC.Collect() in production code.
🎤 Say this in an interview
“The GC reclaims managed memory at a time it chooses, after objects become unreachable. It doesn’t know about unmanaged resources like file handles, so I implement IDisposable and use ‘using’. A finalizer is just a backup, and I avoid calling GC.Collect.”
⚠️ Common trap

Relying on the GC to release a file or connection — it may stay open (and locked) for a long time.
