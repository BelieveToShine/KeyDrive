A coin, a claim ticket, or a small bag — three ways to hand back a result.

What a return really does: copy a value, or copy an address (the object survives on the heap), or copy a small bundle of values (a tuple) — and what each costs the GC.

❓ "What happens in memory when a method returns a value, an object or a tuple?"
👁 See it first
🎯 A return is a copy: of the value (value types), of the address (objects, so the object lives on), or of the bundle (a tuple).
🌍 In real life

🪙 Handing back a coin: the other person gets their own coin; yours is spent. 🎟️ Handing back a claim ticket: the parcel stays in the warehouse; only the ticket moves. 👝 A tuple is a small bag holding two coins: you hand over the bag, no warehouse involved.

🎟️ Returning an object: the frame goes, the object stays
👝 Returning a tuple: a small value bundle

⚡ Performance lens — think like this

Returning two values? Prefer a value tuple (or out) over a small class: no allocation, no GC work.

Returning a new object from a hot method means one allocation per call. If callers can supply a reusable object or buffer (page page 28), you can avoid it.

Returning a collection hands out the same object you hold. If you return your internal list, callers can change it — return a copy or a read-only view when that matters.

🧪 Tiny code
int Total()                   { int sum = 42; return sum; }          // a copy of 42
Person Make()                 { var p = new Person("Asha"); return p; } // a copy of the address
(int Count, decimal Sum) Stats() => (3, 59.5m);                       // a value tuple: no heap

var t   = Total();            // 42
var who = Make();             // the Person survives: who points to it
var r   = Stats();            // r.Count = 3, r.Sum = 59.5
var (count, sum) = Stats();   // deconstruct into two locals

Value tuples ((int, decimal)) are value types; the old Tuple<int, decimal> class is a reference type.

♻️ Who clears this memory?

The callee’s frame: popped at return. A returned object: lives on until the GC finds it unreachable. A returned value or tuple: lives in the caller’s frame and is popped when the caller returns.

🎯 Check yourself
▾ An object created inside a method is destroyed when the method returns.

❌ Wrong. It lives on the heap; it survives as long as something (like the returned reference) points to it.

▾ Returning a value tuple allocates a heap object.

❌ Wrong. Value tuples are value types: copied, no heap object.

▾ Returning an object copies the whole object to the caller.

❌ Wrong. Only the address is copied.

🔥 Interview recall
  • Return = copy: value, address, or tuple of values.
  • Objects outlive the method that made them.
  • Value tuples are allocation-free; Tuple<…> classes are not.
🎤 Say this in an interview
“A return copies a result into the caller: the value for value types, the reference for objects — so the object survives on the heap — and the contained values for a value tuple, which allocates nothing. I use value tuples for multiple returns in hot paths.”
⚠️ Common trap

Returning a reference to a local variable by ref — the frame is about to disappear, so the compiler rejects it.
