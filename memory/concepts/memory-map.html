Concept 1 of 29 · 🗺️ The map

Where does your data actually live?

One picture of the three main places in .NET memory — the stack, the heap and static memory — and who cleans each. The rest of the lab zooms into every box.

❓ "Explain stack, heap and static memory in .NET."
👁 See it first
🎯 Stack = short-lived notes for the running method. Heap = objects. Static = one copy for the whole app.
🌍 In real life

🏢 Think of an office. The stack is the sticky note on your desk: quick to write, thrown away when the task is done.

The heap is the big storage room: boxes (objects) are put there, and a cleaner (the garbage collector) removes boxes nobody has a note for.

The static area is the notice board in the lobby: one copy for the whole building, and it stays up until the building closes.

⚠️ A simplification you should know

Teaching pictures say “value types live on the stack, objects on the heap”. Microsoft’s docs are more careful: a value type keeps its data where the variable is — so a value inside an object lives inside that object on the heap. We will draw this exactly on the next pages.

Also, the runtime may keep small values in CPU registers. That is an implementation detail; the rules on this lab’s pages are the ones the language guarantees.

🧪 Tiny code
static int count = 1;              // static memory: one copy for the whole app

void Hello()
{
    int age = 30;                  // stack: a slot for the number 30
    var p = new Person("Asha");    // heap: the Person; stack: p holds its address
}                                  // method ends: age and p are gone; Person waits for the GC

The word “stack” and “heap” are the names Microsoft’s docs use. Addresses like 0x…A1 in the pictures are made up.

♻️ Who clears this memory?

Stack: the moment the method returns. Heap: the garbage collector (pages 19–23). Static: never during the run; the app’s end releases it.

🎯 Check yourself
▾ A variable of type Person holds the whole Person object inside it.

❌ Wrong. It holds only a reference (address). The object itself is on the heap.

▾ static int count disappears when the method that uses it ends.

❌ Wrong. A static field lives for the whole app, not for a method call.

▾ When a method returns, its locals are gone but objects they pointed to may still exist.

✅ Right. Yes — the stack slot is popped, the heap object waits for the GC.

🔥 Interview recall
  • Three main places: stack, heap, static memory.
  • Stack: per-thread, cleaned when the method returns. Heap: objects, cleaned by the GC. Static: one copy per app.
  • A reference variable on the stack points to an object on the heap.
🎤 Say this in an interview
“Each thread has a stack for method calls and locals. Objects made with new live on the managed heap and the garbage collector reclaims them once nothing references them. Static fields live in static memory for the life of the app.”
⚠️ Common trap

Saying “value types always live on the stack.” A value type lives wherever its variable lives — inside an object, that is on the heap.
