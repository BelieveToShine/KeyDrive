Concept 9 of 29 · ⚙️ Static & methods

A photocopy of a photo vs a copy of an address card.

What the method really receives: always a copy — of the value for value types, of the address for objects. That one rule explains why changing an object “inside” a method shows up outside, and why reassigning a parameter does not.

❓ "If I pass an object to a method, can the method change it? What about reassigning it?"
👁 See it first
🎯 Arguments are always copied. For an object, the copy is the address — so the method can change the object but cannot change which object the caller points to.
🌍 In real life

📷 Value type: you hand a friend a photocopy of a photo. They can scribble all over it; your original photo is fine.

🏠 Object: you hand a friend a copy of an address card. They can walk to the house and repaint it — and you will see the new paint. But if they tear up their card and write another address, your card is unchanged.

🏠 Passing an object: changes are visible to the caller
✂️ Reassigning the parameter: the caller does not see it
🧾 What happens with each kind of argument
You pass…The method gets…Can it change the caller’s data?
an int, bool, struct…a copy of the value❌ no (the copy is separate)
a class objecta copy of the address✅ yes — its fields (same object); ❌ not which object the caller points to
an arraya copy of the address✅ yes — it can change elements (arrays are objects)
a stringa copy of the address❌ strings are immutable: “changing” makes a new string for the method only
a big structa full copy of every field❌ no — and the copy costs time (use in)
⚡ Performance lens — think like this

Passing a class costs only an address. Passing a large struct copies all of it on every call — use in (page page 11) or make it a class.

Because an object parameter can be changed, a method may “return” a result by filling an object the caller made — no new allocation. But hidden changes surprise readers: document them.

Passing a collection and then modifying it inside the method changes the caller’s collection too. Pass a copy (ToList()) only when you need isolation — it allocates.

🧪 Tiny code
void Double(int n)        { n = n * 2; }            // n is a copy: caller's x unchanged
void Rename(Person q)     { q.Name = "Ravi"; }      // same object: caller sees "Ravi"
void Reset(Person q)      { q = new Person("Zed"); }// q's own arrow moves: caller unaffected
void Shout(string s)      { s = s.ToUpper(); }      // new string for the method only

int x = 5;                Double(x);        // x is 5
var p = new Person("Asha"); Rename(p);      // p.Name is "Ravi"
                            Reset(p);       // p still points at the Ravi object

Rule: you can change the object; you cannot change which object the caller points to — unless you pass by ref.

♻️ Who clears this memory?

Parameters live in the frame and vanish at return. The objects they point to are cleaned by the GC only when no one — the caller, a static, another object — still references them. In the Reset example the new Zed object is unreachable the moment the method returns.

🎯 Check yourself
▾ Passing an object to a method copies the whole object.

❌ Wrong. Only the address is copied; the object stays where it is.

▾ A method can change a field of an object it was given, and the caller sees it.

✅ Right. Yes — they share the same object.

▾ Assigning a new object to a parameter changes the caller’s variable.

❌ Wrong. Only the parameter’s copy of the address changes.

🔥 Interview recall
  • Arguments are copied: value → the value; object → the address.
  • You can change the object, not which object the caller points to.
  • ref/out change the caller’s variable itself.
  • Strings are immutable; arrays are objects.
🎤 Say this in an interview
“C# passes arguments by value: value types are copied, and for reference types the reference is copied. A method can therefore mutate the object a caller passed in, but reassigning the parameter doesn’t affect the caller unless it’s passed by ref.”
⚠️ Common trap

Expecting void Reset(Person p) { p = new Person(); } to reset the caller’s object. It cannot — use the object’s own method, return the new object, or pass ref.
