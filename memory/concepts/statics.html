Concept 6 of 29 · 📌 Static memory

The notice board in the lobby — one copy, everyone reads it.

Where static fields live, how many copies exist, when static constructors run, and why a static reference can keep objects alive for the life of the app.

❓ "Where are static variables stored in .NET and when are they cleaned?"
👁 See it first
🎯 A static field belongs to the type, not to any object: one copy for the whole app, alive until the app ends.
🌍 In real life

📌 The notice board in a building lobby. There is exactly one. Everyone in the building reads the same board. It stays up as long as the building is open.

Each flat (object) has its own fridge (instance fields); the notice board (static field) is shared by all flats.

⚓ Why statics can keep objects alive
🧾 Instance vs static
Instance fieldStatic field
How many copies?one per objectone per type (for the whole app)
Created when?each newwhen the type is first initialised (see below)
Lives where?inside the object on the heapstatic memory belonging to the type
Cleared when?when the GC frees the objectnot during the run; ends with the app
⏱️ When does the static part get set up?

A static constructor runs automatically, at most once, before the first instance is created or any static member is used. Static field initializers run first, in the order written, then the static constructor body.

If you do not write a static constructor, the runtime may set up the static fields a little earlier or later (it only promises: before the first static field is used). Do not depend on the exact moment.

If a static constructor throws, the type cannot be used afterwards (the error repeats as a TypeInitializationException).

🔬 Honest note on “where exactly”

Microsoft’s docs say static fields belong to the type and are shared by all instances. Exactly which internal memory area the runtime uses to hold them is an implementation detail that the public docs do not pin down, so this lab draws “static memory” as one box and does not claim more.

🧪 Tiny code
class Counter
{
    public static int Total;      // ONE copy for the whole app
    public int Id;                // one copy per object

    public Counter() { Total++; Id = Total; }
}

var a = new Counter();   // a.Id = 1, Total = 1
var b = new Counter();   // b.Id = 2, Total = 2

static class Cache { public static List<int> Items = new(); }   // lives as long as the app

Counter.Total is reached through the type name, not through an object.

♻️ Who clears this memory?

Nobody during the run. Static fields live until the app ends. Objects that a static field points to are also kept alive, because the GC treats static references as roots. That is the classic way a “cache” turns into a memory leak (page 23).

🎯 Check yourself
▾ Each new Counter() gets its own copy of the static Total.

❌ Wrong. There is one Total for the type.

▾ A List held by a static field is freed when the method that filled it returns.

❌ Wrong. The static reference keeps it alive for the whole app.

▾ Static constructors run once, automatically.

✅ Right. Yes — before first use of the type, at most once.

🔥 Interview recall
  • Static = belongs to the type, one copy per app.
  • Not cleared during the run; static references are GC roots.
  • Static constructor: automatic, at most once, before first use.
🎤 Say this in an interview
“Static fields are per type, not per instance; there is one copy for the app and it lives as long as the app. Because static references are GC roots, objects they reference never get collected — so unbounded static caches leak memory.”
⚠️ Common trap

Putting everything in static collections “for convenience”. Anything added and never removed stays in memory until the app ends.
