One reception desk, a hotel key card, a paper cup — three lifetimes.

What the three DI lifetimes mean for objects in memory: how many instances exist, who holds them, when they are cleaned — and why a scoped object gets reused across your controller, service and repository.

❓ "What is the difference between singleton, scoped and transient in .NET dependency injection, and how do they affect memory?"
👁 See it first
🎯 Singleton = one instance for the whole app. Scoped = one instance per request (shared by every layer). Transient = a new instance every time it is asked for.
🌍 In real life

🏨 Singleton — the hotel’s one reception desk: everyone uses it, it is open as long as the hotel is.

🗝️ Scoped — your key card for one stay: the room door, the gym and the restaurant all accept the same card; you hand it back at checkout, and the next guest gets a new one.

🥤 Transient — a paper cup: every time you ask, you get a fresh one.

🗝️ Scoped: one object, reused across the layers of a request
🥤 Transient: a new object every time
⛓️ The classic bug: a captive dependency

⚡ Performance lens — think like this

Put state in scoped or transient objects and keep singletons stateless or thread-safe — they live forever and are shared by every thread (pages page 6, page 24).

A singleton cache that only grows is a leak (page page 23); give it a size limit.

Transients in a hot path multiply allocations; if an object is expensive to build and has no per-use state, make it singleton (and thread-safe) or scoped.

Disposable transients are held by the container until the scope ends — in a long-lived scope (a background worker that never ends its scope) they pile up. Create a new scope per unit of work.

🔬 Honest notes

Lifetimes, scope validation (“scoped services can’t be injected into singletons”) and disposal behaviour are from Microsoft’s ASP.NET Core and .NET DI documentation. Exactly when a singleton is created (on first request vs at startup) depends on how it is registered; the picture shows the common case. Gen 0/1/2 placement is the general GC behaviour from pages page 20, not something DI documents.

🧪 Tiny code
builder.Services.AddSingleton<IEmailSettings, EmailSettings>();   // one for the whole app
builder.Services.AddScoped<AppDbContext>();                       // one per request (EF Core default)
builder.Services.AddTransient<IEmailBuilder, EmailBuilder>();     // new every time

public class OrdersController(OrderService service) { }           // gets the scoped instances
public class OrderService(AppDbContext db, IOrderRepository repo) { }    // db: the SAME as the controller's
public class OrderRepository(AppDbContext db) : IOrderRepository { }     // …and the same here

// ❌ captive dependency: a singleton must not take a scoped service
// public class CacheService(AppDbContext db) { }   // registered as singleton → scope validation error

Constructor injection hands each class the instance the lifetime rules say it should get. Scoped = shared inside the request.

♻️ Who clears this memory?

Singleton: disposed/cleared at app shutdown. Scoped: disposed when the request’s scope ends, then collected as ordinary garbage. Transient: collected by the GC after nobody references it (earlier disposal only if its scope ends and it is IDisposable).

🎯 Check yourself
▾ A scoped service gets a new instance in every class that asks for it within one request.

❌ Wrong. Within one scope, the same instance is reused.

▾ A singleton can safely hold a scoped DbContext in a field.

❌ Wrong. That is a captive dependency: the DbContext outlives its scope.

▾ A transient service gives a different instance to each consumer.

✅ Right. Yes — a new one every time.

🔥 Interview recall
  • Singleton: one for the app. Scoped: one per request, shared across layers. Transient: new every time.
  • Longer-lived must not depend on shorter-lived (captive dependency).
  • Singletons must be thread-safe; scoped objects die with the request.
🎤 Say this in an interview
“Singleton gives one instance for the app’s lifetime, held by the container; scoped gives one instance per request so the controller, service and repository share the same DbContext; transient creates a new instance on every request to the container. A longer-lived service must not depend on a shorter-lived one, or the shorter-lived object becomes effectively a singleton.”
⚠️ Common trap

Registering a stateful object as a singleton “to save memory”. It is now shared by every request and thread — and never freed.
