A shared whiteboard instead of a photocopy.

What the ref, out and in modifiers change in memory: the parameter stops being a copy and becomes an alias of the caller’s own variable — and what that means for objects, structs and arrays.

❓ "What do ref, out and in do, and how do they differ from passing by value?"
👁 See it first
🎯 ref/out/in make the parameter an alias of the caller’s variable instead of a copy.
🌍 In real life

⚡ Performance lens — think like this

in avoids copying a large struct on every call; it is mostly useful for large readonly struct values. For small values (an int), just pass by value — an alias is not faster.

out is the standard way to return a result plus a success flag without allocating: int.TryParse(text, out var n). It avoids a tuple or a result object.

ref locals and returns are an advanced tool for hot paths (no copy). A ref local cannot be kept across an await, and async methods cannot take ref/in/out parameters, because an alias into a stack frame cannot live in a heap state machine (page page 25).

⚠️ Rule of thumb

If the method only needs to change the object’s contents, no modifier is needed (previous page). Use ref only when the method must replace the caller’s variable itself (point it at a different object or set a new value).

🧪 Tiny code
void AddOne(ref int n)            { n++; }                     // changes the caller's int
void Replace(ref Person q)        { q = new Person("Zed"); }   // moves the caller's p
bool TryParse(string s, out int value)                         // must assign value
{
    if (int.TryParse(s, out value)) return true;
    value = 0; return false;
}
decimal Sum(in BigStruct data)    => data.A + data.B;          // read-only alias: no copy

int x = 5;  AddOne(ref x);                 // x is 6
if (TryParse("42", out var n)) { /* n is 42 */ }
ref int s = ref Slot(arr, 1);  s = 99;     // writes into arr[1]

The modifier is required at the call (except in), so the call site shows that the variable may change.

♻️ Who clears this memory?

Aliases live in frames and vanish at return. The objects involved are cleaned by the GC when unreachable — for example the Asha object once p was redirected. Nothing here frees memory by itself; ref only changes who points where.

🎯 Check yourself
▾ With ref, the parameter is a copy of the caller’s variable.

❌ Wrong. It is an alias of the caller’s variable.

▾ An out parameter must be assigned before the method returns.

✅ Right. Yes — the compiler enforces it.

▾ in lets a method modify a large struct without copying it.

❌ Wrong. in is read-only; it avoids the copy but forbids changes.

🔥 Interview recall
  • ref/out/in = alias to the caller’s variable, not a copy.
  • ref must be initialised; out must be assigned by the method; in is read-only.
  • Use ref only to replace the caller’s variable; mutate objects without it.
🎤 Say this in an interview
“By default arguments are copied. ref, out and in pass an alias to the caller’s variable instead: ref for read-write, out when the method supplies the value, in for read-only access that avoids copying large structs. For reference types, ref lets the method repoint the caller’s variable.”
⚠️ Common trap

Using ref on an object parameter just to “change it”. You can already change its contents without ref — ref is for replacing the variable.
