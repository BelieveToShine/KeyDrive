Concept 17 of 22 · ♻️ Garbage collector

A tap you forgot to close — the GC cannot close it for you.

A .NET “leak” is not lost memory: it is memory that is still referenced but no longer needed. The three classic causes — static collections, event handlers and undisposed resources — with their fixes.

❓ "Can .NET applications leak memory even with a garbage collector? How?"
👁 See it first
🎯 A managed “leak” is an object that is still reachable but no longer needed.
🌍 In real life

🚰 The GC is a cleaner who only throws away what nobody is holding. If you keep a hand on the tap — a static list, an event handler, an open file — the cleaner leaves it alone, even though you stopped using it long ago.

📚 The second classic: a static cache that only grows

🪶 A weak reference holds without keeping alive

A WeakReference lets you keep a “soft link” to an object: the GC may still free the object, and the link’s Target becomes null when it does. Microsoft’s docs describe it for caches that should shrink under memory pressure — but warn that you still need a proper caching policy.

If a normal reference is a hand holding the tap, a weak reference is just looking at it.

🕵️ How do you find a leak?

A forced GC.Collect() followed by “memory is still high” is only a hint, not proof. The reliable way is a memory profiler (or heap snapshots) that shows who still references the growing objects. The answer is almost always a static, an event or a cache.

🧪 Tiny code
static class Bus { public static event Action Tick; }       // static publisher

class Window
{
    public Window()  { Bus.Tick += OnTick; }     // Bus now references this Window
    public void Close() { Bus.Tick -= OnTick; }  // ✅ remove the reference when done
    void OnTick() { }
}

static readonly List<byte[]> Cache = new();      // ⚠️ grows forever unless you evict

var weak = new WeakReference<byte[]>(new byte[1000]);
if (weak.TryGetTarget(out var data)) { /* still there */ }   // may be null after a GC

WeakReference is a tool for caches, not a cure for leaks. Fix the reference first.

♻️ Who clears this memory?

The GC — but only objects with no reachable reference. Your job is to cut the references you no longer need: unsubscribe, evict, dispose, and avoid unbounded statics.

🎯 Check yourself
▾ The GC cannot leak memory, so C# programs never run out of it.

❌ Wrong. Objects that are still referenced are never freed — that is a managed leak.

▾ Forgetting -= on a long-lived publisher can keep a subscriber alive.

✅ Right. Yes — the publisher’s handler list references it.

▾ A static dictionary used as a cache with no eviction is a classic leak.

✅ Right. Yes — static fields are roots.

🔥 Interview recall
  • A leak = still reachable but not needed.
  • Top causes: statics, events, undisposed resources, unbounded caches.
  • Fix: cut the reference (-=, evict, dispose); weak references for soft caches.
🎤 Say this in an interview
“In .NET a leak is an object that is still referenced but no longer needed — typically a static collection, an event subscription that was never removed, or an undisposed resource. I find the root with a memory profiler and cut the reference.”
⚠️ Common trap

Believing “the GC will clean it up”. It only cleans what is unreachable; you decide what is reachable.
