Concept 2 of 22 · 📚 Stack & heap

A stack of plates — one plate for every method call.

How the call stack grows and shrinks: parameters and locals live in a frame that is pushed when a method starts and popped when it returns.

❓ "What is the call stack and what is stored on it?"
👁 See it first
🎯 Every method call gets a frame (parameters + locals) on the stack; returning from the method pops it.
🌍 In real life

🍽️ A stack of plates in a canteen. You can only add a plate on top and only take the top plate off. The plate you added last is the first to go.

A method call is a plate: it holds that method’s own notes (its parameters and local variables). When the method is done, the plate is removed and nobody has to “clean” it.

⚠️ Honest notes

Every thread has its own stack (page 18). Its size is fixed when the thread starts and is small compared with the heap — typically a few MB, and the default depends on the operating system and runtime version.

A stack overflow normally ends the process; you cannot rely on try/catch to recover from it. The cure is to stop the endless recursion (or make it loop), not to catch it.

🧪 Tiny code
int Total(int n)          // n: a parameter, lives in Total's frame
{
    int rate = 18;        // rate: a local, also in Total's frame
    return n * rate;
}                         // frame popped here — nothing to "free" by hand

int Forever(int n) => Forever(n + 1);   // never returns → frames never popped → overflow

Stack memory needs no garbage collector. It is reused simply by moving the “top” back down.

♻️ Who clears the stack?

Nobody has to. When a method returns, its frame is popped and the space is reused by the next call. This is why the stack is so fast: it only moves a “top” marker.

The GC does not clean the stack. But the GC reads the stack: references in frames tell it which heap objects are still in use (page 13).

🎯 Check yourself
▾ A local variable lives on after its method returns, because the GC keeps it.

❌ Wrong. Its frame is popped on return. (An object it pointed to may live on, but the variable itself is gone.)

▾ The most recently called method’s frame is on top of the stack.

✅ Right. Yes — last in, first out.

▾ Recursion with no end case can fill the stack.

✅ Right. Right: each call needs a frame, so the stack runs out.

🔥 Interview recall
  • A frame per method call holds parameters and locals.
  • Push on call, pop on return — last in, first out.
  • Stack memory is reused instantly; the GC does not manage it.
  • Endless recursion → stack overflow.
🎤 Say this in an interview
“Each method call pushes a frame with its parameters and locals onto the thread’s stack, and returning pops it. It is fixed-size and very fast, and the garbage collector does not manage it — but it does scan the stack to find live object references.”
⚠️ Common trap

Believing a deep recursion is “free”. Each level costs a frame; use a loop (or an explicit collection) when depth can be large.
