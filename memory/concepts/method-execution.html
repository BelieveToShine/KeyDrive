Concept 7 of 29 · ⚙️ Static & methods

One clerk serving many customer files.

What really happens when you call a method on an object: a stack frame is pushed, the object’s address travels in as this, and the one shared copy of the code works on that object’s data.

❓ "What happens in memory when you call an instance method?"
👁 See it first
🎯 A method call pushes a frame; this carries the object’s address; the method changes the object on the heap, not the frame.
🌍 In real life

🗂️ A clerk (the method) and many customer files (objects). There is only one clerk’s procedure book for the whole office. When a customer comes, the clerk is handed that customer’s file (this) and works on it. When the clerk is done, the clerk puts the file back with the changes written in — the clerk’s own scratch notes (the frame) are thrown away.

⚡ Performance lens — think like this

A call itself is cheap: it only pushes and pops a frame. The cost you notice comes from what the method allocates (new objects, boxing, strings) — those create work for the GC (see page 4 and page 5).

Because the frame is thrown away at return, the frame itself never needs garbage collection. Only objects do (the references inside a live frame count as roots that keep objects alive). Keep temporary values as locals and you give the GC nothing to do.

🔬 Honest note

Calling this a “hidden argument” is a teaching picture, and so are the made-up addresses and the exact MethodTable layout (the header, type pointer and MethodTable come from Microsoft’s older runtime article and the Book of the Runtime; current versions may differ); Microsoft’s docs describe this as “the current instance”. How the JIT passes it (for example in a CPU register) is an implementation detail.

🧪 Tiny code
class Order
{
    public int Count;                         // data: lives inside each Order object (heap)

    public void AddItem(string name)          // code: one copy for the whole type
    {
        this.Count++;                         // this = the address of the object it was called on
    }                                         // frame (this, name) popped here
}

var order = new Order();
order.AddItem("pen");                         // order.Count is now 1

this. is optional in C# — Count++ means the same. The address is still what makes it work.

♻️ Who clears this memory?

The frame: popped at return — instantly. The object: the GC, after nobody references it. Notice that a method cannot free the object it works on: only the GC can, and only when it is unreachable.

🎯 Check yourself
▾ Each Order object contains its own copy of the AddItem code.

❌ Wrong. The code exists once per type; objects hold only data.

▾ this lets a method find the data of the object it was called on.

✅ Right. Yes — it is the address of that object.

▾ Changes made through this disappear when the method returns.

❌ Wrong. The frame disappears, but the object is on the heap and keeps the change.

🔥 Interview recall
  • Call = push a frame (this + parameters + locals); return = pop it.
  • this = address of the object; data on the heap, code once per type.
  • Changes to fields persist; changes to frame locals vanish.
🎤 Say this in an interview
“An instance method call pushes a stack frame containing this — the reference to the object — plus parameters and locals. The method reads and writes the object’s fields on the heap; when it returns the frame is popped, but field changes persist. The method code itself is shared by all instances of the type.”
⚠️ Common trap

Believing a method “has its own copy” of the object. It only holds an address; changing a field changes the one real object.
