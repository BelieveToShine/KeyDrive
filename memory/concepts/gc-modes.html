Concept 27 of 29 · ⚙️ Tuning & judgement

A shop cleaner vs a factory cleaning crew.

The GC has modes: workstation or server, concurrent or not. They change who does the cleaning and when the app is stopped — not what counts as live. What each one trades, and how to see which one you have.

❓ "What is the difference between workstation and server garbage collection, and what is concurrent GC?"
👁 See it first
🎯 Workstation GC favours a responsive app; server GC favours total throughput on many cores; concurrent GC shortens the pauses of gen 2 collections.
🌍 In real life

🏪 A shop cleaner (workstation GC) tidies quietly while the shop is open so customers are not disturbed. A factory cleaning crew (server GC) is a whole team that cleans fast and in parallel — it finishes sooner and handles much more mess, but uses more people (CPU cores and memory).

Concurrent cleaning: instead of closing the shop for a deep clean, the crew works in the back while it stays open.

🔄 Concurrent (background) GC: the app keeps running while gen 2 is marked
🏭 Workstation vs server: one heap, or one heap per processor
🏭 Server GC: the same twelve objects over four heaps

🔎 Which one am I using?

Do not guess: check at run time with GCSettings.IsServerGC and GCSettings.LatencyMode. Console and desktop apps normally run workstation GC; web hosts such as ASP.NET Core are typically configured for server GC — your project file or runtimeconfig.json decides (System.GC.Server, System.GC.Concurrent).

Why only gen 2? (explanation, not a quoted rule) Gen 0 and gen 1 are small, so stopping the app for them is cheap. Gen 2 can be huge, and reading it all while stopped is what hurts.

In containers or with limited CPU, test before switching — more heaps means more memory. Don’t tune until a measurement tells you to.

🧠 How this ties back to earlier pages

Roots (page 19): the stack slot and statics are roots in every mode. Modes change who cleans and when the app stops, never what counts as live.

Generations (page 20): short gen 0/1 collections are blocking; concurrent GC only helps the long gen 2 ones.

LOH (page 21): large allocations raise the number of gen 2 collections, so they also raise how often background GC is needed.

🧪 Tiny code
Console.WriteLine(System.Runtime.GCSettings.IsServerGC);   // which flavour is running now
Console.WriteLine(System.Runtime.GCSettings.LatencyMode);  // e.g. Batch / Interactive / SustainedLowLatency

// runtimeconfig.json  (or the matching MSBuild properties)
// {
//   "configProperties": {
//     "System.GC.Server": true,
//     "System.GC.Concurrent": true
//   }
// }

Treat these as settings you change after measuring, not as defaults to “optimise”.

♻️ Who clears this memory?

The GC always does, in every mode; the mode only changes who runs it and how long the app waits. Roots (stack locals, statics) decide what is live in all of them. Server GC tends to hold more memory; workstation GC less.

🎯 Check yourself
▾ Server GC is meant for desktop apps.

❌ Wrong. It is meant for multi-core servers; desktop apps use workstation GC.

▾ Concurrent/background GC applies to generation 2 collections.

✅ Right. Yes — it shortens the long ones.

▾ You should switch to server GC as soon as an app feels slow.

❌ Wrong. Measure first; it can use much more memory.

🔥 Interview recall
  • Workstation = responsive; server = throughput on many cores.
  • Concurrent (background) GC shortens gen 2 pauses; gen 0/1 still block.
  • Check with GCSettings.IsServerGC; modes never change what counts as live.
🎤 Say this in an interview
“Workstation GC prioritises responsiveness and low memory; server GC uses multiple heaps and GC threads for throughput on multi-core servers. Concurrent GC runs gen 2 collections in the background to shorten pauses. I measure before changing any of this.”
⚠️ Common trap

Turning on server GC in a small container “for speed” and running out of memory.
