Concept 29 of 29 · ⚙️ Tuning & judgement

Thirteen small cases: find where it lives, who holds it, who clears it.

A practice ward for the whole lab: symptom, evidence, your diagnosis, then reveal — with an answer key back to each page.

❓ "Here is a memory symptom. Where does the data live, what still references it, and who clears it?"
👁 See it first
🎯 You have followed memory from the stack to the garbage collector and async. This is the practice ward: symptom → evidence → which memory place → fix → where to review.
🧭 How to decide

Ask in this order: where does this data live (stack, heap, static)? → who holds a reference to it (a root: stack, static, event)? → who is supposed to clear it (method return, GC, Dispose)? → is more than one thread involved?

🩺 Case 1

Changing a copy changed the original

Symptom. After var b = a; b.Name = "Ravi"; the name in a changed too.

Evidence.

  • a is a class instance.
  • Both variables print the same address in the debugger.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. Copying a reference copies the address, not the object.

Fix. Make a real copy (a record with with, or a struct / clone) when you want independence.

📖 Where to review: page 3.

🩺 Case 2

A list of numbers is slow and creates lots of garbage

Symptom. A loop adds 1,000,000 ints to an ArrayList; the GC runs constantly.

Evidence.

  • ArrayList stores object.
  • A profiler shows a million small objects.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. Boxing: every int becomes a heap object.

Fix. Use a generic List<int> — no boxes.

📖 Where to review: page 5.

🩺 Case 3

The app crashes on a big input and cannot be caught

Symptom. A recursive method works for 100 items and crashes for 100,000.

Evidence.

  • Crash says stack overflow.
  • The method calls itself once per item.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. Each call needs a stack frame; the stack is small and fixed.

Fix. Loop, or use an explicit collection, instead of deep recursion.

📖 Where to review: page 2.

🩺 Case 4

The Reset method does nothing

Symptom. void Reset(Person p) { p = new Person("Zed"); } is called, but the caller’s person is unchanged.

Evidence.

  • The method assigns to the parameter.
  • The caller still prints the old name.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. The parameter is a copy of the address; assigning to it moves only the parameter’s own arrow.

Fix. Change the object’s fields, return the new object, or pass ref if the caller’s variable must change.

📖 Where to review: page 9, page 11.

🩺 Case 5

A base constructor sees a null field of the child

Symptom. The base constructor calls a virtual method; the override prints the child’s field as null.

Evidence.

  • The child’s field initialiser has not run the constructor body yet.
  • Order: base constructor body → child constructor body.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. Calling a virtual method in a constructor runs the override before the child is fully built.

Fix. Do not call virtual members from constructors; use an init method after construction.

📖 Where to review: page 13.

🩺 Case 6

A 50 MB report never leaves memory

Symptom. A handler () => Log(report.Title) is registered on a long-lived event. The report screen is closed but its data stays.

Evidence.

  • The lambda uses only report.Title but captures report.
  • The closure object is referenced by the event’s delegate.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. A capturing lambda keeps the whole captured object alive as long as the delegate is reachable.

Fix. Copy what you need into a local first (var title = report.Title;), use a static lambda, and unsubscribe.

📖 Where to review: page 18.

🩺 Case 7

Memory grows all day and never drops

Symptom. A static Dictionary caches every customer ever looked up.

Evidence.

  • Gen 2 keeps growing.
  • A heap snapshot shows the dictionary as the root.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. A static field is a GC root; nothing in the cache is ever removed.

Fix. Add a size limit or expiry, or use a proper memory cache.

📖 Where to review: pages 6, 23.

🩺 Case 8

Closed screens stay in memory

Symptom. After opening and closing 200 windows, memory still holds 200 window objects.

Evidence.

  • Each window subscribes to a long-lived service event with +=.
  • No -= anywhere.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. The publisher’s handler list keeps every subscriber reachable.

Fix. Unsubscribe in Close/Dispose, or use a weak-event pattern.

📖 Where to review: page 23.

🩺 Case 9

The file is still locked after reading it

Symptom. A report reads a file, then another process cannot delete it for minutes.

Evidence.

  • new StreamReader(path) with no using.
  • The lock vanishes only after some time.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. The GC frees memory but does not close files; a finalizer is late.

Fix. Wrap in using so Dispose runs at the end of the block.

📖 Where to review: page 22.

🩺 Case 10

Memory spikes and gen 2 collections are frequent

Symptom. An API allocates a fresh 100 KB byte array for every request.

Evidence.

  • Allocations over 85,000 bytes.
  • Many gen 2 collections in the counters.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. Big arrays go to the LOH, which is collected with gen 2.

Fix. Rent the buffer from ArrayPool and return it.

📖 Where to review: pages 21, 28.

🩺 Case 11

The counter is lower than expected with two threads

Symptom. 1,000 increments on each of two threads gives about 1,700, not 2,000.

Evidence.

  • The counter is a shared field changed with Value++.
  • Result differs on each run.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. Read-modify-write on shared heap memory is not atomic.

Fix. Interlocked.Increment or a lock.

📖 Where to review: page 24.

🩺 Case 12

It will not compile: a Span cannot be used across await

Symptom. Error: a Span<byte> local is used before and after an await.

Evidence.

  • The method is async.
  • Span is a ref struct.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. Locals across an await live in a heap state machine; a ref struct cannot.

Fix. Use Memory<T> or byte[] across the await; use the Span inside non-async helper code.

📖 Where to review: pages 25, 28.

🩺 Case 13

Works for the first request, then “disposed context” errors

Symptom. A cache service registered as a singleton takes AppDbContext in its constructor.

Evidence.

  • The service is AddSingleton; the context is AddScoped.
  • Errors start after the first request ends.

Your move: what is really happening in memory?

▾ Reveal the answer

Diagnosis. A captive dependency: the singleton holds a scoped object beyond its scope, so it is disposed and stale.

Fix. Make the service scoped, or inject IServiceScopeFactory and create a scope per use.

📖 Where to review: page 26.

🔥 Interview recall
  • Method: where does it live → who references it → who clears it → how many threads?
  • Leaks are references: statics, events, caches, undisposed resources.
  • Allocate less: generics, pools, Span.
  • Shared heap data + threads = races.
🎤 Say this in an interview
“I read a memory problem by asking where the data lives, what still references it, who is supposed to clear it and whether threads share it — then I fix the reference, the lifetime or the allocation, and measure again.”
⚠️ Common trap

Calling GC.Collect() to “fix” memory. Find the reference that keeps it alive.

Tuning GC modes before measuring. Most problems are references and allocations in your code.
