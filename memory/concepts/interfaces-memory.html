A remote control that works with any TV.

What exists in memory for an interface (nothing of its own), what an interface variable holds, and why a struct behind an interface gets boxed.

❓ "When is memory allocated for an interface in C#?"
👁 See it first
🎯 An interface never has memory of its own: it is a label on a variable that points to a real class object.
🌍 In real life

📺 A TV remote. The remote (the interface) only has buttons: power, volume. You can’t watch a remote; there has to be a real TV behind it.

Any TV that supports those buttons works with that remote — a Sony, a Samsung. In code: any class that implements IPayable can be held in an IPayable variable.

📦 A struct behind an interface gets boxed — and unboxed
🧾 Class object vs interface variable
Class objectInterface variable
Takes memory on the heap✅ yes❌ no — it is only a reference slot
Created with new✅ yes❌ never
Can hold data (fields)yesno (an interface has no instance fields)
Points to—any object whose class implements it
🧪 Tiny code
interface IPayable { void Pay(); }
class Invoice      : IPayable { public void Pay() { /* ... */ } }
class Subscription : IPayable { public void Pay() { /* ... */ } }
struct Coupon      : IPayable { public int Value; public void Pay() { } }

// var x = new IPayable();            // ❌ an interface cannot be created
IPayable p = new Invoice();           // reference to a heap Invoice
IPayable q = new Subscription();
IPayable s = new Coupon { Value = 5 };  // struct → boxed on the heap

Behind every interface variable is a real object (or a boxed struct).

♻️ Who clears this memory?

The garbage collector frees the real object (or the box) when no variable — interface-typed or not — still points to it. The interface adds no memory to each object. Type data (the MethodTables with their interface maps) is loaded once per type and is shared by every object — it is not cleared when an object dies.

🎯 Check yourself
▾ An interface variable holds the interface’s fields.

❌ Wrong. Interfaces have no instance fields; the variable holds a reference to an object.

▾ Two different classes can be held in the same interface-typed variable type.

✅ Right. Yes — that is the point of the interface.

▾ Assigning a struct to an interface variable allocates a heap box.

✅ Right. Yes: boxing.

🔥 Interview recall
  • Interfaces have no objects of their own.
  • An interface variable = a reference to an object whose class implements it.
  • p.Pay(): follow p → object → type pointer → MethodTable → interface map → method.
  • A struct behind an interface is boxed (heap object with header + type pointer + a COPY of the value).
🎤 Say this in an interview
“An interface isn’t instantiated; an interface-typed variable holds a reference to an object of a class that implements it, and calls go to that object’s implementation. Assigning a struct to an interface boxes it on the heap.”
⚠️ Common trap

Calling a struct’s interface method in a hot loop through an interface variable allocates one box per assignment. Use generics with a constraint (where T : IPayable) to avoid boxing. Also: calling a mutating method through the interface changes the box, not your original struct variable.
