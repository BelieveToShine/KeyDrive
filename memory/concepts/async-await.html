Concept 25 of 29 · 🧵 Threads & async

A bookmark in a novel — leave the book, come back to the same page.

What the compiler builds for async methods, why locals move from the stack to a heap object at an await, and when that costs an allocation.

❓ "What happens to memory when you use async and await?"
👁 See it first
🎯 await copies the method’s state (the state machine) to a heap object while it waits, so the thread can do other work.
🌍 In real life

📖 You are reading a novel when the phone rings. You put in a bookmark (the state machine) and walk away — the book stays on the shelf (heap) while you do other things. When you come back you open it at the bookmark and carry on. Meanwhile someone else could use the chair (the thread).

🔬 Honest notes

The compiler generates the state machine for you. In Debug builds it is a class; in Release builds it is a struct that is moved to the heap (boxed) only when the method really suspends. These details come from Microsoft’s documentation and developer-blog explanations and can change between compiler versions; the lab’s picture shows the idea.

The code after an await may run on a different thread than the code before it (depending on context). That is another reason locals are saved in the state machine instead of staying on one thread’s stack.

🧪 Tiny code
async Task<int> LoadAsync()
{
    int a = 1;                       // starts in this method's stack frame
    await Task.Delay(100);           // not finished → state machine boxed to the heap, thread freed
    return a + 1;                    // resumes: a is read from the state machine
}

// DON'T: .Result / .Wait() block a thread and lose the benefit
// var x = LoadAsync().Result;
var x = await LoadAsync();

Each async method that really suspends allocates its state (and a Task). That is usually a fair price for not blocking threads.

♻️ Who clears this memory?

The stack frames pop whenever the method suspends or finishes. The state machine object and the Task are ordinary heap objects: the GC frees them once the method has finished and nothing references them. The awaited task keeps the state machine reachable until it completes, so a never-completing await keeps the state machine (and everything its locals reference) alive — a classic hidden leak.

🎯 Check yourself
▾ await blocks the thread until the work finishes.

❌ Wrong. It frees the thread; the method’s state waits on the heap.

▾ Locals that live across an await are stored in the state machine.

✅ Right. Yes — that is how the method continues after resuming.

▾ Span<T> can be kept across an await.

❌ Wrong. It is a ref struct and cannot be stored in a heap object, so the compiler rejects it.

🔥 Interview recall
  • async method = compiler-made state machine.
  • Stack until a real suspension; then the state moves to the heap and the frame pops.
  • Await frees the thread; cost = a heap object and a Task.
🎤 Say this in an interview
“The compiler turns an async method into a state machine that holds its locals and position. If an await doesn’t complete synchronously, the state machine is boxed to the heap, the stack frame is popped and the thread is released; when the awaited work completes it resumes the state machine, the result goes into the Task, and the state machine is later garbage collected.”
⚠️ Common trap

Calling .Result or .Wait() on a Task. That blocks a thread (and can deadlock) — you pay for async without getting its benefit.
