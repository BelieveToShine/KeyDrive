Asking at the door instead of knowing the guest in advance.

What the compiler does with dynamic, how the first call differs from later calls, and what reflection allocates on the heap.

❓ "How does dynamic work at run time and what does it do to memory?"
👁 See it first
🎯 dynamic postpones the “which method?” decision to run time; the call site caches the answer so repeats are cheaper.
🌍 In real life

🚪 A doorman who has no guest list: for each guest he must ask who they are (look up the real type). The first time takes a moment; he then writes it in his notebook (the cached rule) so the same kind of guest is waved through next time.

Normal C# is a doorman with a printed guest list: he knew everyone before the party began (compile time).

🔬 Honest notes

The call-site / binder / cached-rule picture comes from Microsoft’s documentation of the Dynamic Language Runtime (older articles and API pages). Where the call site sits (a compiler-made static field), what a rule contains and what a MethodInfo holds inside are drawn as a teaching picture: internals can change between runtime versions, so the lab gives no timings, sizes or cache limits.

The object header, type pointer and per-type type data come from the classic runtime model (the old MSDN article “How the CLR Creates Runtime Objects” and the Book of the Runtime). Boxing, unboxing, stack frames, statics as GC roots and “unreachable, then collected later” are documented behaviour.

To the compiler, a dynamic variable is typed object underneath, but with all type checking switched off for operations on it. Arguments of a dynamic call are also passed as objects, so value types are boxed there too.

🧪 Tiny code
dynamic d = new Duck();
d.Quack();               // 1st: binder looks at the real type, caches the rule
d.Quack();               // 2nd: cached rule reused
// d.Swim();             // compiles! but throws RuntimeBinderException when run

Order order = new Order();
var m = typeof(Order).GetMethod("Ship");          // reflection: by name
var args = new object[] { 5 };                    // 5 is boxed into the array
object r = m.Invoke(order, args);                 // r is an object
int days = (int)r;                                // unboxing copies 3 into days

Prefer normal typed code. Use dynamic or reflection only when the shape really is unknown until run time.

♻️ Who clears this memory?

The garbage collector, as usual, for the MethodInfo, argument arrays and boxes: they become unreachable when the last variable or array slot that refers to them is gone, and are cleared at a later GC. The call site is reachable from a static field, so it (and its cached rules) stays for the life of the app — a small price per dynamic operation in your code.

🎯 Check yourself
▾ With dynamic, a misspelled method name is caught when you build.

❌ Wrong. It is only caught at run time (RuntimeBinderException).

▾ Repeated dynamic calls on the same type reuse a cached rule.

✅ Right. Yes — that is the call-site cache.

▾ Reflection Invoke with an int argument boxes it.

✅ Right. Yes: arguments travel in an object[].

🔥 Interview recall
  • dynamic → a normal reference; the compiler emits a call site (static field → CallSite object); the binder reads the real type and the result is cached.
  • Errors appear at run time.
  • Reflection allocates MethodInfo, object[] args and boxes (arguments and result); (int)r copies back.
🎤 Say this in an interview
“dynamic defers member binding to run time: the compiler emits a call site, the runtime binder resolves the call using the actual type, and the result is cached in the call site for later calls. Reflection does a by-name lookup at run time and allocates metadata objects and boxed arguments.”
⚠️ Common trap

Using dynamic or reflection inside a tight loop “because it is flexible”. Resolve once (cache the MethodInfo or use a typed delegate) and reuse.
