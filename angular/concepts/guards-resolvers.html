Deep dive · Angular lab · 🚪 Guards

Guards say “may it happen?”; resolvers say “what must be ready?”

canMatch, canActivate, canDeactivate and resolve; redirecting with a UrlTree; and handing resolved data and parameters to a component as inputs.

❓ "How do route guards and resolvers work, and how do you redirect from a guard?"
👁 See it first
🎯 Guards answer “may this navigation happen?”; resolvers answer “what must be ready first?”; route inputs hand the result to the component.
▶️ Watch it happen: may I? what first?
📖 Why did this need to exist?

The routing page gave you the order — match, guards, resolvers, activate. This reference page covers what each hook can return, how to redirect properly, and how data and parameters arrive in the component.

The most common mistake is returning false and then navigating from code: it fights the router. The router offers a better answer — return a UrlTree — and it keeps the guard a pure function of state.

Guards shape the browser experience only; real access control happens on the server.

🚦 What each hook returns
HookQuestionReturnTypical use
canMatchDoes this route definition apply?true / false (false → next matching route)Feature flags, choose a component per role
canActivate (CanActivateFn)May the user enter?true, false, or a UrlTree/RedirectCommandSigned-in check
canDeactivate (CanDeactivateFn)May the user leave?Same; receives the component instance and statesUnsaved edits
resolve (ResolveFn)Load data firstThe data (or a redirect)A product loaded before the page renders

Guards receive the ActivatedRouteSnapshot and RouterStateSnapshot, run in the route’s injection context so they can inject() services, and for nested routes the parent’s guards and resolvers run before the child’s.

↪️ Redirect with a UrlTree
🧪 Guards lab · the ShopUI checkout route
export const signedInGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);
  return auth.isSignedIn() ? true : inject(Router).createUrlTree(['/login'], { queryParams: { returnUrl: state.url } });
};

export const productResolver: ResolveFn<Product> = (route) => inject(ProductApi).get(route.paramMap.get('id')!);

{ path: 'products/:id', component: ProductPage, resolve: { product: productResolver } }
// with withComponentInputBinding(), ProductPage declares:  product = input.required<Product>();

Illustrative sketch. With component input binding, resolved route data, path parameters and query parameters arrive as component inputs — no ActivatedRoute needed.

▾ Go one level deeper (60 seconds)

Not security. Guards run in the browser; users can bypass them. The server must authorise each request.

Preloading. The router preloader does not load routes protected by canLoad guards.

Order. For nested routes, parent and child guards run first, followed by the parent and child resolvers.

🔥 Interview recall
  • canMatch: does the route apply (false → next); canActivate: may enter; canDeactivate: may leave; resolve: data first.
  • Return true, false, or a UrlTree/RedirectCommand; redirect with a UrlTree, not false + navigate().
  • Guards run before resolvers; both run in an injection context.
  • With withComponentInputBinding() resolved data, path, matrix and query params become inputs.
  • Guards are UX; the server enforces security.
  • A slow resolver blocks navigation.
🎤 Say this in an interview
"I use canActivate with a UrlTree to redirect signed-out users, canDeactivate to protect unsaved forms, canMatch to choose route definitions, and resolvers to load data before the component exists. With component input binding the resolved data and params arrive as inputs. Guards only shape the browser experience; the server authorises."
