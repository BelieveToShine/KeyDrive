Pick the moment that matches the job.

Every lifecycle hook and render callback: when it runs, what is safe there, and the modern replacements — computed, afterNextRender and DestroyRef.

❓ "What are the Angular lifecycle hooks, and when do you use ngOnInit versus ngOnChanges or afterNextRender?"
👁 See it first
🎯 A lifecycle hook is a moment you can run code at: when inputs arrive, when the view is ready, when the component goes away. Pick the moment that matches the job.
▶️ Watch it happen: moments to run code
📖 Why did this need to exist?

Page 2 showed that Angular repeatedly checks components. Around that machinery sit a few moments where you may need to act: set something up once the inputs exist, touch the DOM after it exists, clean up when the component leaves.

Doing a job at the wrong moment causes the classic Angular bugs: reading an input in the constructor (empty), changing a value after the view was checked (NG0100), touching window on the server, a subscription that is never cleaned up.

This reference page lists each moment, what is safe to do there, and the modern replacements — signals (computed, effect) and afterNextRender — that let you avoid many classic hooks.

🧭 Which tool for which job?
📚 Every hook: what it does and when to use it
HookWhen it runsUse it for · watch out
constructorCreating the class; dependencies injectedinject(), registering effects and render callbacks · inputs are not available
ngOnChangesBefore ngOnInit, and whenever a classic input changesReact to input changes · not called for signal inputs; use computed/effect
ngOnInitOnce, after inputs have initial values, before the component’s own template is initialisedInitial setup from inputs · avoid heavy work
ngDoCheckOn each check; first call after ngOnInitCustom change checks, profiling counters · runs very often
ngAfterViewInitAfter the component’s view is fully initialisedUsing viewChild results · setting values here can raise NG0100
afterNextRender / afterEveryRenderAfter the next render / every render; browser only; must be called in an injection context (usually the constructor)Measuring, focusing, third-party DOM libraries · phases: earlyRead, write, mixedReadWrite, read — prefer write then read
ngOnDestroy / DestroyRef.onDestroyOnce, before the component is destroyedUnsubscribe, clear timers, close connections

Also exist: content hooks (ngAfterContentInit, ngAfterContentChecked) and ngAfterViewChecked, which run after content projection and after each check of the view. When a component shares an element with directives, the framework does not guarantee the order of a given hook between them — do not rely on it.

🧪 Lifecycle lab · four ShopUI jobs
@Component({ selector: 'app-search-box', changeDetection: ChangeDetectionStrategy.OnPush, template: `<input #box />` })
export class SearchBox {
  box = viewChild.required<ElementRef<HTMLInputElement>>('box');
  category = input.required<string>();
  label = computed(() => `Search in ${this.category()}`);          // derive: no ngOnChanges needed

  constructor() {
    afterNextRender(() => this.box().nativeElement.focus());        // browser only
    inject(DestroyRef).onDestroy(() => this.timer && clearTimeout(this.timer));   // cleanup
  }
}

Illustrative sketch. Nothing touches window or the DOM on the server, and the timer is cleared when the component is removed.

▾ Go one level deeper (60 seconds)

Render phases. afterNextRender and afterEveryRender run callbacks in four phases — earlyRead, write, mixedReadWrite, read — so DOM writes happen before reads, which minimises layout thrashing. The docs advise avoiding earlyRead and mixedReadWrite when possible.

Browser only. These callbacks do not run on the server; the docs recommend them instead of isPlatformBrowser checks in templates, which can cause hydration mismatches and layout shifts (page 10).

DestroyRef also has a destroyed property, so async code can check whether the component is already gone.

🔥 Interview recall
  • Constructor: inject dependencies; inputs are not set yet.
  • ngOnChanges (classic inputs) then ngOnInit (once); ngDoCheck on every check.
  • afterNextRender / afterEveryRender run only in the browser, after rendering, in an injection context.
  • DestroyRef.onDestroy or ngOnDestroy for cleanup.
  • Prefer computed() over copying inputs in hooks; set initial values before the view is checked to avoid NG0100.
  • Do not depend on the hook order between a component and directives on one element.
🎤 Say this in an interview
"I choose the lifecycle moment by the job: inputs are ready in ngOnInit, derived values belong in computed, browser-only DOM work goes in afterNextRender so it is skipped on the server, and cleanup goes in DestroyRef or ngOnDestroy. I avoid setting state after the view is checked, which causes NG0100."
⚠️ Common trap

Reading inputs in the constructor. They are not there yet.

Forgetting cleanup. A component that is removed but whose timer or subscription lives on leaks memory and keeps running.

🌱 ngOnInit

Runs once when inputs have their first values; before the view exists.

🖼️ afterNextRender
