📖 Why did this need to exist?

Pages 1–10 gave you the model: components, change detection, OnPush, signals, templates, services, forms, routes, defer and SSR. The model tells you where to look; a profile tells you what is actually slow.

Fixing by intuition is how apps collect pointless changes — an OnPush here, a computed there, nothing measured. The playbook is the same ladder as every other lab on this site; the instruments are different.

This page covers the instruments (Angular DevTools, the Chrome Performance panel with the Angular track), a triage map from symptom to page, and the one-change-at-a-time habit.

1 · MEASURE ★

📏 How slow, exactly?

Change-detection cycles and milliseconds in Angular DevTools — a number, not a feeling.

2 · READ ★

🔬 What was checked, and why?

Read the profiler: which components ran and what triggered them.

3 · FIND ★

🎯 The biggest wrong thing

A default-strategy tree, a function call in a template, a leaked subscription, a heavy bundle?

4 · GUESS ★

💡 One hypothesis

Missing OnPush? No track? Hot observable? Eager route?

5 · CHANGE ★

🔧 Change one thing

Never two at once.

6 · PROVE ★

✅ Re-measure

Same interaction, fewer checks, fewer milliseconds.

▾ Go one level deeper (60 seconds)

Production builds. Development mode adds extra checks (like the NG0100 second pass), so milliseconds differ from production; compare before and after in the same build.

Slow computations. Angular’s best-practices guides on slow computations and on profiling with Chrome DevTools cover long tasks that block the main thread.

Correctness first. A wrong value is a model bug (pages 2–3); a slow one is a measurement problem. Do not optimise a wrong value.

🔥 Interview recall
  • The ladder: measure → read → find the biggest wrong thing → one hypothesis → one change → prove.
  • Angular DevTools Profiler: each bar is a change-detection cycle; select a bar for per-component time; skipped OnPush components show grey.
  • Chrome’s Performance panel can show an Angular track after ng.enableProfiling() (v20+).
  • Triage: slow interaction (2–4), stale screen (2, 3, 8), memory (6), first load (9–10).
  • One change per recording; keep only what the profile justifies.
  • Compare before and after in the same build.
🎤 Say this in an interview
"When an Angular screen is slow I record the exact interaction in the DevTools profiler, find which components were checked and how long each took, form one hypothesis from change detection, OnPush, track or subscriptions, change one thing, and re-record in the same build to prove it."
⚠️ Common trap

Adding OnPush everywhere without a profile. You get stale screens and no proof of benefit.

Three changes in one commit. You will not know which worked.

🐞 Correctness bug

The screen is wrong: mutation, missing notification, NG0100.

vs.
🐢 Performance bug

The screen is right but late: too many checks, heavy templates, big bundles.
