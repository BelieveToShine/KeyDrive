🎯 Signals form a graph: writable signals at the edges, computed values in between, and effects only where you must touch something outside.
▶️ Watch it happen: a graph of signals
📖 Why did this need to exist?

Page 3 gave you signal and computed in five lines. A real component needs more: state that resets when another value changes, data that loads asynchronously, and a bridge to RxJS (page 6) where streams are still the right tool.

The rule that keeps signal code simple: derive, do not copy. If a value can be computed from other signals, make it computed(); reach for effect() only to talk to the outside world, like writing to localStorage or logging.

This page covers each tool, when to choose it, and the interop with observables.

📚 The toolbox
ToolWhat it doesReach for it when
signal(v)Writable state: .set(), .update(); asReadonly() exposes a read-only viewLocal state
computed(() => …)Read-only, lazy, cached; tracks only the signals actually readAny value derived from other signals
linkedSignal(…)A writable signal whose value is reset by a computation when its source changesA selection that must reset when the options change (e.g. selected shipping option)
effect(() => …)Runs when signals it reads change; asynchronously, during change detectionSide effects: logging, localStorage, a non-signal API — last resort
untracked(() => …)Reads signals without creating a dependencyAn effect that must not re-run for some values
resource / rxResource / httpResourceAsync data as signals (value, status, error); restarts when its signal inputs changeServer data that depends on a signal (page 6, 9)
toSignal(obs$)Observable → signal; subscribes immediately, cleans up automatically; needs an initial value (or requireSync)Show a stream in a template
toObservable(sig)Signal → observable; emits asynchronously via an effect; may collapse quick updatesUse RxJS operators (debounce, switchMap) on a signal

Details: reads after an await inside an async effect are not tracked, so read signals first. Writing signals inside effects can cause ExpressionChangedAfterItHasBeenChecked and circular updates; the docs advise computed signals for state derived from other state.

🔌 Signals and RxJS together
🧪 Signals lab · four ShopUI state problems
products = signal<Product[]>([]);
query = signal('');
visible = computed(() => this.products().filter(p => p.name.includes(this.query())));   // derive, don't copy
count = computed(() => this.visible().length);

// a selection that resets when the options change
shippingOptions = input.required<Option[]>();
selected = linkedSignal(() => this.shippingOptions()[0]);

// a genuine side effect
constructor() { effect(() => localStorage.setItem('q', this.query())); }

Illustrative sketch. The only effect talks to localStorage — something no signal can do for you.

toSignal details. It subscribes immediately (like the async pipe), cleans up when its injection context is destroyed unless manualCleanup is set, uses initialValue until the first emission (or requireSync: true if the observable emits synchronously), and the signal throws if the observable errors.

Resources. httpResource wraps HttpClient: it requests eagerly, goes through interceptors, and a new reactive input cancels the pending request. rxResource takes a stream factory returning an Observable, called again whenever its params change. Check the stability labels in the docs for your version.

linkedSignal is described in the docs as stable since v20.

🔥 Interview recall
  • Derive, do not copy: computed for derived values, effect only for outside-world side effects.
  • computed is lazy and cached and tracks only the signals it actually reads.
  • linkedSignal = writable state that resets when its source changes.
  • Effects run asynchronously during change detection; reads after an await are not tracked.
  • toSignal subscribes immediately and cleans up automatically; toObservable emits via an effect and may collapse updates.
  • resource / rxResource / httpResource expose async data as signals and restart when inputs change.
🎤 Say this in an interview
"I treat signals as a graph: writable signals at the edges, computed values derived from them, linkedSignal for dependent writable state, and effects only for genuine side effects like writing to localStorage. For async data I use resources, and I bridge to RxJS with toSignal and toObservable where streams and operators are the better tool."
⚠️ Common trap

An effect that copies one signal to another. It is slower, can raise NG0100 and loops; use computed or linkedSignal.

Assuming toObservable emits every intermediate value. It collapses quick updates to the latest.

🧮 computed

Read-only; derives from other signals; lazy and cached.

vs.
🔗 linkedSignal

Writable; derives a default from a source and resets when the source changes.
