📖 Why did this need to exist?

Page 6 showed that HttpClient returns observables. Page 7 showed services receive HttpClient by injection. But every service repeating “add the token, handle 401, log the error” is exactly the scatter that interceptors remove.

In the React lab, the API-layer dive built the same idea by hand with a fetch wrapper. Angular gives it a name and a registration point: provideHttpClient(withInterceptors([…])).

This page covers the functional interceptor shape, the common jobs, error handling and the careful rules for retries.

🧱 A functional interceptor
// auth.interceptor.ts
export const authInterceptor: HttpInterceptorFn = (req, next) => {
  const token = inject(AuthService).token();
  const authed = req.clone({ setHeaders: { Authorization: `Bearer ${token}` } });   // a modified copy
  return next(authed);                                                              // pass it on
};

// app.config.ts
provideHttpClient(withInterceptors([authInterceptor, loggingInterceptor, errorInterceptor]))

Illustrative sketch. Functional interceptors run in an injection context, so they can call inject(); the docs recommend them over DI-based class interceptors for their more predictable ordering.

Errors. HttpClient reports failures as an HttpErrorResponse on the observable’s error channel; network and timeout errors have status 0.

▾ Go one level deeper (60 seconds)

Registration. withInterceptors is a feature passed to provideHttpClient; it adds one or more functional interceptors. The older withInterceptorsFromDi() keeps class-based interceptors working during a migration.

Fetch backend. By default HttpClient uses the fetch API; withXhr() switches to XMLHttpRequest. Interceptors work the same either way.

Testing. The docs’ HTTP testing guide shows an auth-header interceptor test with a modified request copy.

🔥 Interview recall
  • An interceptor is middleware around HttpClient: modify the request (clone), observe or change the response (pipe).
  • Functional interceptors via provideHttpClient(withInterceptors([…])); order = array order.
  • Requests are immutable; HttpContext is mutable and carries state across retries.
  • Failures arrive as HttpErrorResponse; network errors have status 0.
  • Never swallow errors with catchError(() => EMPTY).
  • Retry only idempotent requests, with backoff; refresh a token once on 401.
🎤 Say this in an interview
"I register functional interceptors with provideHttpClient: one adds the auth header by cloning the request, one logs and times calls, one normalises errors. I never swallow errors, I retry only safe requests with backoff, and I refresh the token once on a 401 while excluding the refresh call itself from the interceptor."
⚠️ Common trap

Retrying every failure. A retried POST can create two orders.

Mutating the request. It is immutable — clone it.
