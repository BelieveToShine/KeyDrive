❓ "How does dependency injection work in Angular, and what is the difference between root and component providers?"
👁 See it first
🎯 Dependency injection means a class asks for what it needs and Angular supplies it — and where you provide it decides how many copies exist.
▶️ Watch it happen: ask and receive
📖 Why did this need to exist?

Components (pages 1–4) should not build their own HTTP clients, carts or loggers. If they did, every component would create its own copy, and tests could not replace them. Instead the component says “I need a CartService” and the framework hands one over.

This is Angular’s answer to what React solves with context and custom hooks (React lab, pages 8 and the hooks dives): shared logic and state live in services, provided at the right level.

Because Angular is a full framework, the router, HttpClient and forms are all delivered through the same mechanism — so understanding it unlocks the rest of the lab.

🧰 Writing and using a service
@Injectable({ providedIn: 'root' })                       // one app-wide instance, tree-shakable
export class CartService {
  private items = signal<CartItem[]>([]);
  readonly count = computed(() => this.items().length);
  add(item: CartItem) { this.items.update(l => [...l, item]); }
}

@Component({ selector: 'app-cart-button', template: `Cart ({{ cart.count() }})` })
export class CartButton {
  cart = inject(CartService);                                  // ask; Angular supplies
}

Illustrative sketch. inject() works in an injection context: a constructor, a field initialiser, or a factory function.

▾ Go one level deeper (60 seconds)

Two injector trees. Element injectors follow the component tree; environment injectors follow the application and route hierarchy. A lookup tries the element injectors first, then the environment injectors, then fails with NullInjectorError.

viewProviders scope a provider to a component’s own view, not to projected content.

Debugging. Angular DevTools has an Injectors view that shows the injector tree, which helps when a service has the “wrong” instance.

🔥 Interview recall
  • DI: a class asks (inject()), Angular supplies; shared logic and state live in services.
  • providedIn: 'root' = one app-wide, tree-shakable instance.
  • A component’s providers create a new instance per component.
  • Lookup: element injectors first, then environment injectors, else NullInjectorError.
  • useClass / useValue / useFactory / useExisting; InjectionToken for non-class values.
  • Environment providers (HttpClient, Router) go in app config or routes, not components.
🎤 Say this in an interview
"Angular’s dependency injection lets a class ask for what it needs and the framework supplies it. I provide services in root for app-wide state, in a component’s providers when each instance needs its own, and I swap implementations with useClass or useValue in tests. Lookup goes through element injectors, then environment injectors up to root, and a missing provider throws NullInjectorError."
⚠️ Common trap

Providing an app-wide service in a component too. You silently create a second instance.

Putting provideHttpClient() in a component. It is an environment provider.

🌳 Root provider

One shared instance for the app.

vs.
🧩 Component provider

A new instance per component and its subtree.
