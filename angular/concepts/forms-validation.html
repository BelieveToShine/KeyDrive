📖 Why did this need to exist?

The forms page gave you the three systems and the value/validity/touched state. This dive covers the part that takes real forms from demo to production: custom validators, async checks (is this email already taken?), rules across fields, and repeating rows.

The ShopUI checkout has about 12 fields — email, address, phones that repeat, a confirmation field — which hits every one of these.

The patterns are for reactive forms; signal forms express the same rules as a schema (see the forms page).

🔁 Repeating rows with FormArray
🧪 Validation lab · the checkout email and password
// custom sync validator: no spaces
const noSpaces: ValidatorFn = c => /\s/.test(c.value ?? '') ? { spaces: true } : null;

// async validator: ask the server, only after sync rules pass
const emailFree = (api: UserApi): AsyncValidatorFn => c => api.exists(c.value).pipe(map(taken => taken ? { taken: true } : null));

email = new FormControl('', { validators: [Validators.required, Validators.email, noSpaces], asyncValidators: [emailFree(api)], updateOn: 'blur' });

// cross-field: on the group
const same: ValidatorFn = g => g.get('pw')?.value === g.get('confirm')?.value ? null : { mismatch: true };

Illustrative sketch. With updateOn: 'blur' the server is asked once when the user leaves the field instead of on every keystroke.

▾ Go one level deeper (60 seconds)

Timing. updateOn can be set on a control or in FormBuilder options; options are 'change' (default), 'blur' and 'submit'.

Signal forms. The newer system attaches rules to field paths in a schema (required, email, min/max, custom, conditional) and exposes valid(), touched() and errors() as signals; async validation has its own API.

Server rules are not optional. Client validation is a convenience; the server must validate again.

🔥 Interview recall
  • A validator is a function returning an errors object or null.
  • Sync validators run first; async validators run only if all sync validators pass; the control is PENDING meanwhile.
  • updateOn: 'blur' reduces validation and server calls while typing.
  • Cross-field rules live on the FormGroup; repeating rows use FormArray.
  • After adding or removing validators at runtime call updateValueAndValidity().
  • Always validate again on the server.
🎤 Say this in an interview
"I write validators as functions: built-ins and custom sync rules on controls, async validators for server checks that only run after sync rules pass, and group validators for cross-field rules. I set updateOn blur to avoid a request per keystroke, use FormArray for repeating rows, and the server validates again."
⚠️ Common trap

An async validator on every keystroke. One request per character.

An observable that never completes. The control is PENDING forever.

🧮 Sync validator

Cheap, immediate, runs first.

vs.
🌐 Async validator

Server or timer based; runs only after sync rules pass.
