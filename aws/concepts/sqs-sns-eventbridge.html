❓ "What is the difference between SQS, SNS and EventBridge?"
👁 See it first

▶️ Watch it happen: store, announce, route
📖 Why did this need to exist?

The Messaging page showed the shapes. This page compares the three services you will use most, because they overlap and are often confused. The difference is who pulls, who pushes, and who decides where it goes.

AWS's guidance in short: SQS persists messages until they are processed or expire. SNS pushes to a wide range of subscribers and does not persist. EventBridge matches events with rules and sends them to targets. FIFO queues and FIFO topics give strict order; EventBridge does not.

⚖️ Strengths and watch-outs

📬 SQS

✅ Strengths
  • Messages persist until processed or expired
  • A buffer that absorbs spikes
  • FIFO queues for strict ordering; dead-letter queues for failures
⚠️ Watch out for
  • Pull-based: consumers must poll
  • One message is handled by one consumer of the queue
  • Standard queues can deliver duplicates, so consumers must be idempotent

📣 SNS

✅ Strengths
  • Fan-out to a large number of subscribers
  • Many subscriber types: queues, functions, HTTP, email, SMS, mobile push
  • Per-subscriber filters; FIFO topics available
⚠️ Watch out for
  • Messages are not persisted
  • Filtering is configured per subscriber, not in one central place

🧭 EventBridge

✅ Strengths
  • Rules match events by content and choose targets
  • Central routing for many microservices and sources
  • AWS and SaaS events
⚠️ Watch out for
  • No message ordering guarantee
  • Delivery to targets is at least once, so duplicates can occur

▾ Go one level deeper (60 seconds) — what AWS says

AWS describes SQS as pull-based with messages kept until processed or they expire (up to a fixed maximum retention), SNS as push-based with no persistence, and EventBridge as event-driven with rules that match event content and deliver to targets.

SNS filters are set per subscriber, whereas EventBridge rules are central. AWS suggests SNS when you have a large number of subscribers to a topic, and EventBridge when many topics, subscriptions and filters route messages between microservices.

Where strict order is required, use SQS FIFO queues or SNS FIFO topics. EventBridge delivers to targets at least once, so design for duplicates.

🔥 Interview recall
  • SQS = pull, persists until processed or expired. SNS = push, no persistence. EventBridge = rules route events to targets.
  • FIFO queues/topics give strict order; EventBridge has no ordering guarantee.
  • SNS or EventBridge in front, SQS behind each consumer, is the common pattern.
  • Visibility timeout hides a message during processing; a dead-letter queue catches repeated failures.
  • Design consumers to be idempotent.
🎤 Say this in an interview
"SQS is a pull-based queue that keeps messages until they are processed; SNS pushes to many subscribers without storing messages; EventBridge routes events by rules. I combine them — a topic or bus in front, a queue behind each consumer — and use FIFO when order matters, dead-letter queues for poison messages, and idempotent consumers."
⚠️ Common trap

Using SNS where you needed durability. A subscriber that is down misses the message. Subscribe an SQS queue so messages wait.

Second trap: an endless retry loop. A message that always fails keeps returning after the visibility timeout. Set a dead-letter queue.
