S3, EBS, EFS and FSx: object, block and file storage, what each is for and how to choose.

❓ "When would you use S3, EBS or EFS?"
👁 See it first
🎯 Compute is disposable but data is not — pick the storage shape (object, block or file) by how the data is read, and keep it somewhere durable.
▶️ Watch it happen: pick the shape by how it is read
📖 Why did this need to exist?

You have places to run code. But a server can be replaced at any time; the data on it cannot. Photos, invoices, logs, backups and the disk under a database all need durable homes that outlive any one server.

AWS offers three shapes because data is accessed three ways: by name over the web (objects), as a raw disk for one machine (blocks), or as shared folders (files). A wrong pick costs money or speed — object storage is not a database disk, and a disk is not a shared folder.

🧰 The storage services

🪣 Amazon S3

object storage✅ Pick it when
  • Images, documents, backups, logs, data-lake files
  • Read by apps and people over a web API
  • Grows without planning; storage classes and lifecycle rules control cost
⛔ Look elsewhere when
  • Active write-heavy file workloads that need in-place edits and file locking

💽 Amazon EBS

block storage for one server✅ Pick it when
  • The operating-system disk of an EC2 instance
  • A database volume that needs a fast dedicated disk
  • Data is stored redundantly in a single Availability Zone
⛔ Look elsewhere when
  • Sharing one volume between many servers — use a file system

📂 Amazon EFS

shared file system (NFS)✅ Pick it when
  • A shared folder that many servers or containers mount
  • Traditional file permissions and a directory tree
  • A cheaper archive class for cold file data
⛔ Look elsewhere when
  • Plain web assets and media — S3 is simpler and cheaper

🗄️ Amazon FSx

managed file systems✅ Pick it when
  • Specific file systems: Windows File Server, Lustre, NetApp ONTAP, OpenZFS
  • Windows clients that need Windows-style shares
⛔ Look elsewhere when
  • A simple Linux shared folder — EFS is usually enough

▾ Go one level deeper (60 seconds) — keep data safe, not just stored

Durable is not the same as protected. Designing for very high durability means data is unlikely to be lost to hardware failure. It does not protect you from someone — or a script — deleting it. Use versioning and backups for that.

Block vs file vs object. Block storage gives you a raw disk to format. File storage gives you folders with permissions. Object storage gives you whole objects by key; you replace an object, you do not edit it in place.

Access. Use IAM roles (concept 3), and for S3 also bucket policies and Block Public Access. Private subnets can reach S3 through a VPC endpoint (concept 4).

Cost. Prices depend on class, Region and requests; this page gives no figures. Check the pricing pages.

🔥 Interview recall
  • Object (S3), block (EBS) and file (EFS, FSx) — pick by access shape.
  • S3: buckets and objects over an API, regional, many storage classes. EBS: a disk for one server in one AZ. EFS/FSx: shared file systems.
  • EBS volumes live in one zone; use snapshots. S3 spreads objects across zones (except One Zone classes).
  • Durability does not protect against deletion — use versioning and backups.
  • When unsure, S3 is the default for most data.
🎤 Say this in an interview
"I pick storage by its shape. S3 is object storage over an API — my default for files, media and backups. EBS is a block disk for one server in one zone, so I snapshot it. EFS or FSx is for shared file systems that many servers mount. And I remember that high durability is not protection from deletion, so I use versioning and backups."
⚠️ Common trap

Using a server's local disk as the only home for important data. Servers get replaced. Keep the data in S3, a database or an EBS volume that is backed up.

Second trap: an S3 bucket left open "for now". Public buckets are the classic data leak. Keep Block Public Access on and share with presigned URLs or roles instead.
