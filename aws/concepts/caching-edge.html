The layers of caching on AWS — browser, CloudFront, ElastiCache — lazy loading, write-through and the freshness trade-off.

❓ "What is caching, where would you cache on AWS, and what is lazy loading?"
👁 See it first
🎯 A cache keeps a copy of an answer closer to whoever asks, so the slow, expensive place — usually the database — is asked far less often.
▶️ Watch it happen: a cache answers for the database
📖 Why did this need to exist?

You have copies of your app, a load balancer and Auto Scaling. But look at what every copy does: for the same product page, every request asks the same database the same question. Adding more app servers makes it worse, because now more servers ask the database.

A cache fixes that by remembering recent answers. The result is faster pages and less load on the database. The price: a cached copy can be out of date. So caching is always a decision about what to copy, where to keep it, and how long it may stay.

🧰 Where to cache

🌐 Browser cache

on the visitor's device✅ Pick it when
  • Images, scripts and style files that rarely change
  • Controlled by the response headers your app or origin sends
⛔ Look elsewhere when
  • Anything private or fast-changing that must be fresh on every visit

🌍 Amazon CloudFront

a copy near the visitor✅ Pick it when
  • Static files and responses that are the same for everyone
  • Visitors spread across the world
  • You control expiry with Cache-Control headers or TTL settings, and can invalidate early
⛔ Look elsewhere when
  • Personal data that is different for every user

⚡ Amazon ElastiCache

a shared in-memory cache✅ Pick it when
  • Data many app copies read again and again
  • Results of slow database queries, sessions
  • Engines such as Valkey and Memcached
⛔ Look elsewhere when
  • Data you cannot afford to lose — a cache is a copy, not the source of truth

🧠 In-app memory cache

inside one app instance✅ Pick it when
  • Tiny, hot data that is the same everywhere
  • The fastest possible reads, with no network trip
⛔ Look elsewhere when
  • Several instances need to agree — each has its own private copy; use a shared cache

⚖️ Lazy loading: the trade-offs

✅ Strengths
  • Only data that is actually asked for gets cached
  • If a cache node fails or is empty, the app still works — it just reads the database
⚠️ Watch out for
  • A miss costs three trips: cache, database, write back
  • Data can go stale; add a TTL or invalidate on write
  • A newly started cache is empty, so the first requests are slower

▾ Go one level deeper (60 seconds) — freshness and write strategies

Freshness is the whole game. Every cached item needs an expiry time, and a way to throw it away when the source changes. A short TTL is fresher but misses more; a long one is faster but staler.

Write-through writes to the database and the cache together, so the cache stays current — but a new empty node has no data, and much of what is cached may never be read. AWS commonly recommends combining lazy loading with write-through, and adding a TTL to each write to get the benefits of both.

Invalidate rather than update. A simple guide for writes is to delete the cached entry rather than update it; a narrow race remains, so strict consistency may need locks or versioned writes.

CloudFront TTLs. Caching is governed by the origin's Cache-Control headers; without them the behaviour's default TTL applies, bounded by the minimum and maximum TTL. Invalidation requests are not immediate and can be charged beyond a free allowance; versioned names avoid that. Origins can also tag objects so you invalidate by tag.

Engines and names change. Check the ElastiCache documentation for the engines and node options available today.

🔥 Interview recall
  • A cache keeps copies closer to the asker so the slow source is asked less. The price is possible staleness.
  • Layers: browser → CloudFront edge → ElastiCache → database.
  • Lazy loading: check cache; on miss read the database and save a copy. Weakness: stale data — use a TTL or delete on write.
  • Write-through keeps the cache fresh but fills it with data that may never be read; combine with lazy loading and a TTL.
  • CloudFront serves from the edge until expiry; invalidations take minutes; versioned file names avoid them.
🎤 Say this in an interview
"A cache trades freshness for speed. I cache in layers: the browser, CloudFront at the edge for content that is the same for everyone, and ElastiCache in front of the database. I use lazy loading with a TTL, sometimes combined with write-through, and I invalidate or version content when it changes. I never treat the cache as the source of truth."
⚠️ Common trap

Do not treat the cache as the source of truth. It is a copy and can disappear or go stale. Your app must still work, and recover, from the database alone.

Second trap: caching personal data in a shared place. An edge or shared cache that stores one user's page and serves it to another is a serious bug. Cache only what is the same for everyone, or key the cache carefully.

Sits next to your app and holds data and query results, shared by all your app copies.

▾ 💻 Tiny illustrative example 
# lazy loading in plain pseudo-code
item = cache.get(key)
if item is None:               # miss
    item = database.read(key)  # slow path
    cache.set(key, item, ttl=minutes)  # save a copy, with an expiry
return item

Illustrative pseudo-code only — real client libraries have their own method names and options.
