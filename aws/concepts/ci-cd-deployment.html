❓ "How would you set up CI/CD to AWS with zero downtime and a safe rollback?"
👁 See it first
🎯 CI/CD means every change is built, tested and released by the same automatic steps — so shipping is routine, and undoing a bad release is one move.
📖 Why did this need to exist?

The environment is code now. The app is code too. If a person still copies files onto a server by hand, every release is different, every release is slow, and every release is a little scary — so teams release rarely, in big batches, which makes each one riskier.

CI (continuous integration) builds and tests every change automatically. CD (continuous delivery or deployment) takes the tested package and ships it by a repeatable path. The second half of the skill is how it goes live: all at once, to a few users first, or in steps, with a quick way back.

  • Deployment itself — that is CodeDeploy or another tool

🚀 AWS CodeDeploy

deploys with a chosen strategy✅ Pick it when
  • In-place on EC2 or on-premises; blue/green on EC2, Lambda and ECS
  • Traffic shifting for Lambda and ECS: all at once, canary or linear
⛔ Look elsewhere when
  • In-place for Lambda and ECS — those platforms use blue/green

🐙 GitHub Actions and others

your own pipeline tool✅ Pick it when
  • Your code is already on GitHub

  • Storing an access key as a pipeline secret

▾ Go one level deeper (60 seconds) — details that bite

Platform differences. In-place deployments are for EC2 and on-premises instances; Lambda and ECS cannot use in-place and use blue/green with traffic shifting.

Build once, deploy the same package everywhere. If each environment builds its own copy, "it worked in staging" proves little.

Health decides. CodeDeploy tracks application health with rules you configure; wire in alarms (concept 17) so a bad canary stops by itself.

OIDC trust. Add the provider to IAM, create a web-identity role with the expected audience, and restrict the trust policy to your repository and branch. AWS recommends matching on immutable identifiers where available, because names can change.

🔥 Interview recall
  • CI builds and tests every change automatically; CD ships the tested package by a repeatable path.
  • CodePipeline orchestrates, CodeBuild builds and tests, CodeDeploy deploys with a strategy.
  • Blue/green runs the new version beside the old and switches traffic; canary sends a small share first; linear raises it in equal steps.
  • Lambda and ECS deployments use blue/green traffic shifting; in-place is for EC2 and on-premises.
  • Prefer OIDC and an IAM role to a stored access key for pipeline sign-in; scope the trust policy to the repo and branch.
🎤 Say this in an interview
"I use a pipeline: every change is built and tested, then deployed beside the current version and traffic is shifted — all at once for a clean cut-over, canary or linear when I want proof from real users — and shifting back is my rollback. The pipeline signs in with OIDC to an IAM role scoped to the repository, so no access key is stored."
⚠️ Common trap

A stored access key for the pipeline. It is a long-lived secret that leaks through logs, forks and screenshots. Use short-lived credentials through OIDC.

Second trap: an unrestricted OIDC trust policy. If the role trusts the provider without naming your repository and branch, workflows outside your control can assume it.

🔁 Blue/green

The new version waits beside the old, then everyone switches together.

vs.
🐤 Canary

A small share goes to the new version first, so real users test it before everyone does.

▾ 💻 Tiny illustrative example 
# start a CodeDeploy deployment using a canary traffic-shifting configuration (ECS)
aws deploy create-deployment --application-name shop --deployment-group-name prod \
    --deployment-config-name CodeDeployDefault.ECSCanary10Percent5Minutes \
    --revision file://appspec-revision.json

Illustrative shape only — the names and revision file are placeholders; the predefined configuration here sends 10 percent first, then the rest five minutes later.
