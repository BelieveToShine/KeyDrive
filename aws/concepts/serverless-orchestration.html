Serverless runs your work only when something triggers it — so you pay for work done, not for a server waiting.

EventBridge, Lambda and Step Functions: what each is for, how they work together, and how to choose.

❓ "When would you use Lambda, Step Functions or EventBridge?"
👁 See it first
🎯 Serverless means you give AWS a piece of work and a trigger, and AWS runs it only when the trigger fires — so you pay for work done, not for a server waiting.
▶️ Watch it happen: work runs when the trigger fires
📖 Why did this need to exist?

Look at what the earlier concepts gave you: an app that scales and is fast, with queues between its parts. But not all work looks like a web app. A file arrives. A timer fires. An order is approved. Between those moments, nothing happens. Keeping a server running just to wait for them is paying for idle capacity.

Serverless flips that. You write a small unit of work, tell AWS what should start it, and AWS supplies the compute when it fires. When there is a lot to do it scales out; when there is nothing, you pay nothing. The skill is picking the right tool for what kind of work it is: reacting, coding, or orchestrating many steps.

🧰 The tools

λ AWS Lambda

functions that run on a trigger✅ Pick it when
  • Event-driven work: a file, a message, a timer, an API call
  • Short, bursty tasks where you pay while it runs
  • Fed by queues, streams, topics and event buses
⛔ Look elsewhere when
  • Long-running steady services — a container service fits better

🔀 AWS Step Functions

workflow orchestration✅ Pick it when
  • Several steps in order, in parallel, with retries and branches
  • Standard workflows: long-running, durable, auditable; exactly-once execution
  • Express workflows: high-rate, short (up to five minutes), at-least-once
⛔ Look elsewhere when
  • A single quick action — a Lambda function is enough

🧭 Amazon EventBridge

routes events by content✅ Pick it when
  • React to AWS and SaaS events without polling
  • One event, many targets
⛔ Look elsewhere when
  • You need ordering guarantees — it does not provide them

📬 SQS in front of Lambda

a buffer between event and code✅ Pick it when
  • Absorb spikes so the function is not overwhelmed
  • Retry and dead-letter failed messages
⛔ Look elsewhere when
  • Work that must start instantly with no queue

▾ Go one level deeper (60 seconds) — habits that keep serverless safe

Be idempotent. Events and messages can arrive more than once and retries happen. Design the work so doing it twice is safe — especially with Express workflows and EventBridge targets, which are at-least-once.

Keep functions short and stateless. Anything that must be remembered between steps belongs in a database, in storage, or in the workflow's state — not in the function's memory.

Cold starts. When nothing is warm, a new execution environment must start first, adding a delay. Check the Lambda documentation for the ways to reduce it that suit you.

Use the execution role. A Lambda function gets its permissions from an IAM role (concept 3) — give it only what it needs, and keep secrets in a secrets service (concept 15).

🔥 Interview recall
  • Serverless = you supply the work and the trigger; AWS supplies compute only while it runs.
  • EventBridge routes events; Lambda runs code; Step Functions orchestrates multi-step work with retries and state.
  • Standard workflows: long, durable, exactly-once. Express: up to five minutes, high rate, at-least-once. The type is fixed after creation.
  • Lambda fits short, bursty tasks; steady long-running services fit containers better.
  • Put SQS in front of a function to absorb spikes; make work idempotent.
🎤 Say this in an interview
"Serverless means I provide the code or workflow and a trigger, and AWS runs it only when needed. EventBridge routes events, Lambda runs my own code, and Step Functions orchestrates multi-step work with retries — Standard for long, durable, exactly-once flows, Express for short, high-volume ones. I put a queue in front of Lambda for spikes, and I make the work idempotent."
⚠️ Common trap

"Serverless" does not mean "no servers" — and it is not always the right tool. A steady, long-running service may fit a container service better than short-lived functions.

Second trap: using Express workflows for work that must never repeat. Express is at-least-once; for payments and other non-repeatable actions use Standard.

λ Lambda

You write the code. One function, one trigger; great for small, event-driven work.

vs.
🔀 Step Functions

You design the flow of many steps, with retries, branches and waiting; steps are often Lambda functions.

▾ 💻 Tiny illustrative example 
# create a small Lambda function from a zip file; it needs an execution role
aws lambda create-function --function-name make-thumbnail --runtime python3.12 \
    --role <execution-role-arn> --handler app.handler --zip-file fileb://function.zip

Illustrative shape only — the runtime version, role and handler are examples, and supported runtimes change over time.
