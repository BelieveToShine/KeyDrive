SQS, SNS, EventBridge and Kinesis: messages, events and streams, what each is for and how they combine.

❓ "When would you use SQS, SNS, EventBridge or Kinesis?"
👁 See it first
🎯 When one part of your system calls another and waits, they fail together — put a queue, topic or stream in between so each side can scale and fail on its own.
▶️ Watch it happen: a message in between
📖 Why did this need to exist?

Caching and scaling help a request finish faster. But some work does not belong in the request at all: sending an email, resizing an image, charging a card, updating stock. If the web request waits for all of that, it is slow — and if one step fails, the whole request fails.

The fix is to decouple. The web app drops a message or event into a service in the middle and carries on. Workers pick it up when they can. Under load, work queues up instead of failing; when a worker crashes, the message is still there. AWS offers several services because "send something" means different things.

🧰 The four services

📬 Amazon SQS

a queue — pull-based✅ Pick it when
  • A job for one worker; messages wait until processed or expired
  • A buffer so a slow consumer does not slow the producer
  • FIFO queues when strict order matters
⛔ Look elsewhere when
  • You need to notify many subscribers at once → SNS or EventBridge

📣 Amazon SNS

topics — push to subscribers✅ Pick it when
  • Fan-out: one message to many subscribers
  • Subscribers include SQS queues, Lambda functions, HTTP endpoints, email, SMS and mobile push
  • SNS FIFO topics when order matters
⛔ Look elsewhere when
  • You need messages to wait for slow consumers — SNS does not store them; put an SQS queue behind it

🧭 Amazon EventBridge

an event bus with rules✅ Pick it when
  • Route events by their content to one or more targets
  • Many topics and filters between microservices
  • AWS and SaaS events
⛔ Look elsewhere when
  • You need ordering guarantees — EventBridge does not provide message ordering

🌊 Amazon Kinesis Data Streams

a stream — a replayable log✅ Pick it when
  • Huge volumes of ordered events: clicks, logs, telemetry
  • Many readers, each with their own position; replay within retention
⛔ Look elsewhere when
  • A simple job queue — SQS is simpler

▾ Go one level deeper (60 seconds) — habits for async systems

Expect duplicates. Messaging infrastructure can deliver the same message more than once, and EventBridge targets get events at least once. Make consumers idempotent: doing the work twice has the same result as once.

Dead-letter queues. When a message fails repeatedly, move it aside so it does not block healthy messages, and look at it later.

Retention. SQS keeps messages until they are processed or expire (up to a fixed maximum retention); Kinesis keeps data for its retention period; SNS does not persist messages.

Message, event, stream. A message is a command for one handler. An event is a fact many may use. A stream is a log you read at your own position. The words matter because they decide who is responsible for what happens next.

🔥 Interview recall
  • Message (SQS/SNS) = a job; event (EventBridge) = a fact to route; stream (Kinesis) = a replayable log.
  • SQS is pull-based and persists until processed or expired; SNS is push-based and does not persist; EventBridge routes by rules and has no ordering guarantee.
  • FIFO queues and FIFO topics give strict ordering.
  • Combine: SNS or EventBridge → SQS buffer per consumer. Add dead-letter queues.
  • Consumers must be idempotent — duplicates happen.
🎤 Say this in an interview
"I decouple with the right shape: SQS for a job one worker handles, SNS for fan-out to many subscribers, EventBridge to route events by content, and Kinesis for a replayable ordered stream. In practice I put EventBridge or SNS in front and an SQS queue behind each consumer as a buffer, add dead-letter queues, and make consumers idempotent because duplicates happen."
⚠️ Common trap

Treating SNS like a queue. It pushes to subscribers and does not persist messages; a subscriber that is down can miss them. Put an SQS queue behind it.

Second trap: assuming order everywhere. Only FIFO queues, FIFO topics and a single Kinesis shard give ordering. EventBridge does not.

📨 Message

A command for one handler. Removed once handled. You care that it was processed.

vs.
📣 Event

A fact that something happened. Many may react, or none. The sender does not care who.
