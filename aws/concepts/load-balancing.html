Application, Network and Gateway Load Balancers and Route 53: what each sees, how far it reaches and when to pick it.

❓ "When would you use an Application Load Balancer, a Network Load Balancer or Route 53?"
👁 See it first
🎯 A load balancer spreads traffic across healthy copies — and the real choice is how much of the request it should understand, and how far it should reach.
📖 Why did this need to exist?

Compute, storage and a database make one working instance. But one instance is a single point of failure and a ceiling on throughput. The obvious fix is more copies. The new problem: who decides which copy gets each request?

That is what a load balancer does. It sits in front, spreads requests across targets, and stops sending traffic to a target that is unhealthy. On AWS the tools differ in what layer they work at and how far they reach — and "spread the traffic" inside a Region is a different job from sending a visitor to the nearest healthy Region.

🧰 The tools

🚪 Application Load Balancer (ALB)

layer 7 · HTTP and HTTPS✅ Pick it when
  • Web apps and APIs in one Region
  • Route by URL path or host name
  • Targets can be instances, containers and Lambda functions
⛔ Look elsewhere when
  • Raw TCP or UDP traffic → Network Load Balancer

⚖️ Network Load Balancer (NLB)

layer 4 · TCP and UDP✅ Pick it when
  • Handling sudden traffic bursts
  • Keeping the client's source IP
  • A fixed IP for the life of the load balancer
⛔ Look elsewhere when
  • You need to route by URL — that is an ALB

🧱 Gateway Load Balancer (GWLB)

for third-party virtual appliances✅ Pick it when
  • Send traffic through firewalls or inspection appliances and scale them
  • Needs extra integration — read the guide first
⛔ Look elsewhere when
  • Ordinary application load balancing

🧭 Amazon Route 53

DNS routing and health checks✅ Pick it when
  • Send users to the right Region: failover, weighted, latency, geolocation and other policies
  • Health checks decide which answers are used
⛔ Look elsewhere when
  • You need instant failover — DNS answers can be cached by clients

▾ Go one level deeper (60 seconds) — health, targets and the old one

Health checks decide where traffic goes. A load balancer sends requests only to healthy targets, and Route 53 uses health checks to decide which answers to give. Make the health check meaningful: it should test what the app really needs, not just "the process is up".

Weighted records: a weight of 0 stops routing to that resource. If you use weighted records for failover, zero-weight records get traffic only when all non-zero records are unhealthy.

Other Route 53 policies: geoproximity, IP-based and multivalue answer also exist.

Classic Load Balancer: the previous generation. ALB and NLB are the purpose-built replacements and AWS offers a migration wizard that creates an equivalent new load balancer; you then redirect traffic yourself.

Edge: content delivery and edge caching (CloudFront) are in the Caching & Edge concept.

🔥 Interview recall
  • ALB = layer 7, HTTP/HTTPS, path and host routing. NLB = layer 4, TCP/UDP, bursts, fixed IP. GWLB = third-party appliances. Route 53 = DNS across Regions.
  • Load balancers send traffic only to healthy targets; health checks should test real dependencies.
  • Route 53 policies: failover, weighted, latency, geolocation (and more). DNS answers can be cached, so failover is not instant.
  • Classic Load Balancer is the previous generation — migrate to ALB or NLB.
  • A load balancer does not make a single database highly available.
🎤 Say this in an interview
"For web traffic in a Region I use an Application Load Balancer with path and host routing; for TCP or UDP and bursts I use a Network Load Balancer; for firewall appliances a Gateway Load Balancer. Across Regions I put Route 53 in front with latency or failover policies and health checks, remembering that DNS caching means failover is not instant."
⚠️ Common trap

Expecting Route 53 failover to be instant. It answers DNS; clients and resolvers may keep the old answer for a while.

Second trap: a load balancer is not high availability for the data tier. It spreads traffic to the copies you have; if all copies depend on one database, that database is still your single point of failure.

▾ 💻 Tiny illustrative example 
# create an internet-facing Application Load Balancer across two subnets
aws elbv2 create-load-balancer --name shop-alb --type application \
    --subnets <subnet-a> <subnet-b> --security-groups <sg-id>

Illustrative shape only — real setups also add a target group, a listener and health checks.
