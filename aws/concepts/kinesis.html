A Kinesis stream is a log many readers can read at their own pace — the right tool when order, volume and replay matter.

Shards, partition keys, retention, capacity modes and enhanced fan-out: when a stream beats a queue.

❓ "What is Kinesis Data Streams, and when would you choose it over SQS?"
👁 See it first
🎯 A Kinesis stream is a log of events that many readers can read at their own pace and replay — the right tool when order, volume and several consumers matter.
▶️ Watch it happen: a log many can read
📖 Why did this need to exist?

A queue is a to-do list: one worker takes a task and it is gone. But some data is a flow: clicks, logs, sensor readings. Many different systems want the same flow — one for analytics, one for alerts, one for an archive — and sometimes you need to read it again.

A stream keeps the records for a retention period and lets every consumer read at its own position. Reading does not delete. That is a feature (replay), but it means each consumer must remember where it stopped.

🧰 The vocabulary

🔑 Partition key

decides the shard✅ Pick it when
  • Hashed to choose a shard; same key, same shard, so order is kept per key
  • Pick a key with many distinct values to spread load
⛔ Look elsewhere when
  • A key with a few values — it overloads some shards

📦 Shard

the unit of capacity✅ Pick it when
  • Each shard has fixed read and write limits
  • More shards, more throughput
⛔ Look elsewhere when
  • Expecting unlimited speed from one shard

🕰️ Retention

how long records are kept✅ Pick it when
  • Default is 24 hours after creation, extendable up to 365 days
  • Replay inside the window
⛔ Look elsewhere when
  • Treating the stream as permanent storage

🎚️ Capacity modes

on-demand or provisioned✅ Pick it when
  • On-demand: Kinesis manages the shard count
  • Provisioned: you set and change the shard count, and can split a hot shard yourself
⛔ Look elsewhere when
  • On-demand does not isolate a single very hot key — use provisioned for highly uneven keys

▾ Go one level deeper (60 seconds) — limits and modes

Shard limits. Each shard has fixed limits for writes (a records-per-second and a megabytes-per-second cap) and for reads. Check the current numbers in the developer guide; they differ by mode and change over time.

Hot shards. Uneven partition keys can still cause throttling. Provisioned mode lets you split a hot shard manually. On-demand mode spreads evenly and does not detect and isolate a hot hash key.

Retention. The default retention is 24 hours, extendable up to 365 days.

Consumers. Standard consumers use shared read throughput; enhanced fan-out gives registered consumers dedicated throughput, with a cap on registered consumers that depends on the mode.

🔥 Interview recall
  • A stream is a replayable ordered log; reading does not delete.
  • Partition key → hashed → shard; same key, same shard, ordered per key.
  • Retention: 24 hours by default, up to 365 days.
  • On-demand vs provisioned capacity; provisioned lets you split a hot shard.
  • Queue for one-time jobs; stream for many readers and replay.
🎤 Say this in an interview
"A Kinesis stream is a replayable log. Producers choose a partition key that hashes to a shard, so order is kept per key. Records stay for the retention period, many consumers read at their own position, and enhanced fan-out gives a consumer dedicated throughput. I use SQS for one-time jobs and Kinesis when many readers or replay matter, and I watch for hot shards."
⚠️ Common trap

A bad partition key. Using a key with few values sends most records to a few shards, which throttle while others sit idle.

Second trap: forgetting that reading does not delete. Each consumer must track its own position, and records disappear when retention ends.
