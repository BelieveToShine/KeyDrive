Security is layers, not a wall — and governance is guardrails that hold for every account, even when nobody is watching.

SCPs, IAM, WAF, Shield, GuardDuty, Config and Security Hub: how an architect applies protection consistently across everything.

❓ "How would you secure and govern an AWS environment at scale?"
👁 See it first
🎯 Security is layers, not a wall; governance is guardrails that hold for every account, even when nobody is watching.
📖 Why did this need to exist?

Secrets were one slice. But look at the whole system now: many accounts, many people deploying, pipelines creating things at night. What stops someone creating a bucket open to the world? What shows you that a server is under attack? What protects the web app from common web attacks?

The answer is not one product. AWS describes layers: preventive guardrails across the organization, centralized detection, and protection at the edge. Security services are administered from a separate security account, not from the management account that holds the bill.

🧰 The tools

🛡️ Service control policies

guardrails for whole accounts✅ Pick it when
  • Limit what accounts may do across an organization, OU or account
  • Block regions or services you never use
  • Work as deny lists in the default Organizations setup
⛔ Look elsewhere when
  • Granting permission — an SCP never grants; IAM does

🧭 AWS Security Hub

one place for findings and checks✅ Pick it when
  • Collect findings from several security services
  • Check accounts against standards such as the Foundational Security Best Practices
⛔ Look elsewhere when
  • Expecting it to fix things — findings still need action

🕵️ Amazon GuardDuty and AWS Config

detect threats; track configuration✅ Pick it when
  • GuardDuty findings flow into Security Hub
  • Config tracks resource settings against rules; start in monitoring mode, then enforce once trusted
  • Config is a prerequisite for Security Hub CSPM
⛔ Look elsewhere when
  • Switching on enforcement before you have seen the findings

🧱 AWS WAF, Shield and Firewall Manager

protect the edge✅ Pick it when
  • WAF: managed rules for common web attacks; keep them in default mode so they update
  • Shield Advanced for load balancers, Elastic IPs and CloudFront
  • Firewall Manager applies WAF, Shield and security group rules across accounts
⛔ Look elsewhere when
  • Treating the network as the only defense — identity is still the first line

▾ Go one level deeper (60 seconds) — rolling out guardrails safely

Start in monitoring mode. AWS Config rules can run in a monitoring mode and later move to enforcement once their behaviour is trusted. The same idea applies to any new guardrail: watch, fix real problems, then enforce.

Use a security account. AWS's reference architecture recommends delegating administration of security services to a Security Tooling account, which separates security work from the management account that pays the bills.

Management account. Service control policies do not apply to the management account, so keep workloads out of it (concept 1).

Edge. Select AWS managed rules for WAF based on your needs and use them in default mode so they update automatically. Shield Advanced can protect Application Load Balancers, Elastic IP addresses and CloudFront distributions.

Automate response. Findings can trigger automation, for example updating a WAF IP set to block a suspicious host.

🔥 Interview recall
  • Layers: organization guardrails (SCPs), identity (IAM), network and edge (security groups, WAF, Shield), detection (GuardDuty, Config, Security Hub).
  • SCPs filter; IAM grants; the effective permission is the overlap. SCPs do not apply to the management account.
  • GuardDuty findings flow into Security Hub; Config is a prerequisite for the posture checks.
  • Start Config rules in monitoring mode, then enforce. Administer security services from a delegated security account.
  • Identity is the first line of defense; the network supports it.
🎤 Say this in an interview
"I treat security as layers. SCPs in AWS Organizations are the outer guardrail on every account; IAM grants within it. Security groups and WAF guard the network and edge, and GuardDuty, Config and Security Hub detect and gather findings, with response automated from them. I roll guardrails out in monitoring mode first, and run the security services from a delegated security account."
⚠️ Common trap

Turning on a deny guardrail everywhere on day one. It can block legitimate deployments and stop teams. Watch first, fix, then enforce.

Second trap: trusting the network as the only defense. A private network does not help if a stolen identity can reach everything. Identity first; the network supports it.

🪪 IAM policy

Grants an identity permission to do specific things.

vs.
🛡️ SCP

Limits what an account may use at all. Never grants; works with IAM, not instead of it.

▾ 💻 Tiny illustrative example 
{ "Version": "2012-10-17", "Statement": [{
    "Effect": "Deny", "Action": "*", "Resource": "*",
    "Condition": { "StringNotEquals": { "aws:RequestedRegion": ["eu-west-1","eu-central-1"] } } }] }

Illustrative only — an SCP shaped like this denies actions outside two example Regions; real ones exempt global services and need careful testing.
