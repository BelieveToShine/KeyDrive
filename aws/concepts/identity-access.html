▶️ Watch it happen: nobody may until a policy says so
📖 Why did this need to exist?

You now have accounts and Regions, and resources are about to be created in many places. The next question is not "can it be reached?" but "who or what is allowed to create, read or change each thing?" That includes your apps, not just people — an app that can read a database is an identity too.

AWS answers with IAM (Identity and Access Management). Everything is denied by default; you grant access with policies; and AWS pushes you toward temporary credentials — roles for workloads, federation for people — instead of long-lived keys that can leak. This page is the map; the Roles deep dive shows the mechanics.

🧰 The pieces

🎭 IAM role

an identity with temporary credentials✅ Pick it when
  • Apps and services (EC2, Lambda, containers) that need AWS access
  • Cross-account access
  • Anything that should not have a permanent key
⛔ Look elsewhere when
  • A person who needs everyday access — use Identity Center instead

🧑‍🤝‍🧑 IAM Identity Center

sign-in for your workforce✅ Pick it when
  • AWS's recommended way to give people access to accounts
  • One place for users and their permissions across accounts
  • People get temporary credentials
⛔ Look elsewhere when
  • Workloads — those use roles

📜 IAM policy

a JSON document of allowed or denied actions✅ Pick it when
  • Say exactly which actions on which resources
  • Start from AWS managed policies, then tighten to your own
  • Pair with last-accessed data to remove unused permissions
⛔ Look elsewhere when
  • Wildcards for everything ("*") — that is not least privilege

👑 Root user

the all-powerful account owner✅ Pick it when
  • Only the few tasks that really need it
  • Turn on MFA; do not create root access keys
⛔ Look elsewhere when
  • Daily work — never use root for that

▾ Go one level deeper (60 seconds) — habits AWS recommends

Temporary credentials first. AWS recommends that people reach accounts through federation (temporary credentials) and that workloads use roles. Where long-term keys are unavoidable, rotate them when needed, for example when someone leaves.

Root user. Use it only for the few tasks that require it. Do not create root access keys, turn on MFA, and in a multi-account organization remove root credentials from member accounts so nobody can sign in as root there.

Least privilege. Grant only what a task needs. Start with AWS managed policies, then move to customer managed policies that fit. IAM Access Analyzer can generate a policy from the access activity it sees, and last-accessed data shows permissions nobody uses.

Guardrails above IAM. Service control policies in an organization limit what accounts can do whatever their own IAM says — they filter and never grant.

Groups and users. IAM users and groups still exist, but for people, Identity Center is the recommended door.

🔥 Interview recall
  • IAM: who may do what to which resource. Everything is denied by default; policies grant access.
  • A policy statement has Effect, Action, Resource (and optional Condition). An explicit Deny always wins.
  • People: IAM Identity Center and temporary credentials. Workloads: IAM roles. Avoid long-lived access keys.
  • Root user: only for tasks that need it, with MFA and no root access keys.
  • Effective permission = what SCPs allow ∩ what the identity's policies allow. Use IAM Access Analyzer and last-accessed data to tighten.
🎤 Say this in an interview
"IAM is deny-by-default: access exists only where a policy allows it, and an explicit deny always wins. People sign in through IAM Identity Center and get temporary credentials; workloads use IAM roles, so no access keys live in code. I write least-privilege policies with the help of Access Analyzer, keep root locked away with MFA, and use service control policies as guardrails above the accounts."
⚠️ Common trap

Putting an access key in the code, an environment file or a pipeline variable. It is a permanent password for your account. Give the workload a role and let AWS hand it temporary credentials.

Second trap: fixing a permission error by giving administrator access. It works, and it quietly turns every bug and every leaked token into a full-account incident. Add the one missing action instead.

👤 IAM user

A permanent identity with long-lived credentials. Avoid for people when you can.

🎭 IAM role

An identity you assume for a while and get temporary credentials for. The default for workloads.
