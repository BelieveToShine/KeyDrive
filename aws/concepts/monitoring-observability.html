Concept 17 of 19 · 🛠️ Shipping and operating

Monitoring tells you something is wrong; observability helps you find why — but only if you collected the signals before the incident.

CloudWatch, X-Ray and CloudTrail: metrics, logs, traces and audit, plus alarms that turn signals into action.

❓ "How would you monitor an AWS application and get alerted before users notice?"
👁 See it first
🎯 Monitoring tells you something is wrong; observability lets you work out why — and both need metrics, logs and traces gathered in one place before the incident.
📖 Why did this need to exist?

Guardrails say what should happen. They do not tell you what did happen. The app is fast today and slower next week; a deployment looks fine and customers still see errors; the bill climbs and nobody knows which part grew. Without signals, every problem becomes guessing.

The skill is deciding what to collect before you need it. Metrics answer "is something off?". Logs answer "what exactly happened?". Traces answer "where did this one request spend its time?". And a fourth source, CloudTrail, answers "who changed what?". Then alarms turn signals into action.

🧰 The pieces

📡 Amazon CloudWatch

metrics, logs and alarms✅ Pick it when
  • The main monitoring and observability service for metrics, logs and alarms
  • Logs Insights to query logs
  • Service Map and dashboards to see the flow
⛔ Look elsewhere when
  • Auditing who made API calls — that is CloudTrail

🧵 AWS X-Ray

distributed tracing✅ Pick it when
  • An end-to-end view of a request as it travels through your application
  • A map of the underlying components
⛔ Look elsewhere when
  • Only watching a single server — add metrics and logs too

🕵️ AWS CloudTrail

API activity for audit✅ Pick it when
  • Who made a call, when, and which resources were affected
  • Compliance and investigations
  • Event history covers recent management events by default
⛔ Look elsewhere when
  • Watching performance — use CloudWatch

🚨 CloudWatch alarms

turn a signal into action✅ Pick it when
  • Alarm on a metric crossing a threshold
  • Notify people or start automation, such as scaling
⛔ Look elsewhere when
  • Alarm on everything — people will start ignoring them

▾ Go one level deeper (60 seconds) — habits and traps

Three data types. AWS frames observability around logs, metrics and traces. CloudWatch collects metrics and logs; X-Ray provides traces; CloudWatch Service Map and the X-Ray trace map show how services connect.

CloudTrail is audit. It records API activity — who, when and what — and the default event history shows recent management events for your account. Create a trail if you need longer retention.

Decide what to collect before the incident. The one time you need a log is the time it was not turned on. Build logging into your infrastructure templates (concept 13).

Keep monitoring itself monitored. Send security findings (concept 16) to the same place, and alarm when something important turns off. Logs are billed by volume, so collect what you will use (Cost Management is next).

🔥 Interview recall
  • Three signals: metrics, logs, traces. CloudWatch = metrics, logs, alarms; X-Ray = traces; CloudTrail = audit of API calls.
  • CloudTrail for audit and compliance; CloudWatch for operational health and performance.
  • Alarm = metric + threshold + period → action (notify, automate, ticket).
  • Logs Insights queries logs; Service Map and the X-Ray map show the flow.
  • Decide what to collect before the incident; alarms without an owner become noise.
🎤 Say this in an interview
"I collect metrics, logs and traces: CloudWatch for metrics, logs and alarms, X-Ray for distributed traces, and CloudTrail for the audit trail of API calls. I alarm on symptoms users feel and drive action from the alarms, and I build logging into the infrastructure templates so nothing is forgotten."
⚠️ Common trap

Mixing up CloudWatch and CloudTrail. CloudWatch tells you how the system is performing; CloudTrail tells you who did what. You need both.

Second trap: an alarm for everything. A flood of alarms trains people to ignore them. Alarm on symptoms users feel, give each alarm an owner, and use dashboards for the rest.

▾ 💻 Tiny illustrative example 
# an alarm that fires when average CPU stays high; it notifies an SNS topic
aws cloudwatch put-metric-alarm --alarm-name shop-cpu-high --metric-name CPUUtilization \
    --namespace AWS/EC2 --statistic Average --period 300 --threshold 80 \
    --comparison-operator GreaterThanThreshold --evaluation-periods 2 --alarm-actions <topic-arn>

Illustrative shape only — the metric, threshold and periods are examples and must match your workload.
