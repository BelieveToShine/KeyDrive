❓ "How do you choose between EC2, ECS, EKS, Fargate and Lambda?"
👁 See it first
🎯 Compute is where your code runs. The real choice is how much of the machine you want to look after — the more you hand to AWS, the less you manage and the fewer knobs you get.
▶️ Watch it happen: how much do you manage?
📖 Why did this need to exist?

You now have a safe network. Your code still needs somewhere to run. The oldest answer is a virtual server (EC2): rent a computer in the cloud. It works for everything, but you inherit everything — patching the operating system, installing the runtime, planning how to add more copies when traffic grows.

AWS offers a ladder because teams want different trade-offs: control or convenience. AWS's own guidance is to start at the managed end (App Runner or Fargate) and move toward self-management only when your workload needs it.

🧰 The options

🖥️ Amazon EC2

virtual servers✅ Pick it when
  • You need the operating system or special software on the machine
  • Lift-and-shift of an existing server
  • The most control over instance types and the host
⛔ Look elsewhere when
  • A normal web app — you take on patching you do not need

🌐 App Runner and Elastic Beanstalk

AWS runs the platform for web apps✅ Pick it when
  • App Runner: the simplest way to put a web app or API online from an image or source code
  • Elastic Beanstalk: web apps with several languages and Docker; it manages the EC2 runtime and patching
⛔ Look elsewhere when
  • You need fine control over networking and orchestration → ECS or EKS

📦 Amazon ECS

AWS-native container service✅ Pick it when
  • Containers with more control over networking and security than App Runner
  • AWS's most popular container service for teams that do not need Kubernetes
  • Run on Fargate (no servers) or on EC2
⛔ Look elsewhere when
  • Kubernetes is already your standard → EKS

☸️ Amazon EKS

managed Kubernetes✅ Pick it when
  • You already use Kubernetes, or want its ecosystem and portability
  • Run on Fargate or on EC2
⛔ Look elsewhere when
  • A small team that wants less to operate → ECS on Fargate

⚡ AWS Lambda

functions that react to events✅ Pick it when
  • Event-driven work: a file, a message, a timer, an API call
  • Short, bursty tasks where you pay while it runs
⛔ Look elsewhere when
  • Long-running steady services — a container service fits better

📦 AWS Fargate

serverless compute for containers✅ Pick it when
  • Run ECS or EKS containers without managing EC2 instances
  • Spiky workloads, where it tends to win on cost
⛔ Look elsewhere when
  • Steady, highly utilised workloads — EC2 can be cheaper

▾ Go one level deeper (60 seconds) — the shared-responsibility line

EC2: AWS looks after the hardware and the host. The guest operating system is yours to patch and secure.

Fargate is not an orchestrator by itself. It is the serverless compute that ECS and EKS can run on, so you do not manage EC2 instances for those containers. ECS and EKS can both run on Fargate or on EC2, so the choices are not exclusive.

Fargate vs EC2 is mainly a cost question: Fargate tends to win for spiky workloads, while steady, highly utilised workloads can be cheaper on EC2. Check the pricing pages before deciding.

Not covered here: how to add more copies automatically and survive failures (Scaling & Resilience), and how Lambda really works (Serverless & Orchestration). Both are later concepts.

🔥 Interview recall
  • Compute is a ladder: EC2 (most control) → ECS/EKS → Fargate → App Runner/Elastic Beanstalk → Lambda (least to run).
  • EC2: you patch the OS. Beanstalk and App Runner: AWS runs the platform. ECS: AWS-native containers. EKS: managed Kubernetes. Fargate: serverless compute for ECS and EKS.
  • Lambda = event-driven functions, best for short and bursty work.
  • Fargate vs EC2 is mostly cost: Fargate for spiky, EC2 for steady and highly utilised.
  • Start at the managed end and move toward control only for a hard requirement.
🎤 Say this in an interview
"Compute on AWS is a trade-off between control and effort. EC2 gives full control but I patch the OS. App Runner and Elastic Beanstalk host web apps with AWS running the platform. ECS is the AWS-native container service and EKS is managed Kubernetes, and both can run on Fargate so I manage no servers. Lambda runs event-driven functions. I start at the managed end and move left only for a real requirement."
⚠️ Common trap

Do not pick EC2 just because it feels familiar. It works for everything, but it is the option that gives you the most work: patching, hardening, backup and scaling are all yours.

Second trap: Kubernetes is a tool, not a goal. Choosing EKS "because everyone does" means taking on more to operate. If you do not need the Kubernetes API or ecosystem, ECS is usually simpler.

▾ 💻 Tiny illustrative example 
# start one small virtual server — you choose the image, the size and the subnet
aws ec2 run-instances --image-id <ami-id> --instance-type t3.micro --subnet-id <subnet-id>

Illustrative shape only — the image ID, size and subnet are placeholders, and real launches add a role, a security group and storage.
