RDS, Aurora and DynamoDB: relational versus NoSQL, Multi-AZ versus read replicas, and how to choose.

❓ "When would you choose DynamoDB over RDS or Aurora?"
👁 See it first
🎯 A database is where structured data gets queried and updated safely — pick relational when questions are open-ended, and DynamoDB when access patterns are known and scale is huge.
▶️ Watch it happen: relational or DynamoDB?
📖 Why did this need to exist?

Storage keeps files. But when you must search, join, count and update many related records without corrupting them, you need a database engine. Different engines make different trades between consistency, scale and query power.

On AWS the first split is relational (RDS, Aurora) versus NoSQL (DynamoDB). The skill is choosing from the questions you will ask — not from fashion. Then you add the availability tools: Multi-AZ, read replicas, and replication across Regions.

🧰 The database options

🛢️ Amazon RDS

managed relational databases✅ Pick it when
  • Standard engines such as MySQL, PostgreSQL, MariaDB, SQL Server and Oracle, with AWS handling provisioning, patching and backups
  • Joins, SQL and multi-row transactions
  • Multi-AZ for availability; read replicas for read scaling
⛔ Look elsewhere when
  • Huge key-value scale with no joins — DynamoDB may fit better

🌌 Amazon Aurora

AWS-built relational (MySQL/PostgreSQL compatible)✅ Pick it when
  • High-performance, highly available relational workloads
  • Storage replicated across three zones, independent of the number of compute instances
  • Up to many read-only replicas with failover priority
⛔ Look elsewhere when
  • A tiny, simple database where plain RDS is enough

⚡ Amazon DynamoDB

NoSQL key-value and document✅ Pick it when
  • Known access patterns by key, at very large scale
  • Steady low latency
  • On-demand or provisioned capacity
⛔ Look elsewhere when
  • Ad-hoc queries and joins you cannot predict

🧠 ElastiCache and friends

in-memory and specialised✅ Pick it when
  • A cache in front of a database (see Caching & Edge)
  • Other purpose-built databases exist for graphs, search and analytics
⛔ Look elsewhere when
  • Treating a cache as your only copy of the data

DynamoDB vs RDS and Aurora

The two you will be asked about most: strengths and watch-outs, the DynamoDB partition key, capacity modes, consistency choices, and when to use both.

Open the deep dive →
▾ Go one level deeper (60 seconds) — managed does not mean unattended

Managed. RDS handles provisioning, patching and backups. You still choose engine, size, network placement and parameters, and you still own the data design and the queries.

Aurora storage keeps six copies of your data across three Availability Zones, and this does not depend on how many compute instances you run. Aurora can tolerate the loss of copies without losing write availability.

Put databases in private subnets (concept 4), use IAM and secrets (concepts 3 and 15) and back them up (concept 9).

🔥 Interview recall
  • Relational (RDS, Aurora): tables, SQL, joins, transactions. DynamoDB: items by key, scales out by partition.
  • Pick by how you query; start relational when unsure.
  • Multi-AZ = synchronous standby for failover, standby does not serve reads. Read replicas = asynchronous, scale reads, not automatic failover targets.
  • Aurora storage spans three AZs with six copies, independent of instance count.
  • Many systems use both a relational database and DynamoDB.
🎤 Say this in an interview
"I choose a database from the questions I will ask. Joins, ad-hoc SQL and multi-row transactions point to RDS or Aurora; known key lookups at huge scale point to DynamoDB. For availability I use Multi-AZ, and read replicas only for scaling reads — they are not failover targets. Aurora spreads storage across three zones. Many real systems use both."
⚠️ Common trap

Using a read replica as your high-availability plan. It is asynchronous and not an automatic failover target on standard RDS. Use Multi-AZ for failover.

Second trap: choosing DynamoDB because it "scales" and then needing joins. Without known access patterns you will fight the model. Decide your queries first.

🛢️ Relational (RDS / Aurora)

Design the tables, then ask any question with SQL. Great when questions change.

vs.
⚡ DynamoDB

Design for the questions first, then get predictable speed at huge scale.

▾ 💻 Tiny illustrative example 
# create a small PostgreSQL database on RDS, with a standby in another zone
aws rds create-db-instance --db-instance-identifier shop-db --engine postgres \
    --db-instance-class db.t3.micro --allocated-storage 20 --multi-az \
    --master-username admin --manage-master-user-password

Illustrative shape only — the size, storage and flags are examples, and real databases also set a subnet group, security groups, backups and encryption.
