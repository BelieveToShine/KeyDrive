Infrastructure as code turns your environment into files you can review, repeat and roll back.

CloudFormation, the CDK and Terraform: why clicking resources together stops working, how a preview protects you, and which tool to pick.

❓ "What is infrastructure as code, and would you use CloudFormation, the CDK or Terraform on AWS?"
👁 See it first
🎯 Infrastructure as code means your environment is described in files that you can review, repeat and roll back — instead of being a pile of clicks nobody remembers.
▶️ Watch it happen: files instead of clicks
📖 Why did this need to exist?

By now the system is dozens of resources: networks, servers, databases, queues, functions. Someone clicked them together in the console. Ask three questions: Can we build the same thing again? (a second environment, or after a disaster) Who changed what, and why? Does production really match staging? With clicking, the honest answer to all three is "not sure".

Infrastructure as code (IaC) answers all three. You describe what you want and a tool makes AWS match. The file is the record, it goes through review like code, and it is the plan for the disaster-recovery day from the Scaling concept.

🧰 Which tool?

📄 AWS CloudFormation

AWS-native templates and stacks✅ Pick it when
  • You work on AWS only
  • A template describes resources; a stack is the deployed, trackable unit
  • Change sets preview changes
⛔ Look elsewhere when
  • You also manage non-AWS providers in the same code

💻 AWS CDK

infrastructure in a programming language✅ Pick it when
  • Write infrastructure in familiar languages, with loops and functions
  • Constructs package reusable patterns
  • It generates CloudFormation templates
⛔ Look elsewhere when
  • You want a no-code, purely declarative file — and note each account and Region needs a bootstrapped environment

🌐 Terraform

multi-provider, with a state file✅ Pick it when
  • One tool across AWS, other clouds and services
  • A plan shows changes before apply
⛔ Look elsewhere when
  • You want AWS to track state for you — Terraform keeps its own state, which you must store and protect

▾ Go one level deeper (60 seconds) — stacks, drift and state

Stacks. A stack is infrastructure as code deployed and tracked as a single unit; a template is one CloudFormation file. A change set lets you review a change before it runs.

Drift is when the real environment stops matching the template, usually because someone changed something in the console. Treat the console as read-only for anything the code owns, and let the pipeline (next concept) deploy.

CDK bootstrapping. The CDK needs a bootstrapped environment in each account and Region it deploys to.

Terraform state. Terraform records what it manages in its own state; store it remotely, limit access and back it up. There is also a CDK variant for Terraform that lets you write Terraform configuration in a programming language.

🔥 Interview recall
  • IaC = the environment described in reviewed, versioned files; repeatable, reviewable, recoverable.
  • CloudFormation: templates and stacks, change sets to preview. CDK: code that synthesizes into CloudFormation. Terraform: multi-provider with a state file.
  • A CloudFormation change set ≈ a Terraform plan; a template ≈ a configuration.
  • The CDK needs a bootstrapped environment per account and Region.
  • Drift = reality no longer matches the template; avoid console edits for code-managed resources.
🎤 Say this in an interview
"I define environments as code so they are repeatable, reviewable and recoverable. On AWS only I use CloudFormation, often through the CDK so I can use a programming language; if I must manage several providers I use Terraform and protect its state. I preview with change sets or plans, and I keep the console read-only for anything the code owns so there is no drift."
⚠️ Common trap

Fixing things in the console "just this once". The template no longer matches reality, and the next deployment may undo your fix — or fail.

Second trap: leaving the Terraform state file somewhere unprotected. It is the tool's record of your infrastructure and can contain sensitive data; store it remotely, with access limited and backups on.

▾ 💻 Tiny illustrative example 
# a CloudFormation template (YAML) that creates one S3 bucket
Resources:
  ReportsBucket:
    Type: AWS::S3::Bucket
    Properties:
      VersioningConfiguration:
        Status: Enabled

Illustrative only — a real template adds encryption, access rules and tags, and names are chosen per environment.
