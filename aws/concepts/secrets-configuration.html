IAM roles, Secrets Manager, Parameter Store and KMS: where each kind of value belongs and how the app reads it.

❓ "Where do you keep secrets and configuration for an AWS app, and why?"
👁 See it first
🎯 Keep secrets out of code and out of pipelines: ask for them at run time from a guarded place, using the app's own role — or avoid having a secret at all.
📖 Why did this need to exist?

The last concept built a pipeline that deploys without a stored key. But the app itself still needs things: a database password, an API key for a payment provider, and plain settings like "which environment is this?".

The classic leak is putting those in code or in a pipeline variable. Both get copied, logged and shared. The fix has two halves. Secrets (things that must stay hidden) go to a service with access control, audit and rotation. Settings (things that just change) go to a configuration store. Both encrypt with AWS KMS.

🧰 The pieces

🪪 IAM roles

no stored secret at all✅ Pick it when
  • The target accepts IAM sign-in
  • Temporary, automatically rotated credentials
  • Nothing to store, rotate or leak
⛔ Look elsewhere when
  • The other side only understands passwords or keys → get them from Secrets Manager

🔑 AWS Secrets Manager

secrets with rotation✅ Pick it when
  • Database credentials, API keys and tokens
  • Automatic rotation; random secret generation; cross-account sharing; cross-Region replication
  • Rotation of database credentials expects the stored JSON to follow the database secret structure
⛔ Look elsewhere when
  • Large amounts of plain, frequently read configuration — Parameter Store fits that better

⚙️ Systems Manager Parameter Store

configuration and light secrets✅ Pick it when
  • Plain settings and frequently read configuration
  • Standard-tier parameters up to a small size have no charge
  • SecureString values encrypted with KMS
⛔ Look elsewhere when
  • A secret that must rotate on its own — Parameter Store has no automatic rotation

🗝️ AWS KMS

the keys that encrypt✅ Pick it when
  • Both secret services encrypt with KMS keys
  • Control who may use a key with key policies and IAM
⛔ Look elsewhere when
  • Treating KMS as a place to store application secrets — it manages encryption keys

▾ Go one level deeper (60 seconds) — what AWS says

Rotation. Parameter Store does not rotate stored secrets; AWS suggests keeping the secret in Secrets Manager and referencing it from Parameter Store. Secrets Manager adds automatic rotation, random secret generation and cross-account sharing.

Cost shape. Standard-tier parameters have no charge below a small value size, while Secrets Manager charges per secret per month and per API call. This page quotes no prices; check the pricing pages.

Containers. Passing secrets as environment variables carries a higher risk of leakage; one AWS guide describes a sidecar that reads from Secrets Manager and writes to a shared volume.

Ephemeral first. AWS's security baseline recommends ephemeral secrets or a secrets-management service rather than long-lived static credentials.

🔥 Interview recall
  • Best to worst: no secret (IAM role) → Secrets Manager → config file → in the code.
  • Secrets Manager = secrets with rotation, sharing and replication. Parameter Store = configuration (and light secrets) with no automatic rotation.
  • A Parameter Store parameter can reference a Secrets Manager secret.
  • Both encrypt with KMS; IAM policies decide what a role may read.
  • Containers: avoid plain environment variables for secrets where you can.
🎤 Say this in an interview
"I avoid secrets where I can: IAM roles for anything that accepts IAM sign-in. Where a secret is unavoidable it lives in Secrets Manager, which rotates it, and the app reads it with its role. Plain settings go to Parameter Store, which can also reference a Secrets Manager secret. Both encrypt with KMS, and nothing sensitive goes in code or pipeline variables."
⚠️ Common trap

Putting the secret in the pipeline variable "just for now". Variables are copied into logs, forks and screenshots. Use OIDC for the pipeline and roles or Secrets Manager for the app.

Second trap: using Parameter Store for a secret and never rotating it. It stores the value safely but does not rotate it. Without rotation, one leaked secret works forever.
