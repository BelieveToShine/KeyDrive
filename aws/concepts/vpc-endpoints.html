Deep dive · VPC · 🔌 Endpoints

A VPC endpoint is a private door from your network to an AWS service — so private subnets never need the internet to reach AWS.

Gateway endpoints for S3 and DynamoDB, interface endpoints with PrivateLink, and how to choose between them.

❓ "What is a VPC endpoint, and what is the difference between a gateway and an interface endpoint?"
👁 See it first
🎯 A VPC endpoint is a private door from your network to an AWS service — so private subnets can use S3, DynamoDB and more without ever going out to the internet.
▶️ Watch it happen: a private door to a service
📖 Why did this need to exist?

The VPC page put databases and apps in private subnets and gave them a NAT gateway for outbound access. But much of what private servers call is AWS itself: storage, queues, secrets. Sending that traffic through a NAT gateway and out to the internet is slower to reason about, costs money, and widens what must be allowed out.

A VPC endpoint keeps that traffic inside AWS. There are two kinds that work differently, and choosing between them is the whole skill.

🧰 The two kinds

🚪 Gateway endpoint

S3 and DynamoDB only✅ Pick it when
  • You are reaching S3 or DynamoDB from inside the VPC
  • Routes are added to the route tables you choose
  • No additional cost for the endpoint
⛔ Look elsewhere when
  • Reaching them from on-premises, from a peered VPC in another Region or through a transit gateway — it does not reach those

🔌 Interface endpoint

built on AWS PrivateLink✅ Pick it when
  • Many AWS services (and services shared by others through PrivateLink)
  • A network interface with a private IP in your subnet
  • Reachable from on-premises over VPN or Direct Connect, and from peered VPCs or transit gateways
⛔ Look elsewhere when
  • Cost-sensitive S3 traffic from inside the VPC — a gateway endpoint is free to run

▾ Go one level deeper (60 seconds) — details to know

Gateway endpoints work only with S3 and DynamoDB and do not use PrivateLink. They add routes to route tables you associate with the endpoint, and have no additional cost. They do not extend to on-premises networks, to peered VPCs in other Regions or to transit gateways.

Interface endpoints use AWS PrivateLink and elastic network interfaces with private IP addresses from your subnets. You pay an hourly charge while the endpoint runs, plus data processing.

Endpoint policies can restrict what an endpoint may be used for, adding one more guardrail next to IAM and bucket policies.

Security groups attach to interface endpoints, so you can control which of your resources may use them.

🔥 Interview recall
  • VPC endpoint = a private path from your VPC to an AWS service, without the internet or a NAT gateway.
  • Gateway endpoint: S3 and DynamoDB only, a route in the route table, no extra charge, VPC-only.
  • Interface endpoint: PrivateLink, a network interface with a private IP, many services, hourly plus data charges, reachable from on-premises and peered VPCs.
  • You can use both for S3 in one VPC.
  • Endpoints do not replace IAM or bucket policies — they add a network-level guardrail.
🎤 Say this in an interview
"For private subnets I use VPC endpoints so AWS traffic does not go out through a NAT gateway. For S3 and DynamoDB inside the VPC a gateway endpoint is a route table entry with no extra charge. For other services, or when access comes from on-premises or a peered network, I use interface endpoints, which are PrivateLink network interfaces billed by the hour and by data."
⚠️ Common trap

Assuming a gateway endpoint reaches from on-premises. It does not; it works only from inside the VPC. For on-premises access use an interface endpoint.

Second trap: thinking an endpoint replaces permissions. It only changes the network path. IAM and resource policies still decide who may do what.

🚪 Gateway endpoint

A route-table target for S3 and DynamoDB. Free to run, VPC-only.

🔌 Interface endpoint

A network interface with a private IP, via PrivateLink. More services and reach, billed by hour and data.

    --route-table-ids <rtb-id>
