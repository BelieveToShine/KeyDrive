📖 Why did this need to exist?

IAM says who may call what. But before any caller arrives, there is a more basic question: can the packet even get there? A database that the whole internet can reach is a problem no policy fixes after the fact. Networking decides what can physically reach what.

So resources get a VPC: an isolated network you define, with subnets in specific Availability Zones, route tables that decide where traffic goes, and firewalls at two levels. The habit to build: put only what must be public in a public subnet — and everything else in a private one.

  • Make several subnets across zones for resilience
  • Public subnet = a route to the internet gateway; private = no direct route
⛔ Look elsewhere when
  • Putting databases in a public subnet "to make it easy"

🧭 Route tables, internet gateway, NAT gateway

where traffic goes✅ Pick it when
  • A route table pairs a destination range with a target
  • Internet gateway: lets public resources talk to the internet
  • NAT gateway: private resources start outbound connections; unsolicited inbound is blocked
⛔ Look elsewhere when
  • Expecting a NAT gateway to let the internet in — it does not

🛡️ Security groups

a firewall around a resource✅ Pick it when
  • Your main tool: allow rules only, stateful
  • Reference another security group as the source ("only the web tier")
⛔ Look elsewhere when
  • Trying to write a deny rule — security groups only allow

🚧 Network ACLs

a firewall around a subnet✅ Pick it when
  • Stateless, with allow and deny rules checked in order
  • AWS suggests them as a secondary control or subnet-level guardrails
⛔ Look elsewhere when
  • Forgetting the reply rule — stateless means replies need their own rule

▾ Go one level deeper (60 seconds) — what AWS says

A public subnet has a direct route to an internet gateway; a private subnet does not, so its resources need a NAT device to reach the internet. A route table holds routes; each route pairs a destination range with a target such as a gateway.

Security groups act at the resource level and are stateful; network ACLs act at the subnet level and are stateless. AWS suggests using network ACLs as a secondary control or high-level subnet guardrails, because security groups meet most needs.

VPC peering is point-to-point and does not support transitive routing. For a full mesh of many VPCs you would need a huge number of peerings, so AWS points to Transit Gateway, which supports transitive routing and can attach VPNs and Direct Connect.

Spread across zones. A subnet lives in a single Availability Zone, so make subnets in several zones and put copies of your app in each (concept 2).

Pricing. NAT gateways and some connectivity options are billed by the hour and by data processed; check the pricing page before you design around many of them.

🔥 Interview recall
  • VPC = your isolated network; subnets live in one AZ. Public subnet = route to an internet gateway; private = no direct route.
  • NAT gateway lets private resources start outbound connections and blocks unsolicited inbound ones.
  • Security group: resource-level, stateful, allow rules only. Network ACL: subnet-level, stateless, allow and deny, rules in order.
  • Peering is one-to-one and not transitive; a transit gateway is a hub with transitive routing.
  • Only what must be public goes in a public subnet; databases go in private subnets.
🎤 Say this in an interview
"I build a VPC with subnets in several Availability Zones. Anything that must face the internet sits in a public subnet with a route to the internet gateway; apps and databases sit in private subnets, with a NAT gateway for outbound-only access. Security groups are my main firewall — stateful, allow-only — and network ACLs are a stateless subnet-level layer. For many VPCs I use a transit gateway, because peering is not transitive."
⚠️ Common trap

Putting the database in a public subnet. Even with a good password, you have made it reachable by the world. A private subnet takes it off the map.

Second trap: writing network ACL rules for one direction. They are stateless, so the reply traffic needs its own rule. Most "it works in a security group but not here" bugs are this.

aws ec2 create-vpc --cidr-block 10.0.0.0/16
