Deep dive · Scaling & Resilience · 🛟 Disaster recovery

Disaster recovery starts with two numbers — how much data you can lose, and how long you can be down.

RPO and RTO, AWS's four strategies, and when to use Elastic Disaster Recovery, AWS Backup or a database's own replication.

❓ "What are RPO and RTO, and what are the AWS disaster recovery strategies?"
👁 See it first
🎯 Disaster recovery starts with two questions — how much data can we lose, and how long can we be down? — and then buys exactly that much protection, no more.
📖 Why did this need to exist?

Auto Scaling and zones keep the app running through everyday failures. They do not help if someone deletes the wrong data, ransomware encrypts it, or a whole Region is unavailable. For those days you need copies of the data and a plan to run somewhere else.

The trap is buying too much or too little. RPO and RTO turn that argument into numbers the business can agree to. AWS then describes four strategies, in order of speed and cost.

▾ Go one level deeper (60 seconds) — what AWS says

Choose from your objectives. AWS's Reliability Pillar says to use a defined recovery strategy that meets your recovery objectives. Published RTO and RPO ranges for each strategy differ slightly between AWS documents and are indicative targets, not guarantees, so this page quotes none of them.

Pilot light vs warm standby. The key difference: a pilot-light environment cannot process requests without additional action, while warm standby can handle reduced traffic immediately.

Active/active still needs backups. Data corruption can replicate everywhere, so a point-in-time backup is still needed, which means the recovery point is usually not exactly zero.

Elastic Disaster Recovery uses a pilot-light-style approach with continuous data replication; check its documentation for current targets. AWS Backup gives a central place to configure, schedule and monitor backups.

Failover and failback. Plan both: moving to the recovery Region, and moving back when the first Region has recovered. Define your environment as code (a later concept) and test the plan.

🔥 Interview recall
  • RPO = how much data you can lose. RTO = how long you can be down. The business sets them.
  • Four AWS strategies: backup and restore → pilot light → warm standby → multi-site active/active (cheapest/slowest to costliest/fastest).
  • Pilot light cannot serve requests without action; warm standby can serve reduced traffic immediately.
  • Elastic Disaster Recovery = replicate and fail over servers. AWS Backup = restore earlier copies. Databases use their own replication.
  • A replica copies mistakes; a backup lets you go back in time. Test the plan.
🎤 Say this in an interview
"I start from RPO and RTO — how much data we can lose and how long we can be down — then pick the cheapest of AWS's four strategies that meets them: backup and restore, pilot light, warm standby or multi-site active/active. I use Elastic Disaster Recovery for servers, AWS Backup for damaged data, and database replication for databases, and I test the plan."
⚠️ Common trap

A replica is not a backup. If someone deletes a table, replication copies the deletion within moments. You need a restore point from before the mistake.

Second trap: backups only in the Region that failed. Copy backups to the recovery Region, or you cannot restore when you need to.

🔁 Failover

Move production traffic from the Region that is unavailable to the one that works.

vs.
↩️ Failback

Move traffic back to the original Region once it has recovered.
